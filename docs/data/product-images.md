# 상품 이미지 / 상세 설명 수집 메모

작성: 프론트 (2026-08-27)

데이터셋(`product_info.csv`)에 이미지 URL 과 상세 설명 문단이 없어서
(`docs/data/README.md` 4번 항목) 프론트에서 세포라 공개 페이지 기준으로 직접 채웠다.
이 문서는 **어디서 어떻게 가져왔는지**와 **다시 돌릴 때 필요한 규칙**을 남긴다.

## 채운 필드

`frontend/src/mocks/products.sample.json` 의 8개 상품에 아래 필드를 추가했다.
데이터 담당자가 내려주는 기존 필드는 하나도 건드리지 않았다.

| 필드 | 내용 |
|---|---|
| `image_url` | 대표 이미지. 기존엔 항상 `null` 이던 자리 |
| `sku_id` | 세포라 SKU 번호. 이미지 URL 조립 키 |
| `images` | 대표 이미지 외 추가 갤러리 이미지 |
| `variants` | 색상/향/용량 옵션. `{ sku_id, label, image_url }` |
| `description` | About the Product 영문 원문 |

`description` 하위 키는 `frontend/src/types/product.ts` 의 `ProductDescription` 과 같다.
페이지에 없던 항목은 `null`, 항목 전체가 없으면 `description` 자체가 `null` 이다.

## 이미지 URL 규칙

**경로가 두 종류다. 대표 이미지와 갤러리 이미지의 키가 다르다.**

```
대표:   https://www.sephora.com/productimages/sku/s<SKU>-main-zoom.jpg
갤러리: https://www.sephora.com/productimages/product/p<상품ID>-av-<NN>-zoom.jpg
                                          ~~~~~~~   ~~~~~~~~~~~~
                                          하위 경로  소문자 p + 상품ID + 2자리 0채움
```

> **여기서 오래 헤맸다.** 갤러리도 SKU 기준(`s<SKU>-av-<N>`)일 거라 보고 조회했는데
> 표본 12개 중 2개만 존재했다. 그래서 "최신 상품은 긴 ID를 써서 조립이 불가능하다"
> 고 결론 내렸는데 틀렸다. 아카이브 스냅샷의 상품 JSON(`alternateImages`)을 열어보니
> 갤러리는 **상품 ID 기준 `product/` 경로**였다.
>
> 이 사실이 중요한 이유: **SKU 를 몰라도, 아카이브 스냅샷이 없어도 조립된다.**
> SKU 는 아카이브 URL 에서 역으로 찾아야 하는데 200개 중 143개만 성공했다.
> 반면 갤러리는 상품 ID 만 있으면 되므로 CDN 조회만으로 채울 수 있다.
> 실제로 아카이브에서 SKU 를 못 찾은 상품(P427417)과 스냅샷 자체가 없는 상품
> (P443563)도 갤러리는 정상적으로 나왔다.
>
> SKU 를 못 찾은 46개는 **갤러리 첫 장을 대표 이미지로 올렸다.** 제품 컷이 아닌
> 경우도 있지만 그 상품의 실제 사진이라 회색 플레이스홀더보다 낫다.

- `N` 은 1부터. **상품마다 시작 번호와 개수가 다르고, 중간이 비기도 한다.**
  P454380 은 `av-13` 다음 `av-14`, `av-15` 가 없고 `av-16` 부터 다시 있다.
  그래서 "404 나오면 중단" 이 아니라 **연속 3회 404** 를 종료 조건으로 썼다.
  개수 상한을 15 같은 작은 값으로 두면 뒤쪽을 통째로 놓친다 (P429952 는 19장이다).
- 추가 이미지가 아예 없는 상품도 있다 (P269122, P450271).
- 위 규칙에 안 맞고 `av-0202507240851191670700` 같은 긴 ID 를 쓰는 이미지도 섞여 있다.
  조립으로는 못 찾으므로, 페이지 JSON 의 `alternateImages` 를 우선 쓰고
  거기서 못 얻은 상품만 순차 조회로 채웠다.
- 없는 이미지는 404 + 본문 215 바이트로 응답한다. 상태 코드만 보면 판별된다.
- `?imwidth=<px>` 로 CDN 리사이즈가 된다. 폭에 따라 용량이 크게 갈린다.
  같은 파일 기준 128px 7KB · 160px 15KB · 384px 45KB · 768px 178KB · **1024px 532KB** 다.
  **768 을 넘기면 사실상 원본이 온다.** 처음에 갤러리 메인을 1024 로 요청해서
  장당 300~550KB 를 받고 있었고, 이게 사진을 눌렀을 때 수 초씩 걸리던 원인이었다.

  폭은 실제 표시 크기를 재서 정했다 (viewport 1280 / dpr 1 기준).

  | 자리 | 표시 | 요청 폭 | 장당 |
  |---|---|---|---|
  | 갤러리 메인 | 560px | 768 | 약 107KB |
  | 갤러리 썸네일 | 71px | 160 | 약 15KB |
  | 옵션 스와치 | 62px | 128 | 약 7KB |
  | 추천 카드 | 181px | 384 | 약 45KB |

  값은 `frontend/src/lib/image-widths.ts` 한 군데 두고 화면과 워밍 스크립트가 같이 쓴다.
  전에는 스크립트가 값을 따로 복사해 갖고 있었다. 어긋나면 **워밍은 성공했다고 나오는데
  화면은 캐시를 못 맞고 세포라에서 직접 받는다.** 조용히 느려지므로 한 군데로 합쳤다.

  추천 카드는 스와치와 같은 128 을 쓰고 있었다. 카드는 181px 로 표시되므로
  받은 이미지(150px)가 표시 크기보다 작아서 뭉개지고 있었다. 384 로 올렸다.

- 썸네일을 눌렀을 때 그때 처음 받으면 그 대기 시간이 그대로 체류 시간 로그로 잡힌다.
  그래서 상세페이지를 열면 **갤러리 전체를 메인 폭으로 미리 받아둔다**
  (`ProductGallery` 의 프리페치). 지금 보는 이미지와 경쟁하지 않게 우선순위를 낮춰서 받는다.
  측정: 썸네일 클릭 시 메인 교체가 12~38ms (프리페치 전에는 클릭할 때마다 수 초).

이미지를 레포에 커밋하지 않고 CDN URL 을 그대로 쓴다. localhost 에서도 로드된다
(핫링크 차단 없음). 나중에 자체 스토리지로 옮기면 `image_url` / `images` 값만 바꾸면 된다.

넣은 URL 은 전부 `curl` 로 200 을 확인했다.

`variants` 의 `image_url` 은 옵션을 골랐을 때 갤러리에 뜨는 **상품 사진**(`main-zoom`)이고,
`swatch_url` 은 옵션 버튼에 들어가는 62px 짜리 **스와치**다. 세포라가 둘을 따로 준다.
스와치를 갤러리에 쓰면 확대돼서 뭉개지므로 자리를 나눠 뒀다.

## 실험할 때는 로컬 캐시로 받는다

세포라 CDN 에서 직접 받으면 한 장에 수 초씩 걸린다. 이 페이지는 행동 로그를 재기 때문에
이건 단순히 느린 게 아니라 **데이터가 오염되는 문제**다. 이미지가 늦게 뜨면 그동안
화면에 머문 시간이 그대로 체류 시간으로 잡힌다.

그래서 dev 서버가 한 번만 원본을 받아 디스크에 저장하고, 그 뒤로는 로컬에서 준다
(`frontend/plugins/image-cache.ts`). 브라우저에는 1년짜리 `immutable` 캐시 헤더로 내려간다.

```bash
npm run warm-images   # frontend/ 에서. 실험 전에 한 번
```

- **2,985장 · 142.3MB · 받는 데 몇 분** (갤러리 1,182장이 들어오기 전에는 236장 9.3MB 였다)
- 실패 4장. 없는 이미지라 재시도해도 안 된다
- 캐시 폴더(`frontend/.image-cache/`)는 커밋하지 않는다. 사람마다 한 번씩 받으면 된다
- 안 돌려도 화면을 열 때 알아서 채워지지만, **첫 방문자만 느린 화면을 보게 되고
  그 사람 체류 시간 로그가 다른 사람과 달라진다.** 실험 전에 돌리는 게 좋다
- 로컬 평균 3.2ms / 최대 3.9ms (대표 + 갤러리 5장 실측) vs 세포라 첫 요청 4.5초

배포 빌드에는 이 미들웨어가 없으므로 원래 CDN 주소를 그대로 쓴다
(`src/lib/image.ts` 의 `import.meta.env.DEV` 분기).

## 수집 방법

세포라 라이브 사이트는 이 환경에서 전부 막힌다.

- 상품 페이지 HTML 과 `/api/*` 를 403 으로 차단한다. `curl` / `WebFetch` 로는 안 된다.
- 브라우저로 열어도 `Access Denied` 가 뜬다.
- 텍스트 추출 프록시(`r.jina.ai`)는 한동안 됐지만 지금은 자바스크립트 렌더 전
  껍데기만 돌려준다. 본문이 없으므로 설명을 못 뽑는다.
- 이미지 CDN(`/productimages/*`)만 차단이 없다.

### 무엇에 아카이브가 필요하고 무엇에 안 필요한가

| 필요한 것 | 이유 |
|---|---|
| **SKU** | 대표 이미지 키. 스냅샷 URL 쿼리(`?skuId=`)에서 역으로 찾는다 |
| **상세 설명 · 옵션** | 페이지 JSON 에만 있다 |

| 필요 없는 것 | 이유 |
|---|---|
| **갤러리 이미지** | 상품 ID 로 조립된다. CDN 조회만으로 된다 |
| **리뷰** | 페르소나 데이터에 원본이 있다 |

그래서 **web.archive.org 스냅샷** 을 썼다. 세포라는 상품 페이지를 클라이언트에서
그리지만 HTML 안에 상품 JSON 을 통째로 박아두기 때문에, 스냅샷 원본 HTML 만 있으면
이미지·옵션·설명을 전부 얻을 수 있다.

```bash
# 1. 스냅샷 시각 찾기 (슬러그가 정확해야 한다)
curl -s "http://archive.org/wayback/available?url=sephora.com/product/<슬러그>-<PID>"

# 2. 원본 HTML 받기. id_ 를 붙여야 아카이브 배너 없이 원본이 온다
curl -s -L "http://web.archive.org/web/<TS>id_/https://www.sephora.com/product/<슬러그>-<PID>"
```

슬러그를 모르면 CDX 로 찾는다. 전체 `product*` 프리픽스는 너무 커서 504 가 나므로
앞부분을 최대한 좁혀야 한다.

```bash
curl -s "http://web.archive.org/cdx/search/cdx?url=sephora.com/product/<앞부분>*&collapse=urlkey&limit=15&fl=timestamp,original"
```

스냅샷마다 JSON 이 들어있기도 하고 없기도 하다. 받은 HTML 에 `shortDescription` 이
없으면 다른 시각의 스냅샷으로 바꿔서 다시 받아야 한다.

**연도에 규칙이 있다.** 확인해보니 **2018~2021 스냅샷은 안정적으로 JSON 을 갖고 있고,
2025 스냅샷에는 없다.** (P454380 은 2025 에 없고 2020 에 있었고, P427417 은 2018·2020·2025
모두 없었다.) 그래서 수집 스크립트는 2018~2021 구간을 먼저 뒤진다.
상위 30개 대상으로 21개가 이 방식으로 나왔다.

파싱에서 주의할 점:

- 설명 본문은 `shortDescription` 한 덩어리에 `제목: 본문` 이 반복되는 HTML 이다.
  상품 등록 시기에 따라 `<b>` + `<br>` 이거나 `<strong>` + `<p>` 라서 둘 다 처리해야 한다.
- `longDescription` 은 보통 브랜드 소개지만, 상품 설명을 그대로 복사해 둔 상품이 있다.
  그대로 넣으면 화면에 같은 문단이 두 번 나온다.
- 영양제(P443349)는 `Skin Type` / `Skincare Concerns` 대신
  `Beauty Benefit` / `What it tastes like` 같은 다른 제목을 쓴다.

## 주의: 원본 페이지는 데이터셋과 어긋난다

데이터셋은 특정 시점 스냅샷이고 세포라 페이지는 그 뒤로 계속 바뀌었다.

- P420652 는 데이터셋 이름이 `... with Vitamin C` 인데 현재 페이지 기본 선택은
  한정판 `Acai Mango Smoothie` 다. 대표 이미지는 기본 향인 `Berry`(1966258) 로 잡았다.
- 가격도 다르다 (데이터셋 $24.00 / 현재 페이지 $25.00).
- **P450271 은 상품 페이지 자체가 아카이브에 없다.** 한정판 점보 사이즈라 단종됐고
  남은 캡처가 302 리다이렉트 하나뿐이다. 그래서 **같은 제품의 일반 사이즈
  (P417238) 페이지에서 이미지와 설명을 가져왔다.** 용량만 다른 같은 제품이지만
  점보 실물 이미지는 아니다. 옵션과 갤러리 이미지는 비어 있다.

**상품명·가격·성분 등 데이터셋 필드는 전부 원본 값을 그대로 유지했다.**
바꾼 것은 위 표의 5개 필드뿐이다.

즉 `description` 은 **참고용 표시 데이터**이고, 분석·추천의 입력으로 쓸 값은 아니다.
분석에 쓸 필드는 데이터 담당자가 내려주는 기존 필드를 그대로 써야 한다.

## 다시 돌릴 때

수집 결과는 **`frontend/src/mocks/products.collected.json` 한 곳에 모여 있다.**
빌드는 인수 없이 그 파일만 읽는다.

```bash
node scripts/build-products.ts   # 자산 → products.sample.json
node scripts/build-reviews.ts    # 페르소나 → reviews.sample.json
npm run warm-images              # 이미지 로컬 캐시 채우기
```

자산 파일을 출력 파일과 분리해 둔 이유가 있다. 상품 200개 목록은 데이터 담당자가
정하고 바뀔 수 있는데, 자산을 출력 파일에만 두면 목록에서 빠진 상품의 수집 결과가
사라진다. 실제로 P450271(단종 점보)과 P443349(먹는 보충제)가 200개에서 제외됐다.

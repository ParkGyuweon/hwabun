# 커머스 행동 신호 수집·해석·반영 방식 조사

작성: 프론트 (2026-08-28) · 이벤트 10종 근거 추가 (2026-08-31)

**전제: PC 쇼핑만 대상으로 한다.**

이 사이트는 데스크톱 브라우저 사용자만 상대한다. 모바일 대응을 하지 않는다.
이 전제가 아래 값들에 직접 영향을 준다.

- `hover_dwell`, `text_selection` 처럼 **포인터가 있어야 발생하는 이벤트의 수집률이
  사실상 100%** 다. 기기별 결측을 걱정할 필요가 없다.
- 한 화면에 콘텐츠 블록이 여러 개 들어가므로 **체류를 어느 블록에 귀속시킬지가
  모바일보다 어렵다.** `co_visible_blocks` 로 동시 노출 수를 함께 남기는 이유다.
- 업계 자료의 수치는 대개 모바일을 포함한 전체 값이다. **그대로 인용하지 않는다.**

목적: 우리 로그 이벤트 목록과 가중치의 **외부 근거**를 만든다.
현재 이벤트 목록은 화면 배너에 적힌 대로 "마케팅 조사 결과 반영 전 초안" 상태다.

## 1. 먼저 알아야 할 것: 정확한 가중치는 공개되지 않는다

조사에서 가장 중요한 결론이다. **네이버쇼핑·무신사·올리브영 모두 랭킹에 쓰는
지표 "목록"은 공개하지만, 각 지표의 가중치·집계 기간·정규화 방식은 공개하지 않는다.**

- 네이버는 적합도/인기도/신뢰도 3축과 그 하위 항목까지 공개하지만 비중은 비공개
- 무신사는 매출·판매수량·조회수·후기수를 쓴다고 밝히고 공식은 비공개.
  기술 블로그도 집계 스택(Databricks/Spark, Elasticsearch, 90ms 응답)까지만 공개
- 올리브영은 산정 기준 자체를 공식 문서로 공개하지 않는다

따라서 "업체들이 쓰는 비율"을 그대로 베껴올 수는 없다. 대신 쓸 수 있는 것은:

| 근거 종류 | 신뢰도 | 이 문서 표기 |
|---|---|---|
| 플랫폼·도구 공식 문서에 명시된 것 | 높음 | **[공개]** |
| 업계에서 표준처럼 쓰이는 관행·논문 기법 | 중간 | **[관행]** |
| 위 둘에서 우리 프로젝트용으로 유추한 것 | 낮음 | **[추정]** |

**[추정] 항목은 우리가 정한 값이라는 뜻이다.** 문서나 발표에 인용할 때
플랫폼이 그렇게 한다고 쓰면 안 된다.

## 2. 무엇을 수집하나 — 커머스 표준 수집 항목

### 2-1. GA4 이커머스 권장 이벤트 [공개]

GA4 는 이커머스 권장 이벤트 11종을 정의하고, 그중 일부를 퍼널 단계로 인식한다.
최소 구성은 `view_item` → `add_to_cart` → `begin_checkout` → `purchase` 4종이다.

| 단계 | 이벤트 | 우리 구현 |
|---|---|---|
| 상품 열람 | `view_item` | O `page_view` (`page_type=product_detail`) |
| 목록 노출 | `view_item_list` | O `product_impression` |
| 목록 클릭 | `select_item` | O `product_click` (`entry_source=list_grid`) |
| 찜 | `add_to_wishlist` | O `wishlist_toggle` |
| 장바구니 | `add_to_cart` | O `add_to_cart` |
| 장바구니 열람 | `view_cart` | **X — 장바구니 화면이 없다** |
| 장바구니 제거 | `remove_from_cart` | **X — 장바구니 화면이 없다** |
| 결제 시작 | `begin_checkout` | 범위 밖 |
| 배송정보 입력 | `add_shipping_info` | 범위 밖 |
| 결제정보 입력 | `add_payment_info` | 범위 밖 |
| 구매 | `purchase` | 범위 밖 |

범위 안 7단계 중 **5단계를 덮었다.** 목록 노출·클릭은 목록 화면을 만들면서 채웠다.

남은 두 개는 장바구니 화면이 없어서 비어 있다. 그중 **`remove_from_cart` 는
그냥 빠뜨리기 아까운 신호다.**

지금 우리 감점 축은 `rage_click`·`dead_click`·`scroll_backtrack` 세 개뿐이고
전부 **[추정]** 이다. 근거가 약하고, 상품이 싫다는 뜻이 아니라 화면 문제일 수도 있다.
반면 장바구니에서 상품을 빼는 것은 **특정 상품에 대한 재고(再考)** 라서
훨씬 명확한 부정 신호다. 담았다가 뺀 상품과 담아둔 상품을 나누면
`add_to_cart` 의 4.0 가중이 과대평가인지도 검증할 수 있다.

장바구니 화면은 상품 목록·상세만큼 클 필요가 없다. 담은 상품 목록과 수량 조절,
삭제만 있으면 `view_cart` 와 `remove_from_cart` 가 나온다.

우리 프로젝트는 **구매 이전 탐색 구간만** 다루므로 퍼널 뒷부분은 비어 있다.
표준 이벤트만으로는 신호가 너무 적어서 탐색 구간을 촘촘히 봐야 한다.
이게 우리가 주목·좌절 신호를 따로 만든 이유다.

### 2-2. 표준 이벤트가 덮지 못하는 탐색 구간 [관행]

행동 분석 도구들이 공통으로 재는 참여 지표는 다음과 같다.

| 항목 | 무엇을 재나 |
|---|---|
| 체류 시간 | 페이지·섹션에 머문 시간 |
| 스크롤 깊이 | 어디까지 내려갔나 (보통 25/50/75/100%) |
| 섹션 노출 | 어떤 블록이 화면에 들어왔나 |
| 이미지·미디어 열람 | 갤러리 전환, 확대 |
| 옵션 상호작용 | 색·용량 전환 횟수와 왕복 |
| 아코디언·탭 펼침 | 어떤 정보를 일부러 찾아봤나 |
| 텍스트 선택·복사 | 어떤 문구에 반응했나 |
| 재방문·재조회 | 같은 상품을 다시 봤나 |

GA4 는 참여 여부를 **engaged session** 으로 요약한다 [공개].
세션이 **10초 초과**, 또는 **key event 1건 이상**, 또는 **페이지뷰 2건 이상**
중 **하나만 만족하면** 참여 세션으로 센다. 10초 임계값은 설정으로 바꿀 수 있다.

여기서 배울 점은 임계값 자체보다 **여러 조건의 OR 구조**다.
단일 신호로 참여를 판정하지 않는다.

## 3. 어떤 신호로 해석하나 — 항목별 의미와 강도

수집 항목을 그대로 쓰지 않고 **의도(intent)** 로 번역해서 쓴다.
같은 클릭도 무엇을 눌렀는지에 따라 뜻이 다르다.

| 수집 항목 | 해석되는 신호 | 방향 | 강도 | 근거 |
|---|---|---|---|---|
| 구매 | 확정된 선호 | + | 최상 | [공개] 모든 플랫폼이 최상위로 씀 |
| 장바구니 담기 | 구매 의도. 구매로 안 이어져도 관심 신호 | + | 상 | [관행] 논문에 명시 |
| 찜·좋아요 | 지속적 관심. 즉시 구매는 아님 | + | 상 | [공개] 네이버 인기도 항목 |
| 후기 작성 | 구매 후 참여. 상품 신뢰도 근거 | + | 상 | [공개] 무신사 랭킹 항목 |
| 상품 조회 | 최소 관심. 양이 많아 노이즈도 많음 | + | 하 | [공개] 네이버·무신사 공통 |
| 클릭수 | 노출 대비 선택. 제목·이미지 매력도 | + | 중 | [공개] 네이버 인기도 항목 |
| 체류 시간 | 관심의 깊이 | + | 중 | [관행] |
| 스크롤 깊이 | 정보를 실제로 읽었나 | + | 중 | [관행] |
| 옵션 왕복 | 결정 못 함. 관심 높지만 **마찰** 동반 | ± | 중 | [추정] 화장품 특유 |
| 성분·상세 펼침 | 능동적 검증. 신중한 구매자 | + | 중상 | [추정] 화장품 특유 |
| 리뷰 열람 | 결정이 아니라 **확인** 단계 | + | 중 | [추정] |
| 빠른 이탈 | 부적합 | − | 중 | [관행] |
| 같은 곳 반복 스크롤 | 원하는 정보를 못 찾음 (좌절) | − | 중 | [추정] |

### 핵심: 암묵 신호는 하나만 보면 안 된다

체류 시간이 길다는 게 관심일 수도 있고 자리를 비운 것일 수도 있다.
그래서 실무에서는 **여러 신호를 조합**한다. GA4 의 engaged session 이 OR 조건인 것,
추천 시스템이 confidence 행렬을 쓰는 것이 같은 이유다.

## 4. 얼마큼 반영하나 — 세 가지 계열의 반영 방식

"비율"은 목적에 따라 완전히 다르게 정해진다. 세 계열을 섞어 보면 안 된다.

| 계열 | 목적 | 반영 방식 | 대표 |
|---|---|---|---|
| A. 랭킹형 | 상품 순위 정하기 | 지표별 점수 합산 후 정렬 | 네이버쇼핑, 무신사, 올리브영 |
| B. 추천형 | 개인별 취향 예측 | 행동을 선호도 점수로 환산해 모델 학습 | 협업 필터링, 우리 CBF |
| C. 세그먼트형 | 고객 분류·마케팅 실행 | 축별 점수화 후 등급 나누기 | RFM, 대시보드 도구 |

### 4-1. 랭킹형 — 3축 구조 [공개]

네이버쇼핑이 구조를 가장 명확히 공개했다.

| 축 | 하위 항목 | 성격 |
|---|---|---|
| **적합도** | 필드 연관도, 카테고리 선호도 (상품명·카테고리·브랜드 기입 정확도) | 정적. 판매자가 관리 |
| **인기도** | 클릭수, 판매실적, 구매평 수, 찜 수, 최신성, 배송유형·정보 | 동적. 행동 신호 |
| **신뢰도** | 쇼핑 페널티, 상품명 SEO 준수 | 감점 요소 |

배울 점 두 가지:

1. **행동 신호(인기도)는 3축 중 하나일 뿐이다.** 상품 정보 품질(적합도)과
   패널티(신뢰도)가 같은 급으로 들어간다. 행동만으로 순위를 만들지 않는다.
2. **신뢰도는 가점이 아니라 감점 축이다.** 어뷰징을 거르는 자리다.
   무신사에서 일부 입점사가 순위를 조작한 사례가 보도된 만큼 실제로 필요한 축이다.

### 4-2. 추천형 — 암묵 피드백 가중치 [관행]

명시적 별점이 없을 때 행동을 선호도 점수로 환산한다.
`view=1, cart=3, purchase=5` 같은 방식이 흔히 쓰이지만 **표준으로 고정된 값은 아니다.**
전처리 단계에서 정의하는 설계 변수다.

| 기법 | 내용 |
|---|---|
| pseudo-rating | 행동 종류·횟수를 점수로 환산해 별점처럼 씀 |
| confidence 행렬 (Hu et al., Pan et al.) | 관측된 행동에 높은 신뢰도, 미관측에 낮은 신뢰도를 부여 |
| 인기도 인식 가중 | 균일 가중보다 인기도를 고려한 가중이 성능이 좋다는 결과 |

주의할 점 [관행]:

- **균일 가중은 좋지 않다.** 조회처럼 양이 많은 신호가 결과를 지배한다
- **롱테일 편향**이 생긴다. 인기 상품이 계속 추천되는 쪽으로 쏠린다

### 4-3. 세그먼트형 — RFM [관행]

| 축 | 의미 |
|---|---|
| Recency | 최근성 — 관계의 온도 |
| Frequency | 빈도 — 습관의 깊이 |
| Monetary | 금액 — 가치의 크기 |

각 축을 1~5점으로 매겨 조합한다 (최대 125 세그먼트). 축별 가중치는 업체가 정한다.

RFM 은 **구매 이력 기반**이라 구매 데이터가 없는 우리 프로젝트에는 그대로 쓸 수 없다.
다만 "축을 나눠 점수화하고 등급으로 묶는다"는 구조는 참고할 수 있다.

## 5. 플랫폼별 상세

### 5-1. 네이버쇼핑

| 구분 | 내용 | 근거 |
|---|---|---|
| 공개 구조 | 적합도 / 인기도 / 신뢰도 3축 | [공개] |
| 인기도 항목 | 클릭수, 판매실적, 구매평 수, 찜 수, 최신성, 배송유형·정보 | [공개] |
| 적합도 항목 | 필드 연관도, 카테고리 선호도 | [공개] |
| 신뢰도 항목 | 쇼핑 페널티, 상품명 SEO | [공개] |
| 모델 | AI·머신러닝 기반으로 랭킹 요소 추출. 트리 기반 모델 도입 발표 | [공개] |
| 가중치·집계 기간 | **비공개** | — |

특징: **최신성**이 인기도에 들어간다. 신규 상품에 노출 기회를 주는 장치이면서,
동시에 행동 데이터가 시간 감쇠된다는 뜻이기도 하다 [추정].

### 5-2. 무신사

| 구분 | 내용 | 근거 |
|---|---|---|
| 상품 랭킹 지표 | 상품 매출, 판매 수량, 상품 조회 수, 작성 후기 수 | [공개] |
| 브랜드 랭킹 지표 | 인지도, 매출, 상품 조회 수 | [공개] |
| 추천순 | 클릭·좋아요 등 인터랙션을 고려 | [공개] |
| 광고 반영 | **없음.** 100% 순위만 집계 | [공개] |
| 갱신 주기 | 실시간 / 일간 / 주간 / 월간 / 3개월 | [공개] |

#### 값을 정할 때 지킨 규칙

1. **`product_view` = 1.0 을 기준선으로 상대 배치** — 절대값에 의미를 두지 않는다
2. **노출은 0** — 사용자 의지가 아닌 것에 선호를 주지 않는다
3. **감점은 별도 벡터** — `v_u` 분모에 음수를 넣지 않는다
4. **단독 판정 금지** — 0.3 짜리(`scroll_pause`, `hover_dwell`)는 다른 신호와 함께일 때만
5. **같은 행동도 대상에 따라 다르다** — `content_kind` / `section_id` 를 가중치 키에 포함
6. **이중 가산 금지** — 같은 행동을 두 이벤트가 세면 한쪽을 0 으로 (`section_view`)
7. **추정은 추정이라고 쓴다** — 어떤 플랫폼도 남의 가중치를 공개하지 않는다

#### 척도를 AI 추천 설계서에 맞췄다

AI 파트 추천 설계서가 이미 `PRODUCT_VIEW = 1.0` 을 기준으로 `LIKE = 3.0`,
`CART = 4.0` 척도를 정의해 두었다. **두 문서가 다른 척도를 쓰면 구현 단계에서
충돌하므로 그 척도를 그대로 쓴다.** 여기서 더하는 것은 두 가지다.

1. 설계서에 없는 우리 실제 이벤트 이름으로 매핑 (설계서는 `PRODUCT_VIEW` 같은
   일반명, 프론트는 `page_view` 처럼 구현된 이름)
2. 설계서에 없는 **감점 축** — 좌절·이탈 신호

#### 긍정 신호

`v_u` (사용자 벡터) 계산에 들어가는 가중치다. 값이 클수록 그 상품 벡터가
사용자 벡터를 더 끌어당긴다.

| 이벤트 | 가중 | 방향 | 의미 | 근거 |
|---|---|---|---|---|
| `add_to_cart` | **4.0** | + | 구매 의도. 구매 데이터가 없는 환경에서 가장 강한 신호 | 설계서 `CART` [공개] · 장바구니는 구매로 안 이어져도 관심 신호 [관행] |

#### 감점 신호

설계서의 `negative_penalty` 항에 들어간다. **`v_u` 분모에 음수를 넣지 않는다** —
분모가 0에 가까워질 수 있어서, 긍정 벡터와 부정 벡터를 따로 만들고 최종 점수에서 뺀다.

| 이벤트 | 가중 | 방향 | 의미 | 근거 |
|---|---|---|---|---|
| `rage_click` | **−2.0** | − | 반응 없는 곳을 연타. 명확한 좌절 | [추정] |
| `dead_click` | **−1.5** | − | 누를 수 없는 것을 눌렀다. UI 오해 또는 기대 불일치 | [추정] |
| `scroll_backtrack` | **−1.0** | − | 원하는 정보를 못 찾아 되돌아갔다 | [추정] |
| `exit_summary` (짧은 체류) | **−1.0** | − | 빠른 이탈 = 부적합. 단순 이탈은 부정 의도가 아닐 수 있어 낮게 둔다 | 설계서 "단순 이탈은 낮은 Weight" [공개] |

**주의:** 좌절 신호는 상품이 아니라 **화면 구성**의 문제일 수 있다. 특정 상품에서
`rage_click` 이 몰리면 그 상품이 싫다는 뜻이 아니라 그 페이지의 UI 문제일 가능성을
먼저 봐야 한다. 상품 선호와 UI 품질을 같은 축에 넣지 않는다.

#### `section_dwell` 은 섹션에 따라 값이 다르다

같은 체류 1초도 어느 섹션인지에 따라 의미가 다르다. `content_kind` 속성으로
구분되므로 그 값에 따라 가중을 나눈다.

| 섹션 | 가중 | 이유 |
|---|---|---|
| `ingredients` | 1.5 | 능동적 검증. 화장품 고유의 상위 요인 |
| `reviews` | 1.5 | 확인 단계지만 체류가 길고 판단에 직결 |
| `about_product` | 1.0 | 기본 정보 확인 |
| `product_hero` | 0.5 | 진입하면 무조건 보게 되는 자리. 의지가 약하다 |
| `highlights` | 0.5 | 스쳐 지나가는 비중이 높다 |
| `how_to_use` | 1.0 | 사용법을 본다 = 구매를 가정한 탐색 |
| `similar_products` | 0.5 | 이 상품에 대한 관심이 아니라 **이탈 신호에 가깝다** |

`similar_products` 체류가 길면 현재 상품에 만족하지 못했다는 뜻일 수 있다.
그래서 낮게 두고, 이후 `product_click` 이 이어지는지로 판단을 보강한다.

#### 스크롤 단계값

`scroll_depth` 는 도달 지점만 의미가 있다. **누적 합산하면 끝까지 내려간 사용자가
10%·20%·…·100% 를 모두 더해 과대 점수를 받는다.** 상품별로 **도달한 최대 깊이 1건만**
Feature 에 반영한다. 원본 이벤트는 전부 보존한다.

| 최대 도달 | 가중 |
|---|---|
| 25% | 0.2 |
| 50% | 0.5 |
| 75% | 1.0 |
| 100% | 1.5 |

> **구현 불일치 (확인 필요)**
> 프론트는 현재 **10% 단위**로 `scroll_depth` 를 찍는다 (긴 페이지에서 25% 한 칸이
> 2000px 이라 성겼다는 이유, `behavior-log-design.md`). AI 추천 설계서는 25% 단위
> 기준으로 위 단계값을 정의했다. **10% 단위 로그를 25% 구간으로 접어서 매핑할지,
> 설계서 단계를 10% 기준으로 다시 정의할지 정해야 한다.**

#### 원칙 다섯 가지

1. **`product_view` 를 1.0 으로 두고 나머지를 상대적으로 잡는다** — 기준선
2. **노출(`section_view`)은 0** — 사용자 의지가 아니다. 분모로만 쓴다
3. **감점은 별도 벡터** — `v_u` 분모에 음수를 넣지 않는다
4. **단독 판정 금지** — `scroll_pause`, `hover_dwell` 은 0.3 으로 두고 다른 신호와
   함께일 때만 의미를 준다. GA4 참여 판정이 OR 조건인 것과 같은 이유
5. **같은 이벤트도 대상에 따라 값이 다르다** — `content_kind` / `section_id` 를
   가중치 조회 키에 포함한다

#### 검증 방법

이 값들은 가설이므로 Ablation 으로 확인한다.

| 실험 | 확인할 것 |
|---|---|
| 감점 축 제거 | 좌절 신호가 추천 품질에 기여하는가 |
| 암묵 신호(체류·스크롤) 제거 | 클릭류만으로 충분한가 |
| 섹션별 가중을 균일하게 | 섹션 구분이 실제로 효과가 있는가 |
| `section_view` 를 0 대신 0.5 로 | 노출을 신호로 쓰면 인기 상품 편향이 커지는가 |

평가는 **실제 세포라 리뷰 Holdout** 으로 한다 (합성 행동 로그로 추천 정확도를
주장하지 않는다).

### 7-4. 이후 추가된 이벤트 10종 [추정]

7-3 을 쓴 뒤 화면이 늘면서(목록 필터·Quicklook·장바구니) 이벤트가 20종에서 35종이
됐다. 여기서는 **7-3 에 없던 10종**의 값과 근거를 채운다. 척도는 7-3 과 같다
(`product_view` = 1.0 기준선).

#### 목록 탐색 — 필터와 정렬

| 이벤트 | 가중 | 방향 | 의미 | 근거 |
|---|---|---|---|---|
| `filter_change` | **1.0** | + | 조건을 걸어 후보를 좁혔다. **선택한 필터 값 자체가 선호 속성**이다 | 검색·필터 사용자가 브라우징만 한 사용자보다 **전환율 7배** [공개] |
| `sort_change` | **0.5** | ± | 정렬 기준 변경. 상품이 아니라 **판단 기준**에 대한 신호다 | 가격 정렬 = 가격 민감도 [관행] |

`filter_change` 를 1.0 (= `product_view` 와 동일) 으로 둔 이유가 있다. 이 이벤트는
상품 한 개를 가리키지 않는다. **"저자극", "수분" 을 골랐다는 사실 자체가 사용자
속성 벡터에 들어가야** 하고, 그 점에서 상품 하나를 본 것과 비슷한 무게다.
7 배 차이는 필터 사용자가 이미 구매 의도를 가지고 들어왔다는 뜻이기도 해서,
필터를 쓴 세션 전체를 높은 의도 구간으로 볼 근거가 된다.

`sort_change` 를 0.5 로 낮게 둔 것은 **어느 상품도 지목하지 않기 때문**이다.
다만 `sort_key` 값은 버리면 안 된다. `price_asc` 를 고른 사용자와 `rating` 을
고른 사용자는 다른 사람이고, 이건 상품 선호가 아니라 **사용자 축**에 쌓아야 한다.
가격 정렬을 반복하는 페르소나에게 최고가 상품을 추천하면 그 자체로 실패다.

> 데이터 파트 요청으로 두 이벤트의 `product_id` 는 `null` 이다.
> 목록 전체에 대한 행동이라 특정 상품에 귀속시킬 수 없다.

#### Quicklook — 조심해서 다뤄야 하는 신호

| 이벤트 | 가중 | 방향 | 의미 | 근거 |
|---|---|---|---|---|
| `quick_look` | **1.5** | + | 목록에서 요약을 열어봤다. 상세 진입보다 가볍지만 클릭보다 무겁다 | 아래 단서 참고 |
| `quick_look_close` | **0** | — | 메타 이벤트. **`quick_look` 을 사후 판정하는 데 쓴다** | Baymard: 오작동 개방이 잦다 [공개] |

Baymard 사용성 조사가 Quick View 에 대해 두 가지를 지적한다.

1. 다수의 피험자가 Quick View 를 **실제 상품 페이지로 착각**했다
2. **실수로 열리는 경우가 잦아** 오히려 좌절을 만든다
3. 의류·인테리어처럼 **시각 위주 상품에는 유용**하지만, 스펙 위주 상품에는 덜 유용하다

화장품은 이 분류에서 애매하다. 색·제형은 시각 위주지만 성분·용량은 스펙 위주다.
그래서 `quick_look` 을 **단독으로 관심 신호로 쓰지 않는다.** 우리 구현은 닫을 때
`quick_look_close` 에 아래를 함께 남긴다.

```
close_reason      backdrop / esc / button / navigate
dwell_ms          열려 있던 시간
variants_viewed   옵션을 몇 개나 봤나
added_to_cart     담았나
wishlisted        찜했나
```

**집계 규칙:** `dwell_ms` 가 짧고 `close_reason` 이 `backdrop` 이며 아무 상호작용도
없었으면 **오작동 개방으로 보고 가중을 0 으로 낮춘다.** Baymard 가 지적한 오작동
개방을 그대로 선호도로 넣으면 목록에서 손이 스친 상품이 추천에 올라온다.

반대로 `variants_viewed >= 2` 이거나 `added_to_cart` 면 상세 진입 없이 판단이
끝난 것이므로 `product_view` 수준(1.0) 이상으로 본다. 지금 값 1.5 는 이 두 경우의
중간이며, **`quick_look_close` 를 보고 사후에 조정하는 것이 전제**다.

#### 긁어간 문장 — 정보 부족의 직접 증거

| 이벤트 | 가중 | 방향 | 의미 | 근거 |
|---|---|---|---|---|
| `text_selection` | **0.5** | + | 문장을 드래그했다. 읽고 있다는 약한 증거 | 정보 탐색 이론 [공개 이론] |
| `text_copy` | **1.0** | ± | **페이지 밖으로 들고 나갔다.** 관심은 크지만 여기서 답을 못 찾았다 | 정보 탐색 이론 [공개 이론] |

정보 탐색 이론(Information Foraging / Information Scent)은 사용자가 동물이 먹이를
찾듯 **단서의 냄새를 따라 이동**한다고 본다. 냄새가 약하면 그 자리를 떠난다.

복사는 이 관점에서 **양면 신호**다.

- **긍정** — 성분명을 복사할 만큼 그 상품에 관여했다
- **부정** — 우리 페이지 안에서 답을 못 찾아 **밖에서 찾으려고** 들고 나갔다

그래서 `text_copy` 를 `product_id` 에 대한 선호로만 쓰면 안 된다.
**긁힌 성분을 빈도순으로 모으는 쪽이 훨씬 값이 크다.**

> **원문은 저장하지 않는다** (데이터 계약). 대신 긁은 구간을 성분 사전에 대조해
> **표준 명칭만** 남긴다 (`matched_ingredients`). 사용자가 친 글자가 아니라 우리가
> 가진 값이라 원문 저장이 아니다. 사전은 `contracts/product-feature-vocab.json` 으로
> AI 파트가 상품 벡터에 쓰는 것과 같아서, "이 성분을 긁은 사람" 과 "이 성분이 든
> 상품" 이 같은 이름으로 조인된다. 어느 판 사전인지도 `vocab_version` 으로 함께 남긴다.
특정 성분명이 반복해서 복사되면 그건 "이 성분은 설명이 부족하다" 는
브랜드 담당자용 개선 지시다. 대시보드 ③-2 가 이걸 쓴다.

`text_selection` 은 0.5 로 낮다. 드래그는 읽기 습관이라 사람마다 편차가 크다.
어떤 사람은 읽는 줄을 따라 습관적으로 긁고 어떤 사람은 전혀 안 긁는다.
7-3 원칙 4(단독 판정 금지)를 따른다.

> **PC 전용이라는 전제가 여기서 한 번 유리하게 작용한다.** 이 두 이벤트는 포인터가
> 있어야 발생하므로 모바일이 섞이면 기기별로 결측이 생겨 값을 비교할 수 없다.
> 우리는 전 사용자가 데스크톱이라 **수집률이 균일**하고, 낮은 가중을 주더라도
> 사용자 간 비교에는 쓸 수 있다. 낮게 둔 이유는 기기가 아니라 **행동 자체의 모호함**이다.

> **한계:** 복사 행동 자체를 다룬 커머스 연구는 찾지 못했다. 위 해석은 정보 탐색
> 이론을 적용한 것이고, 값은 **[추정]** 이다.

#### 노출 계열 — 가중 0 이지만 없으면 추천 평가가 불가능하다

| 이벤트 | 가중 | 역할 |
|---|---|---|
| `product_view` | **1.0** | 상품 단위 조회. **기준선** (7-3 의 `page_view` 역할을 넘겨받았다) |
| `recommendation_impression` | **0** | 추천 노출. 클릭률의 **분모** |
| `impression_dwell` | **0** | 노출 카드가 화면에 실제로 머문 시간 |
| `recommendation_snapshot` | **0** | 재정렬 시점의 **순위 스냅샷** |

이 네 개는 선호도 벡터에 0 으로 들어간다. 그런데도 남기는 이유가 명확하다.

**`product_view` 로 기준선을 옮긴 이유.** 7-3 은 `page_view` 를 1.0 기준선으로
잡았다. 데이터 파트 요청으로 상품 단위 조회를 `product_view` 로 분리하면서
기준선도 이쪽으로 옮겼다. `page_view` 는 화면 이동을 표현하므로 목록·장바구니
에서도 발생하고, 상품 선호의 기준선으로는 부정확했다. **두 값을 모두 1.0 으로
두면 상세 진입 한 번이 두 번 세어진다.** 두 이벤트가 **둘 다 `product_id` 를
싣고**, 집계는 `product_id` 가 있고 가중이 양수인 이벤트를 전부 그 상품에
귀속시키기 때문이다. 데이터 파트가 페르소나 300명으로 실측했더니 두 이벤트의
귀속 가중 합이 **1,378 로 정확히 같았다.** 그래서 `page_view` 를 0 으로 내렸다.

**나머지 셋은 편향 보정용이다.** 클릭 로그를 그대로 학습에 쓰면 안 된다는 것이
Unbiased Learning-to-Rank 계열 연구의 출발점이다. 사용자는 **위쪽 항목을 더 많이
보기 때문에**, 아래에 놓인 좋은 상품은 선호와 무관하게 클릭이 적다(위치 편향).
보정하려면 **"어느 자리에 몇 번 노출됐는가"** 가 있어야 한다.

- `recommendation_impression` — 노출 횟수. 분모
- `recommendation_snapshot` — **노출 시점의 순위**. 위치 편향 보정의 입력
- `impression_dwell` — 화면에 실제로 머문 시간

`impression_dwell` 이 특히 중요하다. 위치 편향 보정은 보통 "위쪽이면 봤을
확률이 높다" 는 **가정**으로 노출 확률을 추정한다. 우리는 카드가 화면에 얼마나
머물렀는지를 **직접 측정**하므로, 추정 대신 관측값을 쓸 수 있다.
빠르게 스크롤해 지나간 카드와 3 초간 화면 가운데 있던 카드를 같은 1 노출로
세면 클릭률의 분모가 부풀어 지표가 못 쓰게 된다.

> 이 셋이 없으면 "추천이 실제로 먹혔는가" 를 **측정할 수 없다.** 선호도 가중이
> 0 인 것과 쓸모가 없는 것은 다르다. B2B 대시보드가 파는 것이 바로 이 측정값이다.

#### 7-4 이벤트 검증 방법

7-3 과 마찬가지로 값은 가설이다.

| 실험 | 확인할 것 |
|---|---|
| `quick_look` 을 오작동 개방 포함/제외 | Baymard 지적이 우리 화면에서도 재현되는가 |
| `filter_change` 의 필터 값을 사용자 벡터에 반영/미반영 | 명시적 조건이 암묵 신호보다 나은가 |
| `impression_dwell` 로 분모 보정 전/후 | 노출 품질 보정이 추천 지표를 바꾸는가 |
| `text_copy` 를 선호 신호로 사용/미사용 | 양면 신호를 한쪽으로만 쓰면 어떻게 되는가 |

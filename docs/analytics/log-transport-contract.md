# 로그 전송 주기 계약 (제안)

작성: 프론트 (2026-08-28)
상태: **제안.** 백엔드와 합의되면 `contracts/` 로 옮긴다.

백엔드가 단위 검증(TPS·Latency·Consumer Lag)을 하려면 프론트가 **언제 몇 건씩
보내는지**가 고정돼 있어야 한다. 이 문서는 그 값을 정하고 근거를 남긴다.

## 1. 현재 구현값

`frontend/src/lib/logger.ts`

| 항목 | 값 |
|---|---|
| 배치 크기 | 20건 |
| 전송 주기 | 5초 |
| 전송 조건 | **20건 도달 또는 5초 경과 중 먼저 오는 쪽** |
| 전송 방식 | 미연결 (`console.debug` 임시 싱크) |

## 2. 전송 시점을 결정하는 식

`e` = 사용자 1명의 초당 이벤트 수, `B` = 배치 크기, `T` = 전송 주기.

```
e × T ≥ B  →  크기 트리거.  전송 간격 = B / e 초
e × T < B  →  시간 트리거.  전송 간격 = T 초
```

현재 값(B=20, T=5)의 분기점은 **e = 4 이벤트/초** 다.
그보다 느리면 5초마다, 빠르면 20건마다 나간다.

**사용자 1명당 요청 수:**

```
느린 구간 (e < 4):   1 / T        = 0.2 req/s
빠른 구간 (e ≥ 4):   e / B        = e / 20 req/s
```

## 3. 실제 이벤트 발생량 (측정)

`behavior-log-design.md` 에는 **한 방문(1~2분)당 30~60건**으로 적혀 있으나
실제와 맞지 않는다.

| 관측 | 값 |
|---|---|
| 화면에 표시된 누적 로그 (가벼운 조작) | **158건** |
| 스크립트로 1회 훑어내리고 올라오기 | **57건** (`section_dwell` 37 + `section_view` 20) |

57건은 **스크롤 계열 이벤트가 빠진 값**이다. 측정에 쓴 브라우저 창이 표시되지
않는 상태라 `scroll` 이벤트가 발생하지 않았다 (직접 붙인 확인용 리스너도 0건 수신).
`scroll_depth` 와 `scroll_pause` 는 실제 브라우저에서 정상 동작하며 여기서만 안 잡혔다.

즉 **실제 방문당 100~160건 수준**이고 문서의 30~60건은 2~3배 과소 추정이다.

가장 큰 기여자는 `section_dwell` 이다. 섹션을 벗어날 때마다 1건 나가므로
아래로 내려갔다 올라오면 섹션 수의 2배가 쌓인다 (섹션 7개 → 최대 14건, 실측 37건).

> `behavior-log-design.md` 의 추정치를 고쳐야 한다. 아래 규모 계산의 입력값이다.

## 4. 시뮬레이션 규모에서의 요청량

방문당 150건 / 90초 → **e ≈ 1.7 이벤트/초**. 시간 트리거 구간이다.

| 동시 사용자 | 이벤트 TPS | 요청/초 (B=20, T=5) | 평균 배치 크기 |
|---|---|---|---|
| 100 | 170 | 20 | 8.5 |
| 1,000 | 1,700 | 200 | 8.5 |
| 5,000 | 8,500 | 1,000 | 8.5 |
| 10,000 | **17,000** | **2,000** | 8.5 |

**여기서 문제가 보인다.** e가 4보다 작으면 배치가 20건을 못 채우고 5초마다 나가서,
평균 8.5건짜리 요청이 초당 2,000건 발생한다. **이벤트 수는 1.7만 TPS인데 HTTP
요청 수가 불필요하게 크다.**

## 5. 제안: 실사용자와 부하 생성기의 정책을 분리한다

같은 값을 둘 다 쓰면 안 된다. 목적이 다르다.

| | 실사용자 브라우저 | 부하 생성기 (Synthetic) |
|---|---|---|
| 목적 | 이탈 전에 안전하게 보내기 | 목표 TPS 달성 |
| 배치 크기 | **20건** (유지) | **500~2,000건** |
| 전송 주기 | **5초** (유지) | **1초** |
| 이탈 시 전송 | `sendBeacon` 필수 | 불필요 |
| 예상 요청/초 (1만명) | 2,000 | **10~35** |

부하 생성기는 브라우저가 아니므로 이탈 걱정이 없고, 큰 배치로 묶어도 데이터
유실 위험이 없다. **10,000명 시나리오에서 요청 수를 2,000에서 수십 건으로 줄이면서
이벤트 TPS는 그대로 유지된다.** Kafka·Spark 검증에 필요한 것은 이벤트 TPS다.

`actor_type` 필드로 두 경로가 이미 구분된다 (`user` / `synthetic`).

## 6. 확정해야 할 항목

### 6-1. 프론트가 지키는 것

| 항목 | 제안값 | 비고 |
|---|---|---|
| 배치 크기 | 20건 | 실사용자 |
| 전송 주기 | 5초 | 실사용자 |
| 전송 조건 | 크기 또는 시간 중 먼저 | |
| 엔드포인트 | `POST /api/events` | 프론트/백엔드 확정 |
| 요청 본문 | `{ "schema_version": "0.2.0-draft", "events": [ ...LogEnvelope ] }` | 배치와 Event 각각 버전을 보존 |
| 이탈 시 | `visibilitychange`(hidden) · `pagehide` 에서 `sendBeacon` | 마지막 배치 유실 방지 |
| 최대 본문 크기 | 미정 | **백엔드 한계 확인 필요** |

`sendBeacon` 은 본문 크기 상한이 있고 브라우저마다 다르다. 배치 20건이 상한을
넘지 않는지 확인해야 한다. `text_snippet` 이 최대 140자라 한 건이 커질 수 있다.

### 6-2. 백엔드에 확인할 것

| 항목 | 왜 필요한가 |
|---|---|
| 엔드포인트 경로·인증 | 연동 착수 조건 |
| 요청 본문 최대 크기 | 배치 크기 상한을 여기에 맞춘다 |
| 응답 코드 규약 | 성공/부분성공/재시도 구분 |
| 재시도 정책 | 실패한 배치를 프론트가 다시 보낼지, 버릴지 |
| 중복 허용 여부 | 아래 6-3 참고 |
| 순서 보장 필요 여부 | 아래 6-4 참고 |

### 6-3. 중복은 프론트가 막지 않는다

`sendBeacon` 은 전송 성공 여부를 알려주지 않는다. 재시도를 붙이면 **같은 배치가
두 번 적재될 수 있다.** 프론트에서 이걸 완전히 막을 방법이 없다.

대신 모든 이벤트에 **`event_id` (UUID)** 가 붙어 있다.
**적재 단계에서 `event_id` 기준으로 멱등 처리**하는 것을 제안한다.
이 방식이면 프론트가 마음 놓고 재시도할 수 있다.

### 6-4. 순서는 `sequence_no` 로 복원한다

네트워크 순서는 보장되지 않는다. 대신 이벤트마다 다음 세 개가 있다.

| 필드 | 용도 |
|---|---|
| `session_id` | 한 방문 |
| `page_view_id` | 한 페이지 조회 |
| `sequence_no` | 세션 내 발생 순서 (1부터 증가) |

`occurred_at` 은 클라이언트 시계라 신뢰할 수 없다.
**세션 내 순서는 `sequence_no` 로 정렬**하는 것을 제안한다.
서버 수신 시각을 별도 컬럼으로 남기면 지연 측정도 가능하다.

### 6-5. 측정 지점 합의

백엔드가 재려는 지표에 프론트 값이 필요하다.

| 지표 | 필요한 것 |
|---|---|
| 이벤트 TPS | 배치 크기 × 요청 수. 위 4번 표 |
| End-to-end Latency | `occurred_at` (클라이언트) vs 서버 수신 시각. 시계 차이 주의 |
| Event Loss | 전송한 이벤트 수를 프론트가 알 수 없다. **`sequence_no` 의 빈 번호로 서버가 판정**하는 방식 제안 |
| 중복 | `event_id` 중복 건수 |

`sequence_no` 가 세션 내에서 1부터 연속이므로, 서버가 세션별로 번호를 모아
빠진 번호를 세면 유실을 정확히 계산할 수 있다. 이 방식을 쓰려면
**프론트가 순번을 건너뛰지 않는다는 보장**이 필요한데, 현재 구현은 `track()` 이
호출될 때마다 무조건 1 증가시키므로 성립한다.

## 8. 확정 (2026-08-28)

백엔드가 **프론트 계약에 맞추기로** 해서, 아래 값은 프론트 구현이 기준이다.
`frontend/src/types/log.ts` 의 `LogEnvelope` 가 단일 출처다.

### 8-1. 열려 있던 항목 결정

| 항목 | 결정 | 이유 |
|---|---|---|
| 엔드포인트 | **`POST /api/events`** | 백엔드에 이미 구현·테스트가 있어 그쪽을 따랐다 |
| 배치 본문 | `{ schema_version, events: [...] }` | 백엔드 기존 형태 유지 |
| 이벤트별 `schema_version` | **유지** | 배치와 중복이지만, 버전이 섞인 배치도 이벤트 단위로 해석된다 |
| `persona_id` | **null 허용** | 페르소나 선택 전에는 값이 없다. 가짜 값을 채우면 실제 익명 방문과 구분이 안 된다 |
| 이벤트 이름 표기 | **`lower_snake_case`** | `product_click` 형태. 점 표기는 쓰지 않는다 |
| 필드 이름 | 프론트 `LogEnvelope` 그대로 | `event_name` / `occurred_at`. `event_type` / `event_time` 아님 |

### 8-2. 전송 구현

`frontend/src/lib/logger.ts` 에 실제 전송을 붙였다 (기존 TODO 해제).

- 평시: `fetch` + `keepalive`
- 이탈 시: `navigator.sendBeacon` (`visibilitychange` hidden, `pagehide`)
- 실패 시: 배치를 큐 앞으로 되돌리고 다음 주기에 재시도
- 큐 상한 **1000건**. 넘치면 오래된 것부터 버린다 (최근 행동이 더 쓸모 있다)
- 실패 경고는 세션당 한 번만 남긴다

**재시도는 서버의 멱등 처리를 전제로 한다.** `sendBeacon` 은 성공 여부를 알려주지
않으므로 프론트에서 중복을 막을 방법이 없다. 서버가 `event_id` 로 걸러줘야 한다.

로그 전송 실패가 화면에 영향을 주지 않는다. 로그는 부가 기능이다.

### 8-3. 방문당 이벤트 수 재측정

7번의 선행 항목을 실제 브라우저에서 측정했다.

| 구간 | 이벤트 |
|---|---|
| 목록 화면 스크롤 20초 | **89건** |
| 이어서 상세까지 (`sequence_no` 기준 누적) | **102건** |

종류별로는 `section_dwell` 이 압도적이다 (89건 중 58건).
`behavior-log-design.md` 의 "방문당 30~60건" 은 과소 추정이므로 100~160건으로 본다.

전송 로그에 상한은 없다. `logger.ts` 의 `HISTORY_LIMIT = 200` 은 개발용 패널이
되돌아보기 위해 들고 있는 개수이고, 발생·전송량과 무관하다.

# 심은 신호 복원 검사 — 파이프라인이 심은 신호를 복원하는지 검증

- 상태: 2026-09-29 작성. 스크립트 `batch/jobs/check_planted_signals.py` · 테스트 `batch/jobs/test_check_planted_signals.py`
- 관련: [`behavior-log-design.md`](behavior-log-design.md) · [`../ai/evaluation-framework.md`](../ai/evaluation-framework.md) 부록 X (추천 기준선)

## 왜 이 문서가 있나

심사에서 나올 질문: **"생성기에 심은 규칙을 대시보드가 되찾은 것 아니냐."**

맞다. 합성 로그(PC 9,900명)는 `simulator/generator/gen_behavior_logs.py` 가 **규칙으로** 만든다.
그러니 대시보드에 "끝까지 본 방문은 전부 담았다" 가 뜨면 그건 발견이 아니라 우리가 심은 값이다.
우리는 이것을 숨기지 않고 **검증 도구로 쓴다**:

| 복원 값이 | 뜻 |
|---|---|
| 기대 값과 같다 | Kafka → Spark 정제 → 마트까지 신호가 **왜곡 없이** 옮겨졌다 (중복·누락·조인 오류 없음) |
| 기대 값과 다르다 | 정제·집계 어딘가에서 신호가 새거나 부풀었다 → 조사 대상 |

즉 합성 로그 위의 대시보드 숫자는 **"사장님 가게의 통찰"이 아니라 "파이프라인이 정확하다는 증거"** 다.
통찰 주장은 실제 사람 로그(프론트·LLM 에이전트 PA 100명)와 세포라 실제 리뷰에서 온 부분(무엇을 샀나 —
시드·target 상품, 성향 점수 원천)에만 건다. 생성기는 **"어떻게 보는가"(깊이·체류·드래그)만 규칙으로 정하고
"무엇을 사는가"는 실제 리뷰 이력을 따른다**(생성기 `STYLE_EFFECT` 주석). 그래서 아래 표에 없는 것 —
어떤 브랜드·성분·가격대가 팔렸나 — 은 규칙이 아니라 실제 리뷰에서 왔다.

## 방법

- 심은 값은 생성기의 `SCENARIO` · `STYLE_EFFECT` · `DETAIL_LAYOUT` 을 **직접 import** 해서 읽는다. 사본이 없어 생성기를
  고치면 기대 값도 같이 바뀐다.
- target(정답 상품)은 로그에 없으므로 쓰지 않는다. **로그에 보이는 것**(스크롤 깊이·담기·찜·결제·등록 상품 여부·
  페르소나 성향 점수)으로만 잰다. 단위는 상세 방문(page_view_id), 시드(`seed:`)·과거 구매(`hist:`) 세션은 따로 뺀다.
- 판정은 이항 3σ(또는 규칙상 범위 ± 3σ) 안이면 "일치". 20개 넘게 한 번에 보므로 1,000명 표본에서는 가끔 경계에
  걸린다(1,000명에서 방문 횟수가 3σ 를 살짝 넘었고 3,000명에서는 들어왔다) — **3,000명 이상으로 본다.**
- **rule 모드(기본) 로그 전제.** `--behavior hidden_preference` 로그는 깊이·담기를 다른 규칙이 정하므로 이 표가 맞지 않는다.

### 로그에서 깊이가 다르게 보이는 이유

상세는 섹션 7개 단위로 `scroll_depth` 를 남긴다(`visit_detail`). 그래서 **심은 90 은 로그에서 85**,
20/30/40/50 은 14/28/40/50 으로 보인다. 마트나 대시보드에서 "90% 본 방문" 을 찾으면 0건이 나오는 것이 정상이다.

## 심은 규칙과 복원 값

"생성기 원본" 열은 생성기 출력 JSONL 을 **파이프라인을 거치기 전에** 이 스크립트로 잰 값이다(2026-09-29,
`--limit 3000`, rule 모드, 3,000명 · 상세 방문 18,863건). 스크립트와 기대 값 계산이 맞다는 **자기 점검**이지
파이프라인 검증이 아니다. **파이프라인 검증은 오른쪽 열** — 같은 실행을 Kafka 로 보내 정제된 `cleaned_events` 에서
잰 값 — 이고 아직 돌리지 않았다(이 PC 에 `cleaned_events` 가 없다).

| 심은 규칙 (생성기 위치) | 심은 값 | 기대 결과 | 생성기 원본 (자기 점검) | 복원 값 — cleaned_events (실행 후 채움) |
|---|---|---|---:|---|
| 목표 상품은 끝까지 보고 반드시 담는다 (`is_target` → depth 100 · `add_to_cart`, 1602·1638행) | depth 100 · 담기 1.0 | 끝까지 본 방문의 담기율 = 1.00 | 1.000 (n=3,000) | 실행 필요 |
| └ 목표 상품은 페르소나당 1개 (`pos[-1]`) | 1개 | 끝까지 본 방문 / 페르소나 = 1.00 | 1.000 | 실행 필요 |
| 이탈 상품 30% 는 깊이 90 (`p_deep_bounce` · `deep_bounce_depth`, 303~304행) | p = 0.30 | 이탈 방문 중 최대 스크롤 **85%** 비율 = 0.30 | 0.300 (n=10,591) | 실행 필요 |
| └ 나머지는 깊이 20/30/40/50 균등 (`bounce_depth_choices`, 256행) | 균등 | 14/28/40/50% 각 0.175 | 0.179 / 0.175 / 0.173 / 0.173 | 실행 필요 |
| └ 이탈 상품은 100% 에 닿지 않는다 | depth < 100 | 1.00 | 1.000 | 실행 필요 |
| 목표 상품 찜 (`wishlist_p_target`) | p = 0.45 | 끝까지 본 방문의 찜 비율 = 0.45 | 0.458 | 실행 필요 |
| 이탈 상품 찜 (`wishlist_p_bounce`) | p = 0.08 | 담지 않은 일반 이탈 방문의 찜 비율 = 0.08 | 0.081 (n=8,595) | 실행 필요 |
| 목표 상품 결제 (`p_purchase_after_cart` × (1 − `p_payment_failed`)) | 0.45 × 0.95 | 같은 세션 결제율 = 0.427 | 0.435 | 실행 필요 |
| 등록 브랜드 발견 담기 (`p_new_brand_cart`, 349·1645행) | p = 0.12 | 등록 상품 이탈 방문 중 담고 안 뺀 비율 0.094~0.120 (담았다 빼기 분기가 먼저라 하한이 있다) | 0.121 (n=363) | 실행 필요 |
| └ 비교: 일반 상품은 이 경로가 없다 | — | 0.00 | 0.000 (n=10,228) | 실행 필요 |
| 이탈 상품 하나를 담았다 뺀다 (`p_cart_regret`, 1인 최대 1회) | p = 0.22 / 이탈 방문 | 뺀 페르소나 비율 = 평균[1 − 0.78^이탈 수] = 0.568 | 0.564 | 실행 필요 |
| └ 마지막 방문에서 발견 담은 등록 상품 결제 (`p_new_brand_buy` × 0.95) | 0.55 × 0.95 | 0.522 | 0.421 (n=19, 표본 적음) | 실행 필요 |
| 성분 성향 → 전성분 드래그 (`STYLE_EFFECT.ingredient` · `p_ingredient_selection` 0.40 × 최대 2.2배, 378행) — 성향 ≤ 0.5 | 0.40 × 1.0 | 정독 방문의 전성분 드래그율 = 0.400 | 0.394 (n=3,227) | 실행 필요 |
| └ 성향 상위 25% (≥ 0.66) | 0.40 × f(성향) | 0.653 | 0.650 (n=1,558) | 실행 필요 |
| └ 상위 25% / ≤ 0.5 배율 | 최대 2.2배 | 1.63배 (상위 25% 의 실제 성향 분포로 계산) | 1.648배 | 실행 필요 |
| 부정 시드 rage_click (`neg_seed_p_rage`) | p = 0.35 | 시드 상세 방문의 rage_click 비율 = 0.35 | 0.375 (n=536) | 실행 필요 (마트는 시드를 빼므로 cleaned_events 에서만) |
| 뒤로가기 재조회 (`p_history_back`) | p = 0.06 | 재조회 / 이탈 방문 = 0.06 | 0.061 | 실행 필요 |
| └ 재조회는 얕게 (깊이 25) | depth 25 | 1.00 | 1.000 (n=644) | 실행 필요 |
| 방문 횟수 1/2/3회 (`visit_weights`) | 0.35 / 0.40 / 0.25 | 같음 | 0.348 / 0.392 / 0.260 | 실행 필요 |
| 이탈 상품 수 (`bounce_range` (2, 6) → 2~5개) | 균등 | 페르소나당 평균 3.50 | 3.530 | 실행 필요 |

**배율을 "2.2배" 로 말하지 않는다.** 2.2배는 성향 점수 1.0 인 사람의 상한이다. 식은
`1 + 1.2 × max(0, (성향 − 0.5) × 2)` 이고 상위 25% 의 실제 성향이 0.66 이상이라 기대 배율은 약 1.6배다.
대시보드에서 "성분을 따지는 고객은 전성분을 1.6배 더 긁는다" 가 나오면 **그 숫자는 우리가 심은 것이다.**

### 표에 넣지 않은 심은 값 (스크립트 미측정)

`STYLE_EFFECT` 의 나머지 축(가격 → 옵션 선택 2.0배·상단 체류 1.6배, 제형·향 → 스크롤 정지·설명 드래그, 민감도 →
아코디언·전성분 체류, 리뷰 성향 → 리뷰 필터 2.0배·리뷰 체류 2.2배), `p_rec_click` 0.55 · `p_banner_click` 0.12 ·
`p_quick_look` 0.18 · `p_ql_add` 0.12 · `p_quantity_change` 0.18 · `p_view_cart` 0.70 · `p_discount` 0.20 ·
`p_reason_answer` 0.70 · 결제 수단 카카오페이 0.6 / 카드 0.4 · `restock_gap_days` 14~30일 · `window_days` 85일.
같은 방식으로 늘릴 수 있다 — 대시보드 화면에 쓰이는 값부터 추가한다.

## 실행

```bash
# 1) 자기 점검 — 생성기 출력을 직접 (파이프라인 전)
python simulator/generator/gen_behavior_logs.py --limit 3000 --allow-ctr-grain-violations --out /tmp/gen_3000.jsonl
python batch/jobs/check_planted_signals.py --events /tmp/gen_3000.jsonl

# 2) 파이프라인 검증 — 같은 실행을 수집 API 로 보내고 Q2 정제 뒤의 cleaned_events 로
python simulator/generator/gen_behavior_logs.py --limit 3000 --allow-ctr-grain-violations --post http://<수집 API>
#    (Q1 raw_sink → Q2 clean_events_job 가 끝난 뒤, EC2-2 에서)
pip install pyarrow
CLEANED_EVENTS_PATH=data/processed/cleaned_events \
  python batch/jobs/check_planted_signals.py --cleaned --run-id <생성기 로그의 simulation_run_id> --markdown
#    Parquet 대신 JSONL 로 뽑았으면  --cleaned-jsonl <파일>
```

- `--run-id` 는 꼭 준다. cleaned_events 에는 여러 번의 생성기 실행이 쌓여 있다(섞이면 스크립트가 경고한다).
- 끝 줄 "어긋남 N개" 가 0 이 아니면 종료 코드 1 이다. 어긋난 행을 따라 정제(중복 제거·bad_events 분류)부터 본다.
- `--markdown` 출력의 "복원 값" 을 위 표 오른쪽 열에 옮겨 적는다.
- 참고: `--limit 3000` 은 `--allow-ctr-grain-violations` 없이 돌리면 배너 grain 검사(노출 1 < 클릭 2 인 칸 하나)에서
  멈춘다(2026-09-29 확인, 1,000명에서는 통과). 이 검사와 무관한 생성기 쪽 문제다.

이벤트 36종과 가중치

테스트 쇼핑몰에서 사용자가 남기는 행동 신호를 Event 라 부른다. 현재 계약에 36종이 정의돼 있고, 각 Event 에는 선호도 가중치가 붙는다. 이 가중치를 누적해 사용자 벡터를 만들고, 상품 추천(CBF)의 입력으로 쓴다.

이 표는 생성 스크립트가 이벤트 계약과 프론트 가중치 코드를 읽어 만든다. 여기에 숫자를 적어 두지 않는다. 다만 생성은 자동이 아니므로, 관련 코드를 바꾼 뒤에는 node docs/analytics/tools/build-event-guide.mjs 를 다시 실행해 문서를 갱신해야 한다.

가중치 설계 원칙

  • 전환 신호가 가장 높다. add_to_cart 4.0. 구매 데이터가 없는 환경이라 장바구니 담기가 가장 강한 구매 의도 신호다.
  • 노출(impression)은 가중 0 이다. 사용자 의지가 아니므로 선호도에 넣지 않고, CTR 의 분모로만 쓴다.
  • 감점 신호가 있다. remove_from_cart -2.0, rage_click -2.0, dead_click -1.5, scroll_backtrack -1.0. 담았다 뺀 것은 선호를 되돌린 것이고, 좌절 신호는 그 방문의 품질을 깎는다. 다만 좌절 신호는 상품이 아니라 화면 문제일 수 있어 상품 선호와 같은 축에 넣지 않는다.
  • 이중 계상을 막는다. 한 행동에서 두 Event 가 같은 product_id 를 실으면 한쪽을 0 으로 둔다. 상세 진입은 product_view(1.0)가 담당하고 page_view는 0 이다. section_view와 section_dwell도 같은 이유로 갈랐다.

확정값이 아니라 초기 가설이다. Ablation 으로 검증해 조정한다. 가중치 상수의 단일 출처는 frontend/src/types/log.ts 의 EVENT_WEIGHT 이고, 값별 근거는 docs/analytics/event-weight-rationale.html 에 있다.

작성: 프론트 (2026-08-27)
대상: 상품 상세 페이지 (frontend/src/pages/ProductDetailPage.tsx)

이벤트 목록은 frontend/src/types/log.ts, 구현은 frontend/src/hooks/* 에 있다.
이 문서는 왜 그 자리에 그 이벤트를 두었는지를 남긴다.

무엇이 문제였나

초안은 클릭 이벤트 위주였고, 클릭이 아닌 신호는 세 개뿐이었다.
그마저도 전부 trackOnce (방문당 1회) 라서 실제로 남는 양이 이랬다.

  • scroll_depth — 25/50/75/100 네 구간, 방문당 최대 4건
  • section_view — 섹션당 1건
  • exit_summary — 이탈 시 1건

그래서 페이지를 한참 훑어보다 그냥 나간 방문은 거의 빈 세션으로 남았다.
장바구니까지 간 소수만 데이터가 있고, 정작 "왜 안 샀는지" 를 물어볼 방문에는
아무 근거가 없다. 추천 모델 입력으로도 클릭만으로는 신호가 너무 성기다.

버그도 하나 있었다. section_view 가 intersectionRatio >= 0.5 를 조건으로 썼는데,
이 비율은 요소 면적 대비라서 뷰포트보다 긴 섹션은 값이 0.5 를 넘을 수가 없다.
리뷰 섹션처럼 긴 구간은 아무리 읽어도 로그가 찍히지 않았다.

조사: 무엇이 구매 판단에 영향을 주나

1. 이미지가 가장 크다

설문 응답자의 85% 가 상품 정보와 비주얼이 브랜드·판매처 선택에 영향을 준다고 답했다
(inriver).
화장품은 특히 사람 모델이 나온 컷이 있어야 실제 색·질감을 가늠할 수 있다
(Baymard).

그런데 Baymard 사용성 테스트에서 반복해서 나온 문제가 갤러리에서 이미지를 못 찾거나
확대를 못 하는 것이었다 (Baymard).
확대하려다 실패한 사용자는 아무 로그도 안 남기고 사라진다.

2. 성분은 화장품 고유의 상위 요인

응답자의 43.9% 가 성분을 핵심 판단 요소로 꼽았고, 신뢰는 성분 투명성·시험 결과·
표기 명확성에서 온다
(PulseAI Research).
모르는 성분을 만나면 그 부분만 긁어서 따로 검색하는 행동이 뒤따른다.

3. 리뷰는 "결정" 이 아니라 "확인"

뷰티 구매자의 88% 가 별점·리뷰를 본다. 67% 는 다른 구매자의 사진·영상을 본다
(PowerReviews).
94% 는 나쁜 리뷰 때문에 구매를 접은 적이 있다고 답했다
(DemoUp Cliplister).

중요한 건 순서다. 리뷰는 이미 후보에 올린 상품을 확인하는 단계에서 작동한다.
그래서 리뷰 열람은 관심의 시작이 아니라 구매 직전 신호로 읽어야 한다.

4. 옵션(색·용량) 왕복은 화장품 특유의 마찰

Baymard 는 모바일에서 색상 선택 시 이미지를 보려고 위로 다시 스크롤해야 하는 것을
반복 지적한다 (Baymard).
옵션을 A→B→A 로 오가는 건 비교 중이라는 뜻이다.

5. 암묵 신호는 하나만 보면 안 된다

추천 연구에서 체류 시간은 명시적 평점과 상관이 있지만, 창만 띄워두고 안 보는 경우가
있어 그것만으로는 해석이 어렵다. 커서 움직임·스크롤과 함께 볼 때 비로소
관련성의 근거가 된다
(Springer).
같은 연구 계열에서 마이크로 단위 행동으로 스크롤, 하이라이트(텍스트 선택),
확대를 꼽는다
(Jannach 외, Social Information Access).

6. 좌절 신호는 이탈로 이어진다

같은 자리를 연타하는 rage click 은 UI 가 기대대로 반응하지 않는다는 신호이고
세션 이탈로 이어진다 (Conviva).
눌리지 않는 곳을 누르는 dead click 도 같은 계열이다
(Glassbox).

이벤트 이름만으로는 부족하다

로그를 받는 쪽에서 매번 다시 판단해야 하는 게 두 가지 있었다.
둘 다 프론트가 발생 시점에 이미 아는 정보라, 이름 옆에 같이 실어 보낸다.

1. 이 이벤트가 무슨 뜻인가 — intent

text_copy 가 관심인지 확인인지, hover_dwell 이 관심인지 망설임인지는
분석하는 사람마다 다르게 잡는다. 그 판단을 한 곳(EVENT_INTENT)에 고정했다.

exposure  → interest → comparison → validation → conversion
                                                      ↕
                                                  friction
intent뜻해당 이벤트
exposure화면에 떴다scroll_depth, *_impression
interest들여다봤다section_view, section_dwell, scroll_pause, media_view
comparison다른 후보와 견줬다variant_select, scroll_backtrack, recommendation_click, product_click
validation사실을 확인했다text_selection, text_copy, review_*, ingredient_*, accordion_toggle
hesitation살까 말까 쟀다hover_dwell
conversion사는 쪽으로 움직였다add_to_cart, wishlist_toggle, quantity_change
friction기대대로 안 됐다rage_click, dead_click
session경계session_start, page_view, exit_summary

friction 만 깔때기 밖에 있다. 어느 단계에서든 새는 구멍이라서다.

2. 그 자리에 뭐가 있었나 — content_kind

section_id 는 화면 구조상의 이름이라 거기까지만 말해준다.
그런데 about_product 안에는 개요·성분·임상 근거·사용법이 같이 들어 있고,
구매 판단에서 하는 역할이 전혀 다르다. "About the Product 를 40초 봤다" 로는
성분을 본 건지 사용법을 본 건지 알 수 없다.

그래서 콘텐츠 종류를 따로 붙였다 (data-log-content).

체류도 섹션이 아니라 이 블록 단위로 잰다. 그래야
"임상 근거에서 오래 멈췄다" 같은 문장이 나온다.

레이아웃이 바뀌어도 과거 로그를 계속 읽을 수 있어야 하므로,
어느 값도 픽셀 좌표를 쓰지 않는다 (frontend/src/lib/section.ts).

화면당 콘텐츠 수를 줄였다

여기까지 해도 문제가 하나 남는다. 한 화면에 블록이 여러 개 겹쳐 보이면
그 체류가 어느 콘텐츠를 향한 건지 단정할 수 없다.
성분과 사용법이 같이 떠 있는 화면에서 10초 머문 기록은 둘 다에 쌓인다.

그래서 두 가지를 했다.

여백을 넓혔다. 섹션 사이 --space-7(48px) → --space-9(104px),
About 안의 문단 사이 --space-5(24px) → --space-8(72px).
PC 기준 한 화면에 들어오는 블록이 줄어 귀속이 그만큼 깨끗해진다.
스크롤 양은 늘지만, 이 프로젝트는 상품을 파는 게 목적이 아니라
행동 데이터를 얻는 게 목적이라 그쪽을 택했다.

남은 모호함은 로그에 적었다. 여백만으로는 히어로 영역(이미지·가격·옵션·담기)처럼
좌우로 붙어 있는 구조를 못 없앤다. 그래서 숫자로 남긴다.

  • section_dwell.co_visible_blocks — 머무는 동안 같이 떠 있던 블록 수의 최대치
  • scroll_pause.visible_content_kinds — 멈춘 순간 함께 보이던 콘텐츠 종류

분석할 때 co_visible_blocks <= 2 인 건만 골라 쓰면 귀속이 확실한 표본이 된다.
측정해 보면 페이지 평균 3.9개/화면, 히어로 영역이 4개로 가장 밀집한다.

민감도를 어떻게 잡았나

스크롤은 초당 수백 번, mousemove 는 초당 15~60 번 발생해서 그대로 받으면 안 된다
(Nolan Lawson).
대신 발생 빈도가 낮은 시점 을 골라 붙였다. 멈췄을 때, 벗어났을 때, 손을 뗐을 때.

일부러 안 남기는 것

  • 마우스 좌표 궤적 — 양 대비 얻는 게 적고, 세션 리플레이는 이 프로젝트 범위가 아니다.
  • 사용자가 입력한 값 — 텍스트 선택 로그는 입력 요소(input, textarea, contenteditable)를 제외한다. 페이지에 이미 떠 있는 문구만 남긴다.
  • 개별 스크롤 프레임 — 멈춘 지점만 남긴다.

데이터 담당자에게 확인 필요

  1. text_snippet 을 그대로 적재할지, 해시나 성분 사전 매칭 결과만 남길지. 지금은 140자까지 원문을 담고 있다.
  2. section_dwell 이 한 섹션에 여러 건 쌓인다 (벗어날 때마다 1건). 적재 후 합산할지, 프론트에서 방문당 1건으로 합쳐 보낼지.
  3. actor_type 이 synthetic 인 부하 테스트 로그를 같은 테이블에 넣을지 분리할지.
  4. 주목 이벤트(P1)를 P0 와 같은 보존 기간으로 둘지. 양이 6~10배 많다.

1. 먼저 알아야 할 것: 정확한 가중치는 공개되지 않는다

조사에서 가장 중요한 결론이다. 네이버쇼핑·무신사·올리브영 모두 랭킹에 쓰는
지표 "목록"은 공개하지만, 각 지표의 가중치·집계 기간·정규화 방식은 공개하지 않는다.

  • 네이버는 적합도/인기도/신뢰도 3축과 그 하위 항목까지 공개하지만 비중은 비공개
  • 무신사는 매출·판매수량·조회수·후기수를 쓴다고 밝히고 공식은 비공개. 기술 블로그도 집계 스택(Databricks/Spark, Elasticsearch, 90ms 응답)까지만 공개
  • 올리브영은 산정 기준 자체를 공식 문서로 공개하지 않는다

따라서 "업체들이 쓰는 비율"을 그대로 베껴올 수는 없다. 대신 쓸 수 있는 것은:

근거 종류신뢰도이 문서 표기
플랫폼·도구 공식 문서에 명시된 것높음[공개]
업계에서 표준처럼 쓰이는 관행·논문 기법중간[관행]
위 둘에서 우리 프로젝트용으로 유추한 것낮음[추정]

[추정] 항목은 우리가 정한 값이라는 뜻이다. 문서나 발표에 인용할 때
플랫폼이 그렇게 한다고 쓰면 안 된다.

반면 장바구니에서 상품을 빼는 것은 특정 상품에 대한 재고(再考) 라서

add_to_cart 의 4.0 가중이 과대평가인지도 검증할 수 있다.

장바구니 화면은 상품 목록·상세만큼 클 필요가 없다. 담은 상품 목록과 수량 조절,
삭제만 있으면 view_cart 와 remove_from_cart 가 나온다.

우리 프로젝트는 구매 이전 탐색 구간만 다루므로 퍼널 뒷부분은 비어 있다.
표준 이벤트만으로는 신호가 너무 적어서 탐색 구간을 촘촘히 봐야 한다.
이게 우리가 주목·좌절 신호를 따로 만든 이유다.

4. 얼마큼 반영하나 — 세 가지 계열의 반영 방식

"비율"은 목적에 따라 완전히 다르게 정해진다. 세 계열을 섞어 보면 안 된다.

계열목적반영 방식대표
A. 랭킹형상품 순위 정하기지표별 점수 합산 후 정렬네이버쇼핑, 무신사, 올리브영
B. 추천형개인별 취향 예측행동을 선호도 점수로 환산해 모델 학습협업 필터링, 우리 CBF
C. 세그먼트형고객 분류·마케팅 실행축별 점수화 후 등급 나누기RFM, 대시보드 도구

4-1. 랭킹형 — 3축 구조 [공개]

네이버쇼핑이 구조를 가장 명확히 공개했다.

축하위 항목성격
적합도필드 연관도, 카테고리 선호도 (상품명·카테고리·브랜드 기입 정확도)정적. 판매자가 관리
인기도클릭수, 판매실적, 구매평 수, 찜 수, 최신성, 배송유형·정보동적. 행동 신호
신뢰도쇼핑 페널티, 상품명 SEO 준수감점 요소

배울 점 두 가지:

  1. 행동 신호(인기도)는 3축 중 하나일 뿐이다. 상품 정보 품질(적합도)과 패널티(신뢰도)가 같은 급으로 들어간다. 행동만으로 순위를 만들지 않는다.
  2. 신뢰도는 가점이 아니라 감점 축이다. 어뷰징을 거르는 자리다. 무신사에서 일부 입점사가 순위를 조작한 사례가 보도된 만큼 실제로 필요한 축이다.

4-2. 추천형 — 암묵 피드백 가중치 [관행]

명시적 별점이 없을 때 행동을 선호도 점수로 환산한다.
view=1, cart=3, purchase=5 같은 방식이 흔히 쓰이지만 표준으로 고정된 값은 아니다.
전처리 단계에서 정의하는 설계 변수다.

기법내용
pseudo-rating행동 종류·횟수를 점수로 환산해 별점처럼 씀
confidence 행렬 (Hu et al., Pan et al.)관측된 행동에 높은 신뢰도, 미관측에 낮은 신뢰도를 부여
인기도 인식 가중균일 가중보다 인기도를 고려한 가중이 성능이 좋다는 결과

주의할 점 [관행]:

  • 균일 가중은 좋지 않다. 조회처럼 양이 많은 신호가 결과를 지배한다
  • 롱테일 편향이 생긴다. 인기 상품이 계속 추천되는 쪽으로 쏠린다

4-3. 세그먼트형 — RFM [관행]

축의미
Recency최근성 — 관계의 온도
Frequency빈도 — 습관의 깊이
Monetary금액 — 가치의 크기

각 축을 1~5점으로 매겨 조합한다 (최대 125 세그먼트). 축별 가중치는 업체가 정한다.

RFM 은 구매 이력 기반이라 구매 데이터가 없는 우리 프로젝트에는 그대로 쓸 수 없다.
다만 "축을 나눠 점수화하고 등급으로 묶는다"는 구조는 참고할 수 있다.

필터를 쓴 세션 전체를 높은 의도 구간으로 볼 근거가 된다.

sort_change 를 0.5 로 낮게 둔 것은 어느 상품도 지목하지 않기 때문이다.
다만 sort_key 값은 버리면 안 된다. price_asc 를 고른 사용자와 rating 을
고른 사용자는 다른 사람이고, 이건 상품 선호가 아니라 사용자 축에 쌓아야 한다.
가격 정렬을 반복하는 페르소나에게 최고가 상품을 추천하면 그 자체로 실패다.

데이터 파트 요청으로 두 이벤트의 product_id 는 null 이다.
목록 전체에 대한 행동이라 특정 상품에 귀속시킬 수 없다.

이벤트가중방향의미근거

Baymard 사용성 조사가 Quick View 에 대해 두 가지를 지적한다.

  1. 다수의 피험자가 Quick View 를 실제 상품 페이지로 착각했다
  2. 실수로 열리는 경우가 잦아 오히려 좌절을 만든다
  3. 의류·인테리어처럼 시각 위주 상품에는 유용하지만, 스펙 위주 상품에는 덜 유용하다

화장품은 이 분류에서 애매하다. 색·제형은 시각 위주지만 성분·용량은 스펙 위주다.
그래서 quick_look 을 단독으로 관심 신호로 쓰지 않는다. 우리 구현은 닫을 때
quick_look_close 에 아래를 함께 남긴다.

close_reason      backdrop / esc / button / navigate

variants_viewed   옵션을 몇 개나 봤나

집계 규칙: dwell_ms 가 짧고 close_reason 이 backdrop 이며 아무 상호작용도
없었으면 오작동 개방으로 보고 가중을 0 으로 낮춘다. Baymard 가 지적한 오작동
개방을 그대로 선호도로 넣으면 목록에서 손이 스친 상품이 추천에 올라온다.

반대로 variants_viewed >= 2 이거나 added_to_cart 면 상세 진입 없이 판단이
끝난 것이므로 product_view 수준(1.0) 이상으로 본다. 지금 값 1.5 는 이 두 경우의
중간이며, quick_look_close 를 보고 사후에 조정하는 것이 전제다.

긁어간 문장 — 정보 부족의 직접 증거

이벤트가중방향의미근거

정보 탐색 이론(Information Foraging / Information Scent)은 사용자가 동물이 먹이를
찾듯 단서의 냄새를 따라 이동한다고 본다. 냄새가 약하면 그 자리를 떠난다.

복사는 이 관점에서 양면 신호다.

  • 긍정 — 성분명을 복사할 만큼 그 상품에 관여했다
  • 부정 — 우리 페이지 안에서 답을 못 찾아 밖에서 찾으려고 들고 나갔다

그래서 text_copy 를 product_id 에 대한 선호로만 쓰면 안 된다.
긁힌 성분을 빈도순으로 모으는 쪽이 훨씬 값이 크다.

원문은 저장하지 않는다 (데이터 계약). 대신 긁은 구간을 성분 사전에 대조해
표준 명칭만 남긴다 (matched_ingredients). 사용자가 친 글자가 아니라 우리가
가진 값이라 원문 저장이 아니다. 사전은 contracts/product-feature-vocab.json 으로
AI 파트가 상품 벡터에 쓰는 것과 같아서, "이 성분을 긁은 사람" 과 "이 성분이 든
상품" 이 같은 이름으로 조인된다. 어느 판 사전인지도 vocab_version 으로 함께 남긴다.

특정 성분명이 반복해서 복사되면 그건 "이 성분은 설명이 부족하다" 는
브랜드 담당자용 개선 지시다. 대시보드 ③-2 가 이걸 쓴다.

text_selection 은 0.5 로 낮다. 드래그는 읽기 습관이라 사람마다 편차가 크다.
어떤 사람은 읽는 줄을 따라 습관적으로 긁고 어떤 사람은 전혀 안 긁는다.
7-3 원칙 4(단독 판정 금지)를 따른다.

PC 전용이라는 전제가 여기서 한 번 유리하게 작용한다. 이 두 이벤트는 포인터가
있어야 발생하므로 모바일이 섞이면 기기별로 결측이 생겨 값을 비교할 수 없다.
우리는 전 사용자가 데스크톱이라 수집률이 균일하고, 낮은 가중을 주더라도
사용자 간 비교에는 쓸 수 있다. 낮게 둔 이유는 기기가 아니라 행동 자체의 모호함이다.

한계: 복사 행동 자체를 다룬 커머스 연구는 찾지 못했다. 위 해석은 정보 탐색
이론을 적용한 것이고, 값은 [추정] 이다.

노출 계열 — 가중 0 이지만 없으면 추천 평가가 불가능하다

이벤트가중역할
product_view1.0상품 단위 조회. 기준선 (7-3 의 page_view 역할을 넘겨받았다)
recommendation_impression0추천 노출. 클릭률의 분모
impression_dwell0노출 카드가 화면에 실제로 머문 시간
recommendation_snapshot0재정렬 시점의 순위 스냅샷

이 네 개는 선호도 벡터에 0 으로 들어간다. 그런데도 남기는 이유가 명확하다.

product_view 로 기준선을 옮긴 이유. 7-3 은 page_view 를 1.0 기준선으로
잡았다. 데이터 파트 요청으로 상품 단위 조회를 product_view 로 분리하면서
기준선도 이쪽으로 옮겼다. page_view 는 화면 이동을 표현하므로 목록·장바구니
에서도 발생하고, 상품 선호의 기준선으로는 부정확했다. 두 값을 모두 1.0 으로
두면 상세 진입 한 번이 두 번 세어진다. 두 이벤트가 둘 다 product_id 를
싣고, 집계는 product_id 가 있고 가중이 양수인 이벤트를 전부 그 상품에
귀속시키기 때문이다. 데이터 파트가 페르소나 300명으로 실측했더니 두 이벤트의
귀속 가중 합이 1,378 로 정확히 같았다. 그래서 page_view 를 0 으로 내렸다.

나머지 셋은 편향 보정용이다. 클릭 로그를 그대로 학습에 쓰면 안 된다는 것이
Unbiased Learning-to-Rank 계열 연구의 출발점이다. 사용자는 위쪽 항목을 더 많이
보기 때문에, 아래에 놓인 좋은 상품은 선호와 무관하게 클릭이 적다(위치 편향).
보정하려면 "어느 자리에 몇 번 노출됐는가" 가 있어야 한다.

  • recommendation_impression — 노출 횟수. 분모
  • recommendation_snapshot — 노출 시점의 순위. 위치 편향 보정의 입력
  • impression_dwell — 화면에 실제로 머문 시간

impression_dwell 이 특히 중요하다. 위치 편향 보정은 보통 "위쪽이면 봤을
확률이 높다" 는 가정으로 노출 확률을 추정한다. 우리는 카드가 화면에 얼마나
머물렀는지를 직접 측정하므로, 추정 대신 관측값을 쓸 수 있다.
빠르게 스크롤해 지나간 카드와 3 초간 화면 가운데 있던 카드를 같은 1 노출로
세면 클릭률의 분모가 부풀어 지표가 못 쓰게 된다.

이 셋이 없으면 "추천이 실제로 먹혔는가" 를 측정할 수 없다. 선호도 가중이
0 인 것과 쓸모가 없는 것은 다르다. B2B 대시보드가 파는 것이 바로 이 측정값이다.

1. 범위와 우선순위

이 문서는 활성 Event의 intent 의미와 properties 필수값, 타입, enum 및 배열 구조를
정의하는 계약 원본이다. 공통 Envelope, 활성 event_name, 공통 intent enum과
synthetic runtime metadata는 event-schema.json을 실행 원본으로 사용한다.

두 계약이 충돌하면 JSON Schema가 검증하는 범위에서는 event-schema.json을
우선한다. Event별 properties는 이 문서를 기준으로 Collector 또는 Spark semantic
validation에서 검사한다.

표기 규칙:

  • required properties의 키는 properties object에 반드시 존재해야 한다.
  • A 또는 B는 두 키 중 하나 이상이 존재해야 한다.
  • string|null은 키는 필수지만 값은 null일 수 있다는 뜻이다.
  • 상품 대상 Event의 top-level product_id는 필수다.
  • Planned Event는 event-schema.json enum에 등록되기 전까지 전송하지 않는다.

7. Semantic Validation

  1. 활성 Event의 intent가 event-schema.json 조건과 일치해야 한다.
  2. §4의 required properties와 §3 enum을 검사한다.
  3. 상품 대상 Event의 top-level product_id가 존재해야 한다.
  4. actor_type='synthetic'이면 scenario_id, simulation_run_id, generator_type이 필요하다. 이 공통 규칙은 JSON Schema에서도 검사한다.
  5. actor_type='user'에 synthetic runtime metadata가 있으면 경고하고 분석에는 사용하지 않는다.
  6. 위반 Event는 invalid_properties 등 표준 오류 코드로 bad_events에 격리한다.
  7. Collector가 Event별 properties를 검사하지 않는 동안 Spark가 방어적으로 검사한다.

현재 구현과의 차이 및 E2E 확인 대상은 event-logging-design.md에서 추적한다.

1. 목적과 범위

테스트 쇼핑몰에서 사용자와 Persona의 행동을 Event로 수집하고 Kafka, Spark,
DW를 거쳐 상품 반응, 콘텐츠 관심도, Funnel 및 고객군별 인사이트로 변환한다.

이 문서는 화면에서 Event를 발생시키는 시점, KPI 연결 근거, 현재 구현 현황과
검증 계획을 설명한다. Event 이름·intent·properties 타입과 필수 여부는 계약 파일을
단일 출처로 사용하며 이 문서에 Schema 표를 복제하지 않는다.

2. 전송 시점을 결정하는 식

e = 사용자 1명의 초당 이벤트 수, B = 배치 크기, T = 전송 주기.

e × T ≥ B  →  크기 트리거.  전송 간격 = B / e 초
e × T < B  →  시간 트리거.  전송 간격 = T 초

현재 값(B=20, T=5)의 분기점은 e = 4 이벤트/초 다.
그보다 느리면 5초마다, 빠르면 20건마다 나간다.

사용자 1명당 요청 수:

느린 구간 (e < 4):   1 / T        = 0.2 req/s
빠른 구간 (e ≥ 4):   e / B        = e / 20 req/s

3. 실제 이벤트 발생량 (측정)

behavior-log-design.md 에는 한 방문(1~2분)당 30~60건으로 적혀 있으나
실제와 맞지 않는다.

관측값
화면에 표시된 누적 로그 (가벼운 조작)158건
스크립트로 1회 훑어내리고 올라오기57건 (section_dwell 37 + section_view 20)

않는 상태라 scroll 이벤트가 발생하지 않았다 (직접 붙인 확인용 리스너도 0건 수신).
scroll_depth 와 scroll_pause 는 실제 브라우저에서 정상 동작하며 여기서만 안 잡혔다.

1. 범위와 입력 계약

이 문서는 Kafka record를 원본 그대로 보존하는 Raw Dataset raw_events의 grain,
물리 key, 컬럼, 타입, nullable, partition과 보존 규칙을 정의하는 계약 원본이다.

Kafka Value의 공통 Envelope와 Event enum은 event-schema.json,
Event별 properties와 enum은
event-properties-schema.md를 따른다. 이 문서는 그
입력 계약을 복제하거나 변경하지 않는다.

Collector가 HTTP 단계에서 거절해 Kafka에 발행하지 않은 요청은 Raw 저장 범위가
아니다. Kafka에 도달한 record는 JSON 파싱이나 semantic validation에 실패해도 Raw에
보존한다.

같은 event_id가 서로 다른 Kafka 좌표로 수신되면 모두 저장한다. 동일 Topic을 삭제한
뒤 재생성해 offset이 재사용될 수 있으면 kafka_cluster_id를 새 세대 값으로 바꾸거나
저장 경로를 분리해야 한다.

4. 원본 보존 규칙

  1. raw_value는 Kafka Value를 UTF-8 문자열로 변환한 값이며 일부를 제거하거나 다시 직렬화하지 않는다.
  2. properties_json은 조회용이다. 공백과 key 순서를 포함한 정확한 원문은 raw_value를 기준으로 한다.
  3. JSON 파싱 실패, 필수 필드 누락과 enum 오류가 있어도 Raw row는 보존한다.
  4. 같은 event_id가 여러 번 들어와도 Raw에서 제거하지 않는다.
  5. Raw를 update하거나 overwrite하지 않는다. 정제 결과는 Processed Dataset에 쓴다.
  6. Kafka payload에 새 필드가 추가되어도 전체 JSON은 raw_value에 보존한다.

5. 중복과 오류 처리 경계

단계기준처리
Raw Q1Kafka record물리 key 기반 insert-only 적재, event_id dedup 없음
Processed Q2 좌표 방어Raw 물리 key같은 좌표가 반복되면 대표 1건 선택
Processed Q2 업무 dedupevent_id정본 1건을 cleaned_events에 저장
Processed Q2 감사정본이 아닌 유효 후보duplicate_events에 저장
Processed Q2 오류파싱·필수값·semantic validation 실패bad_events에 원문과 Kafka 좌표 저장

동일 event_id의 정본 선정 순서는 다음과 같다.

received_at ASC
→ kafka_topic ASC
→ kafka_partition ASC
→ kafka_offset ASC

Fact, Mart와 Dashboard는 Raw를 직접 집계하지 않고 cleaned_events 또는 그 파생
Dataset만 사용한다. Processed Dataset의 상세 계약은
processed-schema.md를 따른다.

6. Schema 호환 규칙

  • 조회 projection에 컬럼을 추가할 때는 기존 row에 값이 없음을 고려해 nullable하게 확장한다.
  • 필드 이름·타입·의미 변경은 기존 Raw를 덮어쓰지 않고 schema_version으로 구분한다.
  • 알 수 없는 신규 필드나 projection 파싱 실패 때문에 Kafka record를 버리지 않는다.
  • 계약 변경 시 실제 Delta Schema와 컬럼 drift 검증을 함께 갱신한다.

7. 계약 검증 조건

  1. Kafka record 1건이 Raw row 1건으로 저장된다.
  2. Kafka Value와 raw_value가 같고 Topic·Partition·Offset·Key가 함께 저장된다.
  3. 조회 projection의 컬럼 이름·타입·nullable이 §3과 일치한다.
  4. 같은 event_id의 서로 다른 Kafka record가 모두 보존된다.
  5. JSON 파싱 실패 record도 raw_value와 Kafka 좌표를 가진다.
  6. 같은 물리 key가 Replay로 다시 들어와도 Raw row가 중복되지 않는다.
  7. raw_ingest_date가 UTC 기준이며 NULL이 아니다.

1. 문서 목적

이 문서는 Collector가 Kafka에 발행한 Event를 손실 없이 저장하고 재처리할 수 있도록
Raw 저장 방식을 선택한 이유, 배포 구조, 현재 구현 차이와 검증 계획을 설명한다.

raw_events의 grain, key, 컬럼, 타입, nullable, partition과 원본 보존 규칙은
contracts/raw-event-schema.md를 단일 출처로
사용한다. 이 문서는 동일한 컬럼 표를 복제하지 않는다.

2. 저장 흐름과 책임 경계

Frontend / Simulator
→ POST /api/events
→ Backend Collector
→ Kafka activity-events
→ Spark Structured Streaming Q1
→ Delta Lake raw_events
→ Delta Lake cleaned_events / marts
→ MySQL dw KPI Mart
→ Dashboard

Raw는 분석용 정제 테이블이 아니다. Kafka에 도달한 record를 재조회·재처리할 수 있게
보존하며, Collector가 HTTP 단계에서 거절한 요청은 Backend metric 또는 별도 error
sink의 책임이다. 업무 Event 중복 제거와 semantic validation은 Processed 단계에서
수행한다.

3. 배포 및 저장소 선택

  • EC2-1 서비스 영역에는 Backend, MySQL의 app·dw schema와 Redis를 둔다.
  • EC2-2 데이터 영역에는 Kafka, Spark와 Delta Lake를 둔다.
  • Delta Lake는 Raw·Processed·Mart의 재처리 기준을 보존한다.
  • MySQL dw에는 Dashboard가 직접 조회할 KPI Mart만 선별 적재한다.

별도 S3, EBS 데이터 볼륨 또는 공유 파일시스템이 없는 현재 구성에서는 Delta 파일과
_delta_log를 EC2-2 로컬 파일시스템에 함께 둔다. 이는 서비스와 데이터 영역을
분리하는 MVP 구조이며 EC2-2 장애·교체를 견디는 HA 구성은 아니다. 공유 저장소를
도입하기 전에는 여러 EC2에서 하나의 Delta Table을 분산 운영하지 않는다.

6. Delta 적재와 checkpoint 설계

  • Partition은 Event 발생일이 아니라 적재 UTC 날짜인 raw_ingest_date를 사용한다.
  • 늦게 도착한 Event도 실제 Raw 적재 날짜 partition에 저장한다.
  • foreachBatch에서 micro-batch 내부 물리 key 중복을 먼저 제거한다.
  • Delta Table과 물리 key를 비교해 matched row는 수정하지 않고 unmatched row만 넣는다.
  • 정상 재시작은 동일한 checkpoint를 사용한다.
  • 환경·Kafka cluster·Topic 세대가 다르면 checkpoint를 공유하지 않는다.
  • 출력과 checkpoint 경로를 분리하며 하나의 checkpoint를 여러 query가 공유하지 않는다.
  • startingOffsets는 checkpoint가 없는 신규 query에만 적용한다.

같은 이름의 Topic을 재생성해 Offset이 재사용되면 기존 Raw와 섞지 않는다.
KAFKA_CLUSTER_ID를 새 세대 값으로 바꾸거나 저장 경로를 분리한다.

7. 조회 및 운영 원칙

  • Kafka 원본 추적은 cluster·Topic·Partition·Offset으로 수행한다.
  • Collector batch 재구성은 request_id, event_index를 사용한다.
  • 같은 업무 Event의 수신 이력은 event_id로 조회한다.
  • 실제 사용자와 합성 유입은 actor_type, source로 구분한다.
  • Raw는 원본 확인과 재처리에만 사용하며 KPI를 직접 계산하지 않는다.
  • Raw 보존 기간은 EC2-2 가용 용량과 실제 Event 발생량을 측정한 뒤 정한다.

8. 구현 및 E2E 검증 계획

  1. raw_sink_job.py 출력 Schema를 Raw 계약과 대조한다.
  2. 유효 Event를 Collector로 보내 Kafka record와 Raw row를 비교한다.
  3. Kafka Value와 raw_value, 물리 좌표와 key가 동일한지 확인한다.
  4. source를 포함한 조회 projection의 타입과 값을 확인한다.
  5. 같은 event_id 재전송이 Raw에 모두 남는지 확인한다.
  6. JSON 파싱 실패 record도 원문과 Kafka 좌표를 가진 채 저장되는지 확인한다.
  7. 동일 checkpoint 재시작 시 처리 완료 record를 다시 쓰지 않는지 확인한다.
  8. checkpoint 삭제 후 Replay에서 물리 key 중복이 생기지 않는지 확인한다.
  9. EC2-2 프로세스 재시작 후 Delta Table과 checkpoint가 유지되는지 확인한다.

위 검증이 끝나기 전까지 Raw 계약은 Draft로 유지한다.

15. 구현 정합성 완료 조건

  1. 각 Delta Table의 실제 printSchema()가 이 문서의 컬럼·타입·nullable과 일치한다.
  2. §3의 unique key 중복이 0건이다.
  3. Partition column이 NULL인 row가 0건이다.
  4. cleaned_events.event_id 중복이 0건이고 비정본은 duplicate_events에서 추적된다.
  5. synthetic row는 persona_id, scenario_id, simulation_run_id, generator_type이 NULL이 아니다.
  6. source는 Raw payload 값을 우선하며 fallback 사용 건수를 품질 지표로 확인한다.
  7. 상품 Dimension Join 전후 row 수가 의도하지 않게 증가하지 않는다.
  8. 같은 입력 범위 재실행 후 Dataset key와 집계값이 변하지 않는다.
  9. 현재 미구현 Dataset은 구현 전까지 소비자가 존재하는 것으로 가정하지 않는다.

1. 문서 목적

이 문서는 Collector를 거쳐 Kafka에 들어온 Raw Event를 Spark에서 정제, 중복 제거,
세션화, 집계하는 처리 흐름과 설계 근거를 설명한다. 현재 구현 상태와 목표 계약 사이의
차이 및 E2E 검증 항목도 이 문서에서 추적한다.

Dataset별 grain, key, 컬럼, 타입, nullable 및 partition은
contracts/processed-schema.md를 단일 출처로
사용한다. 이 문서에는 동일한 Schema 표를 복제하지 않는다.

Frontend
→ Collector
→ Kafka raw_events
→ Spark Processed Layer
→ DW/Mart Layer
→ Dashboard

4. 핵심 처리 원칙

4.1 시간 기준

  • event_time: 사용자가 행동한 occurred_at을 UTC timestamp로 정규화한 값
  • received_at: Collector 수신 시각
  • processed_at: Spark 처리 시각
  • KPI 순서와 날짜는 event_time을 기준으로 한다.
  • Dashboard 일간 집계는 Asia/Seoul 날짜를 별도로 파생한다.
  • timezone이 없는 입력 timestamp는 정상 Event로 보정하지 않고 오류로 분리한다.

행동 시각, 수집 시각, 처리 시각을 분리해야 지연 Event와 처리 지연을 구분할 수 있다.

4.2 중복 제거와 재실행

Frontend의 sendBeacon 또는 keepalive 재시도 때문에 같은 event_id가 여러 Kafka
record로 들어올 수 있다. Raw에는 모두 보존하고 cleaned_events 전에 정본 1건을
선택한다.

정본 정렬 기준은 다음과 같다.

received_at ASC
→ kafka_topic ASC
→ kafka_partition ASC
→ kafka_offset ASC

선택되지 않은 후보는 duplicate_events에 물리 좌표와 함께 남긴다. 서로 다른
event_id로 발행된 동일 행동은 이 규칙으로 판별할 수 없으므로 Producer가 재전송 시
같은 event_id를 유지해야 한다.

Delta 저장 시 같은 처리 범위를 다시 실행해도 Dataset key 기준 동일 결과로 수렴해야
한다. Kafka 좌표 중복과 event_id 업무 중복은 서로 다른 문제로 검증한다.

4.3 Raw에서 승격하는 값

Processed에서는 조회·조인·필터에 반복 사용되는 값만 typed column으로 승격하고 전체
properties는 JSON으로 보존한다.

  • 공통 Envelope: Event, 사용자, 세션, 페이지, 시간 축
  • Collector metadata: received_at, source, request_id, event_index
  • Synthetic metadata: scenario_id, simulation_run_id, generator_type
  • 상품·콘텐츠 축: product_id, section_id, content_kind, position 등
  • Kafka 추적 축: topic, partition, offset, timestamp, key

정확한 컬럼과 nullable은 Processed 계약을 따른다. Event별 필수 properties가 없거나
타입 변환이 불가능하면 bad_events로 분리한다.

4.4 source와 Synthetic 처리

source는 Collector가 보강한 Kafka payload 값을 우선 사용한다. 이전 데이터 등에서
누락된 경우에만 actor_type='synthetic'이면 simulator, 그 외에는 web으로
fallback하고 사용 건수를 품질 지표로 남긴다.

Synthetic Event는 다음 조건을 만족해야 한다.

  • actor_type='synthetic'
  • persona_id, scenario_id, simulation_run_id, generator_type 존재
  • generator_type은 python_batch 또는 agent_llm
  • 분석용 user_id는 persona_id로 파생
  • 같은 (simulation_run_id, session_id) 안에서 persona_id가 하나로 유지
  • 같은 (simulation_run_id, session_id, sequence_no) 충돌 없음

PA 경로는 FE logger를 바꾸지 않고 runner가 Collector 전송 시점에 metadata를 보강한다.
persona 선택 전 발생한 Event는 Synthetic 필수값을 만족하지 않으므로 PA Event로
전송하지 않는다.

4.5 세션 순서와 Fact grain

세션 순서는 sequence_no → event_time → received_at → event_id로 복원한다.
sequence_no gap은 품질 표시 대상이지 자동 Event 생성 근거가 아니다.

Base Dataset은 Event 1건 grain을 유지한다. 상품 배열이 있는 Event만
product_event_fact에서 item 단위로 펼친다. 서로 다른 grain의 Fact를 row-level로
직접 Join하지 않고, 목표 Mart grain으로 먼저 집계한 뒤 결합한다.

Quick Look은 정규 Funnel 단계가 아니라 product_impression 이후의 비교 분기로
분석한다. section_dwell은 Front에서 여러 delta Event가 들어오므로 Spark에서 동일
콘텐츠 grain으로 합산한다.

확인한 뒤 계약과 설계에 함께 반영한다.

8. 구현·E2E 검증 체크리스트

  1. 실제 Delta Table의 printSchema()가 Processed 계약과 일치한다.
  2. Dataset별 unique key 중복과 partition NULL이 0건인지 확인한다.
  3. Raw 중복 후보가 정본 1건과 duplicate_events로 결정론적으로 나뉜다.
  4. 재실행 전후 Dataset key와 집계값이 동일하다.
  5. 오류 Event가 원문과 Kafka 좌표를 포함해 bad_events에 남는다.
  6. source payload 우선과 fallback 건수를 확인한다.
  7. PA와 PC Event가 Synthetic 필수 metadata를 유지한다.
  8. 세션 순서, sequence gap, late Event 판정이 샘플 시나리오와 일치한다.
  9. 상품 Dimension Join 전후 row 수가 의도치 않게 증가하지 않는다.
  10. Delta 결과에서 MySQL dw Mart와 Dashboard KPI까지 추적 가능하다.

위 검증이 끝나기 전까지 contracts/processed-schema.md의 상태는 Draft로 유지한다.

  5. generator_type, scenario_id, simulation_run_id는 Processed에서 승격된 synthetic metadata를 사용한다.

1. 문서 역할

Dimension과 Mart의 확정 grain, key, 컬럼, 타입, nullable 계약은
../../contracts/dw-schema.md가 단일 출처다. 이

2. 저장 및 조회 흐름

Backend → Kafka → Spark
  → Delta raw_events
  → Delta cleaned_events / Processed Dataset
  → Delta marts
  → MySQL dw schema
  → Dashboard API
  • EC2-1 서비스 영역에는 Backend, MySQL, Redis를 둔다.
  • EC2-2 데이터 영역에는 Kafka, Spark, Delta Lake를 둔다.
  • Delta Lake의 marts는 Spark 계산 결과와 재처리 기준을 보존한다.
  • MySQL dw schema는 Dashboard가 빠르게 조회할 KPI Mart를 제공한다.
  • 별도 S3/EBS/공유 저장소가 없는 현재 구성은 단일 데이터 EC2 장애를 견디는 HA 구조가 아니다.

현재 Q1은 로컬 Parquet와 checkpoint를 사용하는 PoC 구현이다. Delta 적재,
Delta MERGE, MySQL serving projection은 아직 구현·검증되지 않았으므로 현재
Parquet를 최종 저장 방식이나 exactly-once 저장소로 해석하지 않는다.

6. E2E 검증

  1. 확정 Collector 구현이 병합된 상태에서 POST /api/events → Kafka payload를 캡처하고 Event 단위·key·서버 metadata를 확인한다.
  2. 같은 event_id를 재입력해 cleaned_events가 계약의 대표 1건만 남기는지 본다.
  3. source와 synthetic runtime metadata가 Processed 컬럼으로 승격되는지 본다.
  4. items[]가 상품 row로 explode되고 order_value가 상품 수만큼 중복 합산되지 않는지 본다.
  5. 각 Processed Dataset을 목표 Mart grain으로 먼저 집계해 row 증폭이 없는지 본다.
  6. Delta marts와 MySQL dw의 key별 row 수·count·rate·amount를 대조한다.
  7. 분모 0인 비율이 NULL이고, count 부재는 0인지 확인한다.
  8. Dashboard API에서 일자·상품·actor/source·simulation run 필터 결과를 대조한다.
  9. checkpoint 삭제와 Kafka replay 후 Delta key 중복 및 KPI 변화 여부를 검증한다.
  10. PA agent_llm과 PC python_batch가 같은 run 차원 규칙으로 분리되는지 본다.

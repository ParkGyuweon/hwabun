# 추천 평가 체계

- 상태: **팀 합의 (2026-09-01)**. 큰 이슈가 없으면 변경하지 않는다.
- 관련: [`recommendation-design.md`](recommendation-design.md) · [`persona-feature-port.md`](persona-feature-port.md) · [`../../contracts/recommendation-io-spec.md`](../../contracts/recommendation-io-spec.md)

오프라인 평가, 동적 시뮬레이션, LLM 검증은 **분리해서 보고한다.**
세 검증은 우열 관계가 아니라 서로 다른 조건을 보는 평가 축이다.

다만 실제 사용자 테스트가 없는 상황이므로, 가상 사용자 평가를 실제 추천 정확도처럼
과장하지 않고 **조작 가능성을 줄인 통제된 검증 체계**로 설명한다.

---

## 1. 오프라인 평가

### 목적

- 실제 리뷰 이력 기반으로 추천 알고리즘의 초기 가중치와 정적 추천 정확도를 검증한다.
- 전체 평가 체계에서 **대표 정량 정확도 지표**로 사용한다.

### 대상

- PC 페르소나 9,900명
- 실제 Sephora 리뷰 이력 기반

### 검증 방식

- 페르소나별 실제 리뷰를 `submission_time` -> `review_id` 순으로 정렬한다.
- 그 순서에서 **가장 마지막 긍정 리뷰** 1개가 target, 즉 **정답 holdout** 이다.
  긍정은 `rating >= 4` 또는 (`is_recommended` 그리고 `rating >= 3`) 이고,
  같은 날짜는 `review_id` 가 큰 쪽이 뒤다 (Persona 계약 §7.1 · §7.1.1 · §7.1.2).
- **마지막 리뷰가 불만이어도 그 사람을 버리지 않는다.** 우리가 만드는 것은 선호
  상품을 맞히는 추천기이고, 1점 준 상품을 맞히라는 것은 다른 과제다. 불만은
  정답이 아니라 사람의 속성(`latest_review_label`)으로 남는다.
- target 보다 나중에 쓴 리뷰는 시간 절단으로 **seed 에 넣지 않는다.**
- 나머지 긍정 상품은 seed 로 사용한다.
- seed 상품은 이미 사용자가 좋아했거나 구매한 상품으로 간주하므로 **추천 후보에서 제외한다.**
- target 상품은 정답이므로 **추천 후보에서 제외하지 않는다.**
- 추천 결과 Top 10 안에 target 상품이 들어 있으면 hit 로 처리한다.

### Recall@10 의미

- 추천 아이템 10개 안에 정답 아이템이 있는지 확인하는 지표다.
- target 이 Top 10 안에 있으면 `hit = 1`
- target 이 Top 10 안에 없으면 `hit = 0`
- `Recall@10 = hit한 페르소나 수 / 전체 평가 페르소나 수`

### 오프라인 평가로 정하는 것

| 파라미터 | 의미 |
|---|---|
| `w1` | 콘텐츠 유사도 비중 |
| `w2` | 페르소나 속성 친화도 비중 |
| `w3` | 인기도 prior 비중 |
| `λ` | 부정 벡터 감점 계수 |
| `λ_mmr` | MMR 다양성 계수 |
| 스케줄 | seed 개수별 가중치 스케줄 |
| 노출 정책 | viewed / converted 상품 처리 정책 |

### 데이터 분리

- 가중치 튜닝과 최종 성능 보고에 같은 9,900명을 모두 사용하지 않는다.
- train / validation / test 또는 시간 기준 분리를 둔다.
- 예:
  - **train**: 가중치 후보 탐색
  - **validation**: 스케줄 · `λ` · MMR 선택
  - **test**: 최종 성능 보고
- 최종 성능은 **test split 에서만** 대표 지표로 보고한다.

### 주의

- 오프라인 평가는 **초기 가중치를 정하기 위한** 평가다.
- 실제 사용자 로그가 쌓이면 가중치는 다시 재측정 · 재튜닝해야 한다.

## 2. 동적 시뮬레이션

### 목적

- 행동 로그가 실시간으로 누적되는 동적 상황에서 추천 품질이 어떻게 변하는지 검증한다.
- 동시에 파이프라인 · 서빙 정책 · 부하 검증을 수행한다.
- 오프라인 평가의 보조가 아니라, **다른 조건을 보는 동등한 검증 축**이다.
- 단, synthetic 행동 결과를 실제 사용자 테스트와 동일한 정확도라고 주장하지 않는다.

### 대상

- 기본은 PC 페르소나 9,900명
- PA / LLM 100명은 기본 대표 지표에 합치지 않고 **별도로 분리**한다.

### 핵심 원칙

- **추천 모델 점수와 행동 생성 기준을 분리한다.**
- 추천 점수는 **상품 노출 확률에만** 사용한다.
- 노출 이후의 클릭 · 체류 · 위시리스트 · 장바구니 행동은 추천 점수와 독립된
  **hidden preference 함수**로 결정한다.
- 이를 통해 추천 모델이 자신의 순위로 긍정 행동을 만들고 다시 그 행동으로 성능을
  측정하는 **순환 평가 · 자기실현 평가**를 줄인다.

### 방문 후보 선택

- 추천 Top 순서에서만 고르지 않는다.
- 후보 pool 은 여러 출처를 섞는다.
  - 현재 추천 Top 50 일부
  - target 과 같은 카테고리 / 인기 상품 일부
  - 랜덤 탐색 상품 일부
- 추천 rank 는 **어떤 상품이 노출될 가능성이 높은지에만** 영향을 준다.
- target 은 방문 후보로 **강제하지 않는다.**
- target 은 정답 holdout 으로만 유지한다.

### hidden preference 정의

- hidden preference 는 "이 페르소나가 이 상품을 실제로 좋아할 법한 정도" 를 나타내는
  0~1 점수다.
- 추천 모델 점수와 **별도로** 계산한다.
- 현실의 정답이라고 주장하지 않고, 추천 모델과 행동 생성 모델을 분리하기 위한
  **통제 장치**로 사용한다.

#### 예시 공식

```
hidden_pref(u, i) =
    0.30 * seed_review_text_match(u, i)
  + 0.20 * product_attribute_match(u, i)
  + 0.15 * category_match(u, i)
  + 0.10 * brand_affinity(u, i)
  + 0.10 * price_match(u, i)
  + 0.10 * product_quality(i)
  + 0.05 * noise
```

#### 구성 요소

| 요소 | 내용 |
|---|---|
| `seed_review_text_match` | 사용자의 과거 긍정 seed 리뷰 텍스트 임베딩과 후보 상품의 상품 설명 · 성분 · 효능 · 전체 리뷰 요약 임베딩의 유사도 |
| `product_attribute_match` | 피부 타입, 피부 톤, 피부 고민과 상품 속성의 적합도 |
| `category_match` | 페르소나가 과거에 선호한 카테고리와의 일치도 |
| `brand_affinity` | 과거 긍정 리뷰에 등장한 브랜드와의 관계 |
| `price_match` | 과거 구매 · 리뷰 상품 가격대와 현재 상품 가격대의 유사도 |
| `product_quality` | 상품 평점, 리뷰 수, 추천율 등 상품 자체 품질 신호 |
| `noise` | 매번 완전히 같은 행동을 하지 않도록 넣는 확률적 변동 |

### 리뷰 임베딩 사용 원칙

- 리뷰 임베딩은 hidden preference 에 사용할 수 있다.
- 사용자의 **과거 seed 리뷰 텍스트** 임베딩은 사용할 수 있다.
- 후보 상품의 상품 설명 · 성분 · 효능 · 전체 리뷰 요약 임베딩은 사용할 수 있다.
- **target 상품에 대해 해당 사용자가 남긴 미래 리뷰 텍스트는 사용하지 않는다.**
- **target 이후 행동 로그도 사용하지 않는다.**
- 추천 모델이 사용하는 feature 와 완전히 동일한 임베딩 · feature 를 hidden preference 의
  주된 기준으로 재사용하지 않는다.
- 추천 모델은 product_feature vector, attribute affinity, 행동 벡터, prior 를 사용하고,
  hidden preference 는 seed 리뷰 텍스트와 후보 상품의 일반 텍스트 표현을 비교하는
  방식으로 분리한다.

#### 예시

- seed 리뷰 텍스트: *"hydrating, lightweight, doesn't irritate my dry skin"*

| 후보 | 상품 텍스트 | hidden preference | 예상 행동 |
|---|---|---|---|
| 상품 A | hydrating, lightweight gel cream, fragrance-free 가 많음 | 높음 | 오래 보기, 성분 확인, wishlist, add_to_cart 가능성 증가 |
| 상품 B | strong exfoliating acid, tingling, oil control 이 많음 | 낮음 | 짧게 보기, 얕은 스크롤, 빠른 이탈 가능성 증가 |

### 행동 변환

| hidden_pref | 행동 |
|---|---|
| `>= 0.80` | 긴 체류 · 성분/리뷰 확인 · wishlist 확률 높음 · add_to_cart 확률 높음 · 강한 긍정 신호 누적 |
| `0.60 ~ 0.80` | 중상 체류 · 일부 섹션 확인 · 낮은 확률로 wishlist · 약한 add_to_cart 가능성 · 중간 이상 긍정 신호 |
| `0.40 ~ 0.60` | 보통 체류 · 일부 탐색 · 전환 거의 없음 · 중립 또는 약한 긍정 신호 |
| `0.20 ~ 0.40` | 짧은 체류 · 얕은 스크롤 · 전환 없음 · 약한 부정 또는 낮은 관여 신호 |
| `< 0.20` | 빠른 이탈 · 매우 짧은 체류 · 필요하면 rage_click / scroll_backtrack 등 부정 신호 소량 생성 · 강한 부정 신호 가능 |

### 동적 시뮬레이션 Recall@10

- 이름은 **Dynamic Recall@10** 또는 **Interactive Recall@10** 으로 둔다.
- seed 상태에서 시작해 5~6개 상품을 탐색하는 동안 평가한다.
- 각 step 이후 사용자 벡터를 갱신하고 추천 Top 10 을 다시 계산한다.
- target 상품이 Top 10 안에 들어오는 순간 `hit = 1` 로 처리한다.
- 끝까지 Top 10 안에 들어오지 않으면 `hit = 0` 으로 처리한다.
- `Recall@10 = hit한 페르소나 수 / 전체 평가 페르소나 수`

### 정답 / 후보 처리

- seed 상품은 추천 후보에서 제외한다.
- target 상품은 정답 holdout 이므로 추천 후보에서 제외하지 않는다.
- target 을 직접 방문하거나 add_to_cart 한 **이후 이벤트는 Recall@10 판정에 사용하지 않는다.**
- target 이후 이벤트는 트래픽 생성 · 파이프라인 검증 · converted 제외 정책 검증 구간으로
  분리한다.
- target 이 add_to_cart 이후 converted 로 빠지는 것은 정상 동작이다.

### 함께 보고할 지표

| 지표 | 의미 |
|---|---|
| Start HR@10 | 탐색 시작 전 target 이 Top 10 에 있는 비율 |
| Final HR@10 | 마지막 탐색 step 후 target 이 Top 10 에 있는 비율 |
| Ever HR@10 | 탐색 중 한 번이라도 target 이 Top 10 에 들어온 비율 |
| target rank 변화 | 시작 순위 대비 마지막 순위가 얼마나 개선됐는지 |
| MRR | target 이 상위에 있을수록 더 높은 점수를 주는 지표 |
| NDCG | target 또는 관련 상품의 순위 품질 |
| step별 HR@10 곡선 | 탐색이 진행될수록 추천이 좋아지는지 |
| 부정 신호 반영 후 회복력 | 잘못 본 상품이나 빠른 이탈 이후 추천이 회복되는지 |
| 추천 안정성 | 행동 몇 번에 추천 목록이 과도하게 흔들리지 않는지 |

### 주의

- Ever HR@10 은 step 수가 많아질수록 자연스럽게 높아진다.
  따라서 **Ever HR@10 하나만 대표 지표로 쓰지 않고 Start / Final / Ever 를 함께 본다.**
- hidden preference 하나를 현실의 정답처럼 쓰지 않는다.
- 여러 preference 가정과 random seed 에서 성능이 유지되는지 **강건성 평가**로 보고한다.

## 3. 실제 리뷰 이력 순차 재생

### 목적

- synthetic 행동을 최소화하고 실제 데이터 기반성을 높인다.
- 가능한 경우 **동적 시뮬레이션보다 우선 검토한다.**

### 방식

- 과거 리뷰 상품을 시간순 이벤트로 재생한다.
- 긍정 리뷰는 add_to_cart / wishlist 에 가까운 긍정 이벤트로 변환한다.
- 낮은 평점 또는 비추천 리뷰는 짧은 체류 · 이탈 · 부정 신호로 변환한다.
- 마지막 리뷰 상품이 긍정이면 target holdout 으로 둔다 (1절 정본 = 계약 §7.1).
- target 이전까지만 사용자 벡터에 반영한다.
- target 은 추천 후보에서 제외하지 않고 정답으로 평가한다.
- 부족한 UI 이벤트만 synthetic 으로 보강한다.

### 의미

- 완전한 실제 사용자 행동 로그는 아니지만, 임의 synthetic 행동보다 **실제 리뷰 이력에
  더 가깝다.**
- 조작 가능성을 줄이는 우선 방식이다.

## 4. PC 페르소나 9,900명 역할

**역할:** 오프라인 평가와 동적 시뮬레이션 양쪽에서 대표 정량 검증에 사용한다.

**오프라인 평가에서는**

- 실제 리뷰 이력 기반 holdout 평가 대상
- 초기 가중치와 정적 Recall@10 산출 대상

**동적 시뮬레이션에서는**

- 리뷰 순차 재생 또는 hidden preference 기반 synthetic traffic 생성 대상
- 동적 행동 로그 기준 Dynamic Recall@10 산출 대상
- 파이프라인 · 서빙 정책 · 부하 검증 대상

**특징**

- seed 와 target 상품은 실제 리뷰 이력 기반이라 무작위가 아니다.
- 탐색 상품은 추천 Top 일부, 같은 카테고리 / 인기 상품, 랜덤 상품을 섞어 선택한다.
- 페이지 안 행동 여부와 강도는 hidden preference, 확률 파라미터, `persona_style` 에 의해
  결정된다.
- PC 페르소나는 LLM 처럼 자유롭게 판단하지 않지만, **추천 점수와 분리된 hidden preference 에
  따라 반응하는 룰 기반 사용자**로 동작한다.

## 5. PA / LLM 100명 역할

**역할:** 대표 정량 지표에 합치지 않고, 별도의 LLM 기반 검증 축으로 분리한다.

**사용 목적**

- 프론트 드롭다운 / 시연용 페르소나
- LLM 에이전트가 실제 UI 를 조작하는 정성 검증
- LLM 행동이 추천 변화와 자연스럽게 연결되는지 확인
- UI 이벤트와 로그 계약이 실제 흐름에서 맞는지 확인

**보고 방식**

| 축 | 내용 |
|---|---|
| PC 9,900명 오프라인 Recall@10 | 실제 리뷰 기반 **정적** 추천 정확도 |
| PC 9,900명 Dynamic Recall@10 | hidden preference 또는 리뷰 순차 재생 기반 **동적** 추천 정확도 |
| PC 9,900명 실시간 파이프라인 검증 | 수집 · 스트리밍 · 벡터 · 정책 검증 |
| PA / LLM 100명 | 별도 LLM 정성 검증 또는 보조 정량 지표 |
| All 10,000 통합 Recall@10 | **기본 대표 지표로 사용하지 않음** |

## 6. 구현 단계

### 1단계 — 평가 정의 정리

- 오프라인 평가, 동적 시뮬레이션, LLM 검증을 문서와 코드 출력에서 분리한다.
- Recall@10, Dynamic Recall@10, 파이프라인 검증 지표의 의미를 명확히 구분한다.
- PC 9,900명과 PA / LLM 100명의 역할을 분리한다.

### 2단계 — 오프라인 평가 정비

- 실제 리뷰 이력 기반 leave-last-out 평가를 대표 정확도 지표로 둔다.
- train / validation / test 또는 시간 기준 분리를 추가한다.
- 최종 성능은 test split 에서만 보고한다.
- seed 제외, target 유지 원칙을 코드와 문서에 명확히 반영한다.

### 3단계 — 동적 평가용 metadata 추가

- persona 별 seed 상품, target 상품, target 최초 진입 시점, 평가 step 정보를 저장한다.
- target 이후 이벤트와 평가 이전 이벤트를 구분할 수 있게 한다.
- target 은 정답 holdout 으로 유지하고, 방문 후보로 강제하지 않는다.

### 4단계 — hidden preference 모듈 추가

- `hidden_preference.py` 같은 별도 모듈을 만든다.
- `content_match`, `attribute_match`, `category_match`, `brand_affinity`, `price_match`,
  `product_quality`, `noise` 를 계산한다.
- 추천 모델 점수와 hidden preference 계산을 분리한다.

### 5단계 — 리뷰 임베딩 · 텍스트 매칭 추가

- 사용자의 과거 seed 리뷰 텍스트 임베딩을 만든다.
- 후보 상품의 상품 설명 · 성분 · 효능 · 전체 리뷰 요약 임베딩을 만든다.
- target 사용자의 미래 리뷰 텍스트는 사용하지 않는다.
- `seed_review_text_match` 를 hidden preference 의 한 요소로 사용한다.

### 6단계 — 시뮬레이터 행동 생성 로직 수정

- 추천 rank 는 노출 확률에만 사용한다.
- 노출 이후 행동은 hidden preference 로 결정한다.
- 행동 강도에 따라 체류, 스크롤, wishlist, add_to_cart, 이탈, 부정 신호를 생성한다.
- 여러 random seed 와 preference 가정을 실행할 수 있게 한다.

### 7단계 — 동적 평가 지표 추가

- Start HR@10, Final HR@10, Ever HR@10 을 출력한다.
- target rank 변화, MRR, NDCG, step별 HR@10 곡선을 출력한다.
- 부정 신호 반영 후 회복력과 추천 안정성을 출력한다.
- 파이프라인 · 정책 검증 지표와 추천 품질 지표를 분리해서 출력한다.

### 8단계 — 파이프라인 검증 유지

- 수집 API, Kafka, Spark, 사용자 벡터 갱신, converted / viewed 정책, MMR, 부하 검증은
  기존처럼 별도 성공 기준으로 유지한다.
- **추천 정확도 지표와 파이프라인 성공 지표를 합쳐 하나의 성능처럼 말하지 않는다.**

### 9단계 — LLM 100명 검증 분리

- PA / LLM 100명은 대표 정량 지표에 합치지 않는다.
- 실제 UI 조작, 로그 계약, 추천 변화의 자연스러움, 시연 품질을 정성 검증한다.
- 필요하면 별도 보조 지표로만 보고한다.

### 10단계 — 강건성 평가

- 하나의 hidden preference 공식과 하나의 random seed 만 사용하지 않는다.
- 여러 preference weight 조합과 random seed 에서 결과가 유지되는지 확인한다.
- 결과는 평균과 분산, 신뢰구간 형태로 보고한다.

## 최종 정리

- 오프라인 평가, 동적 시뮬레이션, LLM 검증은 분리해서 보고한다.
- 오프라인 평가는 실제 리뷰 이력 기반 leave-last-out 으로 초기 가중치와 정적 추천
  정확도를 검증한다.
- 동적 시뮬레이션은 추천 점수를 행동 결정에 직접 쓰지 않고 **노출 확률에만** 사용한다.
- 노출 이후 행동은 추천 점수와 독립된 hidden preference 가 결정한다.
- hidden preference 는 실제 리뷰 이력, seed 리뷰 임베딩, 상품 텍스트, 피부 고민, 상품 속성,
  가격 · 브랜드 · 카테고리 선호, 상품 품질, 노이즈를 기반으로 만든다.
- hidden preference 는 현실의 정답이 아니라 **추천 모델과 행동 생성 모델을 분리하기 위한
  통제 장치**다.
- 가능한 경우 실제 리뷰 이력을 이벤트로 순차 재생하는 평가를 우선한다.
- Recall@10 은 추천 Top 10 안에 정답 target 상품이 있는지 확인하는 지표다.
- seed 상품은 후보에서 제외하지만, target 상품은 정답 holdout 이므로 후보에서 제외하지
  않는다.
- target 이후 이벤트는 Recall@10 평가 이후의 트래픽 · 정책 검증 구간으로 분리한다.
- 하나의 hidden preference 나 하나의 random seed 결과만 보고하지 않고, 여러 가정에서
  성능이 유지되는지 강건성 평가를 함께 보고한다.
- PC 9,900명은 대표 정량 검증 대상이고, PA / LLM 100명은 대표 지표에 섞지 않고 별도
  검증 축으로 둔다.

### 시드 개수별로는 경향이 없다

같은 실행의 구간별 수치다. **시드가 많을수록 좋아지지 않는다.**

| 시드 | valid | test | test 인원 |
|---|---:|---:|---:|
| 1~2개 | 26.97% | 24.54% | 925명 |
| 3~5개 | 22.52% | 21.54% | 794명 |
| 6개 이상 | 19.17% | 25.00% | **252명** |

**두 분할에서 6개 이상 구간의 방향이 뒤집힌다**(19.17% vs 25.00%). 그 구간이
전체의 13% 뿐이라 구간별 수치를 신뢰할 수 없다는 뜻이다. **"이력이 쌓이면
정확해진다" 를 이 표로 주장하지 말 것.**

시드를 늘려야 하는 이유는 정확도가 오를 것이라는 기대가 아니라, **구간을 나눠
볼 수 있을 만큼 표본이 없다는 것**이다. 하한(긍정 3개)을 올리면 모집단이
20,435명에서 5,000명 근처로 줄어 총량이 오히려 준다. 1인당 이력을 늘리는 길은
**상품 200개를 늘리는 것**뿐이고, 그것은 리뷰 커버리지·속성 통계와 맞바꾸는
결정이라 따로 판단해야 한다.

정직하게 남길 것: **valid 에서는 세 요소 모두 유의하지 않았다.** test 에서만 유의하게
나왔다는 것은 효과 크기가 2,000명 규모 분할의 분해능 근처라는 뜻이다. 그래서
- 스케줄 정정은 **방향**(행동이 쌓이면 콘텐츠 비중을 올린다)으로 유지하고,
- MMR 은 **다양성** 근거로 유지하며,
- 수치를 소수점까지 주장하지 않는다.

## 부록 D — 동적 시뮬레이션 첫 측정 (2026-09-01)

`batch/jobs/eval_dynamic.py`. 노출은 추천 점수가, 행동은 hidden preference 가 정한다.
HR 판정은 **서빙 목록**(노출 정책 + MMR 통과) 기준이고 순위 지표는 점수 기준이다.

**test 1,971명 · 최대 6 step · hidden preference seed 3개**

**seed 를 바꿔도 결과가 유지된다** (Ever 25.9~26.5%). 강건성은 확인됐다.

### 읽어야 할 결론 — 탐색이 추천을 개선하지 못한다

step 별 HR@10 곡선이 **23.5 → 21.6 으로 내려간다.** 순위가 개선된 사람이 34%,
악화된 사람이 51% 다. 즉 **행동이 쌓일수록 target 이 오히려 밀린다.**

원인으로 보이는 것:

1. 탐색으로 들어오는 대부분의 상품은 **전환되지 않는다.** 집계 규칙상 미전환 상품은
   `v_u⁻` 로 가므로, 탐색은 부정 축을 주로 키운다.
2. seed(과거 긍정 리뷰)가 이미 강한 신호라, 새 행동이 그 방향을 흐린다.
3. 상호작용 상품 수가 늘면 스케줄이 `w1` 쪽으로 넘어가는데, 그 벡터가 여러 상품의
   평균이라 방향이 무뎌진다.

**이것을 숨기지 않는다.** 8/28 폐쇄 루프 측정에서도 "루프로는 정확도가 오르지
않는다"는 같은 결론이 나왔고, 그때는 추천 점수로 행동을 만들었기 때문에 순환 평가
의심이 있었다. 이번에는 **추천과 분리된 hidden preference 로 행동을 만들었는데도
같은 결론**이므로, 순환 때문이 아니라 구조 때문이라는 근거가 된다.

Ever HR@10(26%)이 Start(23.5%)보다 높은 것은 탐색 중 한 번이라도 들어온 것을 세기
때문이며, **step 이 많아질수록 자연히 오르는 지표**다. 대표로 쓰지 않는다.

### 강건성 — 가정을 바꿔도 결론이 같다 (2026-09-01 첫 측정 · 계약 정렬 전)

hidden preference 가중치 조합을 네 가지로 바꿔 봤다 (`--pref-profile`).

| 가중치 조합 | Start | Final | Ever | 순위 개선 / 악화 |
|---|---:|---:|---:|---|
| default (합의한 공식) | 23.54% | 21.61% | 26.53% | 36% / 50% |
| text_heavy (텍스트 0.50 — 추천과 가장 멀다) | 23.54% | 20.70% | 25.98% | 35% / 51% |
| attr_heavy (속성·카테고리 0.60 — 추천과 가장 가깝다) | 23.54% | 20.60% | 27.75% | 37% / 53% |
| flat (전 항목 균등) | 23.54% | 19.79% | 26.53% | 34% / 54% |

**네 조합 모두에서 Final < Start 이고 악화가 개선보다 많다.** 여기에 noise seed 3개
(부록 D 표)까지 더하면, "탐색이 추천을 개선하지 못한다" 는 결론은 **하나의 가정이나
하나의 난수에서 나온 것이 아니다.**

추천과 가장 가까운 가정(`attr_heavy`)에서 Ever 가 가장 높은 것(27.75%)은 예상대로다 —
행동이 추천 순위와 닮을수록 target 이 목록에 들어오기 쉽다. 그 조합조차 Final 은
20.60% 로 떨어진다.

## 부록 E — 실제 리뷰 이력 순차 재생 (2026-09-01)

### 세 축을 나란히 (test 1,971명)

| 축 | 지표 | 값 | 무엇이 다른가 |

## 부록 F — 생성기의 정답 심기 제거 (2026-09-01)

6단계를 하다가 **평가 순환보다 더 직접적인 문제**를 찾았다.

`gen_behavior_logs.py` 는 `seeds, target = pos[:-1], pos[-1]` 로 **평가 정답을 알고
있었고**, 그 상품에 대해 `depth=100` + `add_to_cart` 를 강제했다. 즉 생성 로그에는
**정답이 전환 상태로 심겨** 있었다. 이 로그로 추천을 평가하면 자기실현 평가가 된다.

`--behavior hidden_preference` 모드를 추가해 행동을 추천·정답과 분리된 hidden
preference 가 정하게 하고, target 에 전환을 강제하지 않게 했다.

**30명 생성 결과 비교**

| 모드 | 시뮬레이션 전환 | **target 을 담은 사람** |
|---|---:|---:|
| 규칙 기반 (기존, 기본값) | 76건 | **30/30명 (100%)** |
| hidden preference | 35건 | **1/30명 (3%)** |

3% 는 우연히 담긴 것이다. **평가에 쓸 로그는 반드시 `--behavior hidden_preference`
로 만든다.** 규칙 모드는 트래픽·파이프라인·부하 검증용으로 남긴다 — 그 용도에서는
무엇을 담았는지가 중요하지 않기 때문이다.

전환이 76 → 35건으로 준 것은 정답 강제가 사라진 결과다. 퍼널도 노출 1,548 →
클릭 129(8.3%) → 장바구니 35 로 바뀐다.

## 부록 I — 상품 쪽 리뷰 임베딩은 넣지 않는다 (2026-09-01, 측정 후 기각)

합의 §2 의 구성 요소에는 "후보 상품의 상품 설명 · 성분 · 효능 · **전체 리뷰 요약**
임베딩" 이라 적혀 있다. 그 마지막 조각을 만들어 재봤고, **이득이 없어 넣지 않는다.**

만든 것: 상품 200개 × 리뷰 400건 = 8만 조각 임베딩 (GPU 40초).
**평가 대상 페르소나 본인이 쓴 리뷰는 전부 제외**했다 — 그 안에 target 리뷰가 있다.

| 상품 표현 | 추천과 상위10 겹침 | hidden 변별력(σ) | 동적 Ever | 순위 개선 |
|---|---:|---:|---:|---:|
| **설명 · 성분만 (채택)** | **27.3%** | **0.0890** | **29.33%** | **41.2%** |
| 설명 + 리뷰 | 29.4% | 0.0799 | 29.12% | 39.4% |

**모든 지표에서 소폭 나쁘다.** 통제 장치로서는 추천과 더 겹치게 되고(27.3% → 29.4%),
취향 함수로서는 상품 간 구분이 흐려진다(σ 0.089 → 0.080).

원인으로 보이는 것: 리뷰 400건을 평균 내면 "좋아요 · 촉촉해요 · 재구매" 같은
**범용 칭찬어**가 지배해서 상품 고유의 표현이 씻겨 나간다. 그 결과 남는 신호가
카테고리 수준이 되는데, 그건 추천 모델이 이미 쓰는 축이다.

### 비대칭이 흥미롭다

| 리뷰 텍스트를 어디에 | 결과 |
|---|---|
| 추천 모델의 **상품 벡터** (2026-08-31) | 27개 구성 전부 실패 |
| hidden preference 의 **상품 쪽** (오늘) | 이득 없음 (위 표) |
| hidden preference 의 **사용자 쪽** (오늘) | **효과 있음** — 겹침 29.4% → 27.3%, σ 0.082 → 0.089 |

**리뷰는 "이 사람이 무엇을 좋아하는가" 를 말할 때는 쓸모가 있고, "이 상품이
무엇인가" 를 말할 때는 그렇지 않다.** 상품이 무엇인지는 설명·성분이 더 정확하고,
리뷰는 상품마다 비슷해진다.

재현: `python batch/jobs/build_text_embeddings.py --with-product-reviews`
(옵션으로 남겨 뒀다 — "재봤고 아니었다" 가 성립하려면 다시 돌릴 수 있어야 한다)

## 부록 J — 노출 온도로는 선순환이 돌지 않는다 (2026-09-04, 측정 후 기각)

동적 평가는 규칙 5 개정 뒤에도 평균으로 **Final < Start** 다(−1.22%p). 남은 원인
후보로 **노출 쏠림**을 의심했다. 근거는 부록 D 이후 확인된 갈림이었다.

| 탐색 중 담은 상품이 | Start | Final |
|---|---:|---:|
| 정답과 **닮았다** | 79.13% | **92.52%** (+13.39%p) |
| 정답과 **안 닮았다** | 12.55% | 7.08% |

**행동 누적 자체는 작동한다.** 맞는 신호가 쌓이면 오른다. 그렇다면 노출을 추천 점수
쪽으로 더 세게 기울이면 맞는 신호가 쌓이고 Final 이 Start 를 넘어야 한다 — 그것이
선순환의 정의다. 그 가설을 쟀다.

### 무엇을 바꿨나

`eval_dynamic` 은 후보 pool 에서 `exp(score × T)` 확률로 하나를 뽑는다. `T` 를
0(완전 무작위) / 3(현행) / 6 / 12 / greedy(1등 고정)로 바꿨다.
**행동은 그대로 hidden preference 가 정한다 — 노출만 바꾼 것이다.**

### 측정에서 고친 것 — 처치 후 변수로 표본을 거르면 안 된다

러너는 target 을 뽑으면 그 상품의 이벤트를 벡터에 넣은 **뒤** 마지막 순위를 잰다.
그 상품이 전환되면 자기 자신과의 유사도가 1 이라 순위가 튄다. 그래서 target 을 만난
실행을 빼야 하는데, **누가 빠지는지가 조건마다 다르다.**

| 노출 정책 | Start (조건별로 거른 표본) |
|---|---:|
| 무작위 (T=0) | **19.66%** |
| 현행 (T=3) | 15.33% |
| greedy | **10.36%** |

Start 는 노출 **전**에 재는 값이라 사람마다 고정이다. 다섯 행이 같은 사람을 본다면
같은 값이 나와야 한다. greedy 는 점수 1등을 보여주므로 **target 이 이미 상위권인
사람**(= Start 적중)을 먼저 만나 빼 버리고, 남는 사람이 체계적으로 "target 순위가
나쁜 사람" 이 된다. 거르는 기준이 **처치의 결과**이면 조건 간 비교가 깨진다.

그래서 두 가지를 고쳐 다시 쟀다.

- **공통 부분집합** — 다섯 조건 **전부에서** target 을 만나지 않은 사람만 (1,220명 · 61.8%)
- **사람별 고정 시드** — `rng` 를 `persona_id` 로 시드해 조건 간 짝을 맞춘다

Start 가 다섯 행 모두 **5.41%** 로 고정된다. 표본이 하나로 묶였다는 증거다.
(공통 부분집합은 6 step 안에 target 을 못 만나는 어려운 사람들이라 절대 수준이
낮다. **조건 간 비교에만 쓰고 대표 지표와 나란히 놓지 않는다.**)

### 결과 — valid 1,975명 · 공통 부분집합 1,220명 · 6 step

| 노출 정책 | Start | Final | Δ | Ever | 담기 | 시드 브랜드 노출 |
|---|---:|---:|---:|---:|---:|---:|
| 무작위 (T=0) | 5.41% | **4.67%** | −0.74%p | 9.59% | 1.9회 | 42.9% |
| **현행 (T=3)** | 5.41% | 3.77% | −1.64%p | 8.77% | 2.2회 | 62.4% |
| T=6 | 5.41% | 3.28% | −2.13%p | 8.61% | 2.3회 | 76.0% |
| T=12 | 5.41% | 3.44% | −1.97%p | 9.02% | 2.5회 | 84.8% |
| 점수 1등 고정 | 5.41% | **2.95%** | −2.46%p | 8.93% | 2.5회 | 89.2% |

**다섯 조건 전부 Final < Start** 이고, 온도를 올릴수록 점추정이 **더 나빠진다** —
가설이 예측한 방향의 정반대다.

현행(T=3) 대비 차이를 **사람 단위로 짝지어** 부트스트랩했다 (2,000회 · n=1,220).

| | 현행 대비 Final | 95% CI | |
|---|---:|---|---|
| 무작위 (T=0) | +0.90%p | [−0.25, +2.21] | CI 가 0 을 포함 |
| T=6 | −0.49%p | [−1.56, +0.49] | CI 가 0 을 포함 |
| T=12 | −0.33%p | [−1.48, +0.82] | CI 가 0 을 포함 |
| 점수 1등 고정 | −0.82%p | [−1.89, +0.16] | CI 가 0 을 포함 |

**현행과 구분되는 조건이 하나도 없다.** Start 를 넘기는커녕 현행보다 나은 조건조차
찾지 못했다. 점추정만 보면 무작위 노출이 가장 나은 쪽이지만 **CI 가 0 을 포함하므로
방향을 주장하면 안 된다.**

### 왜 안 되나

노출을 세게 걸수록 시드 브랜드 노출이 42.9% → **89.2%** 로 오른다. 그런데
**정답이 시드 브랜드인 비율은 30.6%** 다. 점수를 더 믿을수록 한 브랜드로 좁아지고,
정답의 69.4%는 그 밖에 있다.

**노출은 점수가 이미 아는 것을 증폭할 뿐이다.** 점수가 정답 쪽을 못 가리키면 증폭이
소용없다. 남은 하락의 원인은 노출이 아니라 점수 식 쪽 — **긍정 축이 여러 상품의
평균이 되며 무뎌지는 구조** — 이다. 상품 벡터가 전부 1사분면에 있어(음수 코사인
0쌍) 평균낼수록 카탈로그 중심으로 수렴한다. 다음 과제는 사용자 표현을 평균에서
max/top-k 로 바꾸는 쪽이다.

### 곁들여 — 담기는 늘어난다

노출을 점수 쪽으로 기울이면 담기가 1.9 → 2.5회로 는다. 2026-09-02 노출 정책
실험(`popular_v0` 90건 → `cbf_v1` 108건)과 같은 방향이다.
**담기가 느는 것과 정답을 맞히는 것은 별개다.** 담긴 것이 정답 쪽이 아니면 사용자
벡터만 흐려진다.

> 재현: `Research/eval/eval_exposure_common_subset_20260904.py`
> 09-03 판(`Research/eval/eval_exposure_virtuous_cycle_20260903.py`)의 표는 위에
> 적은 표본 갈림 때문에 **그대로 인용하면 안 된다.** 지우지 않고 남겨 둔다.
> 노출이 어느 자리에서 무엇을 하는지는 [`exposure-role.md`](exposure-role.md).

## 부록 K — 사용자를 한 점으로 두는 것은 그대로 둔다 (2026-09-04, 측정 후 기각)

부록 J 에서 노출을 접고 남은 후보를 쟀다. 사용자 벡터 `v_u` 는 반응한 상품 벡터들의
**가중 평균**이고 코사인을 그 한 점과 잰다. 상품 벡터가 전부 1사분면에 있어(음수
코사인 0쌍) **평균낼수록 카탈로그 중심으로 수렴**한다. 설계 문서도 같은 현상을
적어 두었다 — "시드 6개 이상 → 중심점 근처, 밋밋해짐".

그래서 **사람을 한 점이 아니라 취향 여러 개의 집합**으로 보는 안을 쟀다.
`w₁` 항의 계산 방식만 바꾸고 속성·인기·MMR·스케줄은 그대로다.

| | 무엇 |
|---|---|
| `mean` (현행) | 시드 평균과의 코사인 |
| `max` | 시드 중 **가장 닮은 하나**와의 코사인 |
| `top2` · `top3` | 상위 k개 유사도의 평균 |
| `softmax` | 온도 0.1 로 부드러운 최대화 |
| `blend<a>` | `(1−a)·mean + a·max` |
| `sched` | 시드 5개까지만 혼합, 6개 이상은 평균 |

### valid 에서 고른다 (1,975명 · 짝지은 부트스트랩 2,000회)

| 사용자 표현 | Recall@10 | 시드 1~2 | 3~5 | **6개+** | 현행 대비 |
|---|---:|---:|---:|---:|---|
| **mean (현행)** | 24.05% | 26.75% | 22.40% | **19.17%** | 기준 |
| max | 23.75% | 26.97% | 22.77% | **14.58%** | −0.30%p [−1.47, +0.86] |
| top2 | 23.95% | 26.54% | 23.27% | 16.25% | −0.10%p [−0.81, +0.61] |
| top3 | 23.29% | 26.54% | 21.91% | 15.42% | **−0.76%p [−1.37, −0.10]** |
| softmax | 23.70% | 26.86% | 22.77% | 14.58% | −0.35%p [−1.52, +0.76] |
| **blend0.2** | **24.76%** | 27.62% | 23.27% | 18.75% | **+0.71%p [+0.15, +1.27]** |
| blend0.4 | 24.76% | 27.18% | 23.76% | 18.75% | +0.71%p [+0.00, +1.42] |
| sched | 24.71% | 27.18% | 23.51% | 19.17% | +0.66%p [−0.10, +1.42] |

**순수 교체(max · top-k · softmax)는 넷 다 현행 이하**이고 `top3` 는 유의하게 나쁘다.

**가설이 정반대로 틀렸다.** "시드가 많아 평균이 무뎌진 사람에게서 개선된다" 고 봤는데
**시드 6개+ 구간이 가장 크게 무너진다**(19.17% → 14.58%). `max` 는 가장 큰 값 하나만
보므로, 시드가 늘수록 **그 하나가 우연히 튄 상품일 확률**이 올라간다. 주사위를 여섯 개
굴려 최댓값을 취하면 거의 항상 5~6이 나오는 것과 같다. 평균이 무뎌지는 것은 맞지만,
**그 무뎌짐이 노이즈도 같이 눌러 주고 있었다.**

여유 있게 0 을 넘는 것은 `blend0.2` 하나다 (`blend0.4` 의 하한은 +0.00 으로 0 에 붙어
있어 혼자서는 근거가 못 된다).

### test 에서 한 번 확인한다 — 기각

`blend0.2` 하나를 골라 test 를 **한 번** 봤다. test 에서 다시 훑으면 고른 의미가
없어지므로 `mean` 과 `blend0.2` 만 돌렸다.

| test 1,971명 | Recall@10 | 롱테일 | 시드 1~2 | 3~5 | 6개+ | 현행 대비 |
|---|---:|---:|---:|---:|---:|---|
| **mean (현행)** | **23.39%** | 31.14% | 24.54% | 21.54% | 25.00% | 기준 |
| blend0.2 | 22.93% | 30.89% | 24.22% | 21.41% | 23.02% | **−0.46%p [−1.07, +0.15]** |

**부호가 뒤집혔다.** valid +0.71%p → test −0.46%p. test 에서 유의하게 나쁘지는
않지만 **좋다는 근거가 전혀 남지 않았다. 기각한다. 사용자 표현은 평균 그대로 둔다.**

원인은 미리 적어 둔 그대로다 — **12개 구성을 훑고 제일 나은 것을 골랐고**, 그중
하나는 우연히 valid 에서 잘 나온다. **분할이 값을 했다.** 채택했다면 아래 비용을
치르고도 얻는 것이 없었다.

### 기각이 아니었다면 치렀을 비용 (다음에 같은 안이 나오면 먼저 볼 것)

혼합도 `max` 를 쓰므로 **개별 시드와의 유사도를 각각 재야 한다.** 지금 Redis 는
`(u_sum, w_sum)` 두 개만 들고 있다(1만 명 × 148차원 = 6.5MB, 9장). 채택하면 **그
사람이 반응한 상품 목록**을 유지해야 하고 증분 갱신도 O(148) 한 줄로 끝나지 않는다.

**정확도만으로 정할 안이 아니다.** 오른 폭이 저장·서빙 비용을 살 만한지까지 봐야 한다.

### 남는 질문

**시드 6개+ 구간은 어느 방식으로도 개선되지 않았다.** 부록 J 의 노출 온도로도, 여기의
사용자 표현으로도 안 됐다. 이력이 긴 사람이 왜 더 어려운지는 열린 채로 남는다.

> 재현: `python Research/eval/eval_user_repr_max_sim_20260903.py --split test --modes mean,blend0.2`
> 이 하네스의 `mean` 은 test 에서 23.39% 로 대표 지표와, 시드 구간도 부록 A 와
> 정확히 일치한다. **test 는 이 확인 한 번으로 소진했다.**

## 부록 L — 시드가 많은 사용자가 왜 어려운가 (2026-09-04, 관찰)

부록 J(노출)와 K(사용자 표현)가 둘 다 시드 6개+ 구간을 못 살렸다. 방법을 더 바꿔
보는 대신 **그 사람들이 실제로 무엇이 다른지**를 봤다. 채택을 위한 측정이 아니므로
**test 는 쓰지 않았다** (valid 1,975명).

### 1. 문제가 더 어려운 것이 아니다 — 오히려 더 쉽다

| 시드 | 인원 | Recall@10 | 정답=시드 브랜드 | 정답=시드 카테고리 | 롱테일 | 남은 후보 |
|---|---:|---:|---:|---:|---:|---:|
| 1~2개 | 927 | **26.75%** | 28.0% | 29.6% | 40.2% | 198개 |
| 3~5개 | 808 | 22.40% | 30.9% | 41.7% | 40.2% | 196개 |
| 6개+ | 240 | **19.17%** | **37.9%** | **69.2%** | 39.2% | 191개 |

**정답이 시드 브랜드인 비율도, 시드 카테고리인 비율도 6개+ 쪽이 훨씬 높다.**
브랜드 재구매가 정확도의 대부분인 구조에서 이건 **유리한 조건**이다. 롱테일 비중도
같다. 즉 문제가 어려워서 못 맞히는 것이 아니다.

### 2. 쉬운 케이스에서 무너진다 — 핵심

| 시드 | 정답이 **시드 브랜드**일 때 | 정답이 **새 브랜드**일 때 |
|---|---:|---:|
| 1~2개 | **89.2%** [85, 92] n=260 | 2.4% [1, 4] n=667 |
| 3~5개 | 68.8% [63, 74] n=250 | 1.6% [1, 3] n=558 |
| 6개+ | **50.5%** [40, 61] n=91 | 0.0% [0, 3] n=149 |

같은 "브랜드 재구매" 문제인데 **89.2% → 50.5%** 로 떨어진다.

브랜드 구성비 차이를 없애도 격차는 사라지지 않는다. 1~2개 구간의 비율(28.0%)로
직접 표준화하면 **오히려 커진다.**

| 시드 | 실제 | 재가중 후 |
|---|---:|---:|
| 1~2개 | 26.75% | 26.75% |
| 3~5개 | 22.40% | 20.46% |
| 6개+ | 19.17% | **14.18%** |

격차가 7.6%p → **12.6%p** 로 벌어진다. **브랜드 구성비가 6개+ 구간을 가려 주고
있었다.**

### 3. 기제 — 브랜드 원핫이 후보를 못 좁힌다

`brand` 는 55개 고정 원핫이고 가중치 0.60 이다. 이 항은 **그 브랜드의 상품 전부**를
한꺼번에 밀어올린다. 시드 브랜드가 늘면 밀어올리는 상품이 목록 10칸을 넘어간다.

| 시드 | 시드 브랜드 수 | 같은 브랜드 **후보** 수 | 후보가 10칸 초과 | 브랜드 재구매 적중 |
|---|---:|---:|---:|---:|
| 1~2개 | 1.71개 | 9.4개 | 45.4% | 89.2% |
| 3~5개 | 2.90개 | 16.2개 | 79.2% | 68.8% |
| 6개+ | **6.28개** | **29.9개** | **96.7%** | **50.5%** |

**6개+ 사용자는 브랜드가 후보 29.9개를 가리킨다. 목록은 10칸이다.**
브랜드는 "이 30개 중 어느 것" 을 정해 주지 못하고, 그 선택은 나머지 블록
(concern · ingredient · 카테고리 · 가격)이 해야 한다. 그런데 그 블록들의 lift 는
1.02~1.30x 다 (4-1 표). **브랜드가 좁혀 주던 일이 사라지면 남는 신호가 약하다.**

50.5% 가 "30개 중 무작위 10칸"(≈33%)보다는 높으므로 나머지 블록이 하는 일이
없지는 않다. 다만 89.2% 와의 차이가 그 블록들의 한계다.

### 4. 사용자 벡터는 실제로 무뎌진다 (다만 그게 주범은 아니다)

| 시드 | 시드끼리 유사도 | 카탈로그 중심과의 유사도 | target–시드 평균 | target–시드 최대 | 순위 중앙값 |
|---|---:|---:|---:|---:|---:|
| 1~2개 | 0.2985 | 0.4457 | 0.2424 | 0.3379 | 56위 |
| 3~5개 | 0.2275 | 0.5414 | 0.1989 | 0.3716 | 58위 |
| 6개+ | 0.1815 | **0.6867** | 0.1664 | **0.4427** | 54위 |

설계 문서의 **"시드 6개 이상 → 중심점 근처, 밋밋해짐"** 이 실측으로 확인된다
(중심 유사도 0.4457 → 0.6867). 시드끼리도 덜 닮았다 — 취향이 넓다.

**그런데 순위 중앙값은 세 구간이 거의 같다**(56 / 58 / 54위). 전형적인 경우는
비슷하고, 차이는 **상위 10칸 안**에서만 벌어진다. 무뎌짐이 전반적인 실력을 깎는
것이 아니라, 브랜드가 좁혀 주지 못할 때 10칸 싸움에서 진다는 뜻이다.

### 5. 그래서 max 로는 못 고쳤다 (부록 K 와 이어짐)

`target–시드 최대` 유사도는 6개+ 에서 **오히려 높다**(0.4427). "정답과 아주 닮은
시드가 하나 있다" 는 뜻이라 `max` 가 통할 것처럼 보인다. 실제로는 아니었다.

| 시드 | target 백분위 (mean 기준) | target 백분위 (max 기준) | 후보 점수의 퍼짐 (mean → max) |
|---|---:|---:|---:|
| 1~2개 | 65.4% | 65.0% | 0.1285 → 0.1482 |
| 3~5개 | 64.4% | 63.9% | 0.1269 → 0.1668 |
| 6개+ | 65.2% | 65.3% | 0.1211 → **0.1930** |

**target 의 상대 위치가 전혀 나아지지 않는다.** target 의 max 가 오르는 만큼
**다른 후보의 max 도 같이 오르기** 때문이다. 대신 콘텐츠 항의 퍼짐만 1.6배가 되어,
좋아지지 않은 신호가 속성·인기 항을 더 눌러 버린다 — `w₁` 을 몰래 올린 것과 같다.
부록 K 에서 6개+ 가 19.17% → 14.58% 로 무너진 것이 이것으로 설명된다.

### 결론과 다음

문제는 **"사용자를 어떻게 표현하느냐" 가 아니라 "브랜드 안에서 무엇을 고르느냐"** 다.

2026-08-31 인수인계 문서의 진단은 "정확도가 브랜드 재구매에만 몰려 있고 새 브랜드는
1.4%" 였다. 여기서 한 겹이 더 드러났다 — **브랜드 재구매마저, 시드 브랜드가 늘면
못 맞힌다.** 브랜드가 후보를 10칸 아래로 좁혀 줄 때만 잘 맞히고 있었다.

다음에 볼 것은 **같은 브랜드 30개 중 무엇을 사는가**다. 브랜드 항을 "일치 여부"가
아니라 "그 브랜드 안에서의 개인 적합도" 로 바꾸는 방향이 후보다. 이건 별도 과제다.

## 부록 M — 같은 브랜드 안에서 무엇을 고르는가 (2026-09-04, 신호는 찾았고 정확도로는 안 바뀐다)

부록 L 에서 "브랜드가 후보를 10칸 아래로 좁혀 주지 못할 때 진다" 는 것을 봤다.
그렇다면 **브랜드 안에서 순위를 매기는 신호**가 필요하다. 있는지 찾았다.

**train 에서 찾는다** — 후보를 찾는 단계이므로 valid 는 고르는 데 아껴 둔다.
test 는 부록 K 에서 소진했다.

### 1. 브랜드 안에서 정답의 백분위 (train · 브랜드 재구매 1,813건)

같은 브랜드 후보는 평균 17.3개다. 무작위로 고르면 백분위 50%, Top1 5.8% 다.

| 신호 | 정답 백분위 | 95% CI | Top1 | |
|---|---:|---|---:|---|
| **가격 근접** (그 사람이 낸 값) | **62.7%** | [61.2, 64.2] | 22.7% | **신호 있음** |
| 현행 점수 전체 | 59.9% | [58.5, 61.4] | 18.6% | 신호 있음 |
| 콘텐츠 평균 (`v_u` 코사인) | 59.5% | [58.0, 60.8] | 19.2% | 신호 있음 |
| 콘텐츠 최대 | 59.2% | [57.7, 60.8] | 20.2% | 신호 있음 |
| 속성 친화도 | 55.7% | [54.2, 57.1] | 12.9% | 신호 있음 |
| 평점 | 53.8% | [52.2, 55.4] | 13.7% | 신호 있음 |

**가격이 현행 점수 전체보다 잘 집는다.** 그리고 대조군(브랜드 평균가 근접)이
50% 를 못 넘으므로 **"그 브랜드의 중간 가격이 잘 팔린다" 가 아니라 "그 사람이 낸
값 근처를 또 산다"** 다. 개인화된 신호다.

두 가지가 더 나왔다.

- **인기는 브랜드 안에서 역방향이다** (41.8%). `prior(i)` 항은 인기순으로 미는데
  브랜드 안에서는 **틀린 방향**이다. 가중치가 작아(`w₃` 0.02~0.05) 영향은 제한적
  이지만 방향이 반대라는 것은 기록해 둔다. 시드가 그 브랜드에서 인기 백분위
  54.7% 라 "인기 상품은 이미 샀다" 로 일부만 설명된다 — 나머지는 모른다
- **브랜드 재구매의 71%는 다른 카테고리다** (같은 카테고리 29.1%). 같은 브랜드에서
  같은 것을 또 사는 것이 아니라 **다른 종류를 산다.** 그래서 카테고리 일치는
  신호가 거의 없다(52.6%)

### 2. 왜 지금 모델이 이걸 못 쓰나

`price_bin` 은 **5구간 원핫 · 가중치 0.04** 로 가장 약한 블록이고, 구간이라
$34 와 $36 은 다른 칸인데 $36 과 $49 는 같은 칸이다.

`product-feature-spec.md` 는 "`price_bin` 은 브랜드가 정해지면 따라오는 속성이라
브랜드를 넣은 뒤에는 새로 보태는 것이 없다" 고 적었다. 그 측정은 **전체 평균**
이었다. 정답의 69.4%가 새 브랜드라 **브랜드가 애초에 일을 안 하는 쪽이 평균을
지배한다.** 브랜드 안에서만 보면 가격이 보인다.

### 3. 그런데 점수에 넣어도 정확도는 안 오른다

연속 가격 근접 항을 더해 봤다. `prox(i) = 1 − min(1, |log(price_i/ref)| / log2)`,
`ref` 는 시드 가격의 중앙값이다 (2배 벌어지면 0).

| w_p | 적용 범위 all | 적용 범위 brand (시드 브랜드 후보에만) |
|---|---|---|
| 0.02 | +0.03%p [−0.20, +0.29] | +0.05%p [−0.17, +0.29] |
| **0.05** | +0.02%p [−0.35, +0.39] | **+0.13%p [−0.17, +0.47]** |
| 0.10 | −0.25%p [−0.76, +0.25] | −0.20%p [−0.64, +0.22] |
| 0.20 | −1.34%p [−2.02, −0.67] | −0.47%p [−1.01, +0.07] |

**train 에서조차 CI 가 0 을 넘지 못한다.** 찾는 단계의 데이터에서 안 나오면
valid 로 가져갈 것이 없다. 더 중요한 것은 **살리려던 구간에서 오히려 내려간다는
것**이다 — `brand` 범위 `w_p=0.05` 에서 시드 6개+ 가 22.45% → 21.72%.

### 4. 왜 안 되는지 — 신호는 균일한데 후보 수가 다르다

백분위를 등수로 환산하면 답이 나온다.

| 시드 | 건수 | 같은 브랜드 후보 | 가격 백분위 | 환산 등수 | 10칸 안? |
|---|---:|---:|---:|---:|---|
| 1~2개 | 733 | 11.3개 | 63.1% | 5.2위 | 예 |
| 3~5개 | 802 | 17.0개 | 62.8% | 7.3위 | 예 |
| 6개+ | 278 | **34.0개** | 61.3% | **14.2위** | **아니오** |

**가격 신호의 강도는 세 구간에서 거의 같다** (63.1 / 62.8 / 61.3%). 그런데 후보가
3배가 되니 같은 백분위가 5.2위에서 **14.2위**로 밀린다. 목록은 10칸이다.

후보 34개에서 10칸에 들려면 백분위가 **70.6% 이상**이어야 한다. 가진 것은 61.3%
다. **신호가 있으나 필요한 강도의 절반쯤 모자란다.**

### 결론 — 카탈로그 메타데이터로는 여기까지다

브랜드 안에서 잰 신호 아홉 개 중 **62.7% 를 넘은 것이 하나도 없다.** 가격이 최고고,

구성에서 현행을 넘은 것이 0개였는데, 여기서 그 벽의 **모양**이 드러났다 — 벽은

## 부록 N — CF 를 안 쓴 대가는 얼마인가 (2026-09-04, 참고 수치)

부록 J·K·L·M 이 한 줄로 이어졌다. 노출도 아니고, 사용자 표현도 아니고, 벽은
**"브랜드 안에서 못 고른다"** 인데 그걸 채울 정보가 카탈로그에 없다. 그 자리를
채울 수 있는 것은 사람 간 정보 — CF 다. **얼마인지 숫자로 확정한다.**

2026-08-31 에 "CF 단독 34.75%" 를 쟀지만 **분할 전 · 옛 target 정의**이고
**재현 스크립트가 없었다.** 문서에 숫자만 남고 코드가 사라진 상태였다. 새로 썼다.

### 누출을 어떻게 막았나

CF 는 "이 상품을 산 사람이 다음에 뭘 샀나" 를 쓴다. 평가 대상 9,900명의 리뷰가
그 통계에 들어가면 **정답을 보고 정답을 맞히는 것**이 된다.

그래서 **평가 대상 9,900명의 `author_id` 를 동시발생 통계에서 통째로 뺐다.**

| | |
|---|---|
| 남은 리뷰어 | **249,318명** (상위 200개 상품 리뷰어에서 평가 대상 제외) |
| 긍정 리뷰 | 403,708건 (계약 §7.1 긍정 정의와 동일) |
| 아이템-아이템 | 200×200 코사인, `√(nᵢ·nⱼ)` 정규화. 0 이 아닌 쌍 17,622개 |

평가 대상의 시드도 target 도 이 행렬에 한 톨도 들어가지 않는다.

### 결과 (valid 1,975명 · MMR 까지 같은 파이프라인)

| 방식 | Recall@10 | 롱테일 | 브랜드 재구매 | **새 브랜드** | CBF 대비 |
|---|---:|---:|---:|---:|---|
| CBF 현행 | 24.05% | 32.95% | 74.88% | **1.82%** | 기준 |
| **CF 단독** | **38.99%** | 37.88% | 69.72% | **25.55%** | **+14.94%p** [+12.61, +17.16] |
| CBF+CF α=0.3 | 30.43% | 36.99% | **82.86%** | 7.50% | +6.38%p [+5.06, +7.65] |
| CBF+CF α=0.5 | 35.65% | **38.51%** | **82.86%** | 14.99% | +11.59%p [+9.97, +13.22] |
| CBF+CF α=0.7 | 38.38% | 38.38% | 79.37% | 20.45% | +14.33%p [+12.41, +16.15] |

**차이는 전부 새 브랜드에서 나온다** — 1.82% → 25.55%. 정답의 69.6%가 새 브랜드인데
CBF 는 여기서 무작위(5.11%)보다도 못한다. 부록 M 이 "카탈로그에 그 정보가 없다" 고
결론 낸 자리를 CF 가 정확히 채운다.

예상 밖이었던 두 가지를 적어 둔다.

- **롱테일이 같이 오른다** (32.95 → 37.88%). CF 가 인기 상품만 미는 것이 아니다.
  "정확도를 얻으려면 다양성을 내준다" 는 통념과 반대다
- **하이브리드가 브랜드 재구매에서 둘 다보다 낫다** (82.86% vs CBF 74.88 · CF 69.72).
  **상보적이다** — CBF 가 브랜드 재구매를, CF 가 새 브랜드를 맡는다

### 그런데 채택하지 않는다 — 이유는 정확도가 아니다

**CF 는 리뷰가 없는 신규 등록 상품을 원리적으로 추천할 수 없다.** 동시발생이 0 이라
점수가 0 이다. 브랜드가 상품을 등록해도 **누군가 사기 전까지 안 뜨고, 안 뜨면 아무도
안 산다.** 창업 지원이 기획의 중심이 된 이상(Jira 105) 이건 기능이 없는 것과 같다.

두 번째로, **이 CF 는 우리 데이터가 아니다.** 세포라 리뷰어 249,318명을 빌린 것이다.
신규 브랜드 사이트의 상호작용은 0건이다. **평가에서는 되고 서비스에서는 안 되는
숫자**다.

### 하이브리드를 쓰려면 형태를 바꿔야 한다

위 표의 하이브리드는 **그대로 쓰면 콜드 스타트를 깨뜨린다.** 두 점수를 minmax 로
정규화해 섞기 때문에, CF 이력이 없는 상품은 **0점(최하위)** 을 받는다. 등록 상품을
중립으로 두는 것이 아니라 **적극적으로 밀어낸다.**

쓰려면 **가점 전용**이어야 한다 — 이력이 있는 상품에만 더하고 없는 상품에는 아무것도
하지 않는 형태. 이 문서의 수치는 그 설계를 검증한 것이 **아니다.**

### 이 수치의 지위

**참고 수치다.** test 는 부록 K 에서 소진했으므로 "CF 가 test 에서 몇 %" 는 말할 수
없다. 이 표의 쓰임은 채택 판단이 아니라 **"무엇을 포기했는지" 를 말하는 것**이다.

> `CBF 현행 24.05%` 는 이 하네스의 값이고 공식 valid 는 24.20% 다 (부정 축·브랜드
> 폴백·`view_cap` 없는 독립 재구현). **같은 표 안에서만 비교한다.**
> 재현: `python Research/eval/eval_cf_baseline_20260904.py --split valid`

### 발표에서 말하는 형태

> CF 를 쓰면 valid 기준 **+14.9%p** 입니다. 쓰지 않았습니다 — CF 는 리뷰가 없는
> 신규 등록 상품을 원리적으로 추천할 수 없기 때문입니다. 창업 지원 서비스에서
> 그건 기능이 없는 것과 같습니다. 대신 CBF 로 등록 즉시 추천에 태우는 구조를
> 만들었고, **그 대가가 14.9%p 입니다.**

"못 올렸다" 가 아니라 **"이걸 얻으려고 저걸 줬다"** 다. 그리고 플랫폼에 브랜드가
모여 크로스 테넌트 행동이 쌓이면 CF 는 그때 성립한다 — **지금 없는 것이지 원리적으로
막힌 것이 아니다.**

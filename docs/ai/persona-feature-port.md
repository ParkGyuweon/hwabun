## 1. 무엇을 하는 작업인가

**이관**은 개인 분석 폴더(`Desktop\Research`)에서 만들고 측정까지 끝낸 코드를,
레포에서 팀이 실행할 수 있는 형태로 옮기는 작업이다. **동작을 바꾸지 않는 것이
전제**다. 수치가 달라지면 그것은 개선이 아니라 이관 오류다.

지금 문제는 이것이다. 추천 점수는

```
score(u, i) = w1 x cos(v_u+, v_i) - λ x cos(v_u-, v_i) + w2 x attr_affinity(u, i) + w3 x prior(i)
```

인데, `Recommender` 는 `affinity` 를 **주입받기만 하고** 그것을 만들어 주는 코드가
레포에 없다. 그래서 레포만 클론해서 돌리면 `w2` 항이 항상 0이다.
시드가 적은 구간에서 `w2` 가 0.55~0.80 인 설계인데 그 자리가 비어 있다.

## 3. 결정 사항

### 3-1. `skin_type` 분기는 정본으로 유지한다

복합성(`combination`, 55.3%) 사용자는 `skin_type` 항을 쓰지 않고 그 몫을
`skin_tone` 으로 넘긴다. 계약(`recommendation-io-spec.md`)에 이미 명시돼 있고,
측정된 수치도 이 분기가 적용된 값이다. **실서비스가 쓰는 방식이 이것이므로
그대로 간다.**

| 사용자 `skin_type` | `skin_type` | `skin_tone` | `hair_color` | `eye_color` |
|---|---:|---:|---:|---:|
| `dry` / `oily` / `normal` | 0.40 | 0.40 | 0.10 | 0.10 |
| `combination` | 0.00 | 0.80 | 0.10 | 0.10 |

### 3-2. 친화도 테이블은 리뷰 전체로 만든다 (평가 누출은 기록만)

`affinity_lift.csv` 는 리뷰 전체로 만든다. 오프라인 평가는 각 페르소나의 마지막
리뷰를 정답으로 떼는데, 그 리뷰가 테이블에 이미 들어가 있어 **평가 누출**이 있다.

**실서비스에서는 결함이 아니다.** 과거 리뷰를 전부 써서 친화도를 만드는 것이
정상이고, 미래 데이터를 쓰는 것이 아니다. 문제는 오프라인 평가 숫자에만 생긴다.
그래서 구현은 그대로 두고, 편향 크기를 재서 보고에 각주로 남긴다(§5).

**보고할 때 지킬 것:** 속성 항을 단독으로 인용할 때는 **정답 제외 값 5.88%** 를
쓴다. 정답 포함 값 6.46% 를 쓰면 "속성만으로 인기순(6.15%)을 이긴다" 가 되는데,
정직한 값으로는 이기지 못한다. 전체 성능 수치는 편향이 상대 1% 라 그대로 쓴다.

### 3-3. 세그먼트는 20개다

`skin_type` 4 + `skin_tone` 5 + `hair_color` 6 + `eye_color` 5 = **20**.
행 수 4,000 = 200 x 20 이 맞고, 계약 문서의 "21세그먼트" 는 오기라 정정했다.

## 4. 검증 기준

### 통과 기준 (하나라도 실패하면 미완)

| # | 기준 | 판정 |
|---|---|---|
| 1 | 친화도 테이블 동등성 | 4,000행 전부 절대오차 <= 1e-6 (CSV 반올림 4자리 감안 5e-5) |
| 2 | 정확도 동등성 | 9,900명 leave-last-out Recall@10 이 기존과 \|차이\| <= 0.2%p **그리고** 짝지은 부트스트랩 300회 CI 가 0 포함 |
| 3 | 속성 항 기여 확인 | `w2=0` 조건 대비 CI 가 0을 넘을 것 (빈칸이 메워졌다는 증거) |
| 4 | 레포 단독 실행 | `Desktop\Research` 경로 참조 0건, 필요한 데이터가 레포 안에 있을 것 |
| 5 | 계약 준수 | 20세그먼트 x 200상품 결측 0, 값 0~1, 가중치 합 1, 셀 없으면 기본값 0.5 |
| 6 | 정규화 동일 | skin_tone 5버킷 · eye_color 표기 · brunette→brown 매핑을 케이스 테스트로 고정. 미지의 값에도 죽지 않을 것 |

기준 2의 성격: **"좋아졌다" 가 아니라 "같다" 가 합격이다.**

### 측정만 하고 기록할 것

- 기준선 대비 위치 (무작위 / 인기순 / 속성만 / 현행)
- 9,900명 점수 계산 시간 (설계 문서의 "1만 명 4.6ms" 가 유지되는지)
- 롱테일(인기 101위 밖) Recall — 속성 항은 롱테일을 살리는 쪽이라 여기가 떨어지면 이관이 잘못된 것이다

## 5. 이미 측정한 것 — 평가 누출 편향

`Research/eval_affinity_leakage.py`. 9,900명, 정답 리뷰 12,092건(전체 리뷰의
2.64%)을 뺀 테이블로 같은 평가를 돌려 짝지어 비교했다. 부트스트랩 300회.

| 지표 | 전체 리뷰(현행) | 정답 제외 | 편향 |
|---|---:|---:|---|
| Recall@10 전체 | 22.57% | 22.33% | +0.23%p CI [+0.08, +0.38] |
| Recall@10 롱테일 | 29.33% | 29.07% | +0.26%p CI [-0.03, +0.55] (유의하지 않음) |
| **Recall@10 속성 항만** | **6.46%** | **5.88%** | **+0.59%p** CI [+0.37, +0.82] |

전체에서 작고 속성 항에서 큰 이유는, 정답 리뷰 한 건이 셀 전체를 거의 못 움직이는
대신(shrinkage K=50) **하필 정답 상품 x 그 사람의 세그먼트에 정확히 얹히기**
때문이다. 최종 점수에서는 코사인·인기 항에 희석된다.

부수 확인: 다시 만든 테이블이 `affinity_lift.csv` 와 최대 오차 5e-05 로 일치했다
(= CSV 소수점 4자리 반올림 오차). 기준 1은 통과 가능한 상태다.

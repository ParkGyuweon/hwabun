## 1. 설계 원칙

**속성과 행동을 같은 벡터에 섞지 않는다. 점수 단계에서 합친다.**

상품 벡터는 성분·카테고리 공간에, 사용자 속성은 사용자 공간에 있습니다. 한 벡터로 이어붙이면 코사인 유사도가 두 공간을 뒤섞어 계산합니다. 점수를 따로 내고 가중합하면 각각의 의미가 보존되고, 추천 근거를 항별로 분해해 설명할 수 있습니다.

### 1-1. CBF 에 CF 를 얹는다 (2026-09-04 측정 → **2026-09-07 방향 전환**)

> **이 절은 2026-09-07 에 뒤집혔습니다.** 원래 제목은 "왜 CBF 인가 — CF 를 안 쓴
> 대가를 알고 있습니다" 였고, CF 를 보류한 이유가 둘이었습니다. **하나는 확정된
> 기획으로 사라졌고 다른 하나는 해법을 찾았습니다.**

**CF 가 훨씬 정확합니다.** 한 번도 쓰지 않은 리뷰어에서 뗀 홀드아웃 2,000명
기준입니다 (페르소나로 쓴 사람 전부를 동시발생에서 제외).

| | Recall@10 | 롱테일 | 새 브랜드 정답 |
|---|---:|---:|---:|
| CBF (기존) | 24.15% | 33.06% | **1.44%** |
| CBF + CF 가점 (β=1.0) | **38.55%** | 38.80% | **20.22%** |
| + 학습 결합 (LTR) | **43.90 / 43.75%** | — | — |

**차이는 전부 새 브랜드에서 나옵니다** — 1.44% → 20% 대. 정답의 약 70%가 시드와
다른 브랜드인데 CBF 는 거기서 무작위(5.11%)보다도 못합니다.

**보류했던 이유 ① 크로스 테넌트 — 사라졌습니다.** 확정 기획
(`docs/planning/service-plan.md`)이 **"소비자가 보는 쇼핑몰은 하나"** 로 구조를
못박았습니다. 단일 스토어프론트면 넘을 경계가 없고, 오히려 기획 §11 이 "같은
사용자가 두 브랜드 상품을 함께 조회/구매했는가" 를 **직접 요구**합니다.

**보류했던 이유 ② 신규 등록 상품 — 형태로 해결합니다.** CF 는 이력이 0 인 상품에
점수를 못 줍니다. 그래서 **혼합 형태가 결정적**입니다.

| 정답이 신규 등록 상품일 때 | Recall@10 |
|---|---:|
| CBF 단독 (CF 안 씀) | 24.15% |
| **가점 전용 + 중립 가점** | **18.20%** |
| minmax 혼합 (α=0.7) | **1.55%** |

**minmax 로 섞으면 신규 상품이 사실상 사라집니다**(1.55%). 두 점수를 정규화해
더하면 CF 이력이 없는 상품이 0점(최하위)을 받기 때문입니다. **가점 전용**은
CBF 를 건드리지 않아 18.20% 로 살아 있습니다. **중립 가점**(이력 없는 상품에
0 대신 후보 중앙값)이 손해를 더 줄입니다.

**그래도 남는 손해는 자리로 갚습니다.** 신규 브랜드 전용 칸을 두면 그 사장님의
상품이 오히려 기존 브랜드보다 잘 뜹니다.

| 신규 브랜드 10% 조건 | 전체 | 신규 브랜드가 정답 |
|---|---:|---:|
| 현행 선형 | 34.71 / 35.67% | 3.94 / 3.35% |
| **LTR(증강) + 전용 2칸** | **40.48 / 40.02%** | **43.59 / 42.66%** |

**채택 순서** — 상품별 지지자 수로 CF 를 올립니다 (임계점은 **3명**입니다).

```
0~2명    CBF 단독      CF 를 얹으면 손해 (−0.46%p). 탐색 슬롯으로 노출만 준다
3~30명   CBF + CF 가점  혼합이 CF 단독보다 3~5%p 앞서는 구간
60명~    CF 비중 상향   단독이 혼합을 앞지른다
```

> **채택 절차는 끝났습니다 (2026-09-07 · 09-08).** 하이퍼파라미터는 부록 R-5 에서
> 골랐고(처음 값이 최선에 가까움, holdout_b 확인), `recommender.py` 에 LTR 이 들어갔고
> (`fedc098`, 부록 T), 계약 점수 식은 §4-2 로 바뀌었습니다. 신규 브랜드 전용 칸도
> `Recommender.rank(reserved=N)` 으로 들어갔습니다 (Jira 129, 부록 U).
> 전체 측정은 [`evaluation-framework.md`](evaluation-framework.md) 부록 N·O·P·R·T·U.

## 2. 최종 점수 공식

> **2026-09-07 부터 현행은 이 식이 아니라 학습 결합(LTR)입니다.** 아래 19개 피처
> (이 식의 항들 + CF + 순위·인기·가격 근접 등)를 부스팅 트리에 넣어 점수를 냅니다 —
> 계약 §4-2 · 부록 T. **아래 선형 식은 모델 산출물(`ltr_model.pkl`)이 없을 때의
> 폴백**이고, 3절의 동작 예시와 7절의 가중치 스케줄은 그 폴백의 것입니다. 항 하나하나가
> 무엇을 재는지 이해하는 데는 여전히 이 절이 가장 빠릅니다.

```
score(u, i) = w₁ · cos(v_u, v_i)      ← 행동 기반 (콘텐츠 유사도)
            + w₂ · attr_affinity(u, i) ← 사용자 속성 기반
            + w₃ · prior(i)            ← 인기도 (콜드스타트 보정)
            + w_b · brand_unknown(u, i) ← 어휘집 밖 브랜드 폴백 (4-1-1), w_b = 0.60
```

마지막 항은 **어휘집에 없는 브랜드에만** 붙습니다. 기존 200개는 전부 어휘집 안이라
이 항이 0 이고, 그래서 지금까지의 수치가 그대로입니다.

## 3. 동작 예시 — 숫자로 따라가기

설명을 위해 차원을 4개로 줄인 예시입니다. 실제로는 약 170차원입니다.

**헷갈리기 쉬운 점부터 정리합니다.** 등장인물은 셋인데 성격이 다릅니다.

| | 정체 | 계산 방식 |
|---|---|---|
| 상품 벡터 | 숫자 배열 | 상품 정보를 숫자로 변환 |
| 사용자 벡터 | 숫자 배열 | 사용자가 본 **상품 벡터들의 가중 평균** |
| 속성 점수 | **숫자 하나** | 미리 만든 **표에서 조회** (벡터 아님) |

앞의 둘만 벡터이고 같은 공간에 있어 코사인 유사도가 성립합니다. **속성은 벡터 연산을 하지 않습니다.**

### 3-1. 상품 벡터 (오프라인, 1회)

각 상품이 `[클렌저, 보습, 진정, 고가]` 특성을 얼마나 갖는지 수치화합니다. 카테고리와 highlights에서 기계적으로 생성됩니다.

| 상품 | 클렌저 | 보습 | 진정 | 고가 |
|---|---:|---:|---:|---:|
| **A** 파머시 클렌징밤 | 1.0 | 0.5 | 0 | 0 |
| **B** belif 아쿠아밤 | 0 | 1.0 | 0.5 | 0 |
| **C** 슈퍼굿 선크림 | 0 | 0.3 | 0 | 1.0 |
| **D** 글로우레시피 토너 | 0 | 0.8 | 0.6 | 0 |

### 3-2. 사용자 행동 → 사용자 벡터

사용자가 다음과 같이 행동했다고 가정합니다.

```
A 상세페이지 스크롤 100%  → 가중치 2.5
B 상세페이지 진입만       → 가중치 1.0
```

사용자 벡터는 A와 B 벡터의 가중 평균입니다.

```
분자 = 2.5 × [1.0, 0.5, 0, 0] + 1.0 × [0, 1.0, 0.5, 0]
     = [2.5, 2.25, 0.5, 0]
분모 = 2.5 + 1.0 = 3.5

사용자 벡터 = [0.71, 0.64, 0.14, 0]
```

**행동이 벡터로 전환되는 지점입니다.** 끝까지 스크롤한 A가 2.5배 무겁게 반영되어 벡터가 클렌저 쪽으로 기울었습니다.

사용자 벡터는 **상품 벡터를 재료로 만들어지므로 자동으로 같은 공간에 위치**합니다. 코사인 유사도가 의미를 갖는 이유입니다.

### 3-3. 코사인 유사도 (미열람 상품과 비교)

```
C 선크림과의 유사도 = 0.19
D 토너와의 유사도   = 0.62   ← 더 유사
```

사용자 벡터의 "보습" 성분이 크고 D도 보습 위주라 높게 나왔습니다. C는 "고가" 축으로 치우쳐 멀어졌습니다.

**여기까지 사용자 속성은 전혀 사용되지 않았습니다.**

### 3-4. 속성 점수 (별개 트랙)

사용자가 **지성 피부 / light 톤**이라고 합시다. 이 값은 벡터로 만들지 않고, 리뷰 844,865건으로 미리 집계한 표를 조회합니다.

> "C 선크림에 리뷰를 단 사람 중 지성 피부인 사람들의 평균 평점은?" → 4.6점 → 0.92

| 상품 | 지성 사용자 평점 | light 톤 평점 |
|---|---:|---:|
| C 선크림 | 0.92 | 0.88 |
| D 토너 | 0.70 | 0.85 |

가중치 적용 (`skin_type` 0.4 + `skin_tone` 0.4 + `hair_color`·`eye_color` 0.1씩):

```
C 속성점수 = 0.4×0.92 + 0.4×0.88 + 0.16 = 0.88
D 속성점수 = 0.4×0.70 + 0.4×0.85 + 0.16 = 0.78
```

**이 트랙에서는 C가 우세합니다.** 지성 피부 사용자들의 만족도가 높았기 때문입니다.

### 3-5. 합류 지점은 마지막 덧셈 한 줄뿐

행동 이력 2건이므로 `w = (0.4, 0.5, 0.1)` 구간입니다.

| | 코사인 | 속성 | 인기도 | 최종 점수 |
|---|---:|---:|---:|---:|
| C 선크림 | 0.19 | 0.88 | 0.9 | 0.4(0.19) + 0.5(0.88) + 0.1(0.9) = **0.61** |
| **D 토너** | 0.62 | 0.78 | 0.5 | 0.4(0.62) + 0.5(0.78) + 0.1(0.5) = **0.69** |

→ **D 토너 추천**

### 3-6. 행동이 쌓이면 무게중심이 이동

행동 이력이 10건이 되면 `w = (0.8, 0.2, 0)`으로 전환됩니다.

| | 행동 2건 시점 | 행동 10건 시점 |
|---|---:|---:|
| C 선크림 | 0.61 | 0.33 |
| D 토너 | **0.69** | **0.65** |

속성의 영향력이 줄고 본인 행동이 지배합니다. 초기에는 "같은 피부 타입 사용자들이 선호한 것"으로 시작해 "본인이 실제로 본 것과 유사한 것"으로 옮겨갑니다.

### 3-7. 전체 흐름

```
[상품 정보]                          [리뷰 844,865건]
카테고리·highlights·가격                    │
      │                            상품별 × 속성별 평균 평점
      ▼                                     │

      │                             속성 친화도 표 A
      │  ← 사용자가 본 상품들                 │
      ▼     (행동 가중 평균)                  │

      │                                     │
      ▼                                     │
  코사인 유사도                          표에서 조회
      │                                     │
      └──────────┐         ┌────────────────┘

```

### 3-8. 요약

1. **사용자 벡터는 상품 벡터로 만든다** → 같은 공간이므로 코사인이 성립
2. **속성은 벡터가 아니라 표 조회다** → 리뷰 844,865건으로 사전 집계
3. **둘은 마지막 덧셈에서만 만난다** → 추천 결과를 항별로 분해해 설명 가능

블록별 L2 정규화 → 블록 가중치 → 전체 L2 정규화 순서로 결합합니다. 블록마다 차원 수가 달라 그대로 이어붙이면 큰 블록이 유사도를 지배하기 때문입니다.

### 4-1. `brand` 블록 — 다음 구매를 가장 잘 설명하는 신호

리뷰 데이터에는 `author_id`와 `submission_time`이 있어 **같은 사람의 구매 순서**를 복원할 수 있습니다. 연속한 두 상품이 무엇을 공유하는지 15만 쌍에서 재봤습니다.

| 속성 | 실제 유지율 | 무작위 | lift |
|---|---:|---:|---:|
| **`brand`** | **21.4%** | 3.5% | **6.08x** |
| `price_bin` | 28.9% | 22.2% | 1.30x |
| `clean` | 41.9% | 34.3% | 1.22x |
| `tertiary_category` | 15.7% | 13.3% | 1.18x |
| `secondary_category` | 23.9% | 20.6% | 1.16x |
| `concern` | 31.3% | 27.9% | 1.12x |
| `ingredient` | 54.7% | 53.4% | **1.02x** |

`brand`가 2위의 4.7배입니다. 그런데 콘텐츠 벡터에 없었습니다. 넣은 것만으로:

| | Recall@10 | 롱테일(101위 밖) | 정답 백분위 |
|---|---:|---:|---:|
| 브랜드 없음 | 11.4% | 16.9% | 0.571 |
| **브랜드 추가** | **23.6%** | **31.4%** | **0.642** |

**+12.28%p**, 95% CI [+11.41, +13.10] (대응 부트스트랩 2000회). 새로 맞힌 사람 1,605명 / 놓친 사람 389명.

정답 상품이 시드와 같은 브랜드인 비율이 **30.6%** 입니다(무작위 3.5%). 화장품에서 브랜드 충성도는 잘 알려진 소비자 행동인데 모델이 눈이 멀어 있었습니다.

#### 4-1-2. 브랜드가 좁혀 주지 못하면 나머지 신호는 약합니다 (2026-09-04)

브랜드 원핫은 **그 브랜드의 상품 전부**를 한꺼번에 밀어올립니다. 시드 브랜드가
하나둘일 때는 그것으로 후보가 목록 크기 아래로 좁혀지지만, 이력이 길어지면 그렇지
않습니다.

| 시드 개수 | 시드 브랜드 수 | 같은 브랜드 **후보** 수 | 브랜드 재구매 적중 |
|---|---:|---:|---:|
| 1~2개 | 1.71개 | 9.4개 | **89.2%** |
| 3~5개 | 2.90개 | 16.2개 | 68.8% |
| 6개+ | **6.28개** | **29.9개** | **50.5%** |

**시드 6개+ 사용자는 브랜드가 후보 29.9개를 가리킵니다. 목록은 10칸입니다.**
"이 30개 중 어느 것" 은 나머지 블록(concern · ingredient · 카테고리 · 가격)이
정해야 하는데, 그 블록들의 lift 는 위 표에서 보듯 1.02~1.30x 입니다.

그래서 **같은 브랜드 재구매 문제인데도 89.2% → 50.5%** 로 떨어집니다.
정답이 시드 브랜드인 비율 자체는 6개+ 쪽이 오히려 높습니다(28.0% → 37.9%) —
**문제가 어려워진 것이 아니라 브랜드가 일을 못 하게 된 것입니다.**

이력이 긴 사용자를 살리려면 **브랜드 안에서 순위를 매기는 신호**가 필요합니다.
사용자 표현을 평균에서 max/top-k 로 바꾸는 안은 이 문제를 건드리지 못해
기각됐습니다 (5장 주석 · [`evaluation-framework.md`](evaluation-framework.md) 부록 K).
전체 측정은 부록 L 입니다.

**그 신호를 찾아봤고, 카탈로그 안에는 없었습니다** (2026-09-04, 부록 M).
브랜드 안에서 정답의 백분위를 신호 아홉 개로 쟀는데(무작위 50%) **62.7% 를 넘은
것이 하나도 없습니다.**

| 신호 | 백분위 | | 신호 | 백분위 |
|---|---:|---|---|---:|
| **가격 근접** (그 사람이 낸 값) | **62.7%** | | 속성 친화도 | 55.7% |
| 현행 점수 전체 | 59.9% | | 평점 | 53.8% |
| 콘텐츠 평균 | 59.5% | | 같은 카테고리 | 52.6% |
| 콘텐츠 최대 | 59.2% | | **인기 (`loves_count`)** | **41.8%** |

가격이 **현행 점수 전체보다 잘 집습니다.** 브랜드 평균가 근접(대조군)은 51.5%로
구분되지 않으므로, "그 브랜드의 중간 가격이 잘 팔린다" 가 아니라 **"그 사람이 낸
값 근처를 또 산다"** 는 개인화 신호입니다. 지금 `price_bin` 은 5구간 원핫에
가중치 0.04 라 이 신호를 담지 못합니다.

**그런데 점수 항으로 더해도 정확도는 안 오릅니다.** 시드 6개+ 는 같은 브랜드
후보가 34개라, 백분위 61.3% 는 **14.2위**입니다 — 10칸 밖입니다. 10칸에 들려면
70.6% 가 필요한데 가진 것은 61.3% 입니다. **신호는 있으나 강도가 절반쯤 모자랍니다.**

곁들여 두 가지가 나왔습니다.

- **인기는 브랜드 안에서 역방향입니다** (41.8%). `prior(i)` 항이 미는 방향과
  반대입니다. `w₃` 가 작아 영향은 제한적이지만 방향이 반대라는 것은 기록해 둡니다
- **브랜드 재구매의 71%는 다른 카테고리입니다.** 같은 브랜드에서 같은 종류를 또
  사는 것이 아니라 **다른 종류를 삽니다**

#### 4-1-1. 어휘집에 없는 브랜드는 점수 항으로 받습니다 (Jira 104, 2026-09-03)

`brand` 블록은 어휘집에 담긴 **55개 고정 원핫**입니다. 브랜드가 자기 상품을 직접
등록하는 구조가 되면서 **목록에 없는 브랜드는 그 55차원이 전부 0** 이 됩니다.
정확도에 가장 크게 기여하는 신호(위 표에서 +12.28%p)를 신규 브랜드만 못 받습니다.

브랜드가 등록될 때마다 차원을 늘리고 기존 상품 200개를 다시 인코딩하는 것은 서비스
운영 중에 할 수 없습니다. 그래서 벡터를 건드리지 않고 **점수에 항을 하나 더합니다.**

```
brand_unknown(u, i) = 1   상품 i 의 brand_name 이
                          (a) 어휘집 brand 목록에 없고
                          (b) 사용자 u 가 전환한 상품의 브랜드 집합에 있을 때
                      0   그 밖에는 전부 0
```

문자열 비교라 어휘집이 필요 없고, 처음 보는 브랜드도 그대로 동작합니다. 가중치는
원핫 블록과 같은 **0.60** 입니다. **어휘집에 있는 브랜드는 지금처럼 원핫이 처리하므로
기존 카탈로그의 벡터와 점수가 한 자리도 바뀌지 않습니다** — 당시(CBF 단독) 대표 지표 23.39% 그대로.

> 관계 항으로 **전면 교체**하는 안(brand 블록을 지우고 148 → 93차원)도 재봤습니다.
> valid 에서는 구분되지 않았지만(24.20% vs 24.30%) **test 에서 −0.81%p** 였습니다.
> 신규 브랜드 지원만 필요하다면 폴백으로 충분하고 기존 수치를 지킬 수 있습니다.
> 재현: `Research/eval/eval_brand_relation_feature_20260903.py`

구현은 `batch/jobs/recommender.py` 의 `BRAND_W` · `brand_match()` 입니다.

가중치는 0.60~0.70에서 포화합니다. 0.42까지 낮추면 22.0%, 0.80으로 올려도 23.6%로 더 오르지 않습니다.

> ⚠️ 카탈로그 200개에 브랜드 55종이라 브랜드당 3.6개입니다. 실제 규모에서는 브랜드 후보가 넓어져 이만큼 극적이지 않을 수 있습니다. 다만 30.6%가 같은 브랜드를 다시 산다는 사실 자체는 카탈로그 크기와 무관합니다.

**`lift` 순으로 나머지 가중치를 재배분하는 것은 오히려 손해였습니다** (23.6% → 22.7%). lift는 단독 예측력이라 블록 간 상호작용을 담지 못합니다. 기존 가중치는 그대로 두고 브랜드만 추가합니다.

### 4-2. `concern` 블록 — 리뷰로 보강

`concern`은 가중치가 가장 큰데 200개 중 **44개가 비어 있고** 나머지도 9차원에 평균 1.45개만 켜져 있었습니다. 출처가 `highlights`라서 그렇습니다. 마케팅 문구는 "이 제품이 무엇을 해결하는가"를 다 담지 못합니다.

상품당 리뷰가 평균 2,291건 있습니다. 9개 축을 **리뷰에 실제로 나오는 표현**으로 정의하고(`"cleared up my acne and breakouts"`), 54만 건을 임베딩해 상품별로 집계했습니다. 상위 2축을 태그로 켭니다.

| concern 출처 | Recall@10 |
|---|---:|
| `highlights`만 | 11.4% |
| **`highlights` + 리뷰** | **12.1%** (+0.71%p, CI [+0.12, +1.28]) |
| 리뷰로 전체 대체 | 9.7% |
| 빈 44개만 채움 | 10.8% |

**대체가 아니라 덧셈일 때만 통합니다.** `highlights`를 버리면 오히려 나빠집니다. 마케팅 태그도 정보였습니다.

### 4-3. 시도했지만 채택하지 않은 것 — 사람별 블록 가중치

사람마다 보는 축이 다르다는 가설을 재봤습니다. 시드 상품들이 어느 블록에서 일관된지로 추정합니다(정답을 쓰지 않습니다). 실제로 사람 차이는 있었습니다 — `price_bin`은 16.5%, `secondary_category`는 12.1%가 시드 전부 일치입니다.

브랜드가 **없을 때는** 도움이 됐습니다(11.4% → 11.8%, +0.46%p 유의). 그런데 브랜드를 넣으니 **모든 강도에서 유의하게 악화**됐습니다(−0.28 ~ −2.01%p). 브랜드를 개인화 대상에서 빼도 마찬가지였습니다.

시드 일관성이 사실 브랜드의 대리 변수였고, 진짜 신호가 들어오자 노이즈만 남은 것으로 봅니다. **채택하지 않습니다.**

### 콘텐츠 벡터에서 제외한 것

| 제외 | 이유 |
|---|---|
| `primary_category` | 200개 전부 `Skincare` — 정보량 0 |
| `loves_count` | 상품 속성이 아니라 인기도. 점수의 `prior(i)` 항으로 분리 |
| popularity 태그 | `Community Favorite`, allure 수상 — 인기 신호 |
| **피부타입 적합도** | **6장 속성 친화도 테이블이 담당.** 콘텐츠 벡터는 상품당 1개로 고정되어 사용자별 분기가 불가능하기 때문 |

`ingredient` 블록은 `highlights` 태그(보유율 55%)만으로는 부족하므로 **전성분 문자열을 파싱**해 어휘 30종을 채웁니다. 전성분은 함량 순 나열이므로 **등장 위치로 감쇠**해 미량 성분 과대평가를 막습니다. 상세는 `product-feature-spec.md` 2-2절 참조.

## 5. 사용자 벡터 `v_u` — 행동 기반

사용자가 상호작용한 **상품 벡터들의 가중 평균**입니다. 사용자 속성은 여기 들어가지 않습니다.

> **평균 대신 max/top-k 를 쓰는 안은 2026-09-04 에 기각했습니다** (Jira 108).
> 평균은 상품 벡터가 전부 1사분면에 있어 카탈로그 중심으로 수렴한다는 약점이 있지만,
> **그 무뎌짐이 노이즈 방어이기도 합니다** — `max` 는 시드가 많을수록 "가장 닮은
> 하나" 가 우연히 튄 상품일 확률이 올라가, 시드 6개+ 구간이 19.17% → 14.58% 로
> 무너집니다. 혼합(`0.8·mean + 0.2·max`)은 valid 에서 +0.71%p 였으나 **test 에서
> −0.46%p 로 부호가 뒤집혀** 채택하지 않았습니다.
> 측정 전체는 [`evaluation-framework.md`](evaluation-framework.md) 부록 K.

```
v_u = Σ(wₖ · decay(tₖ) · v_iₖ) / Σ(wₖ · decay(tₖ))
```

## 6. 속성 친화도 `attr_affinity` — 4개 속성 기반

실시간 계산이 아니라 **오프라인에서 만든 조회 테이블**입니다. 리뷰 458,180건(상위 200개 상품)으로 상품 × 세그먼트별 통계를 미리 뽑아둡니다. 서빙 시 딕셔너리 조회 한 번이라 비용이 사실상 0입니다.

테이블: `batch/ingest/data/affinity_lift.csv` (4,000행 = 200상품 × 20세그먼트)

### 6-1. 평점 평균이 아니라 구성비 lift를 씁니다

**당초 안은 "그 상품에 리뷰를 단 해당 세그먼트 사용자들의 평균 평점"이었으나 폐기했습니다.**

측정 결과 4개 속성 모두 판별력이 노이즈 수준이었습니다.

```
판별력 eta^2 :  hair_color 0.00403   skin_tone 0.00328
               eye_color  0.00280   skin_type 0.00262
```

전체 평점 분산의 0.4% 미만이고, 순위 1위가 `hair_color`였습니다. 머리색이 스킨케어 만족도를 가장 잘 설명한다는 것은 인과적으로 성립하지 않으므로 **전부 노이즈**입니다.

원인은 평점 분포입니다. **리뷰의 63.4%가 5점**이라 누가 쓰든 평점이 후하게 나옵니다. 상품 내 세그먼트 간 친화도 차이가 0.03~0.06(0~1 스케일)에 불과해, 표를 만들어도 모든 칸이 거의 같은 값이 됩니다.

**대안: 구성비 lift.** 평점은 다 후하게 주지만 **누가 사는지는 확실히 다릅니다.**

```
lift(상품 i, 세그먼트 s) = (상품 i 리뷰 중 s 비중) / (전체 리뷰 중 s 비중)

affinity = clip((lift - 0.60) / 1.00, 0, 1)
```

상품 내 편차가 0.047 → 0.47로 **10배** 커집니다. 그리고 결과가 해석됩니다.

| 속성 | lift 상위 사례 |
|---|---|
| `skin_type` | `oily` 2.56배 Balancing Force **Oil Control** Toner / `dry` 1.97배 **Cicapair** Tiger Grass Cream |
| `skin_tone` | `deep` 2.91배 Ginzing Vitamin C Eye Cream(**브라이트닝**) / `fair` 1.37배 Cicapair **톤 보정** |
| `hair_color` | `gray` 2.80배 Smart Clinical Repair **Wrinkle** Correcting Serum |
| `eye_color` | `gray` 2.35배 Blueberry Bounce Cleanser (공통점 없음) |

### 6-2. 표본 축소(shrinkage)

표본이 적은 셀은 lift가 튑니다. 기준 비율 방향으로 당깁니다.

```
share_shrunk = (관측수 + K x 기준비율) / (셀 표본수 + K),   K = 50
```

### 6-2-1. 클리핑 구간 `[0.60, 1.60]`

lift를 0~1로 변환할 때의 구간입니다. 초기값 `[0.80, 1.20]`은 범위가 좁아 4,000셀 중 **23.5%가 0 또는 1로 포화**되었습니다. lift 1.82배 상품과 1.35배 상품이 모두 1.000이 되어 상위권 서열이 사라졌습니다.

`[0.60, 1.60]`으로 넓힌 결과입니다.

| 속성 | 포화율 (전) | 포화율 (후) |
|---|---:|---:|
| `skin_type` | 21% | **3.9%** |
| `skin_tone` | 26% | **7.6%** |
| `hair_color` | 27% | **6.1%** |
| `eye_color` | 20% | **7.9%** |

`oily` 기준 상위권이 실제로 구분됩니다.

| 속성 | 세그먼트 | lift 효과크기 | 상품내 편차 | 유의 셀(|z|>3) |
|---|---:|---:|---:|---:|

lift로 바꾸자 `skin_type`이 4위에서 1위로 올라왔습니다.

`hair_color`의 유일한 신호는 `gray`가 안티에이징 제품에 몰리는 것인데, 이는 머리색이 아니라 **연령의 대리변수**로 작동하는 것입니다. `eye_color`는 극단 사례에 공통점이 없어 해석되지 않습니다.

**`hair_color` / `eye_color`는 유지하기로 결정했습니다.** 가중치가 0.10씩(합 20%)이라 잘못된 신호가 순위를 뒤집을 위험이 작고, 사용자 속성 4개를 모두 반영하는 것이 설계 전제입니다. 제거해도 얻는 것이 차원 축소뿐이며 실제 성능 이득은 측정되지 않았습니다. 로그가 쌓이면 실제 지표로 재평가합니다.


### 6-4. `hair_color`의 `brunette` — 데이터 오류 발견

`brunette`는 `brown`의 표기 변형이었습니다.

```
200개 중 99개 상품은 brunette 0%
그런데 4개 상품은 40% 초과, 해당 상품의 brown은 0.6~10%로 붕괴

Microneedling Retinol Patches:  brunette 48.5%  brown 0.6%
Vinosource-Hydra Sorbet:        brunette 47.3%  brown 2.4%
```

같은 사람을 수집 배치에 따라 `brown` 또는 `brunette`로 기록한 것입니다. **평점 기반에서 `hair_color`가 판별력 1위로 나왔던 원인이 이 아티팩트였습니다.** 병합 후 최하위로 내려갔습니다.

`hair_color`는 `brunette` → `brown` 병합, `eye_color`는 `Grey` → `gray` 병합을 전처리에서 적용합니다.

### 6-5. 속성별 가중치 — 사용자 `skin_type`에 따라 분기

| 사용자 `skin_type` | `skin_type` | `skin_tone` | `hair_color` | `eye_color` |
|---|---:|---:|---:|---:|
| `dry` / `oily` / `normal` (44.7%) | 0.40 | 0.40 | 0.10 | 0.10 |
| **`combination` (55.3%)** | **0.00** | **0.80** | 0.10 | 0.10 |

```
attr_affinity(u, i) = w_type  x A[i][u.skin_type]
                    + w_tone  x A[i][u.skin_tone_bucket]
                    + 0.10    x A[i][u.hair_color]
                    + 0.10    x A[i][u.eye_color]
```

`skin_type`과 `skin_tone`을 동등하게 두기로 확정했습니다. 세포라 상위 상품에 선크림·CC크림·톤업 제품이 다수 포함되어 피부 톤이 만족도를 실제로 가릅니다.

**복합성 사용자는 `skin_type` 항을 사용하지 않습니다.** 근거와 처리는 7-4절에 있습니다. 요약하면 복합성은 200개 상품 전부 lift 0.85~1.19(표준편차 0.053)로 판별력이 없고, `skin_tone`은 복합성 사용자 안에서도 유효(표준편차 0.269)하므로 몫을 이관합니다.

**친화도 테이블은 전체 리뷰로 계산한 것 하나만 유지합니다.** 복합성 전용 테이블을 별도로 두는 안은 폐기했습니다 — 복합성/비복합성 독립 검정에서 톤별 상관이 +0.69~+0.82로 신호가 대체로 같은데, 쪼개면 `deep` 톤 셀 표본이 중앙값 23건(최소 0건)까지 떨어져 추정만 불안정해집니다.

### 6-6. skin_tone은 14종 → 5개 버킷으로 묶습니다

`skin_tone`을 `skin_type`과 동등하게 쓰기로 한 이상, 원본 14종을 그대로 쓰면 문제가 생깁니다. 분포가 극단적으로 치우쳐 있습니다 — `dark` 0.05%, `ebony` 0.00%. 상품 200개 × 14종 = 2,800셀인데 하위 셀은 리뷰가 한 자릿수라 통계가 의미 없습니다.

| `light` | light, lightMedium | 42.30% |
| `medium` | medium, mediumTan, olive | 12.31% |

## 7. 가중치 스케줄 — 행동 로그가 쌓이면 이동

### 7-1. 기준 지표: 상호작용한 고유 상품 수

이벤트 수가 아니라 **상호작용한 고유 상품 수**를 기준으로 삼습니다. 스크롤 로그를 25/50/75/100 네 단계로 찍기 때문에, 상품 하나를 끝까지 본 것만으로 이벤트가 5건(상세 진입 + 스크롤 4단계) 발생합니다. 이벤트 수를 쓰면 상품 1개를 정독한 사용자와 상품 5개를 훑은 사용자가 같은 구간에 들어갑니다.

| 항목 | 결정 |

| 정답 | 페르소나당 **1개** (시간순 마지막) |
| 시드 | **나머지 전부** — 상품 3개면 시드 2개, 5개면 시드 4개 |
| 모집단 조건 | 상품 **3개 이상** — 시드가 최소 2개 확보되는 값 |
| 정답 판정 | **소팅 결과 상위 10개**에 정답 상품이 있으면 적중 (`Recall@10`) |

**시작 시점 시드 분포**

| 시드 개수 | 페르소나 | 비중 |
|---|---:|---:|
| 2개 | 5,134 | 51.9% |
| 3개 | 2,189 | 22.1% |
| 4개 | 1,028 | 10.4% |
| 5개 | 585 | 5.9% |
| 6개 이상 | 964 | 9.7% |

**UI와 지표가 1:1로 대응합니다.**

```
[평가]  정답 상품이 상위 10개에 들어오는가
[UI]    "주목할 상품" 섹션에 top-10이 추천 점수 순으로 노출
```

지표가 화면에서 눈으로 확인 가능해집니다.

#### `seen` 정책 — 무엇을 후보에서 뺄 것인가 (프론트 합의)

**장바구니에 담았거나 좋아요를 누른 상품만 제외합니다. 진입만 하고 나간 상품은 후보로 남깁니다.**

| 행동 | `seen` 처리 | 근거 |
|---|---|---|
| `add_to_cart` | **제외** | 이미 확보. 다시 추천할 이유가 없음 |
| `wishlist_toggle` (찜) | **제외** | 명확한 긍정 신호. 이미 담아둠 |
| 상세 진입 후 이탈 | **후보 유지** | 이탈은 "싫어함"이 아님 |

**이탈 상품을 빼지 않는 것이 설계 원칙과 일관됩니다.** 행동 로그 시나리오에서 **"안 산 것 ≠ 싫어한 것"** 을 전제로 삼았습니다(`Research/docs/BEHAVIOR_SCENARIO.md` 10-4절). 봤는데 안 샀다는 것을 부정으로 해석하지 않기로 했으므로, 그것을 이유로 후보에서 빼는 것도 일관되지 않습니다. 실서비스에서도 봤던 상품을 다시 노출하는 리타게팅이 일반적입니다.

> ⚠️ **UI와 반드시 맞춰야 합니다.** 시드 상품은 `add_to_cart`로 환산되므로 **"주목할 상품" 섹션에서 제외**됩니다. 측정도 같은 조건입니다(`cand[si] = False`). UI가 다르게 동작하면 지표와 화면이 어긋납니다.

> **관찰할 것 — 목록 정체.** 이탈 상품이 후보에 남으면, 사용자 벡터가 그쪽으로 기울어 **본 상품이 계속 상위에 뜰** 수 있습니다. 시뮬레이션에서 top-10의 회전율(새 상품이 들어오는 비율)을 관찰하고, 정체가 심하면 **완전 제외 대신 감점(demotion)** 을 검토합니다.

> **참고 — 시드를 2개로 고정하는 안도 검토했으나 채택하지 않았습니다.** 최근 3개만 쓰면 Recall@10이 11.7% → 12.1%로 오르지만, **모델이 좋아져서가 아니라 헤비 유저의 긴 이력을 버려 과제가 쉬워진 것**입니다. 그리고 상품 4개 이상 보유자 48.1%의 데이터를 버리게 됩니다. `w₁` 최적값은 두 방식 모두 0.70으로 같았습니다.

### 7-2-1. 개정 근거 — 실측

페르소나 9,900명 전원에 대해 **시간순 leave-last-out**으로 측정했습니다. 리뷰를 시간순 정렬해 마지막 1건을 정답으로 두고, 앞의 것들(시드)로 추천했을 때 정답이 상위 10개에 들어오는지 봅니다. 생성 로그가 아니라 **실제 리뷰**를 씁니다.

재현: `Research/eval/eval_leave_last_out_baseline.py` · `eval_weight_schedule.py` · `eval_catalog_size_effect.py`

> **모집단이 바뀌었습니다.** 페르소나 조건을 "상위 200개 중 **2개 이상**"에서 **3개 이상**으로 올렸습니다. 시드/목표로 나누면 시드가 최소 2개 확보됩니다(이전에는 60%가 시드 1개였고, 그 벡터는 사실상 상품 하나의 복사본이라 개인화 평가로 약했습니다). 모집단 27,114명, 추출률 36.9%.

**① 항별 기여 (Recall@10)**

| 방식 | 전체 | 정답 51위 밖 | 정답 101위 밖 |
|---|---:|---:|---:|
| 무작위 | 5.0% | 4.9% | 4.9% |
| 인기순만 (w₃=1) | 7.4% | 0.8% | **0.1%** |
| 속성만 (w₂=1) | 6.8% | 6.6% | **8.4%** |
| **콘텐츠만 (w₁=1)** | **11.4%** | 12.8% | 17.2% |
| 이전 스케줄 | 10.6% | 11.5% | 15.0% |
| **개정 스케줄** | **11.7%** | **13.1%** | **17.5%** |

**② 이전 스케줄이 콘텐츠만 쓰는 것보다 못했습니다** (10.6% < 11.4%). 속성·인기도를 많이 섞을수록 손해였습니다. 개정 후에는 11.7%로 콘텐츠만보다 높아집니다 — **적게 섞으면 도움이 됩니다.**

**③ 인기순은 롱테일에서 무너집니다.** 정답이 101위 밖일 때 0.1%입니다. 상위 몇 개만 반복해 보여주므로 당연합니다. **전체 평균은 인기 상품이 정답인 케이스가 지배**해 개인화 실력을 가리므로, 롱테일 지표를 함께 봐야 합니다.

**④ 속성 항은 유지합니다.** 전체 평균으로는 인기순과 비슷하지만(6.8% vs 7.4%), 롱테일에서는 압도합니다(8.4% vs 0.1%). 무대가 다를 뿐입니다. 추천 근거 문구도 이 항에서만 나옵니다.

**⑤ 콜드스타트 줄은 값이 거꾸로였습니다.** 시드 없이 첫 구매 상품을 맞히는 측정입니다.

| w₂ 속성 | w₃ 인기 | Recall@10 |
|---:|---:|---:|
| 0.80 | 0.20 (이전) | 6.8% |
| 0.50 | 0.50 | 15.0% |
| **0.30** | **0.70** (개정) | **16.0%** |
| 0.00 | 1.00 | 17.4% |

행동이 없으면 "다들 사는 것"을 보여주는 게 최선입니다. 순수 인기순이 가장 높지만 **속성을 0.30 남깁니다** — 인기순만 쓰면 신규 사용자 전원이 동일한 목록을 받습니다.

> 본 프로젝트의 페르소나는 리뷰 상품 3개 이상이라 **시드가 최소 2개**입니다. 이 줄은 시뮬레이션에서 밟히지 않고 실서비스 신규 가입자용입니다.

**⑥ 구간을 잘게 나누지 않는 이유 — 신뢰구간이 전부 겹칩니다**

시드 개수별로 최적 `w₁`을 찾고, 부트스트랩(300회)으로 신뢰구간을 냈습니다.

> §7.1 과 정본이 같은 정답을 고르도록 정렬**하면서 §7.1.1(`is_recommended` 를 평점 3

같은 비교를 valid(1,975명)에서 하면 +0.35%p CI [−0.00, +0.76] 로 경계에 걸칩니다.
**효과가 2,000명 규모 분할의 분해능 근처**라는 뜻이므로, 방향(6개 이상 구간에서
콘텐츠 비중을 올린다)은 유지하되 수치를 소수점까지 주장하지 않습니다.

`brand` 블록(55차원)이 들어오면서 **평균을 내도 브랜드 신호가 살아남습니다.** 원핫 벡터라 같은 브랜드를 여러 개 산 사람일수록 그 축이 오히려 뚜렷해지고, 브랜드 재구매가 정확도의 대부분을 설명하는 구조에서 희석이 일어나지 않습니다. 희석은 콘텐츠 블록만 있을 때의 현상이었습니다.

**⑧ 과적합 검사 — train/test 분할**

같은 데이터로 튜닝하고 평가했으므로 70:30으로 나눠 확인했습니다(이전 모집단 기준).

| 스케줄 | train | test |
|---|---:|---:|
| 튜닝 전 | 12.0% | 10.6% |
| 전체로 튜닝 | 12.7% | **11.7%** |
| train으로만 튜닝 | 12.8% | **11.7%** |

**전체로 튜닝한 것과 train으로만 튜닝한 것이 test에서 동일합니다.** 개선이 처음 보는 데이터에서도 유지됩니다.

**⑨ 이 구간이 나중에는 가장 중요해집니다**

`6개 이상`이 9.7%인 것은 **시뮬레이션 시작 시점** 기준입니다.

```
[시작]     시드 2~5개                <- 이번 측정이 본 상태
[로그 축적] + 목표 상품 + 이탈 상품 2~4개 + 세션 반복
[이후]     상호작용 상품 10개 이상     <- 대부분이 6개 이상 구간
```

**로그가 쌓이면 거의 모든 페르소나가 6개 이상 구간으로 이동**합니다. 재측정이 필수이고, 벡터 희석 문제도 그때 다시 봐야 합니다 — 조회·스크롤로 다양한 상품이 들어가면 희석이 아니라 해상도 증가로 작동할 여지가 있습니다.

**⑩ 측정의 한계**

| 한계 | 내용 |
|---|---|
| 행동 로그 없음 | 사용자 벡터를 시드 상품 벡터의 **단순 평균**으로 만들었습니다. **절대 수치가 아니라 방향 판단용**입니다 |
| 시간 감쇠 미적용 | 실제 시드는 `add_to_cart` 이벤트라 `decay(t)`가 붙습니다. 리뷰가 2019~2023년에 걸쳐 있어 차이가 납니다 |
| 2분할 | 다음에는 **train / validation / test 3분할**. 파라미터는 validation으로 고르고 **test는 마지막에 한 번만** |
| 사용자 단위 분할 | 다음에는 **시간 기반 분할** (2019~2022 학습 → 2023 예측) |

**⑪ 평가용 데이터 분할 규칙 — 시뮬레이션과 무관합니다**

> ⚠️ **먼저 짚어둘 것:** 이 분할은 **오프라인 평가 전용**입니다. **시뮬레이션은 페르소나 9,900명 전원이 돌아갑니다.**
>
> ```
> [시뮬레이션]   페르소나 9,900명 전원 -> 행동 로그 생성 -> 트래픽
>                 (분할 없음. 전원 참여)
>
> [오프라인 평가] 실제 리뷰로 leave-last-out
>                 └─ 이때만 train/valid/test로 나눠서 봄
> ```
>
> 두 트랙은 완전히 별개입니다. 오프라인 평가는 생성 로그를 쓰지 않고 실제 리뷰만 씁니다. 분할은 "어느 페르소나의 **평가 결과**를 보고 파라미터를 고를 것인가"의 문제일 뿐, 로그 생성과 무관합니다.

파라미터 선택과 최종 보고를 분리하기 위해 페르소나를 셋으로 나눕니다. `persona_id` 해시 기반이라 **별도 파일 없이 재현**됩니다.

```python
h = int(hashlib.md5(("split-v1|" + persona_id).encode()).hexdigest()[:8], 16) % 10
split = "train" if h < 6 else "valid" if h < 8 else "test"
```

| 집합 | 인원 | 용도 |
|---|---:|---|
| train | 5,954 (60.1%) | 후보 파라미터 탐색 |
| valid | 1,975 (19.9%) | **파라미터 선택** |
| test | 1,971 (19.9%) | **최종 성능 보고 — 한 번만** |

세 집합의 `skin_type` · `skin_tone` · 리뷰 구간 · 시드 개수 분포가 최대 2.4%p 이내로 일치합니다. 에이전트 100명은 이 분할과 별개로 **정성 검증**에만 씁니다.

### 7-3. 페르소나는 콜드 스타트를 별도로 다루지 않습니다

본 프로젝트의 대상은 **리뷰 이력이 2개 이상인 페르소나 10,000명**입니다. 실서비스의 신규 가입자(리뷰 0개·행동 0건)는 시뮬레이션 대상이 아니므로 **별도 콜드 스타트 경로를 구현하지 않습니다.**

시뮬레이션 시작 시점에 페르소나는 **리뷰 상품이 시드로 들어간 상태**입니다(리뷰 2개 이상이 모집단 조건이므로 시드가 최소 1개). 따라서 첫 구간(0개)은 밟히지 않고 80.7%가 `1~2개` 구간에서 출발합니다. 로그가 쌓이면서 구간이 올라갑니다.

> 참고: 상위 200개 상품 리뷰어 247,509명 중 72.8%가 상품 1개짜리라 모집단에서 제외되었습니다. 실서비스에서는 이런 사용자가 다수이므로, 실제 콜드 스타트 대응은 별도 과제로 남습니다.

### 7-3-1. 상품 쪽 콜드 스타트는 다룹니다 (2026-09-03)

기획이 창업 지원으로 바뀌면서 **브랜드가 자기 상품을 폼으로 등록**합니다. 사용자
콜드 스타트와 달리 이쪽은 피할 수 없습니다 — 등록된 상품은 그 즉시 추천 후보가
되어야 하고, 리뷰가 0건이라 벡터의 재료 두 개가 비어 있습니다.

| 필드 | 왜 없나 | 어떻게 채우나 |
|---|---|---|
| `rating` | 리뷰 0건 | 같은 `tertiary_category` 의 **중앙값**. 그 카테고리 표본이 **3개 미만이면 전체 중앙값** |
| `loves_count` | 리뷰 0건 | **0**. 인기도 항이 자연히 바닥값이 됩니다 |

**브랜드에게 직접 물어보면 안 됩니다.** 자기 평점을 적으면 그게 곧 추천 점수가
됩니다. 등록 폼에서 받지 않고 파이프라인이 채웁니다.

표본 3개 미만에서 전체 중앙값으로 내려가는 이유는, 상품 1~2개짜리 카테고리의
"중앙값" 이 그 상품 한둘의 평점일 뿐이기 때문입니다. 등록 상품이 **남의 상품 한 개
평점을 물려받게 됩니다.** 카탈로그 19개 카테고리 중 7개가 여기 해당하고 전체
중앙값과 최대 0.489 벌어집니다 (`For Face` n=2 · 3.833 vs 전체 4.322).

**인기도는 사이트 안에서 다시 폅니다.** `prior(i)` 는 카탈로그 200개 전체의
`loves_count` 를 log1p → minmax 한 값인데, 자기 상품 20개만 파는 신규 브랜드라면
그 20개가 전역 순위 아래쪽에 몰려 **인기도 항이 전 후보에 비슷한 값을 줘 아무것도
구분하지 못합니다** (실측 min 0.0000 max 0.3738). 서빙에서 후보 집합 안에서 다시
0~1 로 폅니다 — minmax 는 아핀 변환이라 이미 정규화된 값에 다시 걸어도 원본 log1p
에 건 것과 같습니다. 상품이 하나뿐이면 0 을 줍니다 (후보가 하나면 인기도가 순위에
영향을 주지 않는 것이 맞습니다).

```python
Recommender(matrix, index, prior, catalog=[이 사이트가 파는 product_id])
```

`catalog` 를 주지 않으면 지금까지와 완전히 동일하게 동작합니다 (평가·기존 배치
경로). **기존 200개의 벡터는 한 자리도 바뀌지 않습니다** — 전부 범위 안이라 자르기가
걸리지 않고, 자기 `rating` 을 쓰므로 중앙값 규칙을 타지 않습니다. test 오프라인
Recall@10 23.39% (롱테일 31.29%) 그대로입니다.

구현은 `batch/jobs/product_encoder.py` 의 `rating_value()` 와
`batch/jobs/recommender.py` 의 `prior_in_catalog()`, 검증은
`batch/jobs/test_cold_start.py` (11건) 입니다. 계약은
[`recommendation-io-spec.md`](../../contracts/recommendation-io-spec.md) 2장.

### 7-4. 속성 항(w₂) 내부 구성 — 복합성 사용자는 다르게

속성 항은 4개 속성의 가중합인데, **`skin_type`이 복합성인 사용자에게는 작동하지 않습니다.**

리뷰 458,614건으로 측정한 결과, 상품 200개에 대한 `skin_type` lift 편차가 이렇습니다.

| 세그먼트 | 사용자 비중 | lift 표준편차 | lift 범위 |
|---|---:|---:|---|
| `oily` | 12.3% | 0.289 | 0.30 ~ 2.56 |
| `dry` | 19.2% | 0.237 | 0.38 ~ 1.97 |
| `normal` | 13.2% | 0.158 | 0.43 ~ 1.55 |
| **`combination`** | **55.3%** | **0.053** | 0.85 ~ 1.19 |

복합성은 200개 상품 전부가 0.85~1.19에 갇혀 있어 사실상 상수입니다. 복합성은 T존 지성 + U존 건성이라 지성용 제품도 건성용 제품도 구매하기 때문입니다. **전체의 55.3%가 복합성이므로 이를 방치하면 속성 항이 사용자 절반에게 무력해집니다.**

**해결: `skin_tone`이 복합성 사용자에게도 유효합니다.**

복합성 리뷰 253,456건만으로 다시 계산한 결과입니다.

| 모집단 | `skin_tone` lift 표준편차 | 상품내 편차 |
|---|---:|---:|
| 전체 사용자 | 0.262 | 0.472 |
| **복합성만** | **0.269** | **0.497** |

편차가 그대로 유지됩니다. 그리고 전체 기준 lift와 복합성 기준 lift의 상관계수가 `deep` +0.959 / `fair` +0.922 / `light` +0.963 / `medium` +0.963 / `tan` +0.943으로, **피부색 신호는 피부 타입과 독립적**입니다.

따라서 `skin_type` 몫을 `skin_tone`으로 이관합니다.

| 사용자 `skin_type` | `skin_type` | `skin_tone` | `hair_color` | `eye_color` |
|---|---:|---:|---:|---:|
| `dry` / `oily` / `normal` (44.7%) | 0.40 | 0.40 | 0.10 | 0.10 |
| **`combination` (55.3%)** | **0.00** | **0.80** | 0.10 | 0.10 |

복합성 사용자 안에서 `skin_tone`이 실제로 갈리는 예시입니다.

밝은 톤이 톤 보정·셀프태닝에, 어두운 톤이 브라이트닝에 몰립니다. 인과적으로 납득되는 신호입니다.

## 8. 다양성 보정 (MMR)

순수 CBF는 필터 버블이 구조적 약점입니다. 상위 N개 선정 시 한 겹 씌웁니다.

```
선택 = argmax [ λ_mmr · score(i) − (1−λ_mmr) · max cos(v_i, 이미 선택된 것) ]
                └ 점수(관련성)            └ 중복 벌점(다양성)
λ_mmr = 0.8   (구현: batch/jobs/recommender.py)
```

**λ_mmr 이 클수록 약하게 거는 것입니다.** λ 가 점수 쪽 계수라 `1.0` 이면 벌점이 0 이
되어 끈 것과 같고, 내릴수록 중복 벌점이 세집니다 (`0.8` 약하게 / `0.5` 세게).
아래 표에서 λ 가 내려갈수록 고유 브랜드가 늘고 정확도가 따라 내려가는 이유입니다.

> **2026-09-08 현재 상태 — 이 절의 수치는 CBF 단독 기준입니다.** 그 뒤 두 가지가
> 브랜드 쏠림을 MMR 보다 훨씬 크게 풀었습니다 (holdout_a 2,000명, 부록 T):
>
> | 구성 | 최다 브랜드 칸 수 | 고유 브랜드 | 10칸 전부 한 브랜드 |
> |---|---:|---:|---:|
> | CBF 단독 (이 절) | 5.92칸 | 4.04종 | 9.8% |
> | + CF 가점 | 4.43칸 | 5.75종 | 3.6% |
> | **+ 학습 결합 (현행)** | **2.62칸** | **8.09종** | **0.1%** |
>
> LTR 에서 `cos_brand` 순열 중요도가 최하위(0.0104)라 **모델이 브랜드를 거의 안 봅니다.**
> 브랜드 상한(한 브랜드 최대 N칸)은 측정에서 전 구간 유의한 손해(4칸도 −2.58%p)라
> 넣지 않았고, 이 결과로 **필요 자체가 사라졌습니다.** MMR 0.8 은 그대로 둡니다 —
> 근거가 정확도가 아니라 다양성이고 CF 채택 후 재스윕하지 않았습니다.
>
> **신규 브랜드 전용 칸 (`reserved`, Jira 129)** 이 다양성 장치로 하나 더 들어갔습니다.
> 메인 k칸 중 N칸을 신규 상품(지지자 < 3명 또는 어휘집 밖 브랜드)에 점수순으로 떼어
> 줍니다. 신규 브랜드 10% 부하에서 그 사장님 상품의 적중률 16.5% → 43.6%, 전체 비용은
> 신규 비율에 따라 부호가 바뀝니다 (10% −1.23%p · 30% +0.58%p · 50% +0.81%p). 지금
> 카탈로그는 신규가 0개라 `reserved=2` 와 `0` 이 같은 결과입니다. 계약 §5-1 · 부록 U.

### 8-2. MMR 은 정확도를 깎지 않습니다

> **선택은 valid, 보고는 test 입니다.** 아래 첫 표(λ 스윕)는 파라미터를 고른
> **valid 1,975명** 기준이고, 채택안의 최종 수치는 **test 1,971명** 기준입니다.
> λ 스윕 표 자체는 2026-09-01 정의에서 잰 값입니다 — λ 선택 근거가 정확도가 아니라
> 다양성이라 다시 재지 않았습니다.

**valid 에서 λ 를 고릅니다.** 어느 λ 에서도 정확도 차이가 유의하지 않습니다 —

| 3개 | 19.40% | 3.57% | 6.8개 | 0.0% | −4.56%p [−5.10, −3.89] |

새 브랜드 적중이 1.5% → 2.4% 로 늘지만 전체가 2.3%p 빠집니다. **시연에서 "한 브랜드만
뜨는 목록"이 문제로 보이면 그때 켜는 스위치**로 남깁니다. 재현은
`batch/jobs/eval_cbf_flow.py` 와 8-2 측정 스크립트입니다.

**MMR 은 새 브랜드 문제의 해법이 아닙니다.** 1.37% → 1.50% 로 거의 움직이지 않습니다.

## 9. 실시간 서빙

**상품이 200개라는 점이 결정적입니다.**

### 오프라인 (배치)

| 산출물 | 크기 |
|---|---|
| `V` 상품 행렬 | 200 × 170 float32 = **133KB** (실측) |
| `A` 속성 친화도 테이블 | 200 × 17세그먼트 = **14KB** |

둘 다 프로세스 메모리에 상주시킵니다.

### 온라인 (요청당)

```
1. user_vector 로드              O(170)
2. scores = V @ user_vector      200 × 170 = 34,000 FLOP
3. + A 조회 후 가중합             O(200)
4. seen 제외(장바구니·좋아요), MMR, 정렬  O(200 log 200)
```

FAISS·벡터DB·ANN 인덱스는 **쓰지 않습니다.** 200개 규모에서는 오버엔지니어링이고, numpy 행렬곱 한 줄이 더 빠릅니다.

### 실측 성능 (2026-08-27, 개발 PC / numpy 싱글 코어)

상품 200개 × 170차원, 사용자 10,000명 조건으로 직접 측정한 값입니다.

> 이 절의 `170` 은 **측정 당시(어휘집 0.2)의 차원**입니다. 현재 어휘집 0.4 는
> **148차원**이라 실제 비용은 여기 적힌 값보다 작습니다. 재실행하지 않은 수치를
> 손으로 환산해 적지 않습니다 — 아래 표는 **상한**으로 읽으십시오.

| 항목 | 실측값 |
|---|---:|
| 추천 1건 (점수 계산 + 상위 10개 추출) | **8.8 μs** |
| 싱글 코어 처리량 | **113,000 RPS** |
| 사용자 10,000명 전원 추천 일괄 재계산 | **4.6 ms** |
| 상품 행렬 `V` 메모리 | 133 KB |
| 사용자 벡터 10,000명 메모리 | 6.5 MB |

**사용자 수는 요청당 비용에 곱해지지 않습니다.** 추천 1건은 `200 × 170` 행렬-벡터 곱 하나이므로, 사용자가 1만 명이든 100만 명이든 단건 비용은 8.8μs로 동일합니다. 사용자 수는 메모리에만 선형으로 영향을 줍니다.

| 사용자 수 | 벡터 보관 메모리 |
|---:|---:|
| 10,000명 | 6.5 MB |
| 100,000명 | 64.8 MB |
| 1,000,000명 | 648.5 MB |

실제 환경에서는 웹 프레임워크 오버헤드와 네트워크 왕복(수십 ms)이 지배적이라 **추천 계산은 전체 응답 시간의 1% 미만**입니다. 병목이 되지 않습니다.

### 서빙 방식 선택

| 방식 | 비용 | 특성 |
|---|---|---|
| **요청 시 계산 (권장)** | 8.8 μs/건 | 최신 행동이 즉시 반영 |
| 배치 미리 계산 | 4.6 ms/전체 | 1초 주기로 돌려도 CPU 0.5% 미만 |

둘 다 성립하므로 구현이 단순한 **요청 시 계산**을 택합니다.

### 실제 병목은 추천 계산이 아니라 로그 적재

추천 연산은 마이크로초 단위라 문제가 되지 않습니다. 부하는 **이벤트 write** 쪽에서 발생합니다. 스크롤 로그를 25/50/75/100 네 단계로 제한한 결정이 여기서 효과를 냅니다 — 1% 단위로 찍었다면 이벤트가 25배로 늘어 DB가 먼저 한계에 도달합니다.

> 참고: 페르소나 10,000명은 동시 접속자가 아니라 전체 사용자 수입니다. 실서비스에서도 동시 접속은 전체의 1~5% 수준이며, 본 프로젝트는 시뮬레이션이라 실트래픽이 발생하지 않습니다. 1만 명 로그를 한꺼번에 처리해도 4.6ms입니다.

### 사용자 벡터 증분 갱신

전체 재계산 없이 O(170)으로 처리합니다.

```python
# 이벤트 1건당
u_sum += w * decay * v_item
w_sum += w * decay
user_vector = u_sum / w_sum
```

Redis에 `(u_sum, w_sum)`만 보관. **10,000명 × 170차원 float32 = 6.5MB**(실측) — 통째로 메모리에 올려도 무방합니다.

### 이벤트 흐름

```
스크롤 75% 이벤트 발생
  → 로그 적재
  → user_vector 증분 갱신 (O(170))
  → 다음 추천 API 호출에 즉시 반영
```

스트리밍 파이프라인이 필요 없습니다. 이벤트 핸들러에서 벡터를 더하는 것이 전부입니다.

## 11. ⚠️ 검증 시 주의

**생성한 페르소나 로그로 가중치를 조정하지 마세요.** 로그를 이 규칙으로 만들 것이므로, 그 로그로 파라미터를 고르면 심어둔 규칙을 되찾을 뿐입니다. 성능이 좋아도 알고리즘의 성과가 아닙니다.

| | 데이터 | 정당한가 |
|---|---|---|
| 파라미터 선택 | **실제 리뷰** | ⭕ |
| 파라미터 선택 | 생성 로그 | ❌ 순환 |
| 시스템 동작 확인 | 생성 로그 | ⭕ |

> **"가중치를 룰로 고정한다"는 표현은 정확하지 않습니다.** 우리도 데이터를 보고 파라미터를 고르므로 **일종의 학습(fitting)입니다.** 다만 파라미터가 3개뿐이고 격자 탐색이라 경사하강법 기반 학습과 규모가 다를 뿐입니다. **과적합 위험은 동일하므로** train/valid/test 분할과 신뢰구간이 필요합니다(7-2-1절 ⑧⑪).
>
> 진짜 제약은 **"생성 로그로는 조정하지 않는다"** 입니다.

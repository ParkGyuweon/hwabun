# B2B 대시보드 프론트 설계 (제안)

작성: 프론트 (2026-08-28)
상태: **제안.** 데이터·백엔드와 합의 후 확정한다.

보는 사람은 **브랜드 담당자**다. 우리 쇼핑몰에 상품을 올린 화장품 브랜드의
마케팅 담당자이고, 알고 싶은 것은 하나로 좁혀진다.

> **왜 사람들이 우리 상품을 안 사는가. 무엇을 보여주면 사는가.**

## 1. 우리가 남들보다 잘 답할 수 있는 것

일반 웹 분석 도구는 클릭과 페이지뷰까지만 본다. 그래서 답이 늘
"상세 페이지 이탈률이 높습니다" 에서 멈춘다. 그 다음이 없다.

우리는 두 가지를 더 갖고 있다.

| 우리만 있는 것 | 어디서 오나 | 답할 수 있게 되는 질문 |
|---|---|---|
| **콘텐츠 단위 주목도** | `section_dwell` + `content_kind` | 성분을 보고 샀나, 리뷰를 보고 샀나 |
| **고객군 속성** | 페르소나 (피부 타입·톤) | 어떤 피부 타입이 무엇을 보고 사나 |
| **좌절 지점** | `rage_click` `dead_click` `scroll_backtrack` | 어디서 막혀서 나갔나 |

**대시보드의 모든 화면은 이 세 가지 중 하나를 파는 데 써야 한다.**
클릭 수·방문 수만 보여주면 무료 도구와 다를 게 없다.

## 2. 화면 구성

브랜드 담당자는 대시보드를 오래 보지 않는다. 첫 화면에서 "문제가 있나 없나"
가 보이고, 있으면 그 자리에서 파고들 수 있어야 한다.

```
① 개요        지금 무슨 일이 일어나고 있나
② 상품 반응    어떤 상품이 되고 어떤 상품이 안 되나
③ 정보 관심도  ★ 무엇을 보여줘야 사나  ← 우리 핵심
④ 고객군      누가 사나
⑤ 마찰       어디서 막히나
```

전 화면 공통 필터: **기간 · 브랜드(고정) · 상품 · 고객군**

---

### ① 개요

한 화면에 **깔때기 하나 + 실시간 흐름 하나**만 둔다.

**의도 깔때기** — `intent` 값을 그대로 쓴다. 별도 계산이 필요 없다.

```
exposure → interest → comparison → validation → conversion
  노출       열람        비교         확인         전환
```

각 단계 사이 이탈률을 보여주고, **가장 크게 새는 구간을 강조**한다.
그 구간을 누르면 ③ 또는 ⑤ 로 이동한다.

`friction` 은 깔때기 옆에 따로 세운다. 단계가 아니라 어디서든 새는 구멍이다.

**실시간 이벤트 흐름** — 실시간 분산 처리가 이 서비스의 정체성이라
지금 데이터가 들어오고 있다는 것이 보여야 한다. 초당 이벤트 수와
최근 이벤트 몇 건을 흘려보낸다.

### ② 상품 반응

브랜드가 올린 상품을 한 줄씩 놓고 깔때기를 가로로 편다.

| 열 | 계산 |
|---|---|
| 노출 | `product_impression` + `recommendation_impression` |
| 클릭률 | `product_click` ÷ 노출 |
| 평균 체류 | `section_dwell` 합 ÷ `page_view` |
| 끝까지 본 비율 | `scroll_depth` 90 이상 도달 ÷ `page_view` |
| 찜 | `wishlist_toggle` (action=add) |
| 장바구니 | `add_to_cart` |
| 이탈 지점 | `exit_summary.last_content_kind` 최빈값 |

**이탈 지점 열이 이 표의 핵심이다.** 전환율이 낮은 상품 옆에
"성분에서 이탈" 이라고 적혀 있으면 그것만으로 할 일이 정해진다.

### ③ 정보 관심도 ★

이 화면이 이 제품의 존재 이유다.

**3-1. 콘텐츠별 주목도**

`content_kind` 20종을 체류 시간 순으로 세운다.

```
ingredient_list   ████████████  38초   전환 기여 2.3x
user_review       ██████████    31초   전환 기여 1.8x
clinical_claim    ███████       22초   전환 기여 2.1x
usage_guide       ████          12초   전환 기여 0.9x
what_it_is        ███            9초   전환 기여 1.0x
```

**전환 기여**는 "그 콘텐츠를 본 방문의 `add_to_cart` 비율 ÷ 전체 평균" 이다.
체류가 길다고 좋은 게 아니라는 걸 같이 보여줘야 한다.
`usage_guide` 처럼 오래 보는데 전환이 안 되는 건 **설명이 어렵다는 신호**다.

집계할 때 `co_visible_blocks <= 2` 인 건만 쓴다. 한 화면에 여러 블록이
겹쳐 있었으면 그 체류가 어느 콘텐츠를 향한 건지 단정할 수 없다.

**3-2. 긁어간 문장**

`text_selection` / `text_copy` 의 `text_snippet` 을 빈도순으로 보여준다.

사용자가 특정 성분명을 긁어서 따로 검색한다는 뜻이라, **어떤 성분이
설명이 부족한지**가 그대로 드러난다. 브랜드가 상세페이지를 고칠 때
가장 직접적인 재료다.

`text_copy` 는 페이지 밖으로 들고 나갈 만큼 관심이 컸다는 뜻이라 따로 센다.

**3-3. 검증 행동**

`accordion_toggle`(성분·사용법 펼침), `ingredient_view_mode_change`(전성분 보기),
`review_filter_apply`(같은 피부 타입 리뷰만) 의 실행률.

이 행동을 한 방문의 전환율을 안 한 방문과 비교해서 보여준다.

### ④ 고객군

페르소나 속성으로 나눈다. **`skin_type` · `skin_tone`** 이 주 축이다.

- 고객군별 전환율
- **고객군별로 무엇을 보는지가 다른가** — ③의 콘텐츠 주목도를 고객군으로 쪼갠다
  (건성은 성분을, 지성은 임상 근거를 오래 보는 식의 차이가 나오면 그게 인사이트다)
- `review_filter_apply` 에서 "나와 같은 피부 타입" 을 고른 비율

### ⑤ 마찰

| 지표 | 이벤트 | 뜻 |
|---|---|---|
| 헛클릭 위치 | `dead_click` + `content_kind` | 눌릴 거라 기대한 지점 |
| 연타 위치 | `rage_click` | 반응 없는 UI |
| 되돌아 읽기 | `scroll_backtrack` + `section_id` | 이해가 안 되는 구간 |
| 망설임 | `hover_dwell` (action=add_to_cart) | 담을까 말까 잰 시간 |

`dead_click` 이 `product_image` 에 몰리면 **확대를 기대했는데 안 되는 것**이다.
사용성 조사에서 반복해 지적되는 문제라, 이게 잡히면 바로 개선 항목이 된다.

## 3. 프론트가 필요한 API

집계는 전부 서버가 한다. 프론트는 원본 로그를 받아서 세지 않는다.
방문당 100~160건이라 브라우저에서 집계할 양이 아니다.

```
GET  /api/dashboard/overview          ① 깔때기 + 요약 수치
GET  /api/dashboard/products          ② 상품별 행
GET  /api/dashboard/content-attention ③ 콘텐츠별 체류·전환
GET  /api/dashboard/text-signals      ③-2 긁어간 문장 빈도
GET  /api/dashboard/segments          ④ 고객군별
GET  /api/dashboard/friction          ⑤ 마찰 지점
SSE  /api/dashboard/live              ① 실시간 흐름
```

공통 쿼리 파라미터

```
from, to        기간 (ISO8601)
brand           브랜드. 담당자는 자기 브랜드만 본다
product_id      선택
skin_type       선택
skin_tone       선택
actor_type      기본 user. 부하 테스트 로그를 섞지 않는다
```

**모든 응답에 표본 수를 같이 준다.** 5명 보고 낸 "전환율 40%" 를
그냥 보여주면 브랜드가 잘못된 판단을 한다. 표본이 적으면 화면에서 흐리게 처리한다.

응답 예시 (③)

```json
{
  "sample_size": 1284,
  "items": [
    {
      "content_kind": "ingredient_list",
      "avg_dwell_ms": 38200,
      "view_rate": 0.62,
      "conversion_lift": 2.3,
      "sample_size": 796
    }
  ]
}
```

## 4. 프론트 구현 방향

- **차트 라이브러리를 아직 안 정했다.** 지금 의존성은 React 뿐이다
- 대시보드는 상세페이지와 완전히 다른 화면이라 **라우터가 필요**하다
  (현재는 목록·상세 둘뿐이라 History API 만 쓰고 있다)
- 로그인·권한이 필요하다. 브랜드 담당자는 자기 브랜드만 봐야 한다
- 실시간은 SSE 를 제안한다. 단방향이고 브라우저 재연결이 기본으로 있다

## 5. 확인 필요

- 집계 주기 (실시간 / 5분 / 1시간). ③ 같은 무거운 집계를 실시간으로 할지
- `conversion_lift` 를 서버가 계산할지, 프론트가 두 수치를 받아 나눌지
- `text_snippet` 원문을 대시보드에 그대로 보여줄지 (성분 사전 매칭 결과만 보여줄지)
- 브랜드 계정과 권한 모델
- 차트 라이브러리

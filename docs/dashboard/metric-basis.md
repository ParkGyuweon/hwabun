# 대시보드 지표별 근거표

작성: 프론트 (2026-09-01)

화면에 있는 지표 하나하나에 대해 두 가지를 적는다.

1. **어떤 이벤트로 계산하나** — 쇼핑몰에서 실제로 받아올 수 있는가
2. **왜 이 지표인가** — 조사에서 나온 마케팅·실무 근거

지어낼 수 없는 지표를 화면에 약속해 두면 파이프라인이 붙었을 때 채울 수가 없다.
반대로 근거 없이 넣은 지표는 발표에서 "이건 왜 있나요" 에 답을 못 한다.
그래서 두 축을 같이 본다.

근거의 출처는 `b2b-dashboard-research.md`(시장·설계 조사)와
`marketing-signal-research.md`(가중치 조사)다. 이벤트 이름과 property 는
`contracts/event-schema.json` 과 `contracts/event-properties-schema.md` 를 따른다.

## 0. 화면 전체를 지배하는 규칙 네 가지

지표 하나하나가 아니라 **배치와 개수**를 정한 근거다. 조사에서 그대로 가져왔다.

| 규칙 | 근거 | 화면에 적용된 모습 |
|---|---|---|
| **지표 8~12개 상한** | 뷰티 브랜드 대시보드의 의사결정 지원 상한이 8~12개로 제시된다. 그 이상은 판단을 돕지 못한다 `[공개]` | Overview 최상단 요약을 4개로 묶고, 화면당 지표를 12개 아래로 유지 |
| **5초 규칙** | 경영진은 5초 안에 핵심을 파악해야 한다. 화면을 5초 보여주고 가린 뒤 "무엇을 봤고 다음에 뭘 할지" 를 물어 검증한다 `[공개]` | Overview 맨 위 **"지금 손봐야 할 것" 한 줄**. 지표 카드보다 위, 가장 크게 |
| **역피라미드** | 결론 → 추세 → 근거 순으로 펼친다 `[공개]` | 모든 화면을 `결론 → 추세 → 표` 세 층으로 고정 |
| **표본 수 병기** | 표본 기반 데이터가 오해를 부르고 실행 불가능하다는 지적이 반복된다. 5명 보고 낸 "전환율 40%" 를 그냥 보여주면 잘못된 판단을 한다 `[추정]` | 모든 수치에 표본 수를 붙이고, 표본이 적으면 흐리게 처리 |

**조사의 가장 중요한 결론:** 브랜드의 불만은 "데이터가 없다" 가 아니라
**"쓸 수가 없다"** 였다. 경쟁 도구가 못 하는 것은 수집이 아니라 **해석**이다.
클릭 수와 방문 수를 더 예쁘게 보여주는 것으로는 팔 수 없다.

그래서 화면의 모든 요소는 아래 셋 중 하나를 팔아야 한다.

| 우리만 있는 것 | 어디서 오나 | 답할 수 있게 되는 질문 |
|---|---|---|
| **콘텐츠 단위 주목도** | `section_dwell` + `content_kind` | 성분을 보고 샀나, 리뷰를 보고 샀나 |
| **고객군 속성** | 페르소나 피부 타입·톤 | 어떤 피부 타입이 무엇을 보고 사나 |
| **좌절 지점** | `rage_click` `dead_click` `scroll_backtrack` | 어디서 막혀서 나갔나 |

## 3. 정보 관심도 ★ — 이 화면이 제품의 존재 이유

| 지표 | 계산에 쓰는 이벤트 | 받아올 수 있나 | 왜 이 지표인가 |
|---|---|---|---|
| **콘텐츠별 주목도** | `section_dwell` 을 `content_kind` 별로 합산 | O | 일반 웹 분석 도구는 클릭과 페이지뷰까지만 본다. 답이 늘 "상세 페이지 이탈률이 높습니다" 에서 멈춘다. 콘텐츠 단위로 쪼개야 그 다음이 나온다 |
| **전환 기여** | 그 콘텐츠를 본 방문의 `add_to_cart` 비율 ÷ 전체 평균 | O | **체류가 길다고 좋은 게 아니라는 걸 같이 보여줘야 한다.** 사용법처럼 오래 보는데 전환이 안 되는 것은 설명이 어렵다는 신호다 |
| 집계 조건 | `section_dwell.co_visible_blocks ≤ 2` 인 건만 | O | 한 화면에 블록이 여러 개 겹쳐 있었으면 그 체류가 어느 콘텐츠를 향한 건지 단정할 수 없다. **PC 쇼핑이라 한 화면에 블록이 여러 개 들어가서 이 조건이 특히 중요하다** |
| **긁어간 성분 TOP 10** ★ | `text_selection`/`text_copy` 의 `matched_ingredients` | O | 사용자가 성분명을 긁어 밖에서 검색했다는 것은 **그 성분의 설명이 부족하다**는 직접적인 증거다. 원문은 저장하지 않고(데이터 계약) 성분 사전 표준명만 남긴다 |
| 성분 사전 | `contracts/product-feature-vocab.json` | O | AI 파트가 상품 벡터에 쓰는 것과 **같은 사전**이다. "이 성분을 긁은 사람" 과 "이 성분이 든 상품" 이 같은 이름으로 조인된다 |
| **검증 행동 실행률** | `ingredient_view_mode_change` · `accordion_toggle` · `review_expand` · `review_filter_apply` | O | 그 행동을 한 방문과 안 한 방문의 전환율을 비교한다. 능동적으로 사실을 확인한 사람이 더 사는가 |

> **성분이 왜 중심축인가** — 조사에서 화장품 시장 세분화의 축으로 성분 선호가
> 반복해 나온다. 히알루론산·레티놀 같은 성분의 인기 변화를 추적하는 것이
> 트렌드 식별의 표준 방법으로 제시된다 `[공개]`.
> 우리 AI 파트가 상품 벡터에 브랜드 블록을 넣어 추천 정확도를
> **11.4% → 23.6%** 로 올린 것도 같은 방향이다. 성분과 브랜드가 화장품에서
> 실제로 작동하는 축이라는 뜻이다.

## 5. 행동 분석 — 의도 퍼널과 마찰

| 지표 | 계산에 쓰는 이벤트 | 받아올 수 있나 | 왜 이 지표인가 |
|---|---|---|---|
| **의도(intent) 퍼널** ★ | 봉투의 `intent` 필드를 그대로 | O | 이벤트 이름이 아니라 **발생 시점에 실린 의미**로 단계를 세므로 이벤트가 늘어나도 퍼널 정의가 흔들리지 않는다. 별도 계산이 필요 없다 |
| 표준 퍼널 | GA4 기준 단계 | O | 의도 퍼널의 대조군. 업계 표준 언어로도 말할 수 있어야 한다 |
| 헛클릭 위치 | `dead_click` + `content_kind` | **실사용자 전용** | 눌릴 거라 기대한 지점. **`product_image` 에 몰리면 확대를 기대했는데 안 되는 것.** 훅은 정상 동작하지만 가상 사용자(러너·코드 생성기)가 이 행동을 만들지 못해, 합성 로그만 도는 동안은 항상 0 이다 |
| 연타 위치 | `rage_click` | O | 반응 없는 UI |
| 되돌아 읽기 | `scroll_backtrack` + `section_id` | O | 이해가 안 되는 구간 |
| 망설임 | `hover_dwell` | O | 담을까 말까 잰 시간 |
| 장바구니 제거율 | `remove_from_cart` ÷ `add_to_cart` | O | |
| 이벤트 발생량 상위 13 | 이벤트별 건수 | O | 수집이 실제로 돌고 있다는 것을 보이는 화면 |

> **주의:** 좌절 신호는 상품이 아니라 **화면 구성의 문제**일 수 있다. 특정 상품에
> `rage_click` 이 몰리면 그 상품이 싫다는 뜻이 아니라 그 페이지의 UI 문제일
> 가능성을 먼저 본다. **상품 선호와 UI 품질을 같은 축에 넣지 않는다.**

## 8. 지금 모의값인 것과 실측인 것

| 구분 | 화면 | 상태 |
|---|---|---|
| **실측** | 리뷰 분석 · 성분 분석 | 리뷰 2,000건과 상품 성분 문자열에서 지금 실제로 계산 |
| **모의** | Overview · 상품 · 정보 관심도 · 고객군 · 행동 | 수집 API 연결 전. 상품 특성(리뷰 수·평점)에 비례하도록 **시드 고정**으로 생성 |

모의값에 `Math.random` 을 쓰지 않는다. 새로고침마다 숫자가 바뀌면 화면을
검토하는 사람이 변화의 원인을 찾느라 시간을 버린다.

화면이 카드마다 `실측` / `모의` 배지로 구분해 보여준다. 집계 API 가 붙으면
`frontend/src/dashboard/lib/metrics.ts` 의 함수 본문만 `fetch` 로 바꾸면 된다.

**모든 모의 지표는 위 표의 이벤트로 실제 산출된다.** 계산식이 없어서 못 채우는
지표는 화면에 두지 않았다.

## 9. 화면에서 뺀 것

이름으로 약속했지만 이벤트로 못 재는 것이라 고쳤다.

| 이전 | 이후 | 이유 |
|---|---|---|
| 구매 전환율 | **장바구니 전환율** | 결제 화면도 `purchase` 이벤트도 없다. 값은 원래부터 `add_to_cart` 였고 이름만 구매였다 |
| 장바구니 재고율 | **장바구니 제거율** | 값이 제거율인데 라벨이 재고율이라 숫자와 뜻이 반대였다 |
| "구매 버튼을 점검하세요" | **"담기 버튼"** | 이 쇼핑몰에 없는 버튼을 점검하라고 안내하고 있었다 |

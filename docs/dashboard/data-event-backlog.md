상태: 제안. 계약 변경은 담당 파트 합의 후 `contracts/` 에 반영한다.

## 0. 지켜야 할 제약

| 제약 | 뜻 |
|---|---|
| **상품·리뷰 데이터는 더 모으지 않는다** | 세포라 상위 200개 상품과 리뷰 3개 이상 남긴 사용자 모집단은 서로 묶여 있다. 상품을 추가하면 페르소나·친화도·holdout 평가가 전부 깨진다 |
| **목표는 재현 가능한 증명** | 실제 소상공인이 상품을 등록한 서비스가 아니라, "브랜드로 나눠서 분산 처리가 되고, 브랜드마다 근거 있는 인사이트를 나눠 갖는다" 를 보이는 것 |
| **페르소나 행동은 실사용자처럼** | 실제 리뷰 이력과 피부 정보를 가진 페르소나가 쇼핑하는 것처럼 로그가 나와야 한다 |
| **백엔드·데이터 일이 과도하게 늘면 안 된다** | 새 기능은 기존 배치·마트 구조 안에 얹는다 |

그래서 아래에서 "추가할 데이터" 는 전부 **상품·리뷰가 아닌 것**이다. 사전(성분·카테고리),
외부 트렌드 피드, 설문 응답, 그리고 이미 있는 데이터의 재해석만 있다.

## 2. 이벤트·로그 수정 목록

이벤트 계약(`event-schema.json` · `event-properties-schema.md`) 변경은 세 종류다.

### 2-1. 새 이벤트

| event_name | intent | required | optional | 왜 |
|---|---|---|---|---|
| `begin_checkout` (Planned → 활성) | `conversion` | `items: object[]` | `cart_value`, `currency` | 이미 정의됨. enum 등록만 |
| `purchase` (Planned → 활성) | `conversion` | `order_id: string`, `items: object[]` | `order_value`, `currency` | 이미 정의됨. `items[]` 원소는 계약 §6대로 `product_id`, `quantity`, `unit_price`(선택 `sku_id`). DW의 `item_revenue`는 `unit_price × quantity`로 파생 — 데이터 파트 확정 필요 |
| **`purchase_reason_select`** (신규) | `validation` | `order_id: string`, `reasons: string[]` (1~2개) | `primary_reason: string`, `free_text_kind: string`, `skipped: boolean` | 구매 직후 한 번, 클릭 설문. 원문 자유 입력은 저장하지 않고 분류만(`free_text_kind`) |

`reasons` enum (뷰티 특화, 10개 이하로 고정):

```
ingredient        성분이 마음에 들어서
skin_fit          내 피부 타입·톤에 맞아서
reviews           리뷰가 좋아서
review_same_skin  나와 같은 피부 리뷰를 보고
price             가격이 맞아서
brand_trust       이 브랜드를 믿어서
texture_finish    제형·마감이 좋아서
clean_claim       무향·비건 등 성분 배제 조건 때문에
recommendation    추천을 받아서
restock           쓰던 걸 다시 사서
```

`restock` 은 재구매의 선언 신호라 `repurchase_kpi` 와 교차 검증에 쓴다.

### 2-2. 기존 이벤트에 속성 추가 (전부 optional, 계약 무해)

| event_name | 추가 속성 | 왜 |
|---|---|---|
| **모든 이벤트** | ~~`tenant_id`~~ 봉투에 싣지 않음 | 2026-09-03 에 `tenant_id`(0.3.0-draft) 가 제안됐으나 **철회**됐다. 정본 `contracts/event-schema.json` 은 `0.2.0-draft` 만 받고 소유 식별자(tenant·business·brand)를 Event 에 직접 쓰지 않는다. 처리 단계에서 `product_id → dim_product` 조인으로 파생한다 (데이터 파트, S15P21A306-125). 프론트 로거는 2026-09-09 에 `tenant_id` 생성·전송과 storefront 의 slug 로직을 제거했다 |
| **브랜드 자체 대상 Event(향후)** | `brand_id: string` (선택) | 상품 없는 플랫폼 공통 Event에는 기록하지 않고, 브랜드관 도입 시 별도 계약으로 명시 |
| `text_selection` / `text_copy` | `selection_kind: ingredient \| claim \| usage \| price \| other` | 지금은 성분만 매칭, 나머지는 버림. 분류만 남기고 원문은 여전히 저장하지 않는다 |
| `section_view` / `section_dwell` (`content_kind=highlight_badge`) | `badge_id: string` (clean 태그 16종 값) | "Vegan 배지는 읽히나" 를 재려면 배지 단위 식별이 필요 |

| `add_to_cart` | `price_usd` (생성기는 이미 실음) → 계약에 명시 | 가격 밴드 분석 분모 |

## 4. 구매 이유 설문 — 행동 추론을 단정하지 않기 위한 장치

### 4-1. 문제

"성분 텍스트를 긁었다 → 성분 때문에 샀다" 는 추론이다. 긁은 사람이 다른 이유로 살 수도
있고, 성분을 본 적 없이 리뷰만 보고 살 수도 있다. 행동 로그는 **주목**을 재고 **동기**를
재지 못한다.

### 4-2. 설계

- 결제 완료 화면에서 **한 번, 클릭만, 건너뛰기 가능**. 최대 2개 선택
- 선택지는 §2-1 의 10개. 뷰티 명사로만 구성한다
- 자유 입력은 받되 저장은 분류값만 (원문 미저장 원칙)
- 화면에는 **선언 이유와 행동 추론을 나란히** 놓는다. 일치하면 확신, 갈리면 "확인 필요" 로 표시

| 표시 | 선언(설문) | 추론(행동) | 해석 |
|---|---|---|---|
| ✔ 확신 | 성분 | 성분 섹션 체류 상위 | 성분 설명이 일한다 |
| ⚠ 갈림 | 리뷰 | 성분 섹션 체류 상위 | 성분을 오래 봤지만 결정은 리뷰가 했다. 리뷰를 앞에 |
| ⚠ 갈림 | 성분 | 성분 섹션 체류 없음 | 다른 곳(광고·입소문)에서 성분을 알고 왔다 |

### 4-3. 합성 데이터에서 설문이 진짜처럼 나오는 방법

생성기는 이미 **hidden preference** 로 행동을 정하고, 페르소나 스타일 축(가격 민감,
리뷰 의존 등)을 리뷰 원문에서 뽑는다(`build_persona_style.py`). 설문 응답을 **같은
스타일 축에서 확률적으로** 뽑으면:

- 행동과 응답이 같은 원인에서 나오므로 둘의 일치율이 자연스럽게 높되 1.0 이 아니다
- 노이즈(다른 이유 선택, 건너뛰기 30% 내외)를 넣어 실사용자 응답률을 흉내낸다
- **`reason_vs_behavior` 마트가 행동 추론의 정확도를 재는 검증 장치**가 된다 — 발표에서
  "우리 행동 추론은 선언 이유와 N% 일치한다" 를 말할 수 있다

PA(LLM 에이전트)는 프롬프트에 프로필과 방금 한 행동을 주고 이유를 고르게 한다.
이미 `reason` 문장을 매 턴 생성하고 있어 추가 비용이 거의 없다.

## 5. 글로벌 뷰티 트렌드 피드 — 매일 아침, AI 가, 백엔드 일 없이

### 5-1. 가능한가

가능하다. 단, "매번 사람이 클로드에게 시키는" 것이 아니라 **배치 잡 하나가 하루 한 번
Claude API 를 호출**하는 구조다. 워크스페이스에 이미 `뷰티트렌드` 스킬(틱톡·인스타 주간
리포트)이 있어 프롬프트와 출력 형식의 프로토타입은 있는 셈이다. 그것을 API 호출로 옮긴다.

### 5-2. 데이터 소스 비교

| 소스 | API | 비용 | 안정성 | 판정 |
|---|---|---|---|---|
| Google Trends | 공식 공개 API 없음(비공식 pytrends 는 차단 잦음) | 무료 | 낮음 | 보조 |
| TikTok Creative Center | 공개 API 없음 | — | 스크래핑 불가 | 제외 |
| Instagram 해시태그 | Graph API, 비즈니스 계정 필수, 7일 30개 해시태그 제한 | 무료 | 중 | 보조 |
| 뷰티 매체 RSS (Allure, Glossy, CosmeticsDesign, BeautyMatter, 코스인, 뷰티누리) | RSS | 무료 | 높음 | **주 소스** |
| Reddit (r/SkincareAddiction, r/AsianBeauty) | 공식 API 무료 티어 | 무료 | 중 | 보조 |
| **Claude API + `web_search` 서버 도구** | 한 호출로 검색·읽기·요약·성분 매핑까지 | 검색 1,000회당 $10 + 토큰 | 높음 | **실행 엔진** |

RSS 를 직접 파싱하는 코드를 우리가 짜는 대신, Claude 호출 하나에 `web_search`
(하루 8회 상한) 를 붙여 검색·요약·**우리 성분 사전으로 매핑**을 한 번에 시킨다.
매핑이 핵심이다. 트렌드 토픽이 우리 성분 30종(확장 시 그 이상)과 고민 9축에 붙어야
"이번 주 글로벌에서 뜨는 성분 X — 우리 몰에서 X 관심도는 지난주 대비 +N%" 가 된다.

### 5-3. 구조 — 백엔드 코드 0줄

```
[cron 07:00 KST]  batch/jobs/trend_daily.py  (Python, 기존 batch/ 안)
     │  Claude API 1회: web_search ≤ 8회, structured output(JSON)
     │  입력: 성분 사전 + 고민 축 + 어제까지의 trend_daily
     ▼
trend_daily/2026-09-03.json   →  (1) DW `trend_daily` 마트 append
                              →  (2) nginx 가 정적으로 서빙 (/data/trend/latest.json)
     ▼
대시보드 ⑥ "시장에서 배우기" 가 fetch  +  ingredient_weekly_interest 와 조인
```

- 백엔드(Spring) 변경 없음. 정적 JSON 을 nginx 가 서빙한다
- 데이터 파트는 마트 append 한 줄
- 모델은 `claude-opus-5`, 구조화 출력으로 스키마 강제. 재시도·폴백은 SDK 기본값
- 하루 비용: 검색 8회 $0.08 + 토큰(입력 ~15K, 출력 ~3K) 약 $0.15 → **월 $7 미만**
- 실패 시 전날 JSON 을 그대로 두면 화면은 안 깨진다

### 5-4. 출력 스키마 (구조화 출력으로 고정)

```json
{
  "date": "2026-09-03",
  "topics": [{
    "topic": "PDRN(연어 DNA) 세럼",
    "region": ["global", "kr"],
    "momentum": "rising",
    "mapped_ingredients": ["PDRN"],
    "mapped_concerns": ["Anti-Aging", "Dullness/Uneven Texture"],
    "summary_ko": "…2문장…",
    "why_it_matters_for_small_brands": "…1문장…",
    "sources": [{"title": "...", "url": "...", "published": "2026-09-01"}]
  }]
}
```

`mapped_ingredients` 가 사전에 없는 값이면 `unmapped` 로 따로 모아 사전 확장(D1) 후보로
쓴다. 트렌드 피드가 사전을 키우는 순환이다.

### 5-5. 대안과 왜 안 고르나

| 대안 | 왜 아닌가 |
|---|---|
| Managed Agents 예약 실행(cron 내장) | 클라이언트 스케줄러가 필요 없다는 장점은 있지만 새 플랫폼 표면이 하나 더 생긴다. 지금은 `batch/` 크론 한 줄이 더 작다 |
| 클로드 코드 스킬을 매주 수동 실행 | 지금 프로토타입은 이것. "AI 가 가져다준다" 를 보이려면 자동이어야 한다 |
| 실시간 소셜 스트리밍 | 소스 API 가 없고 백엔드 부담이 크다. 일 1회로 충분하다 |

## 6. 시뮬레이터 수정 — 실사용자처럼 보이게

| # | 지금 | 바꿀 것 | 왜 |
|---|---|---|---|
| S1 | 긍정 시드 → `add_to_cart` 1회 | 긍정 시드 → `add_to_cart` → `begin_checkout` → `purchase` → `purchase_reason_select` | 구매·재구매·설문 세 지표의 원천 |
| S2 | 같은 상품 중복 리뷰를 평균으로 합침 | 중복 리뷰 = 시간 간격을 둔 **재구매**로 방출 (`restock` 이유) | 리뷰 데이터에 이미 있는 재구매 신호를 살린다 |
| S3 | 한 페르소나 = 시드 세션들 + "지금" 세션 1개 | 마지막 5일 안에 **재방문 2~3회**(둘러보기만, 담기만, 구매) | 실사용자는 한 번에 안 산다. 세션 간 hesitation 이 생긴다 |
| S4 | 라인 재구매 없음 | 같은 브랜드 다른 상품 구매 확률 30.6% | 실측 정의: holdout 정답이 시드와 같은 브랜드인 비율(무작위 3.5%). 200개·55브랜드 조건값 — 인용 시 recommendation-design.md 4-1 주의 문구 병기 |
| S5 | `brand_id` 없음 | 상품 대상 Event는 `product_id`를 기준으로 `dim_product`에서 `brand_id`를 파생 | 통합몰 귀속 계약 |
| S6 | 설문 없음 | 스타일 축 → 이유 확률 + 건너뛰기 30% | §4-3 |
| S7 | 진열 `storefront_*` 는 프론트만 실음 | 브랜드별 진열 프리셋을 생성기도 실음 | 진열 효과 분석이 합성 로그에서도 되게 |

PA 100명은 프론트를 실제로 조작하므로 S1·S6 만 프롬프트에 결제 화면 행동을 추가하면 된다.

## 7. 브랜드 분할 — 어떻게 나눠야 증명이 되나

**실제 `brand_name` 을 그대로 브랜드 단위로 쓴다. 인위적으로 묶거나 쪼개지 않는다.**

| 선택 | 결과 | 판정 |
|---|---|---|
| 200개 상품을 임의로 N개 가짜 브랜드에 배정 | 브랜드 재구매 30.6% 실측이 사라짐. 추천 정확도 12%p 를 만든 신호를 스스로 지움 | ✗ |
| **실제 브랜드 55개 = 입점 브랜드 55개** | 브랜드당 평균 3.6개 상품 = 1인 브랜드 규모와 비슷. 재구매·친화도 신호 보존 | ✔ |
| 55개 중 상품 5개 이상 브랜드만 대시보드 시연 | 표본 규칙(R2)에 걸리지 않는 브랜드로 화면을 보인다. 나머지는 "표본 부족 → 흐림" 이 정직한 화면 | ✔ 시연 전략 |

분산 처리 증명: Kafka 키는 `session_id` 그대로 두고(세션화에 필요), Spark 후속 작업에서는
기존 `tenant_id` 필터·집계 축·물리 partition 의존성을 제거한다. `business_id`·`brand_id`
귀속과 물리 저장 레이아웃은 Dimension·Mart 후속 Jira에서 조회 패턴과 함께 확정한다.
사업자별 접근 권한은 Backend가 검증하고, 코호트 최소 5개 규칙은 Commons Mart에서
별도로 적용한다.

## 8. 공유 인사이트가 "모두에게" 도움이 되는지 — 실효성 시험

커먼즈 C층의 각 인사이트는 아래 시험을 통과해야 화면에 올린다.

**시험 1 — 행동 연결.** 1인 창업자가 할 수 있는 행동은 넷뿐이다. 인사이트가 그중
하나로 곧장 이어지지 않으면 뺀다.

```
① 상세페이지 문구·순서 바꾸기   ② 진열(storefront) 바꾸기
③ 다음 제품의 성분·고민 정하기   ④ 타깃 고객군 문구 바꾸기
```

**시험 2 — 작은 브랜드 수혜.** 상품 3개 브랜드가 상품 15개 브랜드보다 **더** 얻어야 한다.
자기 표본으로 못 보는 것을 코호트에서 보는 것이 취지이기 때문이다.

**시험 3 — 표본 규칙.** R1(5 브랜드)·R2(분모 200)·R3(지배 50%) 통과.

| 커먼즈 인사이트 | 행동 | 3개 브랜드 수혜 | 표본 | 판정 |
|---|---|---|---|---|
| 성분 관심 지수 TOP·추세 | ①③ | 높음 — 자기 로그로는 성분 추세를 낼 수 없다 | 55 브랜드 합산 | ✔ |
| 글로벌 트렌드 ↔ 우리 몰 관심 매핑 | ③ | 높음 — 시장조사를 살 수 없는 사람에게 | 외부 + 합산 | ✔ |
| 피부타입 × 콘텐츠 선호 격자 | ①④ | 높음 | 페르소나 균등 표본 | ✔ (셀 억제 표시) |
| 구매 이유 분포 × 피부 격자 | ①④ | 높음 — 설문 응답 수십 건으로는 분포가 안 나온다 | 합산 | ✔ |
| 콘텐츠별 전환 기여 평균 | ① | 중 | 합산 | ✔ |
| 진열 축별 전환 차이 | ② | 높음 — A/B 를 혼자 돌릴 수 없다 | 진열 값별 ≥5 브랜드 | ✔ (축 값별만) |
| 마찰 패턴(어느 섹션에서 되돌아 읽나) | ① | 중 | 합산 | ✔ |
| 카테고리별 재구매 주기 | ③ | 높음 | `purchase_fact` | ✔ (구매 활성 후) |
| 브랜드 간 전환율 순위 | — | 낮음. 행동으로 이어지지 않고 비교만 남는다 | — | ✗ 뺀다 |
| 상품 단위 벤치마크 | — | 식별 위험, A층 | — | ✗ |

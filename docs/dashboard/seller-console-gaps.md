# 판매자 콘솔에 빠져 있는 기본 기능 (2026-09-17)

> 브랜드 대시보드는 **행동 분석**으로 먼저 자랐다. 그래서 "고객이 어디서 막히나" 는 아홉 화면이 있는데,
> 쇼핑몰이라면 당연히 있어야 할 **판매 운영** 쪽 — 주문이 들어오면 목록으로 쌓이고, 누가 무엇을 얼마에
> 샀는지 줄줄이 보이고, 그걸 합쳐 위 칸에 통계로 뜨는 것 — 이 통째로 없다.
>
> 지금 대시보드가 주문에 대해 아는 것은 숫자 다섯 개뿐이다: 주문 수 · 매출 · 판매 수량 · 팔린 상품
> 가짓수 · 주문 줄 수. **주문 한 건 한 건을 볼 자리가 없다.**

## 1. 지금 있는 것

| 기능 | 경로 | 상태 |
| --- | --- | --- |
| 판매 요약 숫자 | `GET /api/seller/dashboard?brandId=` | 있음 (주문·매출·수량·가짓수·줄 수·리뷰·피드백) |
| 행동 마트 7종 | `GET /api/seller/dashboard/{overview…purchase}` | 있음 |
| 고객 의견 | `GET /api/seller/feedback?brandId=` | 있음 · 화면 있음 |
| 정산(월별) | `GET /api/settlements?brandId=` | **엔드포인트만 있고 화면이 없다** |
| 상품 등록·상태 변경 | `POST /api/products` · `PATCH /{id}/status` | 있음 · 화면 있음 |
| 등록 상품 목록 | `GET /api/products` | 있음 · 화면 있음(썸네일 목록) |

## 2. 빠진 것

우선순위는 "사장님이 하루에 몇 번 여는가" 로 잡았다.

| # | 기능 | 왜 필요한가 | 필요한 것 | 담당 |
| --- | --- | --- | --- | --- |
| 1 | **주문 목록** | 주문이 들어왔는지 확인하는 것이 판매자 화면의 첫 용도다. 지금은 "16건" 이라는 숫자만 있고 그 16건이 무엇인지 볼 방법이 없다 | `GET /api/seller/orders?brandId=` (신규) | 백엔드 · 프론트 |
| 2 | **주문 상세** | 한 주문에 무엇이 몇 개 들어갔는지. 문의가 오면 이걸 먼저 본다 | 위 응답에 품목 배열 포함 | 백엔드 · 프론트 |
| 3 | **상품별 판매 집계** | 무엇이 팔리는지. 행동 마트의 "관심도" 와 다르다 — 이건 실제 결제다 | 같은 응답에서 프론트가 접는다 | 프론트 |
| 4 | **일별 매출 추이** | 어제보다 나은지. 지금 추이 그래프는 방문이지 매출이 아니다 | 같은 응답에서 프론트가 접는다 | 프론트 |
| 5 | **구매 고객 목록** | 누가 재구매했는지. 재구매 마트가 비어도 주문에서 바로 센다 | 같은 응답에서 프론트가 접는다 | 프론트 |
| 6 | **정산 화면** | 엔드포인트는 이미 있는데 화면이 없어 아무도 못 본다 | 화면만 | 프론트 |
| 7 | 주문 상태 변경(배송) | `shop_order.status` 는 `CREATED·PAID·CANCELLED·REFUNDED` 뿐이라 배송 단계가 없다 | ERD 확장 필요 | 백엔드 (이번 범위 밖) |
| 8 | 재고 수량 | `product_variant` 에 재고 컬럼이 없다 | ERD 확장 필요 | 백엔드 (이번 범위 밖) |

7·8 은 테이블을 바꿔야 해서 이번에 넣지 않는다. 시연에 필요한 것은 1~6 이다.

## 3. 왜 프론트 혼자 못 하나

주문은 **다른 회원의 데이터**다. 지금 있는 `GET /api/orders` 는 로그인한 **회원 본인의** 주문만 준다
(`where o.member_id = ?`). 판매자가 자기 브랜드에 들어온 주문을 보려면 서버가 `order_item.brand_id` 로
걸러 주는 경로가 따로 있어야 한다. 프론트에서 우회할 방법이 없고, 우회해서도 안 된다.

3·4·5 는 1의 응답 하나면 프론트가 전부 접어서 만든다. 그래서 **신규 엔드포인트는 하나면 된다.**

## 4. 신규 엔드포인트 계약

```
GET /api/seller/orders?brandId={brandId}&from=YYYY-MM-DD&to=YYYY-MM-DD&limit=200
```

- 인증: SELLER 토큰 + `brand.seller_account_id = actor` (기존 판매자 API 와 같은 규칙)
- `status = 'PAID'` 만 준다. 결제가 끝나지 않은 주문은 판매가 아니다
- **내 브랜드 품목만** 싣는다. 한 주문에 다른 브랜드 상품이 섞여 있어도 그 줄은 빼고, 금액도 내 줄의 합이다
- 정렬은 결제 시각 내림차순. `limit` 기본 200 · 상한 1000

```json
{
  "brand_id": "ssafy-beauty",
  "range": { "from": "2026-09-04", "to": "2026-09-17" },
  "orders": [
    {
      "order_id": "ORD-...",
      "buyer_id": "M0001",
      "buyer_nickname": "유림",
      "status": "PAID",
      "paid_at": "2026-09-17T14:02:11+09:00",
      "currency": "KRW",
      "brand_amount": 32200,
      "item_count": 2,
      "items": [
        { "product_id": "SB000001", "product_name": "제로 포어 토닝 패드",
          "variant_label": "150ml", "quantity": 2, "unit_price": 16100, "line_amount": 32200 }
      ]
    }
  ]
}
```

`brand_amount` 는 주문 총액이 아니라 **내 브랜드 줄의 합**이다. 이름을 `total_amount` 로 두면 다른 브랜드
몫까지 내 매출로 읽힌다. 기존 요약 API 의 `revenue`(= `sum(line_amount)`) 와 같은 기준이다.

`buyer_nickname` 은 회원이 쇼핑몰에서 쓰는 표시 이름이다. 이메일·연락처는 싣지 않는다 — 판매자가 주문을
확인하는 데 필요하지 않고, 필요해지면 그때 따로 연다.

## 5. 화면

`주문` 탭을 사이드바 `상품` 과 `고객` 사이에 둔다. 한 화면 안에 넷을 쌓는다.

1. 상단 칸 넷 — 기간 매출 · 주문 수 · 판매 수량 · 평균 주문 금액. 기존 요약 칸과 같은 모양
2. 일별 매출 막대 — 주문을 결제일로 접는다
3. 주문 표 — 결제 시각 · 주문번호 · 구매자 · 품목 · 수량 · 금액. 줄을 펴면 품목이 보인다
4. 상품별 판매 표 — 상품 · 수량 · 매출 · 주문 수

**값이 없으면 0 과 "-" 다.** 모의로 채우지 않는다 (`martAdapter` 와 같은 규칙).

정산은 `주문` 탭 아래 접힌 칸으로 둔다. 월 · 총액 · 상태만 적는다.

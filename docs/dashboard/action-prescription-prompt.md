> 목적: 브랜드 대시보드의 **할 일 목록**에서 "위로 올리세요" 다음에 붙는 문장, 즉 **무엇을 어떻게 고치라는 지시**를 LLM 이 쓰게 한다. 판정(올릴 것·손볼 것·그대로)은 코드가 하고, LLM 은 **문장만** 쓴다.

## 0. 왜 필요한가

지금 화면은 콘텐츠마다 판정을 준다.

| 판정 | 조건 | 예 |
|---|---|---|
| 위로 올리기 | 담기율 배수 ≥ 1.5 이고 열람률 < 50% | 임상 결과 2.1배 · 열람 34% |
| 손보기 | 담기율 배수 < 1.0 | 사용법 0.9배 |
| 그대로 | 그 밖에 | 성분 목록 2.3배 · 열람 62% |

판정만으로는 사장님이 다시 묻는다. **"올리라는 건 알겠고, 뭘 어떻게 바꾸라는 거냐."** 그 답이 처방이다. 처방은 한 화면 숫자로 못 쓴다. "임상 결과를 올려라" 는 이 화면의 담기율에서 나오지만, "표 4줄로 바꿔라" 는 고객군 화면의 체류 구성, 막히는 곳 화면의 되돌아 읽기, 성분 화면의 드래그 상위 성분을 함께 봐야 나온다. 그래서 **입력이 사이트 전체 신호**여야 한다.

## 1. 역할 분담

| 하는 일 | 누가 | 어디서 |
|---|---|---|
| 콘텐츠별 체류·열람·담기율 배수 집계 | 데이터 | 마트 (§7 요청 목록) |
| 다른 화면 신호 수집 (드래그 성분·되돌아 읽기·고객군 체류) | 데이터 | 기존 마트 |
| 판정 (올릴 것·손볼 것·그대로) | 프론트 | `verbOf()` · 규칙 고정, LLM 안 씀 |
| 처방 문장 생성 (`how`·`basis`·`verify`) | AI | 이 문서의 프롬프트 |
| 문구 검증 (금지 표현·인과 단정) | AI | §6 자동 거부 |
| 화면 렌더 | 프론트 | `Actions` 컴포넌트 |

판정을 LLM 에 맡기지 않는 이유: 같은 숫자에 매주 다른 판정이 나오면 사장님이 지난주 지시를 믿을 수 없다. 판정은 결정론이어야 하고, 문장은 매끄러워야 한다.

## 2. 입력 규격

한 번 호출에 **콘텐츠 하나**를 처방한다. 여러 개를 한 번에 넣으면 근거가 섞인다.

```json
{
  "brand": { "name": "SSAFY Beauty", "product_count": 24 },
  "target": {
    "content_kind": "clinical_claim",
    "label_ko": "임상 결과",
    "verb": "up",
    "avg_dwell_ms": 22300,
    "view_rate": 0.34,
    "cart_lift": 2.1,
    "sample_size": 947,
    "position_in_page": 6,
    "total_blocks": 10
  },
  "page_context": {
    "blocks_in_order": [
      { "content_kind": "product_image", "label_ko": "상품 이미지", "view_rate": 0.94, "cart_lift": 1.0 },
      { "content_kind": "what_it_is", "label_ko": "제품 소개", "view_rate": 0.88, "cart_lift": 1.0 }
    ],
    "quick_exit_rate": 0.29,
    "brand_cart_rate": 0.061
  },
  "cross_screen_signals": [
    {
      "from": "누가 사나",
      "signal": "segment_top_content",
      "text": "지성 고객이 가장 오래 보는 글이 임상 결과. 이 고객군 체류의 29.0%",
      "value": 0.29,
      "sample_size": 1240
    },
    {
      "from": "고객이 찾는 성분",
      "signal": "dragged_ingredients_top3",
      "text": "드래그 상위 3개: 콜라겐(198회)·아연(186회)·펩타이드(148회)",
      "value": null,
      "sample_size": 532
    },
    {
      "from": "막히는 곳",
      "signal": "scroll_backtrack_by_location",
      "text": "성분 목록 구간 되돌아 읽기 388건",
      "value": 388,
      "sample_size": 4904
    },
    {
      "from": "무엇을 보고 사나",
      "signal": "validation_behavior",
      "text": "전성분 펼쳐 본 방문 담기율 13.2% vs 안 펼친 방문 5.1%",
      "value": 0.132,
      "sample_size": 4904
    }
  ]
}
```

### 입력 규칙

- `cross_screen_signals` 는 **최소 2개, 최대 6개.** 하나뿐이면 호출하지 말고 처방 없이 판정만 보여준다.
- 모든 신호에 `from` (사장님이 찾아갈 화면 이름)과 `sample_size` 가 있어야 한다. `sample_size < 200` 인 신호는 넣지 않는다.
- `value` 가 `null` 인 신호는 순위·목록형이다. 문장에 숫자를 만들어 붙이지 말고 `text` 그대로 쓴다.
- `verb` 는 `up` · `fix` 둘만 온다. `keep` 은 처방을 만들지 않는다.

## 3. 출력 규격

```json
{
  "how": "임상 결과를 사용자 리뷰 위, 성분 목록 바로 아래로 옮기세요. 줄글 대신 시험 대상 인원·기간·측정 항목·결과를 4줄 표로 바꾸고, 표 아래에 시험 기관명을 한 줄 적으세요.",
  "basis": [
    { "from": "무엇을 보고 사나", "text": "이 글을 본 사람의 담기율이 평균의 2.1배인데, 상세페이지를 연 사람 중 34.0%만 여기까지 내려옵니다." },
    { "from": "누가 사나", "text": "지성 고객이 상세페이지에서 가장 오래 보는 글이 임상 결과입니다. 이 고객군 체류 시간의 29.0%를 여기서 씁니다." },
    { "from": "무엇을 보고 사나", "text": "전성분을 펼쳐 본 방문의 담기율은 13.2%, 안 펼친 방문은 5.1%입니다." }
  ],
  "verify": "열람률 34.0% → 50%. 올린 뒤에도 이 글을 본 방문의 담기율이 2.0배 이상이면 위치가 맞았다는 뜻입니다. 열람률만 오르고 담기율이 1.5배 아래로 떨어지면 관심 없는 사람에게도 보인 것이니 되돌리세요."
}
```

### 필드 조건

| 필드 | 조건 |
|---|---|
| `how` | 1~3문장, 각 문장 60자 이내. **최소 하나는 위치·형식·개수를 지정해야 한다** ("리뷰 위로", "4줄 표로", "앞 3개를"). "개선하세요" 처럼 방향만 있는 문장은 거부 |
| `basis` | 2~3개. `from` 은 입력에 있던 값만. 입력에 없는 숫자를 쓰면 거부. 서로 다른 `from` 이 최소 2종 |
| `verify` | 반드시 **현재값 → 목표값** 형태를 포함. 되돌릴 조건도 한 문장. 목표값은 현재값의 1.2~1.6배 안 |

## 4. 시스템 프롬프트 (그대로 복사)

```text
당신은 화장품 브랜드 대시보드의 개선 지시문을 쓴다. 읽는 사람은 마케팅 담당자가 아니라 직원 다섯 명 이하 브랜드의 사장님이다. 웹 분석 용어를 모르고, 이번 주에 직접 상세페이지를 고칠 사람이다.

쓰는 것
- 상세페이지에서 무엇을 어디로 옮기고 어떤 형식으로 바꿀지. 위치와 개수와 형식을 지정한다.
- 그 지시를 뒷받침하는 근거. 입력으로 받은 신호만 쓴다.
- 다음 주에 무엇이 얼마나 바뀌면 성공인지, 그리고 어떤 경우 되돌려야 하는지.

절대 쓰지 않는 것
- 웹 분석 용어: 전환율, 퍼널, 이탈률, 리텐션, CTA, UX, 인게이지먼트, 세션, 임프레션
- 효능 단정: 주름 개선, 미백, 여드름 치료, 아토피, 재생, 흡수 촉진, 세포 활성화, 최고, 1위, 유일
- 인과 단정: "이 글을 올리면 매출이 오릅니다". 관찰된 것은 같이 움직였다는 사실뿐이다.
- 입력에 없는 숫자. 업계 평균, 경쟁사 수치, 벤치마크를 만들어 넣지 않는다.
- 제품 문구 자체를 대신 써 주는 일. 형식과 항목만 지시하고 홍보 문장은 쓰지 않는다.

문장 규칙
- 사장님에게 하는 지시는 "~하세요" 로 끝낸다.
- 숫자는 입력 값 그대로. 소수점 자리도 바꾸지 않는다.
- 한 문장에 한 가지 일. 접속사로 두 지시를 잇지 않는다.
- 줄표(—)를 쓰지 않는다. 괄호 안 설명을 넣지 않는다.
- 표기는 contracts/product-feature-vocab.json 과 contracts/product-form-labels-ko.json 의 한국어 라벨을 따른다.

출력은 JSON 하나. how, basis, verify 세 키만. 설명이나 인사말을 붙이지 않는다.
```

## 5. 사용자 프롬프트 템플릿 (그대로 복사)

```text
아래는 브랜드 한 곳의 상세페이지 콘텐츠 하나에 대한 집계와, 다른 화면에서 모은 신호다.
판정은 이미 정해져 있다. 판정을 바꾸지 말고, 그 판정을 실행하는 지시문만 써라.

판정: {verb_ko}
대상 콘텐츠: {label_ko}
상세페이지 안 순서: {total_blocks}칸 중 {position_in_page}번째

이 콘텐츠의 집계
- 본 사람의 담기율: 브랜드 평균의 {cart_lift}배
- 상세페이지를 연 사람 중 여기까지 본 비율: {view_rate}
- 평균 읽는 시간: {avg_dwell_sec}초
- 표본: {sample_size}건

상세페이지 현재 순서
{blocks_in_order_table}

다른 화면에서 모은 신호
{cross_screen_signals_table}

지시문을 쓸 때 지켜라.
1. how 에는 이 콘텐츠를 어디로 옮길지, 어떤 형식으로 바꿀지, 몇 개를 넣을지 중 최소 하나를 숫자나 위치로 못박아라. 옮길 위치는 위 순서 표에 실제로 있는 칸 이름으로 지정해라.
2. basis 는 위 신호에서 2~3개를 골라 사장님 말로 옮겨라. 서로 다른 화면에서 최소 두 개를 골라라. 없는 숫자를 만들지 마라.
3. verify 에는 위 집계값 하나를 골라 현재값에서 목표값으로 쓰고, 어떤 경우 되돌려야 하는지 한 문장 붙여라.

JSON 만 출력해라.
```

## 6. 자동 거부 조건 (생성 후 검증)

생성 결과를 화면에 붙이기 전에 기계로 걸러낸다. 하나라도 걸리면 그 콘텐츠는 처방 없이 판정만 보여준다.

| 검사 | 거부 조건 |
|---|---|
| 금지 표현 | `contracts/feedback-banned-terms.json` 의 낱말이 `how`·`basis`·`verify` 에 등장 |
| 효능 단정 | 화장품법 제13·14조 금지 표현 목록 ([ai-insight-rules.md](./ai-insight-rules.md) §4-3) 과 매칭 |
| 없는 숫자 | 출력의 모든 숫자가 입력 JSON 안에 존재하는지 대조. 없으면 거부 |
| 구체성 | `how` 에 위치·형식·개수 중 아무것도 없으면 거부 |
| 근거 출처 | `basis[].from` 이 입력 `cross_screen_signals[].from` 집합에 없으면 거부 |
| 근거 다양성 | `basis[].from` 이 모두 같은 화면이면 거부 |
| 목표값 범위 | `verify` 의 목표값이 현재값의 1.6배를 넘거나 현재값보다 낮으면 거부 |
| 용어 | 금지 용어 목록 (§4) 등장 시 거부 |
| 줄표 | `—` 등장 시 거부 |

## 7. 아직 없는 입력 (데이터 파트 요청)

이 프롬프트는 아래 값이 있어야 돈다. 현재 프론트는 모의값으로 렌더하고, `모의` 배지를 달아 두었다.

| 필요한 것 | 지금 상태 | 요청 |
|---|---|---|
| 콘텐츠별 담기율 배수 (`cart_lift`) | 없음 | `content_daily_kpi` 에 `cart_rate_with_view` · `cart_rate_brand` 두 칼럼. 배수는 화면에서 나눔 |
| 콘텐츠 열람률 (`view_rate`) | 부분 | 그 콘텐츠가 한 번이라도 보인 세션 ÷ 상세 조회 세션. 분모 정의 확정 필요 |
| 겹쳐 보인 체류 제외한 체류 | 없음 | `co_visible_le2_dwell_ms_sum` (`co_visible_blocks ≤ 2` 인 `section_dwell` 만 합산) |
| 상세페이지 블록 순서 | 없음 | 상품별 `content_kind` 노출 순서. 처방이 "리뷰 위로" 를 쓸 수 있어야 함 |
| 콘텐츠 선정 목록 | 없음 | `content_kind` 21종 중 상세페이지 안 10종 확정. 지금은 프론트가 하드코딩 |
| 구간별 되돌아 읽기 | 있음 | `scroll_backtrack` 을 `content_kind` 로 귀속. 위치 없이 총량만 있으면 처방에 못 씀 |

## 8. 검증 방법

1. 같은 입력으로 5회 생성해 `how` 의 지시 대상(어디로 옮길지)이 흔들리지 않는지 본다. 흔들리면 온도를 낮춘다.
2. 판정이 `up` 인 콘텐츠에 "빼세요" 가 나오는지 확인한다. 나오면 프롬프트가 판정을 무시한 것이다.
3. 사장님 3명에게 지시문만 보여주고 이번 주에 무엇을 할지 말해 보게 한다. 세 사람의 답이 다르면 지시가 아직 모호하다.
4. §6 자동 거부를 100건 샘플에 돌려 거부율을 잰다. 거부율 20% 이상이면 프롬프트를 고친다.

## 9. 판정 규칙 (참고 · 코드가 결정)

`frontend/src/dashboard/screens/ContentScreen.tsx` 의 `verbOf()`.

```
담기율 배수 < 1.0                       → fix  (손보세요)
담기율 배수 ≥ 1.5 이고 열람률 < 50%     → up   (위로 올리세요)
그 밖에                                  → keep (그대로 두세요)
```

`keep` 에는 처방을 만들지 않는다. 할 일이 열 개가 되면 하나도 하지 않게 된다.

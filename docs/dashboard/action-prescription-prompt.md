## 0. 판 이력

| 판 | 날짜 | 무엇이 바뀌었나 |
|---|---|---|
| 0.1 | 2026-09-09 | 첫 규격. 역할 분담·3키 스키마·자동 거부 9개 |
| 0.3 | 2026-09-09 | AI 파트 실측 회신 반영. 아래 여섯 가지 |

v0.1 을 실제 모델로 돌린 결과 두 가지가 깨졌다. AI 파트가 gpt-4.1-nano·mini 각 온도 0·1 로 20회 돌려 확인한 것이다.

| v0.1 의 문제 | 원인 | v0.3 의 처리 |
|---|---|---|
| `basis` 가 20/20 문자열로 옴 | 시스템 프롬프트가 키 이름만 말하고 원소 모양을 안 알려 줌 | §5 마지막에 **출력 JSON 골격**을 박고, 호출 시 `response_format = json_schema (strict)` 로 강제 (§4-1) |
| 판정이 `up` 인데 아래 칸으로 옮기라고 함 (nano 5/5) | 템플릿에 "지금보다 앞 칸" 이라는 말이 없음 | **옮길 위치를 프론트가 계산해서 입력으로 준다** (`insert_after`, §2-1). LLM 은 그 칸 이름을 문장에 옮기기만 한다 |
| 억지 개수 ("1개를 넣으세요") | "숫자나 위치를 못박아라" 를 채우려는 압박 | 위치는 필수, **형식·개수는 근거가 있을 때만.** 없으면 쓰지 말라고 명시 (§4) |
| `verify` 가 "0.34를 목표 0.50으로" | 화살표 문자를 안 정했고 비율을 소수로 넘겼음 | 화살표 문자를 고정하고, **비율은 템플릿에서 34.0% 로 미리 포맷** (§6) |
| `from` 에 없는 화면 이름을 만듦 | 대상 콘텐츠 집계에 화면 이름이 안 붙어 있었음 | `from` **허용 목록을 프롬프트에 명시**하고, 대상 집계에도 화면 이름을 붙임 (§6) |
| "34.0%로 브랜드 평균보다 높고" (34% 는 낮은 값) | 숫자만 검사하니 비교 판단이 통과 | §5 에 **비교 판단 금지** 한 줄, §7 에 검사 항목 하나 추가 |

## 1. 왜 필요한가

지금 화면은 콘텐츠마다 판정을 준다.

| 판정 | 조건 | 예 |
|---|---|---|
| 위로 올리기 | 담기율 배수 ≥ 1.5 이고 열람률 < 50% | 임상 결과 2.1배 · 열람 34% |
| 손보기 | 담기율 배수 < 1.0 | 사용법 0.9배 |
| 그대로 | 그 밖에 | 성분 목록 2.3배 · 열람 62% |

판정만으로는 사장님이 다시 묻는다. **"올리라는 건 알겠고, 뭘 어떻게 바꾸라는 거냐."** 그 답이 처방이다. 처방은 한 화면 숫자로 못 쓴다. "임상 결과를 올려라" 는 이 화면의 담기율에서 나오지만, "표 4줄로 바꿔라" 는 고객군 화면의 체류 구성, 막히는 곳 화면의 되돌아 읽기, 성분 화면의 드래그 상위 성분을 함께 봐야 나온다. 그래서 **입력이 사이트 전체 신호**여야 한다.

## 2. 역할 분담

| 하는 일 | 누가 | 어디서 |
|---|---|---|
| 콘텐츠별 체류·열람·담기율 배수 집계 | 데이터 | 마트 (§9 요청 목록) |
| 다른 화면 신호 수집 | 데이터 | 기존 마트 |
| 판정 (올릴 것·손볼 것·그대로) | 프론트 | `verbOf()` · 규칙 고정, LLM 안 씀 |
| **옮길 위치 계산 (`insert_after`)** | 프론트 | §2-1 규칙 · LLM 안 씀 |
| 처방 문장 생성 (`how`·`basis`·`verify`) | AI | 이 문서의 프롬프트 |
| 문구 검증 (자동 거부 11개) | AI | §7 · 생성하는 쪽이 입력을 들고 있으므로 |
| 생성 결과 저장 (일 1회) | AI | §8 응답 봉투 |
| 화면 렌더 | 프론트 | `Actions` 컴포넌트 |

판정을 LLM 에 맡기지 않는 이유: 같은 숫자에 매주 다른 판정이 나오면 사장님이 지난주 지시를 믿을 수 없다. 판정은 결정론이어야 하고, 문장은 매끄러워야 한다.

### 2-1. 옮길 위치는 프론트가 정한다 (결정 ①)

AI 파트가 "mini 는 매번 최상단으로 올리라고 한다" 고 알려 왔다. 규칙상 틀리지 않지만 처방이 단조로워지고, 더 잘 먹히는 칸을 아래로 밀어내는 일이 생긴다. 이 판단은 문장 감각이 아니라 규칙 문제라서 **프론트가 계산해서 입력으로 넘긴다.**

```
insert_after = 대상보다 담기율 배수가 높은 칸 중 가장 아래에 있는 칸
               그런 칸이 없으면 "맨 위" (insert_after = null)
```

읽는 말로: **더 잘 먹히는 칸은 그대로 위에 두고, 그 바로 아래에 넣는다.** 임상 결과(2.1배)라면 성분 목록(2.3배) 바로 아래가 된다. 성분 특징(1.6배)이라면 사용자 리뷰(1.8배) 바로 아래다. 두 처방이 서로 다른 자리를 가리키므로 단조로워지지 않고, 순서 자체가 담기율 순으로 수렴한다.

`fix` 판정에는 `insert_after` 를 넘기지 않는다. 자리를 옮기는 처방이 아니다.

## 3. 입력 규격

한 번 호출에 **콘텐츠 하나**를 처방한다. 여러 개를 한 번에 넣으면 근거가 섞인다.

```json
{
  "brand": { "name": "SSAFY Beauty", "product_count": 24 },
  "target": {
    "content_kind": "clinical_claim",
    "label_ko": "임상 결과",
    "verb": "up",
    "dwell_sec": 22,
    "view_rate_text": "34.0%",
    "cart_lift_text": "2.1배",
    "sample_size": 947,
    "position_in_page": 6,
    "total_blocks": 10,
    "insert_after": "성분 목록"
  },
  "page_context": {
    "blocks_in_order": [
      { "label_ko": "상품 이미지", "view_rate_text": "94.0%", "cart_lift_text": "1.0배" },
      { "label_ko": "제품 소개", "view_rate_text": "88.0%", "cart_lift_text": "1.0배" }
    ],
    "quick_exit_rate_text": "29.0%",
    "brand_cart_rate_text": "6.1%"
  },
  "cross_screen_signals": [
    {
      "from": "누가 사나",
      "signal": "segment_top_content",
      "text": "지성 고객이 가장 오래 보는 글이 임상 결과입니다. 이 고객군 체류의 29.0%입니다.",
      "sample_size": 1240
    },
    {
      "from": "고객이 찾는 성분",
      "signal": "dragged_ingredients_top3",
      "text": "드래그 상위 3개는 콜라겐 198회, 아연 186회, 펩타이드 148회입니다.",
      "sample_size": 532
    },
    {
      "from": "막히는 곳",
      "signal": "scroll_backtrack_by_location",
      "text": "성분 목록 구간에서 위로 다시 올려 읽은 기록이 388건입니다.",
      "sample_size": 4904
    },
    {
      "from": "무엇을 보고 사나",
      "signal": "validation_behavior",
      "text": "전성분을 펼쳐 본 방문의 담기율은 13.2%, 안 펼친 방문은 5.1%입니다.",
      "sample_size": 4904
    }
  ]
}
```

### 입력 규칙

- **비율·배수는 미리 사람이 읽는 문자열로 넘긴다.** `0.34` 를 주면 모델이 그대로 쓴다. `view_rate_text` 처럼 `_text` 로 끝나는 필드가 그것이다. 원시 수치가 필요하면 별도 필드로 나란히 두되, 프롬프트 템플릿에는 `_text` 만 넣는다.
- `cross_screen_signals` 는 **최소 2개, 최대 6개.** 하나뿐이면 호출하지 말고 처방 없이 판정만 보여준다.
- 모든 신호에 `from` (사장님이 찾아갈 화면 이름)과 `sample_size` 가 있어야 한다. `sample_size < 200` 인 신호는 넣지 않는다.
- 신호의 `text` 는 이미 완성된 한 문장이다. 모델은 이것을 다듬을 수만 있고, 여기 없는 비교·판단을 더할 수 없다.
- `verb` 는 `up` · `fix` 둘만 온다. `keep` 은 처방을 만들지 않는다.
- `from` 에 올 수 있는 화면 이름은 여섯 개뿐이다 (§6 템플릿에도 같은 목록을 넣는다). `무엇을 보고 사나` · `누가 사나` · `고객이 찾는 성분` · `상품마다 어디서 멈추나` · `고객이 고쳐 달라는 것` · `막히는 곳`.

## 4. 출력 규격

```json
{
  "how": "임상 결과를 성분 목록 바로 아래로 옮기세요. 줄글 대신 시험 대상 인원·기간·측정 항목·결과를 4줄 표로 바꾸세요.",
  "basis": [
    { "from": "무엇을 보고 사나", "text": "이 글을 본 사람의 담기율이 평균의 2.1배인데, 상세페이지를 연 사람 중 34.0%만 여기까지 내려옵니다." },
    { "from": "누가 사나", "text": "지성 고객이 상세페이지에서 가장 오래 보는 글이 임상 결과입니다. 이 고객군 체류 시간의 29.0%를 여기서 씁니다." },
    { "from": "무엇을 보고 사나", "text": "전성분을 펼쳐 본 방문의 담기율은 13.2%, 안 펼친 방문은 5.1%입니다." }
  ],
  "verify": "열람률 34.0% → 45.0%. 담기율이 1.5배 아래로 떨어지면 원래 자리로 되돌리세요."
}
```

### 필드 조건

| 필드 | 조건 |
|---|---|
| `how` | 1~3문장, 각 문장 60자 이내. `up` 이면 첫 문장이 **`insert_after` 칸 이름을 그대로 써서 위치를 지정**해야 한다. `fix` 면 위치를 건드리지 말고 형식·항목을 고치라고 써야 한다. **형식·개수는 근거가 있을 때만 쓴다.** 근거 없이 "3개를 넣으세요" 같은 빈 숫자를 만들면 거부 |
| `basis` | 2~3개. 원소는 `{from, text}` 객체. `from` 은 입력에 있던 값만. 입력에 없는 숫자나 비교 판단을 쓰면 거부. 서로 다른 `from` 이 최소 2종 |
| `verify` | **`현재값 → 목표값`** 형태를 이 화살표 문자 그대로 포함. 목표값은 현재값의 1.2~1.6배 안. 되돌릴 조건 한 문장 필수 |

### 4-1. 호출 설정

프롬프트만으로는 `basis` 가 문자열로 새어 나온다. AI 파트가 20/20 으로 확인했다. 반드시 스키마를 강제한다.

| 항목 | 값 | 이유 |
|---|---|---|
| 모델 | **gpt-4.1-mini** | nano 는 v0.3 에서도 칸 이름을 못 쓴다 (구체성 거부 5/5). 쓰지 않는다 |
| 온도 | 0 | 온도 1 은 지시 위치가 세 갈래로 갈렸다 |
| `response_format` | `json_schema` · `strict: true` | `how`·`basis[{from,text}]`·`verify` 골격 강제 |

## 5. 시스템 프롬프트 (그대로 복사)

```text
당신은 화장품 브랜드 대시보드의 개선 지시문을 쓴다. 읽는 사람은 마케팅 담당자가 아니라 직원 다섯 명 이하 브랜드의 사장님이다. 웹 분석 용어를 모르고, 이번 주에 직접 상세페이지를 고칠 사람이다.

쓰는 것
- 상세페이지에서 무엇을 어디로 옮기고 어떤 형식으로 바꿀지. 옮길 위치는 입력으로 받은 칸 이름을 그대로 쓴다.
- 그 지시를 뒷받침하는 근거. 입력으로 받은 신호 문장만 쓴다.
- 다음 주에 무엇이 얼마나 바뀌면 성공인지, 그리고 어떤 경우 되돌려야 하는지.

절대 쓰지 않는 것
- 웹 분석 용어: 전환율, 퍼널, 이탈률, 리텐션, CTA, UX, 인게이지먼트, 세션, 임프레션
- 효능 단정: 주름 개선, 미백, 여드름 치료, 아토피, 재생, 흡수 촉진, 세포 활성화, 최고, 1위, 유일
- 인과 단정: "이 글을 올리면 매출이 오릅니다". 관찰된 것은 같이 움직였다는 사실뿐이다.
- 입력에 없는 숫자. 업계 평균, 경쟁사 수치, 벤치마크를 만들어 넣지 않는다.
- 입력에 없는 비교 판단. 숫자는 옮겨 쓰되 "평균보다 높다", "낮다", "좋다", "나쁘다" 같은 판단은 입력 문장에 그 말이 있을 때만 쓴다. 34.0% 를 받아 "평균보다 높고" 라고 쓰면 안 된다.
- 제품 문구 자체를 대신 써 주는 일. 형식과 항목만 지시하고 홍보 문장은 쓰지 않는다.

문장 규칙
- 사장님에게 하는 지시는 "~하세요" 로 끝낸다.
- 숫자는 입력 값 그대로. 소수점 자리도 바꾸지 않는다. 입력이 34.0% 면 34.0% 라고 쓴다.
- 한 문장에 한 가지 일. 접속사로 두 지시를 잇지 않는다.
- 줄표 기호를 쓰지 않는다. 괄호 안 설명을 넣지 않는다.
- 표기는 contracts/product-feature-vocab.json 과 contracts/product-form-labels-ko.json 의 한국어 라벨을 따른다.

출력은 아래 골격의 JSON 하나. 설명이나 인사말을 붙이지 않는다.
{"how": "지시 1~3문장", "basis": [{"from": "화면 이름", "text": "근거 한 문장"}], "verify": "지표 현재값 → 목표값. 되돌릴 조건 한 문장."}
```

## 6. 사용자 프롬프트 템플릿 (그대로 복사)

`{...}` 는 §3 입력에서 채운다. 비율은 `_text` 필드를 쓴다.

```text
아래는 브랜드 한 곳의 상세페이지 콘텐츠 하나에 대한 집계와, 다른 화면에서 모은 신호다.
판정과 옮길 위치는 이미 정해져 있다. 그것을 바꾸지 말고, 실행하는 지시문만 써라.

판정: {verb_ko}
대상 콘텐츠: {label_ko}
상세페이지 안 순서: {total_blocks}칸 중 {position_in_page}번째
옮길 위치: {insert_after} 바로 아래
  (판정이 손보기면 이 줄은 "위치 그대로" 로 온다)

이 콘텐츠의 집계 (화면 이름: 무엇을 보고 사나)
```

## 7. 자동 거부 조건 11개 (생성 후 검증)

AI 파트에서 걸고 결과에 함께 내려 준다. 생성하는 쪽이 입력 JSON 을 들고 있어야 "없는 숫자" 를 대조할 수 있다. 프론트는 `prescription` 이 null 이면 판정만 그린다.

| # | 검사 | 거부 조건 |
|---|---|---|
| 1 | 금지 표현 | `contracts/cosmetic-claim-banned-terms.json` 의 `banned` 낱말이 `how`·`basis`·`verify` 에 등장 |
| 2 | 기능성 표현 | 같은 파일 `functional_only` 낱말이 등장했고 그 상품에 기능성 심사 기록이 없음 |
| 3 | 실증 필요 | `needs_evidence` 낱말 등장. 거부하지 않고 꼬리표를 달아 사람 검토로 보냄 |
| 4 | 없는 숫자 | 출력의 모든 숫자가 입력 JSON 안에 존재하는지 대조 |
| 5 | **없는 비교 판단** | "평균보다 높/낮", "좋다", "나쁘다", "충분하다" 류 표현이 입력 신호 `text` 에 없으면 거부 |
| 6 | 위치 일치 | `verb = up` 인데 `how` 에 `insert_after` 칸 이름이 없거나 다른 칸 이름이 있으면 거부 |
| 7 | 방향 일치 | `verb = up` 인데 "빼세요"·"지우세요"·"아래로" 가 등장하면 거부 |
| 8 | 근거 출처 | `basis[].from` 이 §3 허용 목록 여섯 개에 없으면 거부 |
| 9 | 근거 다양성 | `basis[].from` 이 모두 같은 화면이면 거부 |
| 10 | 목표값 범위 | `verify` 에 화살표가 없거나, 목표값이 현재값의 1.6배 초과 또는 현재값 이하면 거부 |
| 11 | 줄표 | 줄표 기호 등장 시 거부 |

## 8. 응답 봉투와 생성 주기 (결정 ②)

AI 파트가 제안한 봉투를 그대로 쓴다. 필드 두 개만 더한다.

```json
{
  "content_kind": "clinical_claim",
  "verb": "up",
  "prescription": { "how": "...", "basis": [{ "from": "...", "text": "..." }], "verify": "..." },
  "rejected_by": [],
  "needs_evidence": [],
  "model": "gpt-4.1-mini",
  "prompt_version": "0.3",
  "input_hash": "sha256:...",
  "generated_at": "2026-09-09T18:00:00"
}
```

- **생성 주기는 일 1회.** 화면 진입마다 부르지 않는다. 같은 숫자에 같은 문장이 나와야 사장님이 지난주 지시를 믿는다.
- `input_hash` 는 §3 입력 JSON 의 해시다. **해시가 같으면 재생성하지 않고 저장된 문장을 그대로 내려 준다.** 온도 0 이어도 모델 업데이트로 문장이 흔들리므로 저장본이 기준이다.
- `rejected_by` 에는 §7 의 번호나 코드(`banned_term`·`no_such_number`·`unsupported_comparison`·`slot_mismatch`·`direction_mismatch`·`basis_from`·`basis_diversity`·`verify_range`·`em_dash`)를 담는다.
- `needs_evidence` 가 비어 있지 않으면 프론트가 "실증자료 필요" 꼬리표를 처방 옆에 붙인다.

## 9. 아직 없는 입력 (데이터 파트 요청 · 우선순위 확정)

AI 파트가 처방 품질에 직접 닿는 것으로 1·4·5를 꼽았다. 그 순서로 적는다.

| 순위 | 필요한 것 | 지금 상태 | 요청 |
|---|---|---|---|
| 1 | 콘텐츠별 담기율 배수 | 없음 | `content_daily_kpi` 에 `cart_rate_with_view` · `cart_rate_brand` 두 칼럼. 배수는 화면에서 나눔 |
| 2 | `scroll_backtrack` 의 `content_kind` 귀속 | 총량만 | 위치 없이 총량만 있으면 "성분 목록 구간 되돌아 읽기" 근거를 못 씀. **이것 없이는 근거 하나가 통째로 빠진다** |
| 3 | 상세페이지 안 `content_kind` 10종 확정 | 프론트 하드코딩 | 계약 21종 중 상세페이지 안에서 읽는 것만 확정 |
| 4 | 상품별 블록 노출 순서 | 없음 | `insert_after` 계산에 필요. 지금은 담기율 순서로 대체 중 |
| 5 | 콘텐츠 열람률 분모 | 부분 | 그 콘텐츠가 한 번이라도 보인 세션 ÷ 상세 조회 세션. 분모 정의 확정 |
| 6 | 겹쳐 보인 체류 제외 합계 | 없음 | `co_visible_le2_dwell_ms_sum` (`co_visible_blocks ≤ 2` 인 `section_dwell` 만) |

## 10. 검증 방법

1. 같은 입력으로 5회 생성해 `how` 의 옮길 위치가 흔들리지 않는지 본다. **v0.3 에서는 `insert_after` 를 입력으로 주므로 위치는 흔들릴 수 없다.** 흔들리면 검사 6번이 잡는다.
2. 판정이 `up` 인 콘텐츠에 "빼세요" 가 나오는지 확인한다. 검사 7번이 자동으로 잡는다.
3. 사장님 3명에게 지시문만 보여주고 이번 주에 무엇을 할지 말해 보게 한다. 세 사람의 답이 다르면 지시가 아직 모호하다.
4. §7 자동 거부를 100건 샘플에 돌려 거부율을 잰다. 거부율 20% 이상이면 프롬프트를 고친다. 데이터 마트가 나온 뒤에 돈다.

## 11. 판정 규칙 (참고 · 코드가 결정)

`frontend/src/dashboard/screens/ContentScreen.tsx` 의 `verbOf()`.

```
담기율 배수 < 1.0                       → fix  (손보세요)
담기율 배수 ≥ 1.5 이고 열람률 < 50%     → up   (위로 올리세요)
그 밖에                                  → keep (그대로 두세요)
```

`keep` 에는 처방을 만들지 않는다. 할 일이 열 개가 되면 하나도 하지 않게 된다.

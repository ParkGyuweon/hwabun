# 4. 시연 시나리오

기본 공개 주소는 `https://j15a306.p.ssafy.io/`입니다. 쇼핑몰과 판매자 대시보드는 같은 도메인의 다른 진입 화면입니다. 아래 시나리오는 실제로 존재하는 버튼과 메뉴를 기준으로 작성했습니다. 발표 전 최신 배포 화면과 계정 권한을 한 번 확인하세요. 페르소나와 에이전트가 만든 기록은 합성 데이터이며 실제 소비자 통계라고 표현하지 않습니다.

## 0. 발표 전에 확인할 것

1. EC2-1의 Nginx, `shop-backend`, `backend`, `mysql`, `recommend`가 떠 있고 HTTPS 첫 화면이 열리는지 확인합니다. EC2-2의 Kafka, Spark Master와 Worker, `spark-raw-sink`가 실행 중인지 확인합니다.
2. 테스트용 MEMBER 계정과 SELLER 계정을 준비합니다. 실제 판매자 로그인은 팀이 발급한 계정으로 하며, 새 DB를 시드에서 만들었다면 `shop_backend/seed/shop_backend_seed.sql`의 SSAFY Beauty 판매자 계정이 예시입니다. 시드 비밀번호는 공개 운영용으로 재사용하지 않습니다.
3. 판매자 대시보드에서 왼쪽 아래 Mart 상태와 각 카드의 출처 표시를 봅니다. 실측 마트가 없으면 모의 데이터로 대체될 수 있으니 시연을 시작하기 전에 실측 여부를 확인합니다. 페이지가 보인다는 것만으로 MySQL 데이터가 연결된 것은 아닙니다.
4. `/pipeline` 시연을 할 경우 추천 컨테이너의 내부 8300 포트를 SSH 터널로 열고, `SPARK_MASTER_UI`와 `DW_MYSQL_*`가 설정됐는지 확인합니다. EC2-1의 현재 Nginx 설정은 `/live`, `/pipeline`을 공개 프록시하지 않습니다. EC2-1에서 `sudo docker inspect -f '{{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}' ec2-1-recommend-1`로 컨테이너 IP를 확인한 뒤, 발표 PC에서 `ssh -N -L 8300:<확인한 컨테이너 IP>:8300 ubuntu@j15a306.p.ssafy.io`로 연결하고 `http://localhost:8300/pipeline`을 엽니다. SSH 인증에는 발급된 개인키를 사용합니다.
5. 재생 버튼은 Kafka에 대량의 합성 이벤트를 추가합니다. 사전 적재 데이터가 이미 있으면 중복 실행하지 않습니다. 발표 중에는 필요할 때만 짧게 보여주고, 에이전트 100명 버튼은 LLM 비용과 실행 시간이 발생하므로 별도 승인 없이는 누르지 않습니다.

## 1. 소비자 쇼핑몰: 개인화 전후 비교

| 순서 | 화면과 클릭 위치 | 발표자가 하는 행동 | 확인할 결과와 설명 |
| --- | --- | --- | --- |
| 1 | `/` 첫 화면, 헤더 오른쪽 `로그인` | 새 MEMBER로 가입하거나 준비된 테스트 계정으로 로그인하고 피부 프로필을 입력 | 같은 통합 쇼핑몰 안의 여러 브랜드 상품을 조회. 가입 직후 추천은 프로필 기반 시작점 |
| 2 | 첫 화면 상품 목록과 히어로 | 현재 히어로 상품과 추천 상품 상위 몇 개를 관객에게 보여주고 기록 | 뒤에서 바뀌는 대상을 비교할 기준. 추천 결과는 로그인 회원의 행동 상태를 사용 |
| 3 | 목록에서 SSAFY Beauty 상품 카드, 예: `SB000001` | 카드를 눌러 상품 상세로 이동하고 상세 설명이나 리뷰 섹션을 둘러봄 | 상세 조회와 섹션 행동 이벤트가 수집기에서 Kafka로 이동. 상품이 없는 목록 섹션은 특정 브랜드로 귀속시키지 않음 |
| 4 | 상품 상세의 하트/좋아요 버튼 | 상품에 좋아요를 누른 뒤 화면의 `뒤로 가기` 또는 브라우저 뒤로 가기로 목록 복귀 | 몇 초 뒤 히어로와 추천 순서를 다시 확인. 방금 좋아요한 상품 자체는 이미 반응한 상품이라 목록 추천에서 제외될 수 있고, 같은 브랜드의 다른 상품이 올라오는 것이 자연스러운 결과 |
| 5 | 다른 상품 상세의 옵션 선택과 `장바구니` 버튼 | 옵션이 둘 이상인 상품이라면 옵션을 바꿔 본 뒤 담고 헤더 장바구니로 이동 | `variant_select`, `add_to_cart`, `view_cart` 등 구매 전 신호를 보여줌. 선택한 상품에 옵션이 하나뿐이면 옵션 왕복 설명은 생략 |
| 6 | 장바구니의 주문 버튼 | 로그인 상태에서만 주문을 진행. 포트원 테스트 채널이 설정돼 있으면 카카오페이 테스트 결제창을 진행 | 성공 뒤 주문과 `purchase` 이벤트 확인. 카카오페이 인증이 준비되지 않았으면 결제를 강행하지 않고 장바구니까지 보여줌 |

좋아요 직후 추천은 실시간 소비 경로입니다. 구매나 조회가 **판매자 일별 Mart에 반영되는 것은 Q2부터 Q4 배치 및 DW 발행 이후**입니다. 이 둘을 즉시 같은 숫자로 비교하지 않습니다. 주문 원장 화면은 Shop Backend MySQL을 읽어 Mart 갱신과 다른 시점에 바뀔 수 있습니다.

## 2. 판매자 대시보드: 내 데이터와 업계 비교

주소 `https://j15a306.p.ssafy.io/dashboard.html`에 접속합니다. 쇼핑몰 헤더의 `로그인` 창 아래 `대시보드 로그인` 링크로도 이동할 수 있습니다. SELLER 계정으로 로그인하고 왼쪽 상단에 내 브랜드명이 표시되는지 확인합니다. 여러 브랜드 권한이 있는 계정이면 브랜드 선택 상자에서 발표 대상 브랜드를 고릅니다. `개발자 모드`는 모의 데이터용이므로 실측 시연에서는 사용하지 않습니다.

| 순서 | 왼쪽 메뉴와 클릭 위치 | 보여줄 내용 | 데이터 주의점 |
| --- | --- | --- | --- |
| 1 | `요약` 클릭, 오른쪽 위 `최근 7일/14일/30일` 선택 | 핵심 인사이트 한 줄, 방문과 상세 진입, 전환 추이 | 카드의 실측/모의 표시와 선택 브랜드 확인 |
| 2 | `상품` 클릭 | 상품별 진단 표에서 관심, 장바구니 비율, 이탈, 옵션 왕복 항목 확인 | 상세 조회 표본이 적은 상품은 진단에서 제외되거나 약하게 표시됨 |
| 3 | `상세페이지` 클릭 후 상단 `설명 글`, `막히는 자리` 탭 전환 | 어떤 콘텐츠를 읽었는지와 어디서 막혔는지 비교 | 섹션 체류와 마찰 지표는 해당 이벤트가 있는 경우에만 나타남 |
| 4 | `고객` 클릭 | 피부 타입과 톤별 관심, 전환, 비슷한 브랜드와 비교한 위치 확인 | 브랜드 이름이나 타사의 개별 원천 데이터는 보이지 않음. 표본 부족이면 수치가 억제될 수 있음 |
| 5 | `시장` 클릭 | 고객이 찾는 성분과 자사 상품의 차이 확인 | 익명 업계 집계와 내 브랜드 지표의 출처를 구분해 설명 |
| 6 | `주문` 클릭 후 상단 `주문`, `정산` 탭 전환 | 실제 주문 원장과 정산 내역 확인 | 주문과 정산은 Shop Backend 원장 경로로, Spark Mart와 갱신 시점이 다름 |
| 7 | `고객의 말` 클릭 후 상단 `공개 리뷰`, `받은 피드백` 탭 전환 | 평가와 고객이 개선을 요청한 내용을 확인 | 공개 리뷰와 내 브랜드 피드백은 다른 데이터 범위 |
| 8 | 필요 시 `상품 등록` 클릭 | 등록 화면과 고객 화면 미리보기 확인 | 등록 기능은 분석 지표가 아니라 판매자 작업 기능 |

발표 멘트 예시: "한 브랜드의 원천 행동은 다른 브랜드 담당자에게 보이지 않습니다. 판매자는 본인 상품의 경로를 보고, 업계 비교는 표본 기준을 통과한 익명 집계로만 봅니다."

## 3. 처리 파이프라인 화면: 수집과 일별 배치 구분

SSH 터널에서 `http://localhost:8300/pipeline`을 엽니다. 화면 상단의 `초당` 선택 상자와 `▶ 페르소나 시작` 버튼은 실제 합성 이벤트를 생성합니다. 사전 재생 데이터를 초기화하고 운영 담당자가 허락한 리허설에서만 시작합니다. 일반 발표에서는 이미 쌓인 데이터를 조회하는 것으로 충분합니다.

| 화면 위치 | 읽는 법 |
| --- | --- |
| `① 사이트 활동` | 페르소나 PC, 에이전트 PA, 실제 회원 이벤트가 각각 얼마나 들어왔는지 표시 |
| `② Kafka 파티션` | 3개 파티션의 생산량, 추천 소비 위치와 lag 표시. 세션 키 기준 분배이지 3중 복제나 고가용성은 아님 |
| `③ Spark` | 살아 있는 Worker 수와 Core, 실행 중인 Spark 앱 표시. Q1 Raw Sink와 일별 배치가 다른 작업임 |
| `④ dw 마트` | MySQL에 발행된 Mart별 행 수와 갱신 상태. Kafka 이벤트가 들어왔다고 즉시 증가하는 칸이 아님 |
| `⑤ 대시보드` | 상태가 바뀐 사용자 수와 대시보드 링크. 링크가 열린다는 것과 Mart가 최신이라는 것은 다름 |

실시간 추천 변화는 Kafka 소비자의 세션 상태 반영을 보여줍니다. Spark는 Q1 Raw를 지속 적재하지만 Q2 정제, Q3 Fact, Q4 Mart, Q5 검증, DW 발행은 매일 03:00 KST의 배치 또는 운영자의 수동 배치로 갱신됩니다. 시연에서 방금 누른 좋아요를 일별 KPI에 즉시 반영된 것처럼 말하지 않습니다.

`http://localhost:8300/live`는 파티션별 소비량과 최근 사용자 변화를 크게 보여주는 별도 화면입니다. `▶ 에이전트 100명`은 발표 PC에서 `simulator/agents/agent_launcher.py`를 켠 경우에만 동작하며 GMS 비용이 발생합니다. 버튼을 누르기 전에 담당자 승인과 비용 한도를 확인합니다.

## 4. 실패 시 대체 진행

- 추천 결과가 안 바뀌면 `/pipeline`의 Kafka 연결, lag, 추천 상태를 확인합니다. 직접 HTTP 경로로 받은 이벤트는 Kafka 파티션과 Spark 적재를 증명하지 못하므로 분산 처리 성공이라고 말하지 않습니다.
- `dw` Mart가 0행이거나 판매자 화면에 `모의`가 표시되면, 현재 배포 데이터가 없다고 밝히고 준비된 설명 자료로 구조만 소개합니다. 임의로 실측이라고 바꾸지 않습니다.
- 카카오페이 테스트 결제창이 준비되지 않았거나 외부 인증이 실패하면 결제 단계는 생략합니다. 이미 담기까지의 관심과 전환 전 신호는 보여줄 수 있습니다.
- 배치 상태 확인은 EC2-2의 `systemctl status hwabun-daily-batch.service`, `/opt/hwabun/data/validation/pipeline-report.json`, DW projection 보고서 순서입니다. 발표 도중 전체 재배치를 즉석 실행하지 않습니다.

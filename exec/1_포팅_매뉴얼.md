IDE는 실행 필수 요소가 아닙니다. 개발 PC의 확인된 예시는 IntelliJ IDEA `2023.3.8`이며, 프로젝트 자체가 IDE 버전을 고정하지는 않습니다. Java 21과 각 모듈의 Gradle Wrapper, Node 22를 사용하면 IDE 없이도 빌드할 수 있습니다. JVM은 Dockerfile의 Eclipse Temurin 21 JDK 빌드 이미지와 JRE 실행 이미지가 기준입니다.

```text

                                  → /api/prescription, /api/headline → Recommend:8300
Shop Backend → EC2-1 MySQL shop_backend
Recommend → Kafka, MySQL dw
EC2-2 Spark Q1 → Raw Parquet → Q2/Q3/Q4 → Mart Parquet → DW 발행 → EC2-1 MySQL dw
```

`platform.html`의 운영 지표는 프론트 모의 데이터입니다. 판매자 대시보드는 마트 API가 응답하지 않으면 모의 지표로 대체할 수 있습니다. 화면이 열리는 것만으로 실제 DW 연동이 검증된 것은 아닙니다.

## 2. 클론, 빌드와 배포 순서

### 2.1 공통 준비

1. EC2 두 대에 GitLab 접근 권한, Docker Engine, Compose v2 플러그인, Git을 준비합니다. EC2-1에는 호스트 Certbot도 설치합니다.
2. 동일한 검증 커밋을 두 서버에 체크아웃합니다. 실제 서버의 기존 운영 브랜치와 미커밋 변경은 덮어쓰지 말고 먼저 확인합니다.
3. EC2-1 도메인 `j15a306.p.ssafy.io`가 EC2-1 공인 IP를 가리키게 합니다. 다른 도메인으로 옮길 때는 `deploy/nginx/default.conf`의 `server_name`, 인증서 경로, `ALLOWED_ORIGINS`도 함께 바꿉니다.
4. 두 서버 사이의 사설 IP와 보안 그룹을 확인합니다. 예시 운영 IP는 EC2-1 `172.26.8.48`, EC2-2 `172.26.1.194`이며 서버를 재생성하면 달라질 수 있습니다.

```bash
git clone https://lab.ssafy.com/s15-bigdata-dist-sub1/S15P21A306.git S15P21A306
cd S15P21A306
git rev-parse HEAD
docker compose version
```

Docker 빌드 전에 직접 모듈을 검증하려면 Java 21과 Node 22 환경에서 아래를 실행합니다. 서버에서 Compose로 빌드할 때도 같은 Gradle Wrapper와 `npm ci`가 Dockerfile 안에서 실행됩니다. Maven Central, npm registry, Docker Hub 및 최초 Spark Kafka connector 다운로드에 대한 네트워크 접근이 필요합니다.

```bash
cd ~/S15P21A306/backend && ./gradlew test bootJar --no-daemon
cd ~/S15P21A306/shop_backend && ./gradlew test bootJar --no-daemon
cd ~/S15P21A306/frontend && npm ci && npm run build
```

필요 포트는 EC2-1 공개 80/443, 관리자 SSH 22, EC2-1에서 EC2-2로 Kafka 9092 및 Spark Master UI 18080, EC2-2에서 EC2-1 사설망으로 MySQL 13306입니다. 9092, 13306, 18080은 상대 서버의 사설 IP 또는 보안 그룹으로 출처를 제한합니다. MySQL 3306과 Grafana 3000은 인터넷에 공개하지 않습니다. [AWS 보안 그룹 안내](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/security-group-rules-reference.html)를 참고하세요.

### 2.2 EC2-2: Kafka와 Spark

```bash
cd ~/S15P21A306/deploy/ec2-2
cp .env.example .env
# 아래 환경 변수 표에 따라 .env를 편집하고 비밀번호 파일 권한을 제한
```

`KAFKA_ADVERTISED_HOST`는 EC2-1에서 닿는 EC2-2 사설 IP나 DNS를 넣습니다. `http://`, 포트, `localhost`는 넣지 않습니다. `kafka-init`의 `Exited (0)`은 토픽 생성 완료입니다. `spark-raw-sink`는 Q1으로 상시 실행하며 `/opt/hwabun/data/raw_events`에 Parquet을 누적합니다. Spark의 첫 Kafka connector 실행에는 Maven 다운로드가 필요합니다. Docker Volume과 `/opt/hwabun/data`는 `docker compose down -v`로 지우지 마세요.

### 2.3 EC2-1: MySQL, 인증서, 웹 서비스

```bash
cd ~/S15P21A306/deploy/ec2-1
cp .env.example .env
chmod 600 .env
sudo mkdir -p /opt/hwabun/certbot/www/.well-known/acme-challenge
sudo docker compose config --quiet
```

`.env.example`에는 과거 외부 MySQL Compose 값을 설명하는 `DW_MYSQL_HOST=shop-backend-mysql` 줄과 현재 단일 Compose용 `DW_MYSQL_HOST=mysql` 줄이 함께 있습니다. 실제 `.env`에서는 중복을 제거하고 **`DW_MYSQL_HOST=mysql`, `DW_MYSQL_PORT=3306`을 한 번만** 둡니다. `MYSQL_PASSWORD`, `MYSQL_ROOT_PASSWORD`, `SHOP_BACKEND_JWT_SECRET`, `GRAFANA_ADMIN_PASSWORD`, PortOne 설정을 채웁니다. `KAFKA_BOOTSTRAP_SERVERS=<EC2-2 사설 IP>:9092`여야 하며 EC2-1 자기 주소가 아닙니다.

Nginx는 인증서 파일이 없으면 시작하지 않습니다. 새 도메인 최초 발급은 80 포트가 비어 있을 때 호스트에서 수행합니다.

```bash
sudo certbot certonly --standalone -d j15a306.p.ssafy.io \
  --email <인증서 알림 메일> --agree-tos --no-eff-email
sudo certbot certificates
sudo docker compose up -d --build mysql
sudo docker compose up -d --build
sudo docker compose exec nginx nginx -t
curl -I https://j15a306.p.ssafy.io
```

기존 인증서가 있으면 재발급하지 말고 `sudo certbot certificates`로 먼저 확인합니다. HTTP 80은 인증서 검증 경로와 HTTPS 리다이렉트에 필요합니다. 갱신 방식은 Certbot 설정에 맞춰야 하며, webroot로 전환한 경우 `sudo certbot renew --dry-run` 뒤 `sudo docker compose exec -T nginx nginx -s reload`를 점검합니다. [Let's Encrypt 안내](https://letsencrypt.org/getting-started/)를 참고하세요.

`shop_backend/mysql-erd.sql`과 `shop_backend/seed/shop_backend_seed.sql`은 **빈 MySQL Volume의 최초 기동에만** 자동 실행됩니다. 기존 데이터베이스에 SQL 파일을 넣고 컨테이너를 다시 시작해도 마이그레이션되지 않습니다. `contracts/dw/schema.sql`은 새 `dw` DB를 만들 때 관리자 검토 후 별도 적용합니다. 기존 `dw`는 `deploy/ec2-1/migrations/`의 해당 마이그레이션을 확인하고 덤프 백업 후 적용해야 합니다. DB 덤프 복원 절차는 [3_데이터베이스_덤프.md](3_데이터베이스_덤프.md)에 있습니다.

### 2.4 EC2-2: 일일 Mart 배치와 발행

EC2-2 `.env`에 고정된 비밀 `COMMONS_HASH_SALT`, EC2-1의 사설 IP를 쓰는 `DW_MYSQL_HOST`, `DW_MYSQL_PORT=13306`, `DW_MYSQL_DB=dw`, `DW_MYSQL_USER=dw_writer`, 비밀번호를 넣습니다. EC2-1 MySQL에 `dw_writer` 쓰기 권한과 `dw_reader` 조회 권한을 별도로 만듭니다. EC2-1의 추천 서버와 Shop Backend는 `dw_reader`를 사용합니다. `DW_PROJECTION_MARTS`가 예전 7종으로 남아 있으면 현재 22종으로 갱신하거나 줄을 제거해 Compose 기본값을 사용합니다.

```bash
cd ~/S15P21A306/deploy/ec2-2
sudo docker compose up -d --no-build --force-recreate spark-master spark-worker
sudo docker compose exec -T spark-master bash -ec 'test -n "$COMMONS_HASH_SALT"'
sudo docker compose --profile dw build dw-projection
sudo cp hwabun-daily-batch.service hwabun-daily-batch.timer /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now hwabun-daily-batch.timer
systemctl list-timers --all hwabun-daily-batch.timer
```

타이머는 매일 18:00 UTC, 다음 날 03:00 KST에 실행합니다. `/home/ubuntu/S15P21A306` 경로가 아닌 위치에 클론했다면 systemd service와 `HWABUN_REPO_ROOT`를 수정해야 합니다. 한 번 수동 실행하려면 `sudo systemctl start hwabun-daily-batch.service`를 쓰고 `sudo journalctl -u hwabun-daily-batch.service -n 100 --no-pager`로 결과를 확인합니다. Q2 정제, Q3 Fact, Q4 Mart, Q5 검증, MySQL 발행 순서입니다. 현재 스크립트는 Q5가 실패해도 발행을 시도하고 마지막에 비정상 종료 코드를 남깁니다. 따라서 `systemd failed`만 보고 미발행이라고 단정하지 말고 Q5 보고서와 DW 발행 보고서를 각각 확인해야 합니다.

```bash
# EC2-2에서 확인
sudo docker compose ps -a
test -f /opt/hwabun/data/validation/pipeline-report.json
sudo docker compose --profile dw run --rm --no-deps dw-projection --help

# EC2-1에서 확인. 비밀번호 값은 출력하지 않음
sudo docker compose ps
curl -I https://j15a306.p.ssafy.io/dashboard.html
```

Spark Master UI는 EC2-2 기본값 `127.0.0.1:18080`입니다. EC2-1 추천 서버의 `/pipeline`에서 읽으려면 EC2-2 `.env`에 `SPARK_MASTER_UI_BIND_IP=<EC2-2 사설 IP>`, EC2-1 `.env`에 `SPARK_MASTER_UI=http://<EC2-2 사설 IP>:18080`을 넣고 보안 그룹에서 EC2-1만 18080에 허용합니다. `/json`은 `/json/`으로 리다이렉트될 수 있으므로 `curl -L`로 확인합니다.

## 4. 배포 시 특이사항과 운영 확인

- 현재 Kafka는 단일 브로커, RF1, 암호화와 브로커 인증 없는 사설망 MVP입니다. 고가용성이라고 설명하지 않습니다.
- Q1은 Kafka 오프셋 checkpoint를 갖습니다. Raw Parquet을 초기화할 때 `checkpoints/raw-events`도 같은 시점에 정리하고 Q1을 멈춘 상태에서 수행해야 합니다. 일반 배포에서는 둘 다 보존합니다.
- Mart 저장소는 Delta Lake가 아닌 Parquet이고 MySQL `dw`는 대시보드와 추천 서버를 위한 조회 projection입니다. 마트는 Q4 배치가 다시 만들며 Q1처럼 계속 갱신되지 않습니다.
- `COMMONS_HASH_SALT`는 재배포 후에도 같은 값이어야 Commons 브랜드 가명이 안정적입니다. 값이 없으면 Q3가 실패합니다.
- `dw-projection`은 Compose profile `dw`라서 일반 `up`만으로 실행되지 않습니다. systemd 배치가 호출하거나 수동으로 `sudo docker compose --profile dw run --rm dw-projection`을 실행합니다.
- DW 발행은 Mart별 staging 검증 후 교체합니다. 전체 22개가 하나의 원자적 트랜잭션은 아니므로 발행 보고서에서 Mart별 성공 여부를 확인합니다.
- Jenkins로 shop-backend를 배포하면 재기동 전에 `deploy/ec2-1/apply-shop-migrations.sh`가 멱등 member 마이그레이션을 먼저 적용하고, 실패하면 재기동하지 않습니다. 발표 기간 배포 순서와 배포 후 점검은 `deploy/ec2-1/README.md` "발표 기간 배포 순서"에 있습니다.

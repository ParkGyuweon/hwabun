# PA 에이전트 — LLM 이 실제 브라우저로 프론트를 조작한다

PC 9,900명이 코드로 합성 로그를 만든다면, PA 100명은 **LLM 이 화면을 읽고 다음
행동을 골라** 진짜 브라우저(Playwright + Chromium)를 움직입니다. 프론트도 수집
서버도 실물이라, 계약이 실제로 지켜지는지가 여기서 드러납니다.

> **정성 검증 축입니다.** 대표 정량 지표(PC 9,900명 오프라인 평가)에 합치지
> 마십시오 — `docs/ai/evaluation-framework.md` 5절.

## 파일

| 파일 | 역할 |
|---|---|
| `agent_runner.py` | 러너. 화면 → 텍스트 → LLM → 행동 → 로그 |
| `model_server.py` | GPU 서버에 모델만 올리는 최소 서버 (OpenAI 호환) |

## 모델을 고르는 세 가지 방법

| 방법 | 어디서 도는가 | 크레딧 | 언제 쓰는가 |
|---|---|---|---|
| 기본 (GMS) | 원격 API | 100명 × 15턴 ≈ **900** | 최종 보고용 1회 |
| `--local-model HF_ID` | 러너 프로세스 안 | **0** | 노트북에서 빠르게. 워커마다 모델이 한 벌씩 올라가 VRAM 이 곱해진다 (8GB 면 1개) |
| `--api-base URL` | 별도 모델 서버 | **0** | GPU 서버에 큰 모델을 올려 두고 브라우저만 노트북에서 |

```bash
# 배선만 확인 (LLM 호출 0회)
python simulator/agents/agent_runner.py --limit 3 --script click_product,add_to_cart

# 노트북 GPU 로
python simulator/agents/agent_runner.py --limit 10 --local-model Qwen/Qwen2.5-3B-Instruct

# GPU 서버에 모델을 올려 두고 (서버 쪽)
python simulator/agents/model_server.py --model Qwen/Qwen2.5-7B-Instruct --port 8501
# 노트북 쪽
python simulator/agents/agent_runner.py --limit 10 \
    --api-base http://<서버>:8501/v1 --model Qwen/Qwen2.5-7B-Instruct
```

프론트(`localhost:5173`)가 떠 있어야 합니다. `--post http://localhost:8080` 을 주면
파일 대신 수집 API 로 보냅니다.

## 주문(checkout)·목록 정렬(sort_list) — Jira 321, 2026-09-16

행동 목록에 `checkout` 과 `sort_list` 가 있다. 이전 PA 100명 실행은 purchase 0건 · sort_change 0건이었다.

- `--checkout` 을 주면 스위처 대신 **PA 회원으로 로그인**한다 (`{pid}@persona.hwabun.local` / `hwabun1234`,
  shop_backend 시드). 로그인이 없으면 프론트가 서버 주문을 `!member` 로 막아 결제까지 못 간다.
- `checkout` 은 장바구니 → 주문하기 → 주문 완료 → 구매 사유 설문(응답 70% · 건너뛰기 30%, 생성기와 같은 값)을
  한 동선으로 누르고 **세션을 끝낸다**. 담은 것이 1개 이상이고 상세를 3개 이상 본 뒤에만 열린다 (leave 와 같은 문턱).
- 전제: 프론트에 결제 키(`VITE_PORTONE_*`)가 **없어야** 한다. 키가 있으면 카카오페이 창이 떠서 에이전트가 넘지 못한다.
  키 없는 프론트는 `/api/orders/{id}/pay` 로 PAID 표시(테스트 주문)가 되고 `purchase` 이벤트 모양은 같다.
- `sort_list` 는 세션당 한 번, target 은 화면의 정렬 이름(인기순 · 평점 높은순 · 가격 낮은순 · 가격 높은순).
- `click_banner`: 목록 위 히어로 배너(AdBanner)가 보이면 화면 텍스트에 `[배너] 브랜드 · 배지 · 문구` 한 줄로 실리고
  행동이 열린다. **프롬프트는 중립**이다("맞아 보이면 들어가고 아니면 무시") — 배너 효과를 재는 실험이라 유도하지 않는다.
  이전엔 러너가 배너를 아예 못 봐서 PA 실행의 banner_click 이 0건이었다.

```bash
# 배선 확인 (LLM 0회) — 프론트 5173 + shop_backend 8090 이 떠 있어야 한다
python simulator/agents/agent_runner.py --checkout --limit 1     --script click_product,add_to_cart,back_to_list,click_product,back_to_list,click_product,back_to_list,checkout
```

## 정렬 문구는 중립 · 배너 대조군 `--no-banner` — Jira 326, 2026-09-16

- 파일럿(20명 × 2조건)에서 `sort_list` 30회가 **전부 '가격 낮은순'** 이었다. 프롬프트가 "가격이 신경 쓰이면 가격 낮은순…" 예시를 든 탓.
  예시를 빼고 네 정렬을 같은 무게로 나열, 허용 밖 보정 폴백도 무작위로 바꿨다. nano 는 예시 하나에 이렇게 끌린다.
- `--no-banner`: 프론트는 배너를 그대로 그리지만 러너가 화면 텍스트에서 `[배너]` 줄을 빼고 `click_banner` 도 열지 않는다.
  노출 A/B 의 대조군. 배너 노출 로그(`recommendation_impression`, `list_id=hero_banner`)는 두 조건 모두 프론트가 남긴다.
- 파일럿 결과(배포 서버, 09-16): 배너를 본 20명 중 **6명 클릭(30%), 4명은 첫 화면에서**, 배너 상품 상세 4·찜 1·담기 1.
  전체 담기는 85 vs 89 로 같고 찜은 34 vs 62(n=20, 잡음 범위). 클릭 이유는 전부 "새 브랜드 신상품". 데이터는 레포 밖(Research/banner-ab-20260916).
- 배포 프론트에는 09-16 부터 포트원 키가 있어 `checkout` 이 카카오페이 창에서 멈춘다 → 프론트 `?pay=test` 스위치 요청 중. 그 전엔 배포본 실행은 결제 없이.

## 페르소나가 행동을 이끄는가 — `--prefer-category`

09-07 100명 본실행에서 **담은 상품이 본인 리뷰 카테고리 안인 비율이 57%** 였는데,
카탈로그에서 무작위로 골라도 56% 다 (lift 1.02x). 개인 안에서는 일관해도(1인당 15턴,
재진입률 8.8%, 교정률 0.1%) 사람 사이 차이가 안 났다. 두 층이 겹친 결과다 —
첫 화면의 기획전 레일(`skin_match_v0`)이 리뷰 카테고리를 57% 밖에 못 맞추고(노출층),
모델은 그 레일 안에서 카테고리를 가리지 않고 눌렀다(레일 안 lift 1.08x, 판단층).

프로필에는 상품 **이름**만 있고 종류가 없었다. `--prefer-category` 를 켜면
① 프로필에 "주로 사 온 종류: Moisturizers, Cleansers" ② 목록 줄마다 `(Cleansers)`
③ 행동 기준 "내가 주로 사 온 종류를 먼저 보십시오" 가 붙는다.
**100명 실측(09-08, 900크레딧): 효과 없음.** 담기 lift 1.02x → **1.00x** (n=222), 상세 진입
1.14x → 1.05x, 레일 안 선택 1.08x → 1.06x. 5명 예비(1.59x)는 표본 노이즈였다. 판단 513건의
`reason` 중 "종류·카테고리" 를 언급한 것 **2건** — 모델(nano)이 프로필의 종류 줄을 판단 근거로
쓰지 않는다. 형식 지표는 그대로 좋다 (교정 1 · 실패 1 · 재진입률 7.8% · 담기 판단 = 이벤트 227).
**결론: 페르소나 차이가 안 나는 원인은 판단층이 아니라 노출층** — 기획전 레일이 내 종류를
56% 밖에 안 보여주면 프롬프트가 뭐라 해도 고를 게 없다. 다음 손잡이는 프론트 `skin_match_v0`
(또는 추천 API 연결)이고, 러너 프롬프트는 여기서 멈춘다. 플래그는 실험 기록으로 남긴다.

**`--prefer-strict` 도 같다 (20명, 180크레딧).** 권고형이 묻힌 것이라면 금지형은 다를까 해서
목록 줄에 내 종류를 `★` 로 찍고 "★ 없는 상품은 고르지 마십시오 · reason 에 종류를 적으십시오" 로
바꿨다. 같은 20명 비교: 담기 lift 1.37x(권고형) → **1.26x**, 상세 진입 1.31x → 1.21x.
클릭 91건 중 다른 종류 35건 — 화면에 ★ 는 거의 항상 있었다(99명 중 97명, 보인 것의 60%).
reason 에 종류를 적은 것 **0/98**. 형식(교정 0 · 실패 0 · 재진입률 10.2%)은 여전히 완벽하다.
**nano 는 형식 지시는 따르고 선택 기준 지시는 무시한다** — 강도를 올려도 안 바뀐다.
남은 손잡이는 둘: ① 모델을 올린다 (mini, 크레딧 5배 추정) ② 종류 필터를 러너 코드로 강제한다
(허용 행동을 코드가 거르는 것과 같은 자리 — 모델은 ★ 안에서만 고른다). 결정 전까지 둘 다 안 한다.

**`--prefer-filter` (2026-09-14, Jira 241) — 종류 필터를 코드로 강제.** 목록에 내 종류(리뷰 이력
상위 3개) 카드가 하나라도 보이면 그 카드만 모델에게 보여 준다. 100명 본실행
(`agent_events_20260914_filter.jsonl`, 70분, 워커 4): 담기 lift **0.89x** · 재진입률 **51.2%** ·
상세 진입 고유 상품 19개 — 09-08 보다 나빠 보이지만 **이 결과는 무효다.** 판단 기록과 이벤트를
짝지어 보니 LLM 이 고른 브랜드와 실제 열린 상품 브랜드가 **62% 어긋났다**(09-08 실행은 1%).
원인은 `norm()` 이 `[^a-z0-9]` 를 지워 **09-09 사이트 한국어화 뒤 카드 이름이 전부 빈 문자열**이
된 것 — 빈 이름은 `name in want` 에 항상 참이라 화면 첫 카드가 매번 열렸고, 필터 없을 때는
"첫 카드" 가 우연히 고른 카드와 같아 드러나지 않았다. 09-09 이후 PA 실행은 전부 같은 함정 위에
있었다(그 사이 본실행은 없었다). 고침: `norm()` 한글 보존, `find_card()` 는 4자 미만 이름 건너뛰고
가장 길게 겹치는 카드 선택. 스크립트 모드 2명×3클릭에서 고른 상품 = 열린 상품 6/6 확인.
**필터 효과 자체는 아직 재지 않았다** — 고친 러너로 다시 돌려야 한다(약 1,100 크레딧).

**재실행 (2026-09-14 오후, `agent_events_20260914_filter_v2.jsonl`, 100명 · 워커 4 · 69.6분, Jira 293).** 러너를 한국어
사이트에 맞춘 뒤(이름 매칭 한글 보존 · 카테고리 탭 코드→한글 라벨 · 가격 원화 표기/파싱) 돌렸다. 먼저 유효성:
**고른 브랜드 = 열린 브랜드 99%** (8/771 불일치, 09-08 과 같은 수준). 결과 (비교는 09-08 `--prefer-category` 100명):

| | 09-08 prefcat | **09-14 --prefer-filter** |
|---|---:|---:|
| 담기 lift (본인 리뷰 카테고리 안 / 무작위 기대) | 1.00x (56.3/56.2%) | **1.11x (62.1/55.9%)** |
| 상세 진입 lift | 1.06x | **1.10x** |
| 담기 · 1인당 | 227 · 2.27 | 340 · 3.40 |
| 담긴 고유 상품 · 상세 고유 상품 | 28 · 32 | **43 · 46** |
| 노출 고유 상품 | 65 | 91 |
| 재진입률 · 재진입한 사람 | 7.8% · 38명 | **21.5% · 80명** |
| 조작 실패 | 1 | 16 |

**읽기.** 종류 필터는 페르소나 차이를 **만들긴 한다**(1.00x → 1.11x) — 프롬프트 세 종류가 전부 1.0x 였던 것과 달리 코드가
거르면 움직인다. 그러나 화면만으로 잡을 수 있다고 본 상한 1.64x 에는 한참 못 미친다. 이유는 필터가 **지금 화면에
내 종류 카드가 있을 때만** 작동하기 때문이다 — 첫 화면 12장 중 내 종류는 보통 3~7장이고, 그 안에서 고르니 같은
상품을 다시 여는 일이 늘었다(재진입 7.8% → 21.5%). 다양성은 오히려 좋아졌다(고유 상품 28 → 43, 노출 65 → 91 —
카테고리 탭이 제대로 잡히면서 첫 화면이 사람마다 달라진 효과). 조작 실패 16건은 필터로 숨긴 카드를 스크롤 뒤
다시 찍은 경우로, 로그 품질엔 영향 없다(실패 턴은 이벤트를 남기지 않는다).

**다음 손잡이는 러너가 아니라 노출층이다.** 내 종류 카드가 화면에 더 많이 나오게 하는 것 — 프론트 목록 레일을
추천 API(`/api/recommend`, 속성·이력 반영)에 붙이는 일. 러너 프롬프트·필터 실험은 여기서 닫는다.


**dry-run · `--script` 는 기본 출력이 `agent_events_dryrun.jsonl` 로 갑니다.**
09-08 에 `--dry-run --limit 1` 이 기본 경로에 써서 09-07 본실행 33,217건을 덮어썼다.
본실행 결과는 항상 `--out` 에 날짜를 넣어 남기십시오.

## 판단 근거는 따로 남는다 — `--decisions`

`reason` 이 콘솔에만 찍히면 실행이 끝나는 순간 사라집니다. 실제로 8/31 GMS 100명
실행의 근거 문장이 그렇게 없어졌습니다. 그래서 턴마다 별도 파일로 남깁니다.
경로는 `--out` 옆에 `*_decisions.jsonl` 로 자동 생성되고, `--decisions off` 로 끕니다.

**이벤트에 넣지 않습니다.** 이벤트는 계약(36종)이고 property 도 계약이 정한 것만
씁니다 — `reason` 은 거기에 없습니다. 이벤트 로그와는
`persona_id` + `simulation_run_id` + 시각으로 붙습니다.

| 필드 | 뜻 |
|---|---|
| `screen` · `allowed` | 그 턴에 무슨 화면이었고 어떤 선택지를 줬는가 |
| `llm_action` · `llm_target` · `reason` | 모델이 뭐라고 했고 근거를 뭐라 댔는가 |
| `action` · `target` | **코드가 무엇으로 바꿨는가** |
| `corrected` | 둘이 다르면 교정된 턴 |
| `succeeded` | 그 조작이 실제로 먹혔는가 |

**`corrected` 가 특히 중요합니다.** 러너는 허용 밖 행동을 조용히 교정합니다.
그 비율을 모르면 "LLM 이 판단했다" 고 말할 근거가 얼마나 되는지 알 수 없습니다.

워커를 여러 개 쓰면 조각으로 쓰였다가 하나로 합쳐집니다.

## 왜 모델 서버를 따로 두는가

배정된 GPU 서버에는 주피터만 있고 `node` 도 `sudo` 도 없어 프론트와 Chromium 을
올릴 수 없습니다. 그래서 **모델만** 서버에 두고 브라우저는 노트북에 남깁니다.
노트북 VRAM 8GB 제약이 사라져 7B 이상을 쓸 수 있습니다.

`model_server.py` 는 러너의 `ask()` 가 보내는 것만 받고 `response_format` 같은
모르는 필드는 무시합니다. 작은 모델이 서두를 붙이는 버릇이 있어 `{"action": "` 를
프리필로 넣습니다. GPU 한 장이라 생성은 락으로 직렬화합니다.

**인증이 없습니다.** 사내망에서만 띄우고 끝나면 내리십시오.
**V100 에는 bfloat16 이 없습니다** — `float16` 으로 고정돼 있습니다.

## 로그는 그 사람 것만 남는다 — 페르소나 게이트

`App.tsx` 가 페르소나를 `useState(personas[0])` 로 들고 있어 **페이지를 새로 열면
선택이 PA00001 로 돌아갑니다.** URL 파라미터도 저장소도 없습니다. 그래서 러너는
화면을 먼저 열고 드롭다운으로 페르소나를 고르는데, 그 사이 화면의 이벤트가 전부
PA00001 로 기록됐습니다.

| 2026-09-02 100명 실행 | |
|---|---:|
| 전체 | 49,749건 |
| **PA00001 에 쌓인 것** | **21,767건 (44%)** · 세션 146개 |
| 다른 사람 한 명당(중앙값) | 439건 |

세션이 섞이지는 않습니다 — 페르소나를 바꾸면 새 세션이 시작되므로 **앞 세션
통째로**가 PA00001 몫이 됩니다. `persona_id` 가 채워져 있어 전송 필터도 통과해서
수집 API 로 그대로 나갑니다.

**전환을 앞으로 옮기는 걸로는 못 고칩니다** — 그다음 `goto` 가 선택을 되돌려
그 사람 로그가 통째로 사라집니다 (실측 확인).

그래서 `LogSink` 가 컨텍스트마다 게이트를 하나 들고, **전환 전 이벤트는 파일에도
남기지 않습니다.** 전환 뒤에도 다른 사람 `persona_id` 로 오는 것이 있으면(프론트가
배치로 모아 보내기 때문) 같이 버리고, 실행 요약에 몇 건인지 찍습니다.

근본 수정은 프론트가 `?persona=` 를 읽는 것이었고, 제안 패치가
**적용됐습니다** (`Research/handoff/frontend-persona-url-param.md` → dev `10dd3b3`).
러너는 아직 화면을 먼저 열고 페르소나를 고르는 순서라 `LogSink` 게이트를 그대로
둡니다 — 게이트는 배치 전송으로 섞여 오는 남의 이벤트도 같이 막습니다.
러너가 `?persona=` 로 바로 들어가게 바꾸는 것은 별건입니다.

**2026-09-03 이전 로그는 이 오염을 안고 있습니다.** 사람 단위로 재려면
`--exclude=PA00001` 로 빼십시오.

## 실행이 좋아졌는지 재는 법

    python simulator/agents/analyze_run_quality.py <이전.jsonl> <나중.jsonl>

재진입률·왕복비·커버리지·교정률을 두 실행에 같은 잣대로 매깁니다. 사람 수가
달라도 되도록 1인당 값과 비율을 함께 냅니다. 프롬프트를 고칠 때마다 이걸로
전후를 비교합니다 — 고친 사람이 좋아졌다고 말하는 것과 수치가 좋아진 것은
다릅니다.

## 러너가 지키는 것

- **실행 메타데이터를 러너가 채웁니다** — `actor_type=synthetic`,
  `generator_type=agent_llm`, `scenario_id`, `simulation_run_id`.
  `clean_events_job` 이 `actor_type` 으로 `user_id`·`source`·`is_synthetic` 을
  파생하므로, 이게 틀리면 거절도 안 되고 조용히 잘못된 데이터가 됩니다
- **페르소나 선택 전 이벤트는 전송에서 제외합니다** — `persona_id` 가 없기 때문입니다
  (파일에는 남깁니다)
- **허용되지 않은 행동은 코드가 교정합니다.** LLM 이 지어낸 상품명으로 엉뚱한
  클릭이 남지 않도록 target 도 화면 기준으로 다시 잡습니다
- **워커는 프로세스로 나눕니다** — Playwright sync API 가 스레드 안전하지 않습니다.
  한 번의 실행이 여러 `simulation_run_id` 로 쪼개지지 않도록 부모가 ID 를 정해
  모든 샤드에 물려줍니다

# 주간 업무 정리

작성: 추유림 (2026-08-28)

## 담당 역할

- 프론트엔드 UI 개발
- 사용자 행동 로그 트리거 구현
- 행동 데이터의 마케팅 활용 방안 기획

## 1. 프로젝트 기획

- 가상 소비자의 화장품 쇼핑 행동을 분석하는 B2B 마케팅 시뮬레이션 플랫폼으로 방향을 구체화했다.
- 소비자용 화장품 쇼핑 화면과 기업용 마케팅 분석 대시보드가 필요하다는 점을 정리했다.
- 추천 알고리즘 자체보다 **사용자 행동 로그의 수집·처리·분석**을 프로젝트 핵심으로 설정했다.
- 추천 기능은 CBF 기반 POC로 먼저 구현하고, CF와 하이브리드 추천은 확장 기능으로 정리했다.

## 2. 데이터셋 확인

- 데이터 담당자로부터 상품 데이터, 리뷰 데이터, 필드 통계 샘플을 전달받아 구조를 확인했다.
- 프론트 화면 구성에 필요한 상품명, 브랜드, 카테고리, 가격, 평점, 리뷰, 피부 관련 필드를 검토했다.
- 프론트엔드와 데이터 파트가 공통으로 쓸 상품 식별자와 응답 구조가 필요하다는 점을 정리했다.
- **데이터셋에 상품 이미지 URL과 상세 설명 문단이 없다는 것을 확인했고, 프론트에서 직접 수집했다** (4번 항목).

## 3. 프론트엔드 구현

Sephora 상품 상세페이지를 기준으로 화면을 구현했다.
컴포넌트 22개 · 커스텀 훅 5개 · 약 3,250줄.

| 영역 | 구현 내용 |
|---|---|
| 초기 환경 | React 19 + TypeScript + Vite |
| 상세페이지 | 상품 기본정보, 이미지 갤러리, Highlights, 성분, 리뷰, 유사·추천 상품 |
| 이미지 갤러리 | 대표 이미지 + 추가 이미지 썸네일, 클릭 전환 |
| 옵션 선택 | 색·향·용량 스와치, 선택 시 대표 이미지·SKU 전환 |
| 리뷰 | 리뷰 목록, 요약, 필터 바 |
| 공통 | Accordion, Chip, StarRating, EmptyState |
| 개발용 | 로그 확인 패널, 페르소나 전환, 임시 상품 이동 바 |

행동 로그를 영역 단위로 수집할 수 있도록 Section 구조로 화면을 나눴다.

## 4. 상품 이미지·상세 설명 수집

데이터셋에 없는 필드를 세포라 공개 페이지 기준으로 채웠다.

- 수집 결과: 상품 8종 · 갤러리 이미지 74장 · 옵션 29종 · 리뷰 40건
- 추가한 필드: `image_url`, `sku_id`, `images`, `variants`, `description`
- 세포라가 상품 페이지 HTML과 API 를 403 으로 차단해서 **web.archive.org 스냅샷**에서 추출했다
- 이미지 URL 은 전부 응답 코드로 검증했다
- 수집 경로와 재실행 방법은 `docs/data/product-images.md` 에 남겼다

**주의로 남긴 것**: 데이터셋은 특정 시점 스냅샷이라 현재 세포라 페이지와 상품명·가격이
어긋난다. 수집한 `description` 은 표시용이며 분석·추천 입력으로 쓰면 안 된다.
데이터 담당자가 내려주는 기존 필드는 하나도 변경하지 않았다.

## 5. 행동 로그 구현

수집 이벤트 20종을 구현했다.

| 분류 | 이벤트 |
|---|---|
| 진입·이동 | `session_start`, `page_view`, `product_click` |
| 콘텐츠 열람 | `media_view`, `accordion_toggle`, `review_expand`, `ingredient_view_mode_change` |
| 관심 표현 | `wishlist_toggle`, `add_to_cart`, `quantity_change`, `variant_select` |
| 추천 반응 | `recommendation_click` |
| 탐색 | `review_filter_apply` |
| 주목(암묵) | `section_dwell`, `scroll_pause`, `hover_dwell` |
| 좌절 | `rage_click`, `dead_click`, `scroll_backtrack` |
| 이탈 | `exit_summary` |

### 설계에서 바꾼 점

초안은 클릭 이벤트 위주였고 클릭이 아닌 신호가 세 개뿐이었다.
실제 구매 판단에 영향을 주는 신호(이미지 열람, 성분 확인, 옵션 왕복, 좌절)를
놓치고 있어서 **주목·좌절 신호를 추가**했고, 트래킹 버그 2건을 수정했다.

이벤트 이름만으로는 의미가 부족해서 속성 두 개를 붙였다.

- `intent` — 이 이벤트가 무슨 뜻인가
- `content_kind` — 그 자리에 뭐가 있었나

같은 클릭도 무엇을 눌렀는지에 따라 뜻이 달라지기 때문이다.

방문당 로그량은 1~2분 기준 30~60건으로 추정된다 (초안 5~10건에서 증가).
설계 근거는 `docs/analytics/behavior-log-design.md` 에 정리했다.

### 일부러 남기지 않는 것

- 마우스 좌표 궤적 — 양 대비 얻는 게 적고 세션 리플레이는 범위 밖
- 사용자가 입력한 값 — 텍스트 선택 로그에서 입력 요소 제외
- 개별 스크롤 프레임 — 멈춘 지점만 남긴다

## 6. 실험 데이터 품질 (이미지 로딩)

행동 로그를 재는 페이지에서 이미지 로딩 지연은 단순한 성능 문제가 아니다.
**이미지가 늦게 뜨면 그 대기 시간이 그대로 체류 시간으로 잡혀 측정값이 오염된다.**

두 가지를 처리했다.

1. **로컬 캐시** — dev 서버가 원본을 한 번만 받아 디스크에 저장하고 이후 로컬에서 제공.
   실험 전 일괄 선다운로드 스크립트(`npm run warm-images`)를 만들었다.
   브라우저 캐시만 쓰면 캐시를 비운 사람마다 실험 조건이 달라지기 때문이다.
2. **요청 크기 교정** — 갤러리 메인을 `imwidth=1024` 로 받고 있었는데, 세포라 CDN 은
   768 을 넘기면 사실상 원본을 준다(장당 300~550KB). 실제 표시 크기를 재서 768 로 낮추고,
   상세페이지 진입 시 갤러리 전체를 미리 받아두게 했다.

| 항목 | 개선 전 | 개선 후 |
|---|---|---|
| 썸네일 클릭 → 메인 교체 | 수 초 | 12~38ms |
| 메인 이미지 | 300~550KB | 평균 107KB |
| 워밍 캐시 전체 | 19MB | 9.3MB |
| 추천 카드 이미지 | 150px (표시 180px보다 작아 뭉개짐) | 400px |

## 7. 마케팅 활용 방안 조사

행동 신호를 어떤 비율로 반영할지 근거를 만들기 위해 실제 커머스를 조사했다.
정리는 `docs/analytics/marketing-signal-research.md` 에 남겼다.

### 핵심 결론

**네이버쇼핑·무신사·올리브영 모두 랭킹에 쓰는 지표 목록은 공개하지만
가중치·집계 기간·정규화 방식은 공개하지 않는다.** 따라서 남의 비율을 그대로
가져올 수 없고, 우리 값으로 정한 뒤 근거와 함께 문서화해야 한다.

| 플랫폼 | 공개된 것 | 비공개 |
|---|---|---|
| 네이버쇼핑 | 적합도 / 인기도 / 신뢰도 3축과 하위 항목 | 가중치, 집계 기간 |
| 무신사 | 매출·판매수량·조회수·후기수, 광고 미반영, 기간별 랭킹 | 공식, 가중치 |
| 올리브영 | 구매 데이터가 핵심이라는 정도 | 산정 기준 전체 |

### 우리 설계에 반영할 점

- **행동 신호만으로 순위를 만들지 않는다.** 네이버는 상품 정보 품질과 패널티를
  행동 신호와 같은 급으로 둔다. 감점 축이 필요하다
- **균일 가중은 위험하다.** 조회처럼 양이 많은 신호가 결과를 지배한다
- **암묵 신호는 단독으로 판정하지 않는다.** GA4 의 참여 세션 판정도 OR 조건이다
- **시간 감쇠·집계 기간이 필요하다.** 네이버는 최신성, 무신사는 기간별 랭킹을 둔다
- 화장품은 피부 타입·고민 같은 콘텍스트 정보를 함께 쓴 모델이 성능이 더 좋다는
  연구 결과가 있다. AI 파트의 성분 인코딩 방향과 일치한다

행동별 가중치는 정답이 아니라 초기 가설로 두고 실험으로 검증해야 한다는 방향으로 정리했다.

## 8. 추천 설계 검토 — 속성 신호 실측

CF 비중을 늘리는 방향을 검토하면서, 추천 설계의 전제를 데이터로 확인했다.

### 확인한 것

| 측정 | 결과 |
|---|---|
| 속성별 상품 선호 lift (`affinity_lift.csv` 4,000행) | \|lift−1\| 중위 **0.079~0.100** — 기준 대비 8~10% 이동. 강한 선호(lift>1.5)는 2~4% |
| 같은 피부타입 = 비슷한 행동인가 (페르소나 10,000명, 5천만 쌍) | 공통 상품 보유율 5.21% vs 5.21%, **리프트 1.000배** |
| 속성값 자체의 일관성 | 10,000명 중 **6,280명(63%)이 자기 리뷰들 사이에서 속성을 다르게 적음** |
| 사용자당 상품 수 | **중위 3개**. 공통 상품 2개 이상인 사용자 쌍 1.61% |
| item-item 공동 리뷰어 (페르소나 표본) | 상품 쌍의 46.1%가 0명, 중위 1명 |

AI 파트가 별점 기반 속성 친화도에서 이미 같은 문제를 발견해 둔 상태였다
(η² < 0.004, 리뷰 63.4%가 5점). 구성비 lift로 바꿔 편차가 10배 커졌지만
절대 크기는 여전히 작다는 것을 위 측정으로 확인했다.

### 결론

- **속성 항은 약한 신호를 불안정한 키로 조회하는 구조다.** 행동이 생기면 속성
  의존을 빠르게 줄여야 한다
- **CF 방향은 user-user 가 아니라 item-item 이다.** 사용자당 상품이 3개면
  유사도 대부분이 공통 상품 1개에 기반해 노이즈가 된다
- **CF 학습 데이터는 페르소나 표본이 아니라 전체 리뷰를 써야 한다.** 페르소나
  10,000명에서는 item-item 지지도도 부족하다. 전체 리뷰에는 상품 2개 이상 평가한
  사용자가 67,264명 있다
- **분산 부하는 CF 행렬이 아니라 로그 스트림에서 나온다.** 계산량을 만들려고
  통계적으로 약한 알고리즘을 고르는 것은 잘못된 교환이다

계획서 6장(추천 방식)과 11장(가상 소비자 결과의 한계) 수정안을 이 측정 결과
기준으로 작성했다. 전체 리뷰 데이터에서의 item-item 지지도 실측은 원본 데이터가
없어 하지 못했고 미결정 항목으로 남겼다.

## 9. 빅데이터 전문가 미팅

- 데이터를 활용할 최종 목적을 먼저 정한 후 필요한 행동 로그를 설계해야 한다.
- 프론트엔드 로그 수집은 화면 동작에 영향을 주지 않도록 비동기로 구현해야 한다.
- 로그 유실·중복·정합성을 고려해 이벤트 스키마를 설계해야 한다.
- Kafka·Spark 분산 처리에서는 TPS, 처리 지연시간, Consumer Lag, 이벤트 유실 여부를 측정해야 한다.
- 추천 난도가 높아지면 CBF 수준으로 범위를 제한하고 데이터 파이프라인 완성도를 우선해야 한다.
- 가상 소비자의 행동 결과를 실제 고객 선호나 매출 증가 효과로 해석하지 않도록
  결과의 한계를 명확히 설정해야 한다.

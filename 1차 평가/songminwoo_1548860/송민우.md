# 프로젝트 아키텍처 설계 내용

이번 주에는 사용자 행동 이벤트를 실시간으로 수집하고 처리하기 위한 Kafka와 Spark 기반 분산 데이터 아키텍처 초안을 설계했습니다.

전체 데이터 흐름은 다음과 같이 구성했습니다.

```text
사용자 행동 발생
        ↓
Backend Event Producer
        ↓
Kafka Cluster
  └─ Topic / Partition
        ↓
Spark Structured Streaming
        ↓
이벤트 검증·가공·집계
        ↓
운영 DB / Data Warehouse
        ↓
서비스 조회·통계·분석
```

## 1. 이벤트 생산 영역

사용자가 상품을 조회하거나 클릭하는 등의 행동이 발생하면 Backend가 이벤트를 생성해 Kafka로 전달하는 구조를 설계했습니다.

실제 Event Schema가 아직 확정되지 않았기 때문에 초기 PoC에서는 임시 `PRODUCT_VIEW` Event를 사용하도록 계획했습니다.

```json
{
  "eventId": "uuid",
  "eventType": "PRODUCT_VIEW",
  "userId": "user-1",
  "productId": "product-10",
  "eventTime": "2026-08-28T10:00:00Z"
}
```

`eventId`는 이벤트 중복 여부를 판별하는 데 사용하고, `eventTime`은 시간 단위 집계와 End-to-End Latency 측정에 활용하도록 설계했습니다.

## 2. Kafka 이벤트 수집 영역

Backend와 Spark를 직접 연결하지 않고 Kafka를 중간 계층으로 배치했습니다.

Kafka는 Backend에서 생성된 이벤트를 Topic에 저장하고, Spark가 자신의 처리 속도에 맞춰 이벤트를 가져갈 수 있도록 하는 역할을 담당합니다.

이 구조를 통해 순간적으로 이벤트가 많이 발생하더라도 Kafka가 버퍼 역할을 수행하며, Spark에 장애가 발생했을 때도 마지막 Offset부터 처리를 다시 시작할 수 있도록 설계했습니다.

초기 Topic은 다음과 같이 구상했습니다.

```text
Topic: product-events
Event Type: PRODUCT_VIEW
```

이후 `PRODUCT_CLICK`, `PRODUCT_PURCHASE` 등의 이벤트가 추가될 경우 하나의 Topic에서 `eventType`으로 구분할지, 이벤트별로 Topic을 분리할지 검토할 예정입니다.

## 3. Partition 구조

Kafka는 Partition 단위로 병렬 처리를 수행하고 Partition 내부에서만 이벤트 순서를 보장하므로 Partition Key가 중요하다고 판단했습니다.

Partition Key 후보는 다음과 같이 검토했습니다.

- 상품별 조회 수와 이벤트 순서가 중요하면 `productId`
- 사용자 행동 흐름과 순서가 중요하면 `userId`

PoC 환경에서는 Kafka와 Spark의 최소 연결 확인이 목적이므로 1개의 Partition으로 시작하고, 운영환경에서는 예상 TPS, Consumer 수, 필요한 순서 보장 범위를 측정한 후 Partition 수를 결정하도록 설계했습니다.

## 4. Spark 실시간 처리 영역

Spark Structured Streaming은 Kafka의 `product-events` Topic을 구독해 이벤트를 읽고 처리하는 역할을 담당합니다.

Spark의 처리 과정은 다음과 같이 설계했습니다.

1. Kafka에서 Raw Event 수신
2. JSON Schema Parsing
3. 필수 필드와 데이터 형식 검증
4. 잘못된 이벤트 필터링
5. 상품별 또는 사용자별 이벤트 집계
6. 처리 결과를 최종 저장소에 기록

초기 PoC에서는 Kafka Event가 Spark Console에 정상적으로 출력되는지 먼저 확인하고, 이후 JSON Parsing과 집계 로직을 추가하도록 계획했습니다.

Spark가 중단된 이후에도 이전 처리 위치부터 이어갈 수 있도록 Checkpoint를 설정하고, Kafka Offset과 Streaming 처리 상태를 저장하는 구조도 고려했습니다.

## 5. 데이터 저장 영역

Spark가 가공하고 집계한 결과는 사용 목적에 따라 운영 DB와 데이터 웨어하우스에 저장하도록 설계했습니다.

- 서비스 화면에서 빠르게 조회해야 하는 데이터는 운영 DB에 저장
- 장기간 누적 데이터 분석과 통계에 필요한 데이터는 데이터 웨어하우스에 저장

예를 들어 현재 인기 상품이나 실시간 조회 수는 운영 DB에 저장하고, 일별·월별 사용자 행동 분석 데이터는 데이터 웨어하우스에 저장할 수 있습니다.

저장소의 구체적인 기술은 실제 서비스 요구사항과 데이터 활용 목적이 확정된 후 결정할 예정입니다.

## 6. Cluster 구성 방향

개발환경과 운영환경의 목적을 분리해 구성 방향을 검토했습니다.

개발환경은 최소 Pipeline 연결 확인을 위해 다음과 같이 구성할 예정입니다.

```text
Kafka Broker 1대
Partition 1개
Replication Factor 1
Spark Local 실행
Console 또는 임시 파일 Sink
```

운영환경에서는 다음 항목을 고려해 Kafka와 Spark Cluster 규모를 결정하도록 설계했습니다.

- 예상 이벤트 TPS
- Kafka Broker와 Partition 수
- Replication Factor
- Spark Worker 수
- Consumer 병렬 처리 수
- 장애 복구 방식
- 데이터 보관 기간
- Consumer Lag 발생 여부

## 7. 모니터링 구조

시스템의 처리 성능과 병목을 확인하기 위해 다음 지표를 측정 후보로 선정했습니다.

- Kafka 이벤트 유입 TPS
- Spark 이벤트 처리량
- Processing Latency
- End-to-End Latency
- Consumer Lag
- Spark Micro-batch 처리 시간
- `inputRowsPerSecond`
- `processedRowsPerSecond`

Consumer Lag이 계속 증가하면 Kafka로 들어오는 이벤트 속도보다 Spark 처리 속도가 느리다는 의미이므로 Partition 수, Consumer 병렬 처리 수 또는 Spark 처리 성능을 조정할 수 있도록 계획했습니다.

## 8. 아키텍처 설계 결과

이번 설계를 통해 Backend, Kafka, Spark, 저장소의 역할을 분리하고 각 구성 요소가 독립적으로 확장될 수 있는 구조를 구상했습니다.

Event Schema가 확정되지 않은 상황에서도 임시 `PRODUCT_VIEW` Event를 사용해 다음 최소 Pipeline부터 검증할 수 있도록 설계했습니다.

```text
Dummy Event Producer
        ↓
Kafka product-events Topic
        ↓
Spark Structured Streaming
        ↓
Console Sink
```

최소 연결을 확인한 이후 실제 Event Schema, Partition Key, Cluster 규모, 최종 저장소를 단계적으로 확정할 예정입니다.



# 이번 주 학습 내용
## 1. 분산 데이터 파이프라인 구조
이번 주에는 사용자 행동과 같은 이벤트가 발생한 뒤 수집, 처리, 저장되는 전체 데이터 파이프라인 구조를 공부했습니다.
구상한 데이터 흐름은 다음과 같습니다.
이벤트 발생 서비스
    ↓
Kafka Producer
    ↓
Kafka Topic / Partition
    ↓
Spark Structured Streaming
    ↓
가공 및 집계
    ↓
운영 DB 또는 Data Warehouse
서비스에서 PRODUCT_VIEW와 같은 이벤트가 발생하면 Producer가 Kafka로 이벤트를 전송합니다. Kafka는 이벤트를 Topic에 저장하고, Spark Structured Streaming은 Kafka에 저장된 이벤트를 읽어 실시간으로 가공하거나 집계합니다. 처리된 결과는 사용 목적에 따라 운영 DB 또는 데이터 웨어하우스에 저장할 수 있습니다.
이 구조에서 Kafka는 이벤트를 전달하고 보관하는 중간 계층이고, Spark는 실제 데이터를 가공하고 집계하는 처리 계층이라는 차이를 이해했습니다.
## 2. Kafka의 역할
Kafka는 대량의 이벤트를 안정적으로 저장하고 여러 시스템에 전달하기 위한 분산 이벤트 스트리밍 플랫폼입니다.
일반적인 메시지 전달뿐만 아니라 이벤트를 일정 기간 보관할 수 있기 때문에 Consumer가 일시적으로 중단되더라도 다시 실행한 후 이전 이벤트부터 이어서 처리할 수 있습니다.
Kafka를 사용하면 이벤트를 생성하는 서비스와 이벤트를 처리하는 시스템을 직접 연결하지 않아도 됩니다. Producer는 Kafka에 이벤트만 전송하고, Spark나 다른 Consumer는 필요한 시점에 Kafka에서 이벤트를 가져갑니다.
이를 통해 다음과 같은 장점을 얻을 수 있습니다.
- Producer와 Consumer 간 결합도 감소
- 순간적으로 이벤트가 많이 발생했을 때 Kafka가 버퍼 역할 수행
- Consumer 장애 후 중단된 위치부터 처리 재개
- 여러 Consumer가 동일한 이벤트를 서로 다른 목적으로 활용
- Partition을 활용한 병렬 처리와 확장
- Replication을 통한 장애 대응
## 3. Kafka 핵심 구성 요소
Producer
Producer는 Kafka에 이벤트를 전송하는 애플리케이션입니다.
예를 들어 사용자가 상품을 조회하면 백엔드 서비스나 이벤트 수집기가 다음과 같은 이벤트를 생성해 Kafka에 전송할 수 있습니다.
{
  "eventId": "uuid",
  "eventType": "PRODUCT_VIEW",
  "userId": "user-1",
  "productId": "product-10",
  "eventTime": "2026-08-28T10:00:00Z"
}
Broker와 Cluster
Broker는 Kafka 서버 한 대를 의미합니다. 여러 Broker를 묶으면 Kafka Cluster가 됩니다.
개발환경에서는 Broker 한 대로도 테스트할 수 있지만, 운영환경에서는 장애 대응과 부하 분산을 위해 여러 Broker로 Cluster를 구성해야 합니다.
Topic
Topic은 이벤트를 종류나 목적에 따라 분류하는 논리적인 저장 공간입니다.
예를 들어 상품 관련 이벤트를 저장하기 위해 다음과 같은 Topic을 사용할 수 있습니다.
product-events
Topic 내부에는 PRODUCT_VIEW, PRODUCT_CLICK, PRODUCT_PURCHASE와 같은 이벤트가 들어갈 수 있습니다. 이벤트 유형별로 Topic을 분리할지, 하나의 Topic에서 eventType으로 구분할지는 이벤트 양과 처리 방식에 따라 결정해야 합니다.
Partition
Partition은 하나의 Topic을 여러 개로 나눈 물리적인 저장 단위입니다. Kafka는 Partition을 통해 이벤트를 병렬로 저장하고 처리할 수 있습니다.
각 Partition은 이벤트가 순서대로 추가되는 로그 형태로 구성됩니다. Kafka는 Topic 전체의 순서를 보장하지 않고, 동일한 Partition 내부에서만 이벤트 순서를 보장합니다.
따라서 순서가 중요한 이벤트는 동일한 Key를 사용해 같은 Partition으로 전달해야 합니다.
예를 들어:
- 상품별 이벤트 순서와 집계가 중요하면 productId
- 사용자 행동 순서가 중요하면 userId
를 Partition Key 후보로 사용할 수 있습니다.
Partition 수를 늘리면 Consumer가 병렬로 이벤트를 처리할 수 있지만, 지나치게 많은 Partition은 관리 비용과 리밸런싱 비용을 증가시킬 수 있습니다. 따라서 운영환경의 Partition 수는 예상 TPS, Consumer 수, 순서 보장 범위를 고려해 결정해야 합니다.
Offset
Offset은 Partition 내부에서 각 이벤트가 가지는 순번입니다.
Consumer는 자신이 어디까지 이벤트를 읽었는지 Offset을 통해 관리합니다. Consumer가 중단되더라도 마지막으로 처리한 Offset을 기준으로 다시 읽을 수 있습니다.
Consumer
Consumer는 Kafka에 저장된 이벤트를 읽어 처리하는 애플리케이션입니다. 이번에 구상한 구조에서는 Spark Structured Streaming이 Kafka Consumer 역할을 수행합니다.
Consumer Group
여러 Consumer를 하나의 Consumer Group으로 구성하면 Kafka Partition을 Consumer들이 나누어 처리합니다.
하나의 Consumer Group 안에서는 하나의 Partition을 동시에 한 Consumer만 담당합니다. 따라서 Consumer 수가 Partition 수보다 많으면 일부 Consumer는 처리할 Partition이 없어 대기하게 됩니다.
반면 Consumer Group이 서로 다르면 각 그룹은 동일한 이벤트를 독립적으로 읽을 수 있습니다. 예를 들어 Spark 분석 시스템과 로그 저장 시스템이 서로 다른 Consumer Group을 사용하면 같은 이벤트를 각각 처리할 수 있습니다.
Replication
Replication은 Partition 데이터를 여러 Broker에 복제하는 기능입니다.
Partition에는 Leader와 Follower Replica가 존재하며, 일반적으로 Producer와 Consumer는 Leader를 통해 데이터를 주고받습니다. Leader Broker에 장애가 발생하면 복제본 중 하나가 새로운 Leader 역할을 수행할 수 있습니다.
개발환경에서는 단일 Broker와 Replication Factor 1로 테스트할 수 있지만, 운영환경에서는 장애 대응을 고려해 복제 구성을 결정해야 합니다.
## 4. Kafka에서 Spark로 이어지는 처리 과정
Kafka에 저장된 이벤트는 Spark Structured Streaming이 읽어 처리합니다.
전체 처리 과정은 다음과 같습니다.
1. 서비스가 PRODUCT_VIEW 이벤트를 생성합니다.
2. Producer가 이벤트를 Kafka의 product-events Topic에 전송합니다.
3. Kafka가 이벤트를 Partition에 저장합니다.
4. Spark Structured Streaming이 Kafka에서 이벤트를 읽습니다.
5. Spark가 JSON 데이터를 Schema에 맞게 변환합니다.
6. 상품별 조회 수나 시간대별 이벤트 수를 집계합니다.
7. 처리 결과를 Console, 파일, DB 또는 데이터 웨어하우스에 저장합니다.
PoC 단계에서는 먼저 Kafka의 Raw Event가 Spark Console에 출력되는지 확인한 뒤, JSON Parsing과 집계 로직을 추가하는 방식으로 진행할 수 있습니다.
## 5. Spark Structured Streaming
Spark Structured Streaming은 지속적으로 들어오는 데이터를 테이블처럼 처리할 수 있도록 지원하는 스트리밍 처리 기능입니다.
Kafka에서 이벤트를 읽은 후 다음과 같은 작업을 수행할 수 있습니다.
- JSON Event Schema Parsing
- 필요한 필드 선택
- 잘못된 이벤트 필터링
- 상품별 또는 사용자별 이벤트 집계
- 시간 구간별 조회 수 계산
- 처리 결과를 외부 저장소에 기록
Spark는 기본적으로 들어온 이벤트를 작은 단위로 묶어 처리하는 Micro-batch 방식을 사용할 수 있습니다.
또한 Checkpoint를 설정하면 Spark가 처리한 Kafka Offset과 작업 상태를 저장할 수 있습니다. Spark가 중단됐다가 재실행되더라도 Checkpoint를 이용해 이전 처리 위치부터 이어서 실행할 수 있습니다.
## 6. 운영 DB와 데이터 웨어하우스의 차이
Spark가 이벤트를 가공하고 집계한 결과를 어디에 저장할지도 공부했습니다.
가공과 집계는 Spark가 수행하는 처리 작업이며, DB와 데이터 웨어하우스는 처리 결과를 보관하는 저장소입니다.
운영 DB
운영 DB는 서비스가 현재 데이터를 빠르게 조회하거나 수정하기 위해 사용합니다.
예시는 다음과 같습니다.
- 현재 상품 조회 수
- 사용자별 최근 행동
- 실시간 인기 상품 목록
- 서비스 화면에 바로 표시할 집계 결과
운영 DB는 짧은 응답 시간과 빈번한 읽기·쓰기가 중요합니다.
데이터 웨어하우스
데이터 웨어하우스는 대량의 과거 데이터를 저장하고 분석하기 위한 저장소입니다.
예시는 다음과 같습니다.
- 일별·월별 상품 조회 추이
- 전체 사용자 행동 분석
- 상품 카테고리별 통계
- BI Dashboard와 리포트
- 장기간 누적된 이벤트 분석
따라서 동일한 Spark 처리 결과라도 서비스에서 즉시 조회해야 한다면 운영 DB에 저장하고, 장기간 분석에 사용한다면 데이터 웨어하우스에 저장할 수 있습니다. 필요하면 두 저장소에 동시에 전달하는 구조도 가능합니다.
## 7. Event Schema 설계
실제 Event Schema가 아직 확정되지 않은 상황에서도 전체 파이프라인을 검증할 수 있도록 임시 PRODUCT_VIEW Event를 사용하는 방식을 공부했습니다.
임시 Schema에 포함할 수 있는 필드는 다음과 같습니다.
- eventId: 이벤트를 구분하기 위한 고유 ID
- eventType: 이벤트 종류
- userId: 이벤트를 발생시킨 사용자
- productId: 조회한 상품
- eventTime: 실제 이벤트가 발생한 시간
eventId는 중복 이벤트를 판별하는 데 사용할 수 있고, eventTime은 End-to-End Latency를 측정하거나 시간 기준 집계를 수행할 때 사용할 수 있습니다.
실제 Schema가 확정되기 전에는 임시 Schema가 테스트용이라는 점을 문서에 명확히 기록해야 합니다.
## 8. 스트리밍 시스템의 주요 성능 지표
TPS
TPS는 초당 처리되는 이벤트 수입니다.
Kafka로 초당 얼마나 많은 이벤트가 들어오는지와 Spark가 초당 얼마나 많은 이벤트를 처리하는지 확인할 때 사용할 수 있습니다.
Processing Latency
Spark가 이벤트를 읽은 후 가공과 집계를 완료하는 데 걸리는 시간입니다.
End-to-End Latency
이벤트가 실제로 발생한 시점부터 최종 저장소에 반영될 때까지 걸리는 전체 시간입니다.
이벤트의 eventTime과 최종 처리 시각을 비교해 측정할 수 있습니다.
Consumer Lag
Consumer Lag은 Kafka에 저장된 최신 Offset과 Consumer가 처리한 Offset의 차이입니다.
Consumer Lag이 계속 증가한다면 Kafka로 들어오는 이벤트 속도보다 Spark의 처리 속도가 느리다는 의미입니다. 이 경우 Partition 수, Consumer 수, Spark 처리 성능 등을 점검해야 합니다.
Batch Duration
Spark가 하나의 Micro-batch를 처리하는 데 걸리는 시간입니다. Batch Duration이 지속적으로 증가하면 처리 병목이 발생하고 있을 가능성이 있습니다.
처리량
Spark의 inputRowsPerSecond와 processedRowsPerSecond를 비교하면 이벤트 입력 속도와 실제 처리 속도를 확인할 수 있습니다.
## 9. 개발환경과 운영환경의 차이
PoC를 위한 개발환경은 최소 구성으로 시작할 수 있습니다.
Kafka Broker 1대
Partition 1개
Replication Factor 1
Spark Local 실행
Console 또는 임시 파일 Sink
이 환경의 목적은 운영 성능을 검증하는 것이 아니라 Kafka에서 Spark까지 이벤트가 정상적으로 전달되는지 확인하는 것입니다.
운영환경에서는 다음 요소를 추가로 검토해야 합니다.
- 예상 이벤트 TPS
- 필요한 Partition 수
- Broker 수
- Replication Factor
- Consumer 병렬 처리 수
- 장애 복구 방식
- 데이터 보관 기간
- Consumer Lag 감시
- Spark Checkpoint 저장 위치
- 최종 DB 또는 데이터 웨어하우스 구성

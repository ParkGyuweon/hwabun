# 추천 시스템 설계안 (CBF)

> 관련 문서: [`product-feature-spec.md`](./product-feature-spec.md) (상품 벡터 명세), [`product-feature-sample.md`](./product-feature-sample.md) (실제 계산 샘플), [`recommendation-io-spec.md`](./recommendation-io-spec.md) (입출력 구조)

> 세포라 데이터셋 기반 · 2026-08-27
> 전제: 상품 200개 / 페르소나 10,000명 / 리뷰 844,865건(4개 속성 전부 채워진 것)

## 1. 설계 원칙

**속성과 행동을 같은 벡터에 섞지 않는다. 점수 단계에서 합친다.**

상품 벡터는 성분·카테고리 공간에, 사용자 속성은 사용자 공간에 있습니다. 한 벡터로 이어붙이면 코사인 유사도가 두 공간을 뒤섞어 계산합니다. 점수를 따로 내고 가중합하면 각각의 의미가 보존되고, 추천 근거를 항별로 분해해 설명할 수 있습니다.

## 2. 최종 점수 공식

```
score(u, i) = w₁ · cos(v_u, v_i)      ← 행동 기반 (콘텐츠 유사도)
            + w₂ · attr_affinity(u, i) ← 사용자 속성 기반
            + w₃ · prior(i)            ← 인기도 (콜드스타트 보정)
```

## 3. 동작 예시 — 숫자로 따라가기

설명을 위해 차원을 4개로 줄인 예시입니다. 실제로는 약 170차원입니다.

**헷갈리기 쉬운 점부터 정리합니다.** 등장인물은 셋인데 성격이 다릅니다.

| | 정체 | 계산 방식 |
|---|---|---|
| 상품 벡터 | 숫자 배열 | 상품 정보를 숫자로 변환 |
| 사용자 벡터 | 숫자 배열 | 사용자가 본 **상품 벡터들의 가중 평균** |
| 속성 점수 | **숫자 하나** | 미리 만든 **표에서 조회** (벡터 아님) |

앞의 둘만 벡터이고 같은 공간에 있어 코사인 유사도가 성립합니다. **속성은 벡터 연산을 하지 않습니다.**

### 3-1. 상품 벡터 (오프라인, 1회)

각 상품이 `[클렌저, 보습, 진정, 고가]` 특성을 얼마나 갖는지 수치화합니다. 카테고리와 highlights에서 기계적으로 생성됩니다.

| 상품 | 클렌저 | 보습 | 진정 | 고가 |
|---|---:|---:|---:|---:|
| **A** 파머시 클렌징밤 | 1.0 | 0.5 | 0 | 0 |
| **B** belif 아쿠아밤 | 0 | 1.0 | 0.5 | 0 |
| **C** 슈퍼굿 선크림 | 0 | 0.3 | 0 | 1.0 |
| **D** 글로우레시피 토너 | 0 | 0.8 | 0.6 | 0 |

### 3-2. 사용자 행동 → 사용자 벡터

사용자가 다음과 같이 행동했다고 가정합니다.

```
A 상세페이지 스크롤 100%  → 가중치 2.5
B 상세페이지 진입만       → 가중치 1.0
```

사용자 벡터는 A와 B 벡터의 가중 평균입니다.

```
분자 = 2.5 × [1.0, 0.5, 0, 0] + 1.0 × [0, 1.0, 0.5, 0]
     = [2.5, 2.25, 0.5, 0]
분모 = 2.5 + 1.0 = 3.5

사용자 벡터 = [0.71, 0.64, 0.14, 0]
```

**행동이 벡터로 전환되는 지점입니다.** 끝까지 스크롤한 A가 2.5배 무겁게 반영되어 벡터가 클렌저 쪽으로 기울었습니다.

사용자 벡터는 **상품 벡터를 재료로 만들어지므로 자동으로 같은 공간에 위치**합니다. 코사인 유사도가 의미를 갖는 이유입니다.

### 3-3. 코사인 유사도 (미열람 상품과 비교)

```
C 선크림과의 유사도 = 0.19
D 토너와의 유사도   = 0.62   ← 더 유사
```

사용자 벡터의 "보습" 성분이 크고 D도 보습 위주라 높게 나왔습니다. C는 "고가" 축으로 치우쳐 멀어졌습니다.

**여기까지 사용자 속성은 전혀 사용되지 않았습니다.**

### 3-4. 속성 점수 (별개 트랙)

사용자가 **지성 피부 / light 톤**이라고 합시다. 이 값은 벡터로 만들지 않고, 리뷰 844,865건으로 미리 집계한 표를 조회합니다.

> "C 선크림에 리뷰를 단 사람 중 지성 피부인 사람들의 평균 평점은?" → 4.6점 → 0.92

| 상품 | 지성 사용자 평점 | light 톤 평점 |
|---|---:|---:|
| C 선크림 | 0.92 | 0.88 |
| D 토너 | 0.70 | 0.85 |

가중치 적용 (`skin_type` 0.4 + `skin_tone` 0.4 + `hair_color`·`eye_color` 0.1씩):

```
C 속성점수 = 0.4×0.92 + 0.4×0.88 + 0.16 = 0.88
D 속성점수 = 0.4×0.70 + 0.4×0.85 + 0.16 = 0.78
```

**이 트랙에서는 C가 우세합니다.** 지성 피부 사용자들의 만족도가 높았기 때문입니다.

### 3-5. 합류 지점은 마지막 덧셈 한 줄뿐

행동 이력 2건이므로 `w = (0.4, 0.5, 0.1)` 구간입니다.

| | 코사인 | 속성 | 인기도 | 최종 점수 |
|---|---:|---:|---:|---:|
| C 선크림 | 0.19 | 0.88 | 0.9 | 0.4(0.19) + 0.5(0.88) + 0.1(0.9) = **0.61** |
| **D 토너** | 0.62 | 0.78 | 0.5 | 0.4(0.62) + 0.5(0.78) + 0.1(0.5) = **0.69** |

→ **D 토너 추천**

### 3-6. 행동이 쌓이면 무게중심이 이동

행동 이력이 10건이 되면 `w = (0.8, 0.2, 0)`으로 전환됩니다.

| | 행동 2건 시점 | 행동 10건 시점 |
|---|---:|---:|
| C 선크림 | 0.61 | 0.33 |
| D 토너 | **0.69** | **0.65** |

속성의 영향력이 줄고 본인 행동이 지배합니다. 초기에는 "같은 피부 타입 사용자들이 선호한 것"으로 시작해 "본인이 실제로 본 것과 유사한 것"으로 옮겨갑니다.

### 3-7. 전체 흐름

```
[상품 정보]                          [리뷰 844,865건]
카테고리·highlights·가격                    │
      │                            상품별 × 속성별 평균 평점
      ▼                                     │
 상품 벡터 V (200 × 170)                     ▼
      │                             속성 친화도 표 A
      │  ← 사용자가 본 상품들                 │
      ▼     (행동 가중 평균)                  │
 사용자 벡터 v_u                              │
      │                                     │
      ▼                                     │
  코사인 유사도                          표에서 조회
      │                                     │
      └──────────┐         ┌────────────────┘
                 ▼         ▼
              w₁ × 유사도 + w₂ × 속성점수 + w₃ × 인기도
                         │
                         ▼
                     추천 목록
```

### 3-8. 요약

1. **사용자 벡터는 상품 벡터로 만든다** → 같은 공간이므로 코사인이 성립
2. **속성은 벡터가 아니라 표 조회다** → 리뷰 844,865건으로 사전 집계
3. **둘은 마지막 덧셈에서만 만난다** → 추천 결과를 항별로 분해해 설명 가능

## 5. 사용자 벡터 `v_u` — 행동 기반

사용자가 상호작용한 **상품 벡터들의 가중 평균**입니다. 사용자 속성은 여기 들어가지 않습니다.

```
v_u = Σ(wₖ · decay(tₖ) · v_iₖ) / Σ(wₖ · decay(tₖ))
```

### 행동 가중치

| 행동 | 가중치 | 비고 |
|---|---:|---|
| 목록 노출 | 0 | 봤다는 증거가 아님 |
| 상세 진입 | 1.0 | |
| 스크롤 25% | 0.5 | |
| 스크롤 50% | 1.5 | |
| 스크롤 75% | 2.0 | 실질 관심 신호 |
| 스크롤 100% | 2.5 | |
| 장바구니 담기 | 4.0 | |
| 리뷰 작성 | **(rating − 3) × 2** | 범위 −4 ~ +4 |

리뷰 가중치를 `rating − 3`으로 두는 게 핵심입니다. 그냥 `rating`을 쓰면 1점 준 상품도 취향 벡터에 양수로 들어갑니다. 이 방식은 **싫어한 상품의 반대 방향으로 벡터를 밀어냅니다.**

로그 스키마의 스크롤 4단계(25/50/75/100)가 여기서 그대로 소비됩니다.

### 시간 감쇠

```
decay(t) = exp(−Δt / τ),  τ = 30일
```

CBF의 약점인 "취향 변화 대응 지연"을 완화합니다.

## 6. 속성 친화도 `attr_affinity` — 4개 속성 기반

실시간 계산이 아니라 **오프라인에서 만든 조회 테이블**입니다. 리뷰 458,614건(상위 200개 상품)으로 상품 × 세그먼트별 통계를 미리 뽑아둡니다. 서빙 시 딕셔너리 조회 한 번이라 비용이 사실상 0입니다.

테이블: `batch/ingest/data/affinity_lift.csv` (4,000행 = 200상품 × 21세그먼트)

### 6-1. 평점 평균이 아니라 구성비 lift를 씁니다

**당초 안은 "그 상품에 리뷰를 단 해당 세그먼트 사용자들의 평균 평점"이었으나 폐기했습니다.**

측정 결과 4개 속성 모두 판별력이 노이즈 수준이었습니다.

```
판별력 eta^2 :  hair_color 0.00403   skin_tone 0.00328
               eye_color  0.00280   skin_type 0.00262
```

전체 평점 분산의 0.4% 미만이고, 순위 1위가 `hair_color`였습니다. 머리색이 스킨케어 만족도를 가장 잘 설명한다는 것은 인과적으로 성립하지 않으므로 **전부 노이즈**입니다.

원인은 평점 분포입니다. **리뷰의 63.4%가 5점**이라 누가 쓰든 평점이 후하게 나옵니다. 상품 내 세그먼트 간 친화도 차이가 0.03~0.06(0~1 스케일)에 불과해, 표를 만들어도 모든 칸이 거의 같은 값이 됩니다.

**대안: 구성비 lift.** 평점은 다 후하게 주지만 **누가 사는지는 확실히 다릅니다.**

```
lift(상품 i, 세그먼트 s) = (상품 i 리뷰 중 s 비중) / (전체 리뷰 중 s 비중)

affinity = clip((lift - 0.60) / 1.00, 0, 1)
```

상품 내 편차가 0.047 → 0.47로 **10배** 커집니다. 그리고 결과가 해석됩니다.

| 속성 | lift 상위 사례 |
|---|---|
| `skin_type` | `oily` 2.56배 Balancing Force **Oil Control** Toner / `dry` 1.97배 **Cicapair** Tiger Grass Cream |
| `skin_tone` | `deep` 2.91배 Ginzing Vitamin C Eye Cream(**브라이트닝**) / `fair` 1.37배 Cicapair **톤 보정** |
| `hair_color` | `gray` 2.80배 Smart Clinical Repair **Wrinkle** Correcting Serum |
| `eye_color` | `gray` 2.35배 Blueberry Bounce Cleanser (공통점 없음) |

### 6-2. 표본 축소(shrinkage)

표본이 적은 셀은 lift가 튑니다. 기준 비율 방향으로 당깁니다.

```
share_shrunk = (관측수 + K x 기준비율) / (셀 표본수 + K),   K = 50
```

### 6-2-1. 클리핑 구간 `[0.60, 1.60]`

lift를 0~1로 변환할 때의 구간입니다. 초기값 `[0.80, 1.20]`은 범위가 좁아 4,000셀 중 **23.5%가 0 또는 1로 포화**되었습니다. lift 1.82배 상품과 1.35배 상품이 모두 1.000이 되어 상위권 서열이 사라졌습니다.

`[0.60, 1.60]`으로 넓힌 결과입니다.

| 속성 | 포화율 (전) | 포화율 (후) |
|---|---:|---:|
| `skin_type` | 21% | **3.9%** |
| `skin_tone` | 26% | **7.6%** |
| `hair_color` | 27% | **6.1%** |
| `eye_color` | 20% | **7.9%** |

`oily` 기준 상위권이 실제로 구분됩니다.

```
                 [0.80,1.20]   [0.60,1.60]
 1위 lift 1.82x     1.000         1.000
21위 lift 1.27x     1.000         0.667   <- 서열 복원
51위 lift 1.09x     0.717         0.487
```

### 6-3. 속성별 판별력 측정 결과

| 속성 | 세그먼트 | lift 효과크기 | 상품내 편차 | 유의 셀(|z|>3) |
|---|---:|---:|---:|---:|
| **`skin_type`** | 4 | 0.132 | 0.411 | **32.2%** |
| **`skin_tone`** | 5 | 0.161 | 0.472 | **23.6%** |
| `eye_color` | 5 | 0.148 | 0.530 | 19.8% |
| `hair_color` | 6 | 0.162 | 0.604 | 16.1% |

lift로 바꾸자 `skin_type`이 4위에서 1위로 올라왔습니다.

`hair_color`의 유일한 신호는 `gray`가 안티에이징 제품에 몰리는 것인데, 이는 머리색이 아니라 **연령의 대리변수**로 작동하는 것입니다. `eye_color`는 극단 사례에 공통점이 없어 해석되지 않습니다. **두 속성의 존치 여부는 미결정 사항입니다.**

### 6-4. `hair_color`의 `brunette` — 데이터 오류 발견

`brunette`는 `brown`의 표기 변형이었습니다.

```
200개 중 99개 상품은 brunette 0%
그런데 4개 상품은 40% 초과, 해당 상품의 brown은 0.6~10%로 붕괴

Microneedling Retinol Patches:  brunette 48.5%  brown 0.6%
Vinosource-Hydra Sorbet:        brunette 47.3%  brown 2.4%
```

같은 사람을 수집 배치에 따라 `brown` 또는 `brunette`로 기록한 것입니다. **평점 기반에서 `hair_color`가 판별력 1위로 나왔던 원인이 이 아티팩트였습니다.** 병합 후 최하위로 내려갔습니다.

`hair_color`는 `brunette` → `brown` 병합, `eye_color`는 `Grey` → `gray` 병합을 전처리에서 적용합니다.

### 6-5. 속성별 가중치 — 사용자 `skin_type`에 따라 분기

| 사용자 `skin_type` | `skin_type` | `skin_tone` | `hair_color` | `eye_color` |
|---|---:|---:|---:|---:|
| `dry` / `oily` / `normal` (44.7%) | 0.40 | 0.40 | 0.10 | 0.10 |
| **`combination` (55.3%)** | **0.00** | **0.80** | 0.10 | 0.10 |

```
attr_affinity(u, i) = w_type  x A[i][u.skin_type]
                    + w_tone  x A[i][u.skin_tone_bucket]
                    + 0.10    x A[i][u.hair_color]
                    + 0.10    x A[i][u.eye_color]
```

`skin_type`과 `skin_tone`을 동등하게 두기로 확정했습니다. 세포라 상위 상품에 선크림·CC크림·톤업 제품이 다수 포함되어 피부 톤이 만족도를 실제로 가릅니다.

**복합성 사용자는 `skin_type` 항을 사용하지 않습니다.** 근거와 처리는 7-4절에 있습니다. 요약하면 복합성은 200개 상품 전부 lift 0.85~1.19(표준편차 0.053)로 판별력이 없고, `skin_tone`은 복합성 사용자 안에서도 유효(표준편차 0.269)하므로 몫을 이관합니다.

**친화도 테이블은 전체 리뷰로 계산한 것 하나만 유지합니다.** 복합성 전용 테이블을 별도로 두는 안은 폐기했습니다 — 복합성/비복합성 독립 검정에서 톤별 상관이 +0.69~+0.82로 신호가 대체로 같은데, 쪼개면 `deep` 톤 셀 표본이 중앙값 23건(최소 0건)까지 떨어져 추정만 불안정해집니다.

### 6-6. skin_tone은 14종 → 5개 버킷으로 묶습니다

`skin_tone`을 `skin_type`과 동등하게 쓰기로 한 이상, 원본 14종을 그대로 쓰면 문제가 생깁니다. 분포가 극단적으로 치우쳐 있습니다 — `dark` 0.05%, `ebony` 0.00%. 상품 200개 × 14종 = 2,800셀인데 하위 셀은 리뷰가 한 자릿수라 통계가 의미 없습니다.

| 버킷 | 원본 값 | 전체 리뷰 대비 |
|---|---|---:|
| `fair` | porcelain, fair, fairLight | 24.30% |
| `light` | light, lightMedium | 42.30% |
| `medium` | medium, mediumTan, olive | 12.31% |
| `tan` | tan | 3.08% |
| `deep` | deep, rich, dark, ebony | 2.43% |

5개 버킷이면 가장 작은 `deep`도 약 26,600건이라 상품당 평균 130건 확보됩니다. 통계적으로 쓸 수 있는 수준입니다.

`skin_type`은 원본 4종(combination/dry/normal/oily)을 그대로 씁니다. 두 속성 모두 4~5개 세그먼트가 되어 해상도도 맞습니다.

### 6-7. 표기 정규화 요약

| 속성 | 처리 |
|---|---|
| `skin_tone` | 14종 → 5버킷 (위 표), `notSureST` 63건 결측 처리 |
| `hair_color` | `brunette` → `brown` 병합 (6-4절) |
| `eye_color` | `Grey` → `gray` 병합 |
| `skin_type` | 원본 4종 유지 |

## 7. 가중치 스케줄 — 행동 로그가 쌓이면 이동

**행동 로그가 얼마 없을 때는 속성이 주도하고, 쌓이면 코사인 유사도가 넘겨받습니다.**

### 7-1. 기준 지표: 상호작용한 고유 상품 수

이벤트 수가 아니라 **상호작용한 고유 상품 수**를 기준으로 삼습니다. 스크롤 로그를 25/50/75/100 네 단계로 찍기 때문에, 상품 하나를 끝까지 본 것만으로 이벤트가 5건(상세 진입 + 스크롤 4단계) 발생합니다. 이벤트 수를 쓰면 상품 1개를 정독한 사용자와 상품 5개를 훑은 사용자가 같은 구간에 들어갑니다.

### 7-2. 스케줄

| 상호작용 고유 상품 수 | w₁ (코사인) | w₂ (속성) | w₃ (인기도) |
|---|---:|---:|---:|
| 0개 (시뮬레이션 시작 시점) | 0.00 | **0.80** | 0.20 |
| 1~2개 | 0.35 | 0.55 | 0.10 |
| 3~5개 | 0.60 | 0.35 | 0.05 |
| 6개 이상 | **0.80** | 0.20 | 0.00 |

전환의 논리는 단순합니다. 처음에는 우리가 아는 것이 피부 속성뿐이므로 **"같은 속성 사용자들이 선호한 것"** 으로 시작하고, 행동이 쌓이면 **"본인이 실제로 본 것과 유사한 것"** 으로 옮겨갑니다.

인기도(w₃)는 초반에만 소량 섞습니다. 속성만으로 순위를 매기면 같은 속성 조합 사용자들이 동일한 목록을 받게 되는데(`skin_type` × `skin_tone` = 20개 조합), 인기도가 그 안에서 검증된 상품을 상위로 올려줍니다. 상품 6개 이상 상호작용하면 0으로 빠집니다.

### 7-3. 페르소나는 콜드 스타트를 별도로 다루지 않습니다

본 프로젝트의 대상은 **리뷰 이력이 2개 이상인 페르소나 10,000명**입니다. 실서비스의 신규 가입자(리뷰 0개·행동 0건)는 시뮬레이션 대상이 아니므로 **별도 콜드 스타트 경로를 구현하지 않습니다.**

시뮬레이션 시작 시점에 페르소나는 속성만 갖고 행동 로그는 비어 있으므로, 위 스케줄의 첫 구간(0개)이 자연스럽게 그 역할을 합니다. 로그가 쌓이면서 구간이 올라갑니다.

> 참고: 상위 200개 상품 리뷰어 247,509명 중 72.8%가 상품 1개짜리라 모집단에서 제외되었습니다. 실서비스에서는 이런 사용자가 다수이므로, 실제 콜드 스타트 대응은 별도 과제로 남습니다.

### 7-4. 속성 항(w₂) 내부 구성 — 복합성 사용자는 다르게

속성 항은 4개 속성의 가중합인데, **`skin_type`이 복합성인 사용자에게는 작동하지 않습니다.**

리뷰 458,614건으로 측정한 결과, 상품 200개에 대한 `skin_type` lift 편차가 이렇습니다.

| 세그먼트 | 사용자 비중 | lift 표준편차 | lift 범위 |
|---|---:|---:|---|
| `oily` | 12.3% | 0.289 | 0.30 ~ 2.56 |
| `dry` | 19.2% | 0.237 | 0.38 ~ 1.97 |
| `normal` | 13.2% | 0.158 | 0.43 ~ 1.55 |
| **`combination`** | **55.3%** | **0.053** | 0.85 ~ 1.19 |

복합성은 200개 상품 전부가 0.85~1.19에 갇혀 있어 사실상 상수입니다. 복합성은 T존 지성 + U존 건성이라 지성용 제품도 건성용 제품도 구매하기 때문입니다. **전체의 55.3%가 복합성이므로 이를 방치하면 속성 항이 사용자 절반에게 무력해집니다.**

**해결: `skin_tone`이 복합성 사용자에게도 유효합니다.**

복합성 리뷰 253,456건만으로 다시 계산한 결과입니다.

| 모집단 | `skin_tone` lift 표준편차 | 상품내 편차 |
|---|---:|---:|
| 전체 사용자 | 0.262 | 0.472 |
| **복합성만** | **0.269** | **0.497** |

편차가 그대로 유지됩니다. 그리고 전체 기준 lift와 복합성 기준 lift의 상관계수가 `deep` +0.959 / `fair` +0.922 / `light` +0.963 / `medium` +0.963 / `tan` +0.943으로, **피부색 신호는 피부 타입과 독립적**입니다.

따라서 `skin_type` 몫을 `skin_tone`으로 이관합니다.

| 사용자 `skin_type` | `skin_type` | `skin_tone` | `hair_color` | `eye_color` |
|---|---:|---:|---:|---:|
| `dry` / `oily` / `normal` (44.7%) | 0.40 | 0.40 | 0.10 | 0.10 |
| **`combination` (55.3%)** | **0.00** | **0.80** | 0.10 | 0.10 |

복합성 사용자 안에서 `skin_tone`이 실제로 갈리는 예시입니다.

```
[deep 톤]  3.06배  Ginzing Vitamin C Eye Cream (브라이트닝)
           2.72배  Greek Yoghurt Foaming Cream Cleanser
[fair 톤]  1.37배  Cicapair Tiger Grass Color Correcting (톤 보정)
[light 톤] 1.16배  Self Tanning Bronzing Face Drops (셀프태닝)
```

밝은 톤이 톤 보정·셀프태닝에, 어두운 톤이 브라이트닝에 몰립니다. 인과적으로 납득되는 신호입니다.

## 8. 다양성 보정 (MMR)

순수 CBF는 필터 버블이 구조적 약점입니다. 상위 N개 선정 시 한 겹 씌웁니다.

```
선택 = argmax [ λ · score(i) − (1−λ) · max cos(v_i, 이미 선택된 것) ]
λ = 0.7
```

추천 목록에 클렌저만 5개 뜨는 상황을 막습니다.

## 9. 실시간 서빙

**상품이 200개라는 점이 결정적입니다.**

### 오프라인 (배치)

| 산출물 | 크기 |
|---|---|
| `V` 상품 행렬 | 200 × 170 float32 = **133KB** (실측) |
| `A` 속성 친화도 테이블 | 200 × 17세그먼트 = **14KB** |

둘 다 프로세스 메모리에 상주시킵니다.

### 온라인 (요청당)

```
1. user_vector 로드              O(170)
2. scores = V @ user_vector      200 × 170 = 34,000 FLOP
3. + A 조회 후 가중합             O(200)
4. 이미 본 상품 제외, MMR, 정렬    O(200 log 200)
```

FAISS·벡터DB·ANN 인덱스는 **쓰지 않습니다.** 200개 규모에서는 오버엔지니어링이고, numpy 행렬곱 한 줄이 더 빠릅니다.

### 실측 성능 (2026-08-27, 개발 PC / numpy 싱글 코어)

상품 200개 × 170차원, 사용자 10,000명 조건으로 직접 측정한 값입니다.

| 항목 | 실측값 |
|---|---:|
| 추천 1건 (점수 계산 + 상위 10개 추출) | **8.8 μs** |
| 싱글 코어 처리량 | **113,000 RPS** |
| 사용자 10,000명 전원 추천 일괄 재계산 | **4.6 ms** |
| 상품 행렬 `V` 메모리 | 133 KB |
| 사용자 벡터 10,000명 메모리 | 6.5 MB |

**사용자 수는 요청당 비용에 곱해지지 않습니다.** 추천 1건은 `200 × 170` 행렬-벡터 곱 하나이므로, 사용자가 1만 명이든 100만 명이든 단건 비용은 8.8μs로 동일합니다. 사용자 수는 메모리에만 선형으로 영향을 줍니다.

| 사용자 수 | 벡터 보관 메모리 |
|---:|---:|
| 10,000명 | 6.5 MB |
| 100,000명 | 64.8 MB |
| 1,000,000명 | 648.5 MB |

실제 환경에서는 웹 프레임워크 오버헤드와 네트워크 왕복(수십 ms)이 지배적이라 **추천 계산은 전체 응답 시간의 1% 미만**입니다. 병목이 되지 않습니다.

### 서빙 방식 선택

| 방식 | 비용 | 특성 |
|---|---|---|
| **요청 시 계산 (권장)** | 8.8 μs/건 | 최신 행동이 즉시 반영 |
| 배치 미리 계산 | 4.6 ms/전체 | 1초 주기로 돌려도 CPU 0.5% 미만 |

둘 다 성립하므로 구현이 단순한 **요청 시 계산**을 택합니다.

### 실제 병목은 추천 계산이 아니라 로그 적재

추천 연산은 마이크로초 단위라 문제가 되지 않습니다. 부하는 **이벤트 write** 쪽에서 발생합니다. 스크롤 로그를 25/50/75/100 네 단계로 제한한 결정이 여기서 효과를 냅니다 — 1% 단위로 찍었다면 이벤트가 25배로 늘어 DB가 먼저 한계에 도달합니다.

> 참고: 페르소나 10,000명은 동시 접속자가 아니라 전체 사용자 수입니다. 실서비스에서도 동시 접속은 전체의 1~5% 수준이며, 본 프로젝트는 시뮬레이션이라 실트래픽이 발생하지 않습니다. 1만 명 로그를 한꺼번에 처리해도 4.6ms입니다.

### 사용자 벡터 증분 갱신

전체 재계산 없이 O(170)으로 처리합니다.

```python
# 이벤트 1건당
u_sum += w * decay * v_item
w_sum += w * decay
user_vector = u_sum / w_sum
```

Redis에 `(u_sum, w_sum)`만 보관. **10,000명 × 170차원 float32 = 6.5MB**(실측) — 통째로 메모리에 올려도 무방합니다.

### 이벤트 흐름

```
스크롤 75% 이벤트 발생
  → 로그 적재
  → user_vector 증분 갱신 (O(170))
  → 다음 추천 API 호출에 즉시 반영
```

스트리밍 파이프라인이 필요 없습니다. 이벤트 핸들러에서 벡터를 더하는 것이 전부입니다.

## 11. ⚠️ 검증 시 주의

생성한 페르소나 로그로 **가중치를 학습시키지 마세요.** 로그를 이 규칙으로 만들 것이므로, 학습하면 심어둔 규칙을 되찾을 뿐입니다. 성능이 좋아도 알고리즘의 성과가 아닙니다.

- 가중치: 룰로 고정 (위 표)
- 검증: **실제 리뷰 데이터**로 수행 (예: 사용자의 고평점 상품이 추천 상위에 들어오는지 holdout 평가)

## 12. 구현 순서

1. `skin_tone` 5개 버킷 매핑 + `eye_color` `Grey`/`gray` 정규화
2. 상품 200개 확정 (`Mini ` 변형 병합)
3. 상품 벡터 `V` 생성 (카테고리 + highlights + 가격)
4. 속성 친화도 테이블 `A` 생성 (베이지안 스무딩 포함)
5. 점수 함수 + MMR 구현
6. 실제 리뷰 holdout으로 베이스라인 평가
7. 페르소나 로그 생성 → 행동 항(w₁) 검증

## 13. 미결정 사항

- `prior(i)` 정의: `loves_count` 기반인지 리뷰 수 기반인지
- MMR의 λ 값 (0.7은 초기값, 튜닝 필요)
- 시간 감쇠 τ = 30일 (생성 로그의 시간 범위에 따라 조정)
- `ingredients` TF-IDF 추가 시점
- `hair_color` / `eye_color`를 속성 항에 유지할지 (판별력 최하위, `hair_color`는 연령 대리변수로 의심)
- 콘텐츠 벡터의 블록 가중치 (측정 결과 같은 카테고리 이웃 91.1%로 과도, 중간안 A 권고)

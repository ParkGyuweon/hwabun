# 상품 카탈로그 N+1 성능 개선 보고서

> 기록일: 2026-09-13
> 대상: `shop-backend`의 상품 목록·상세 API (`/api/products`, `/api/products/{id}`)
> 관측 환경: 로컬 Shop Backend `:8090` + Prometheus + Grafana + Chrome DevTools
> 범위: **백엔드 목록 API의 DB N+1 제거**. 프론트엔드 호출 구조는 이번 변경 범위에서 수정하지 않았다.

## 1. 무엇을 개선하려 했는가

상품 상세 페이지를 새로고침했을 때 브라우저 Network에서 수백 건의 요청이 발생했다. 이 현상은
두 층의 N+1 가능성을 의미했다.

1. **클라이언트 HTTP N+1**: 상품 목록을 받은 뒤 상품마다 상세 API를 다시 호출하는 문제
2. **서버 DB N+1**: 목록 API가 받은 상품을 순회하면서 브랜드와 옵션을 상품마다 다시 조회하는 문제

이번 작업의 목표는 두 번째 문제, 즉 `GET /api/products` 한 번이 내부적으로 만드는 DB read 수를
상품 수와 무관한 상수 수준으로 줄이는 것이었다. 프론트 HTTP 호출을 바꾸면 원인을 섞어버릴 수
있으므로, 프론트는 수정하지 않고 백엔드 변화만 측정했다.

## 2. 처음에 예상한 문제와 검증 방법

### 예상

기존 목록 API는 활성 상품을 먼저 읽고, Java Stream에서 각 상품을 처리했다. 이 과정에서 상품마다
다음 조회가 반복될 것으로 예상했다.

```text
상품 목록 1회
상품별 브랜드 활성 상태 확인  N회
상품별 브랜드명 조회        N회
상품별 활성 옵션 조회        N회
상품 하이라이트 일괄 조회     1회
```

따라서 예상 DB read 수는 `2 + (3 × N)`이다. 상품 수가 늘면 응답 데이터뿐 아니라 DB 왕복도
선형으로 증가하는 전형적인 서버 측 N+1 구조다.

### 왜 HTTP 지표만으로는 부족했는가

HTTP p95가 낮아도 목록 API 안에서 DB를 몇 번 읽었는지는 알 수 없다. 또한 Hibernate 통계만으로
측정하면 `JdbcTemplate`으로 수행하는 성분·하이라이트 조인이 누락된다. 그래서 카탈로그 읽기
경로의 Repository/JdbcTemplate DB 조회를 모두 `endpoint`, `source` 태그와 함께 계수하는
`shop_backend_catalog_db_operations_total` 메트릭을 추가했다.

Grafana에는 다음 패널을 구성했다.

- `DB reads per product-list request (5m)`: 목록 요청 1건당 DB read 수
- `Products returned per list request (5m)`: 목록 요청 1건당 반환한 상품 수
- `Catalog DB reads by endpoint and source`: 어떤 조회가 반복되는지 확인하는 시계열
- 기존 HTTP 요청량, 상세/목록 비율, p50/p95/p99, Hikari 커넥션 풀, 오류 지표

## 3. 개선 전 측정 결과

상품 상세 페이지를 새로고침한 뒤 Grafana의 최근 5분 증가량을 기준으로 측정했다.

| 지표 | 개선 전 | 의미 |
| --- | ---: | --- |
| 목록 1회 반환 상품 수 | 208개 | 페이지네이션 없이 활성 상품 전체를 반환했다. |
| 목록 1회당 DB read | 626회 | `2 + (3 × 208)`과 정확히 일치했다. |
| 상품 1개당 추가 DB read | 3회 | 브랜드 확인, 브랜드명, 옵션 조회가 상품마다 반복됐다. |
| 상세 / 목록 HTTP 요청 비율 | 320.0 | 프론트 HTTP N+1도 동시에 존재한다는 신호다. |
| 상품 API HTTP 요청 | 467회 | 최근 5분 누적값이므로 새로고침 한 번의 절대값은 아니다. |
| 상품 API p95 | 22.724ms | 개별 API는 빠르지만 요청·DB read 총량이 과도했다. |
| Hikari active / pending | 순간 최대 약 2 / 0 | 로컬에서는 대기열이 없었지만 부하가 겹치면 위험해질 구조다. |
| 상품 API 4xx·5xx | 관측되지 않음 | 해당 관측 창에서 오류 시계열이 없었다. |

### 수치로 확인된 원인

```text
1   활성 상품 목록 조회
1   상품 하이라이트 일괄 조회
208 브랜드 활성 상태 확인
208 브랜드명 조회
208 활성 옵션 조회
---
626 DB reads = 2 + (3 × 208)
```

`Catalog DB reads by endpoint and source`에서 `list · brands`와 `list · variants`가 각각 상품 수에
비례해 증가하는 것으로 예상이 확인됐다. 즉, 이 문제는 단순히 “응답이 느리다”가 아니라,
상품 개수가 커질수록 DB 부하가 같이 커지는 구조적 문제였다.

## 4. 해결 방법을 찾으며 검토한 선택지

| 선택지 | 장점 | 고려한 한계 |
| --- | --- | --- |
| JPA `fetch join` | 엔티티 중심 구현을 유지할 수 있다. | 옵션은 1:N 관계라 행이 중복되고, 목록 카드에 필요한 최저가 집계를 처리하기 복잡하다. |
| 브랜드·옵션을 `IN (...)`으로 배치 조회 | 기존 Repository를 비교적 적게 바꿀 수 있고 3~4회로 줄일 수 있다. | Java에서 다시 맵을 조립해야 하며, 목록 DTO 전용 읽기에는 중간 단계가 남는다. |
| 목록 전용 SQL projection | 필요한 열만 읽고, 브랜드 조인과 옵션 최저가 집계를 DB에서 끝낼 수 있다. 결과 행 중복이 없고 2회로 고정된다. | SQL이 스키마에 직접 결합되므로 스키마 변경 시 함께 관리해야 한다. |

## 5. 선택한 해결책과 이유

목록 전용 SQL projection을 선택했다.

`CatalogController.listRows()`에서 다음을 한 번에 수행한다.

1. `product`와 상태가 `ACTIVE`인 `brand`를 조인한다.
2. 활성 `product_variant`를 `product_id`별로 집계해 목록 카드에 필요한 최저 정가·최저 할인가를 만든다.
3. 목록 DTO에 필요한 열만 projection으로 읽는다.
4. 하이라이트는 기존의 `IN (...)` 일괄 조회를 유지해 상품별 추가 쿼리가 생기지 않게 한다.

이 선택은 목록 카드가 엔티티 전체가 아닌 표시용 요약 정보만 필요하다는 점에 맞는다. 1:N 옵션을
그대로 조인해 중복 상품 행을 만드는 대신, DB에서 먼저 상품별 가격을 집계했다. 따라서 기존 API의
응답 형태를 유지하면서 목록 경로의 DB read를 정확히 2회로 제한할 수 있다.

```text
1  상품 + 활성 브랜드 + 활성 옵션 최저가 projection 조회
1  상품 하이라이트 일괄 조회
---
2 DB reads
```

## 6. 개선 후 측정 결과

같은 로컬 환경에서 백엔드를 재시작하고 상품 상세 페이지를 다시 새로고침해 측정했다.

| 지표 | 개선 전 | 개선 후 | 변화 |
| --- | ---: | ---: | ---: |
| 목록 1회 반환 상품 수 | 208개 | 208개 | 동일 |
| 목록 1회당 DB read | 626회 | **2회** | **624회 감소 (99.68%)** |
| 상품 1개당 추가 DB read | 3회 | **0회** | N+1 제거 |
| 상세 / 목록 HTTP 요청 비율 | 320.0 | 208.0 | 프론트 영역이므로 여전히 높음 |
| 상품 API p95 | 22.724ms | 21.867ms | 약 3.77% 감소 |
| Hikari pending | 0 | 0 | 로컬 대기열 없음 |
| 상품 API 오류 | 관측되지 않음 | 관측되지 않음 | 기능 오류 징후 없음 |

Grafana의 개선 후 그래프에서는 목록의 DB read가 `2.0`으로 표시됐고, 반환 상품 수는 동일하게
`208`이었다. 따라서 데이터 범위나 페이지 크기를 줄여서 수치를 좋게 만든 것이 아니라, 동일한
208개를 조회하는 DB 접근 방식을 바꿔 얻은 결과다.

Chrome DevTools에서는 여전히 약 376개 요청과 48.4MB 전송량이 보였다. 이는 이번 작업에서
수정하지 않은 클라이언트 HTTP N+1 및 이미지 등 프론트 자원 요청의 영향이다. 이 수치를 백엔드
목록 SQL 개선 효과로 해석하면 안 된다.

## 7. 결과 해석

개별 요청의 p95는 원래도 약 23ms로 낮았기 때문에, 이번 개선의 핵심 효과는 단일 요청 시간을
극적으로 낮추는 것이 아니다. 상품 수 208개에서 626번 발생하던 DB read를 2번으로 줄여,
동시 사용자 증가 시 DB 커넥션·CPU·I/O에 누적될 불필요한 부하를 제거한 것이다.

특히 상품 수가 1,000개가 되면 개선 전 구조는 3,002 DB reads까지 증가하지만, 현재 목록
projection 구조는 여전히 2회다. 이것이 N+1 제거가 p95 수치보다 확장성 관점에서 중요한 이유다.

## 8. 남은 개선 과제와 주의점

### 우선순위 높음

1. **프론트 HTTP N+1 제거**
   - 상세/목록 비율이 개선 후에도 208이다.
   - 목록을 받은 뒤 모든 상품 상세를 호출하지 않도록, 추천 6개를 바로 반환하는 전용 API 또는
     목록 카드에 필요한 필드를 담는 API 계약이 필요하다.

2. **페이지네이션 도입**
   - DB read는 2회가 됐지만 목록 API가 여전히 208개를 한 번에 반환한다.
   - `page`, `size`, 정렬·카테고리 필터를 도입하면 응답 JSON, 직렬화 비용, 프론트 렌더링 비용도 줄일 수 있다.

3. **프로덕션 데이터 규모에서 실행 계획 확인**
   - 현재 옵션 최저가를 구하는 파생 집계는 작은 로컬 데이터에서는 충분하다.
   - 데이터가 커지면 `product(status, brand_id)` 및 `product_variant(product_id, status, price_krw)` 계열
     인덱스 후보를 `EXPLAIN ANALYZE`와 실제 p95/p99로 검증한 뒤 추가한다.

### 운영·품질 측면

4. **목록 결과 캐시와 HTTP 캐시**: 카탈로그 갱신 빈도가 낮다면 짧은 TTL 캐시나 ETag를 적용한다.
5. **성능 회귀 방지**: 배포 전 목록 요청 1회당 DB read가 2를 넘으면 알림 또는 성능 테스트가 실패하도록 한다.
6. **SQL projection 유지보수**: 목록 DTO나 스키마가 바뀌면 projection SQL과 매핑을 함께 수정하고,
   목록 응답 계약 테스트로 누락을 방지한다.
7. **동시 부하 테스트**: 단일 새로고침뿐 아니라 동시 사용자 수를 늘려 Hikari pending, DB CPU,
   p95/p99, 오류율을 함께 비교한다.

## 9. 재측정 절차

1. Shop Backend를 최신 코드로 `8090` 포트에서 실행한다.
2. 기존 요청이 섞이지 않도록 상품 화면 호출 없이 5분 이상 기다린다.
3. 브라우저 캐시를 비우고 동일한 상품 상세 페이지를 한 번 새로고침한다.
4. Prometheus scrape 이후 Grafana에서 아래를 캡처한다.
   - `Products returned per list request (5m)`
   - `DB reads per product-list request (5m)`
   - `Catalog DB reads by endpoint and source`
   - `Detail / list ratio (5m)`
   - 상품 API p50/p95/p99, Hikari pending, HTTP 오류
5. 최근 5분 증가량은 다른 브라우저 활동이 섞일 수 있으므로, 단일 재현 조건과 실행 시각을 함께 기록한다.
